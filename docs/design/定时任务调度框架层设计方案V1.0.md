## 1. 选型:robfig/cron 还是别的

### 1.1 结论

**用 `github.com/robfig/cron/v3`(锁 `v3.0.1`),但只把它当「表达式 → 下次触发时间」的解析器 + 触发循环用,其余全部自己写。**

### 1.2 已有生产先例可抄

本机 `D:\gocodes\ai\WeKnora`(腾讯 WeKnora,多副本 K8s 部署)就用 robfig/cron 做数据源定时同步,代码在 `internal/datasource/scheduler.go`,配套测试 `internal/datasource/scheduler_test.go`,前端在 `frontend-react/src/pages/knowledge/components/DataSourceSyncLogs.tsx`。

**先说它证明了的**(这几条本来就是我方案的核心假设,现在有生产代码背书):

1. **多副本重复触发是真问题,不是理论风险。** WeKnora 的注释原文:「robfig/cron fires at absolute wall-clock times... So **multiple instances will fire at the same moment**」—— robfig 不知道也不关心有几副本,所有副本在同一绝对时刻一起触发。这是选型时**唯一真正要自己解决**的问题,其余全是配套。
2. **`cron + asynq` 的分层是真实现的路,不是纸上谈兵。** §1.5 说的演进路径,WeKnora 就是这么跑的:cron 只负责「到点了入队」,重活交给 asynq。
3. **`Stop()` 的优雅停机写法**:`ctx := s.cron.Stop(); <-ctx.Done()`(`scheduler.go:78-81`),与我 §2.9 一致。
4. **`cron.Recover` 是必须的**(`scheduler.go:45`),与我 §2.4 一致。

**再说它暴露了我方案里两个洞的**(已回填到 §2.3 / §2.4 / §6.2 / §7):

- 我漏了**热更新**:WeKnora 的 `AddOrUpdate` / `Remove`(`scheduler.go:84-109`)在 DB 改了频率后立刻 `Remove` 老 entry + `AddFunc` 新 entry。**我 §3 的 PATCH 只写了「写 DB」,漏了「立刻重注册 cron entry」—— 那样改频率要等重启才生效。**
- 我 §2.5 把「无 Redis 时怎么去重」写成了「基本不去重」,而 WeKnora 的第一层是**查 DB**(`HasRunningSync`,`datasource_repo.go:193`),不依赖 Redis 就已经能防住主要场景。我的 `sys_job_run` 表本来就够用,却没利用起来 —— 回填成 §2.3 的 Layer 0。

⚠️ **但它的去重分支其实没被测到**(见 §7),别照抄它的测试强度。

### 1.3 三个候选逐个看

| | **robfig/cron/v3** | **go-co-op/gocron/v2** | **hibiken/asynq** |
|---|---|---|---|
| 本质 | cron 表达式解析 + 进程内调度 | 链式 API 的任务调度器 | Redis 支撑的**任务队列**(不是调度器) |
| 依赖 | **零依赖**,3 个文件,MIT | MIT | MIT,但**Redis 是硬依赖** |
| 版本状态 | v3.0.0(2019-06 起),未归档,MIT | v2,MIT | v0.x,API 未冻结 |
| 分布式去重 | ❌ 自己写 | ✅ Locker / Elector(**在独立仓库** `go-co-op/gocron-redis-locker`) | ✅ 原生 |
| 持久化 / 重试 / 队列 | ❌ | ❌(UI 在独立项目 `gocron-ui`) | ✅ |
| 多副本去重锁的实际成本 | ~60 行 Lua | 引入独立仓库 + 第二个 Redis 客户端 | 全家桶 |

### 1.4 为什么是 robfig

**① 我们真正缺的东西,三个库一个都不提供。**

需要的是:任务注册表、分布式锁、执行历史表、手动触发 API、Prometheus 指标、优雅停机。这 6 项 robfig 0 个,gocron 0 个,asynq 只给「队列」这一项。三个库都只覆盖了「什么时候触发」—— 而这一项恰恰是**唯一不值得自己写**的部分(cron 表达式的解析、时区、DST、`@every` 描述符是纯边缘情况堆出来的)。

**② gocron 的 Locker 是「另一个 Redis 客户端 + 它自己的日志 + 它自己的降级判断」。**

这直接违反本仓已经花了三个 session 在收敛的那条规矩 —— 「有没有 Redis」只能在一个地方判断(`kvstore.Resolve` / `cachex.Build` / `auth.ResolveRevocation` 三处,都是同一个模式)。引入 gocron locker 等于开第四个判断点,而它的失败模式我们看不见、也接不进 `app_*` 指标。自己写 60 行 Lua,锁的 TTL、续期、降级全部在我们自己的日志和 metrics 里。

**③ asynq 是队列,不是调度器,范畴不对。**

asynq 解决的是「5 万条上传任务要重试、要背压、要能重放」。我们现在的任务是「每天 03:00 清 30 天前的执行记录」—— 为了这个引入 Redis 强依赖队列,是拿最重的工具解最轻的问题,而且直接推翻本仓 `auto|redis|memory` 的整套降级设计。

**④ robfig 零依赖这一点在这个仓里是硬价值。**

本仓已有 30+ 直接依赖、阿里云 SDK 全家桶、casbin、gorm、hertz。为一个「解析 cron 表达式」引入第二个调度框架,不值。

### 1.5 什么情况下我会改主意

**明源增量同步(需求 #1)如果将来要做到「5 万条、失败重试、积压可见、手动重放」,就上 asynq —— 但挂在 cronx 底下当 worker backend,不换调度层:**

```
cronx 触发 → asynq Enqueue → worker 消费
```

触发仍然是 cron(调度语义不变),执行搬到队列(执行语义变强)。`Job.Handler` 从 `func(ctx)` 变成「enqueue + return」,对上层 API、前端页面、监控全透明。**这是演进路径,不是现在的方案。**

### 1.6 用 robfig 必踩的坑(直接写进代码注释)

**第一个坑:5 段还是 6 段。我们和 WeKnora 明确分歧。**

WeKnora 开了 `cron.WithSeconds()`(`scheduler.go:44`),全部用 6 段(`0 0 * * * *`、`*/2 * * * * *`),连测试都靠 `* * * * * *` 每秒触发来等 tick。他们的场景合理 —— 数据源同步粒度可以到分钟级以下。

**本模块不开 `WithSeconds`,用标准 5 段。** 理由:

- 框架任务的粒度全是小时/天级(`0 3 * * *`),6 段在这里纯粹是多写一段、多一个写错的机会
- **6 段表达式在前端是给用户填的**,多一个字段就多一类「我以为填了秒其实没填」的投诉
- WeKnora 前端也是把 cron 表达式原样给用户填(`DataSourceEditorDialog`),且只对 5 个预设做了中文映射,其余原样显示(`frontend/src/utils/cronHumanize.ts:4-10`)—— 表达式可读性差是这套方案的通病,我们要靠 §3 的「未来 5 次预览」补掉

```go
// ⚠️ 必须 WithLocation,不能用 time.Local。
// 容器里 TZ 没设时 time.Local == UTC,`0 3 * * *` 会在北京时间 11:00 跑。
// 这不是理论风险 —— 我们 config 里 system.timezone 写着 Asia/Shanghai,
// 而进程时区是 UTC,两者不一致时**看起来配置生效了,实际没生效**。
// WeKnora 没设 WithLocation,是它还没踩到这个坑(它没配时区敏感的任务)。
cron.New(
    cron.WithLocation(loc),   // ← 必须
    cron.WithChain(
        cron.Recover(cronxLogger{}),          // panic 兜底
        cron.SkipIfStillRunning(cronxLogger{}),// 同 key 不堆积
    ),
)
```

另外三个坑:

1. **`SkipIfStillRunning` 只在单副本内生效**,跨副本必须靠 §2.3 的锁。WeKnora 只用了 `Recover`,防重叠靠 Layer 0 的 DB 查询 —— 两条路都行,我们两条都要。
2. **`cron.ParseStandard` 在保存时就该用来校验表达式**。WeKnora 的 `addEntryLocked` 在 `AddFunc` 返回 err 时直接跳过注册(`scheduler.go:124-126`)—— 如果没有 UI 拦截,表达式写错的后果是**任务静默不跑,日志里一行 WARN 都没有别人的**。我们前端有 `POST /jobs/validate` 兜住。
3. **robfig 不提供「手动触发」**。`POST /:key/run` 必须走我们自己的通道(§2.4),不能指望 `cron.Run(id)` —— 它是立刻执行当前 entry,但那绕过了锁、history、超时三层。

## 2. 设计

### 2.1 分层:代码定义任务,数据库只存运行态

沿用本仓「字典 = 代码 enum 契约的中央仓库,禁止新增/删除」([dict-readonly-edit-mode]) 的同一条规矩:

```
handler   ← 只在代码里(Go 函数),DB 里凭空长不出任务
cron_expr ← DB 可覆盖(改频率是运维刚需),留空则用代码里的默认值
enabled   ← code.Enabled && DB.Enabled(DB 行不存在时只看 code)
```

**为什么允许 DB 覆盖 cron 表达式**:把「每天 03:00 清理」改成「每天 05:00」是真实的运维需求,不能为了纯洁性逼人改代码重发版。但**只允许改时间,不允许改任务本身** —— 否则就是「删一条字典项」那种已经在本仓踩过一次的问题。

**删除任务 = 从代码里删。** DB 行残留由启动时的 reconcile 检出(`is_active=0` + WARN),不会复活。

### 2.2 Job 定义

```go
// pkg/cronx
type Job struct {
    Key         string        // 全局唯一,snake_case;框架任务前缀 framework.,业务任务前缀 biz.
    Name        string        // 中文名(展示用,DB 行里可覆盖)
    Description string
    Cron        string        // 代码默认表达式(DB 可覆盖)
    Timeout     time.Duration // 单次执行超时,0 → 配置默认 30m
    Enabled     bool          // 代码侧开关;DB 再叠一层 AND
    Handler     func(ctx context.Context) error
}
```

⚠️ **`Handler` 必须幂等。** 见 §2.5 —— 这是模块级的硬契约,不是建议。

### 2.3 两层去重(L0 查库 / L1 加锁)

多副本去重要防两件不同的事,**只防一件不够**:

- **防「上一次没跑完就又跑」** —— 长任务 + 高频 cron 天然重叠
- **防「两个副本在同一瞬间同时开跑」** —— robfig 按绝对墙钟时刻触发,所有副本在同一毫秒醒

#### Layer 0:查库(免费,无 Redis 也有效)

```sql
SELECT 1 FROM sys_job_run WHERE job_key = ? AND status = 'running' LIMIT 1
```

**这张表我们本来就要建**(`sys_job_run` 是执行历史,`status='running'` 的行天然就是「谁在跑」),所以 Layer 0 是一行索引查询,成本可忽略,而且**不依赖 Redis**。

> WeKnora 的第一层就是这个 —— `HasRunningSync`(`internal/datasource/scheduler.go:150` / `datasource_repo.go:193`),它把「上一次还在跑就跳过」交给 DB 而不是 Redis。这个选择是对的:**DB 是所有副本都有的东西**,拿它做第一层,比任何外部锁服务都少一个失效点。

⚠️ **但 Layer 0 有竞态**:它是 check-then-act。两个副本在同一毫秒都 SELECT 到「没在跑」,然后都 INSERT,都跑。**关掉这个窗口是 Layer 1 的唯一职责。** 我们不能只靠 Layer 0(也不能只靠 Layer 1 —— Layer 1 的 TTL 一到,长任务还没跑完锁就没了)。

#### Layer 1:Redis 锁(关掉 Layer 0 的竞态窗口)

```go
// pkg/cronx/lock.go
type Locker interface {
    // TryLock 返回是否拿到。没拿到 = 别的副本在跑。
    TryLock(ctx context.Context, key, owner string, ttl time.Duration) (bool, error)
    // Renew 只有持锁方能续期(compare-and-pexpire)
    Renew(ctx context.Context, key, owner string, ttl time.Duration) (bool, error)
    Unlock(ctx context.Context, key, owner string) error  // compare-and-delete
}
```

两条 Lua,都是 CAS:

```lua
-- renew: 只有值还是我才续期
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0
-- unlock: 只有值还是我才删
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

`owner` 用 `instanceID + 启动时刻 + 随机串` —— 必须是**每次运行都不同**的值。用固定的 instanceID 的话,A 副本重试两次会拿到同一个 owner,第一次的 CAS 释放就会误删第二次的锁。

**三个必须写进注释的坑:**

1. **释放必须是 CAS,不能 `DEL`。** 任务 A 跑超时 → 锁 TTL 到期 → B 抢到锁开始跑 → A 结束时执行 `DEL` → **把 B 的锁删了**。C 副本立刻抢到并发跑。CAS 是唯一防线。
2. **锁 TTL 必须显著小于任务时长,或者开看门狗续期。** 否则锁在任务跑到一半时自然过期,第二个副本直接抢进来。默认 `lock_ttl: 30s` + 续期间隔 `ttl/3`,长任务全程续。
3. **无 Redis 时退化成「只有 Layer 0」,不是「完全不防」。** 见 §2.5。

### 2.4 执行一次

```
触发(定时 or 手动)
  → Layer 0: SELECT 1 FROM sys_job_run WHERE job_key=? AND status='running'
      └─ 有 ──> 跳过(上一次还在跑)
  → Layer 1: TryLock
      └─ 失败 ──> 定时:计 app_job_lock_skipped_total + DEBUG 日志,**不写执行记录**
              └──>   手动:HTTP 409「任务正在执行中」(同步返回,运维立刻知道)
  → 写 sys_job_run(status=running, trigger_type, instance_id, trace_id, degraded)
  → ctx, cancel := context.WithTimeout(ctx, job.Timeout)
  → 看门狗 goroutine 每 ttl/3 续期锁
  → job.Handler(ctx)   ← panic 由 cron.Recover + 本模块双保险拦住
  → 停看门狗 → Unlock(CAS)
  → 更新 sys_job_run(status=success/failed, finished_at, duration_ms, error 截断 2KB)
```

**两层各挡各的,别指望其中一层**:Layer 0 挡住长任务重叠,Layer 1 挡住同一毫秒的双开。只上 Layer 0 → 竞态;只上 Layer 1 → 长任务跑到一半锁过期了照样重叠。

**定时触发抢不到锁时不写执行记录**:10 个副本每分钟各写一条「我被跳过了」,历史表会被噪声淹掉,而真正的信息(「去重生效了」)用 metrics 一个 counter 就表达得更准。手动触发是例外 —— 它必须给调用方一个同步反馈,所以走 409,不进历史表。

> WeKnora 这里选择**写**一行 `SyncLogStatusCanceled`(`scheduler.go:186-190`)。它的场景是单个数据源、用户会在 UI 上看到「这次为什么没跑」,值得留痕。我们是全平台 N 个任务 × 10 副本,同样的做法会把历史表冲垮 —— 除非将来某个任务确实需要「为什么这次没跑」的可追溯性,再按任务单独开。

**`error` 字段截断 2KB**:一次 panic 的 stack trace 轻松几十 KB,不截断的话单条记录就能把表撑爆。

### 2.4.1 改频率必须热更新,不能等重启

⚠️ **这是最容易漏的一条**。`PATCH /jobs/:key` 改了 `cron_expr` 之后,只写 DB 是不够的 —— robfig 已经注册好的 entry 还挂着旧表达式,**要等进程重启才生效**。

```
PATCH /jobs/:key
  1. 校验新表达式(POST /jobs/validate 同一套 cron.ParseStandard)
  2. 写 DB
  3. 若 cron 表达式变了:
       old := entries[job.Key]
       cron.Remove(old)              // ← 漏了这步,改了不生效
       new := cron.AddFunc(newExpr, ...)
       entries[job.Key] = new
  4. 若启停变了:
       停用 → cron.Remove(entries[job.Key])
       启用 → cron.AddFunc(...)
```

`entries map[string]cron.EntryID` 要有 `sync.RWMutex` 保护(WeKnora 用了 `sync.Mutex`,`scheduler.go:33-34`)—— 注册表在启动时批量写、运行期由管理端 API 改,是并发读写。

> 这也是 robfig 没有的东西:`cron.Cron` 内部有锁保护它自己的 entry,但**你要从外部按 job_key 反查 entry id**,就得自己维护这张映射。WeKnora 的 `entries map[string]cron.EntryID` 就是干这个的,照抄。

### 2.5 无 Redis 时怎么办(本模块最容易做错的地方)

| 场景 | 缓存 / 吊销的现行做法 | **cron 该怎么做** |
|---|---|---|
| 后端不可用 | 缓存 → fail-open(退回查库);吊销 → fail-**closed**(宁可全拒) | **降级但不停摆:只剩 Layer 0 + 大声告警 + 写进执行记录** |
| 理由 | 缓存失效只影响性能 | 重复执行会**写坏数据**(明源同步写两遍、清理删两遍) |

两个极端都不对:

- **直接抄缓存的 fail-open**(无 Redis 就随便跑)漏掉了「重复执行 = 数据错误」这一档
- **直接 fail-closed**(没锁就不跑)也不行 —— Redis 抖一下就让全站定时任务停摆,明源同步不更新、过期授权不下榜,是**更难发现的静默故障**

**折中的准确表述(因为有 Layer 0,比原来想的乐观)**:

> 降级后**仍然防得住「上一次还在跑」**,防不住「同一毫秒双开」。

这个区别要写进告警文案 —— 写「可能重复执行」运维会当成「一定会重复」从而关掉全部任务;写清楚降级后**还剩哪一层**,运维才知道自己承担的实际风险有多大。

**三条支撑:**

1. **所有 `Handler` 必须幂等**,这是模块硬契约。绝大多数框架任务天然幂等:
   ```sql
   UPDATE biz_family_grant SET status='expired'
    WHERE status='active' AND expires_at < NOW()   -- 跑两遍结果一样
   ```
   `DELETE FROM sys_job_run WHERE started_at < ?` 同样幂等。
2. 降级时照常执行,但每次运行:WARN 日志带 `job_lock_degraded=true`、执行记录写 `degraded=true`、管理页顶部挂红色横幅 + `/readyz` 降级。
3. **声明为非幂等的任务(`Job.Idempotent = false`)在降级模式下直接跳过 + 告警**,不赌。

`lock_mode: off` 显式关锁 —— 单副本开发/预发用,启动打日志说明「没锁」。

配置档位跟本仓同构:

| mode | 行为 |
|---|---|
| `auto`(默认) | 有 Redis 用 Redis 锁,没有退**进程内锁** + 降级告警 |
| `redis` | 强制 Redis,没配直接启动失败(**生产多副本必须用这个**,与 `kv.mode` / `auth.revocation_mode` 同一条规矩) |
| `memory` | 进程内锁(用 `syncx` 已有原语),即使有 Redis 也不连。仅单副本 |
| `off` | 完全不锁,谁到谁跑。**仅本地开发** |

### 2.7 崩溃遗留的 `running` 行 —— 必须自愈

进程被 kill 时,`status=running` 的行**永远不会自己变 failed**。历史表会逐渐堆满「幽灵运行中」,而且管理页上显示为正在执行,运维会以为任务还挂着。

**启动时扫描修复**:

```go
// main.go 装配 cronx 时跑一次
// 条件:status='running' AND started_at < now - (job.Timeout + 10min)
// → 置 failed,error='进程异常退出(实例 xxx),启动时回收'
```

不需要心跳。理由:真在跑的任务,`started_at` 到现在也不会超过它自己的 Timeout —— 反正到了 Timeout 它自己就会被 ctx 取消并写成 failed。判据是**时间**,不是**实例存活**,这样也就不需要额外的心跳表和心跳 goroutine。

### 2.8 配置

```yaml
# ========== 定时任务(cronx) ==========
job:
  enabled: true
  # ⚠️ 必须显式写,不能留空取 time.Local —— 容器里 TZ 未设时 time.Local == UTC,
  #    `0 3 * * *` 会跑在北京时间 11:00,而配置文件里明明写着 Asia/Shanghai。
  timezone: Asia/Shanghai
  lock_mode: auto         # auto | redis | memory | off
  lock_ttl: 30s           # 锁 TTL;长任务靠看门狗每 ttl/3 续期
  lock_renew: true        # 长任务续期开关
  default_timeout: 30m    # Job.Timeout 为 0 时用这个
  shutdown_timeout: 30s   # 优雅停机等在跑任务的上限
  history_retention_days: 30
  history_retention_max: 50000   # 条数上限(与天数双保险)
```

`history_retention_days` / `history_retention_max` 是两个而不是一个:天数防「长尾运行」,条数防「一天跑几万次」把表撑爆。

### 2.9 优雅停机

沿用 `piiaudit` / `cryptaudit` 已有的 stopCh/doneCh 范式,但多一步:**停机要等在跑的任务**。

```
Shutdown(ctx):
  1. cron.Stop()                    # 不再触发新的
  2. 等在跑任务完成,上限 cfg.ShutdownTimeout
  3. 超时未完成的 → 用 shutdownCtx 取消它们的 ctx,记 failed
  4. flush 历史批写缓冲(同 cryptaudit 模式)
  5. 停看门狗
```

第 4 步不能省:执行记录是异步批写的,直接退进程会丢掉最后一批 —— 而那批里很可能正好是「停机时被取消的任务」这条最该看到的记录。

## 3. HTTP API

基路径 `/rapid-admin/v1/system/jobs`(与 `/system/dicts` 同一 group)。

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|
| GET | `/jobs` | `job:list` | 任务列表(代码注册表 × DB 覆盖合并后的**生效配置** + 运行时状态) |
| GET | `/jobs/:key` | `job:list` | 详情 + 最近 10 次执行 |
| POST | `/jobs/validate` | `job:list` | 校验 cron 表达式,返 `valid` + **未来 5 次触发时间** |
| PATCH | `/jobs/:key` | `job:update` | 改 cron 覆盖值 / 启停 / 备注。**必须立刻重注册 cron entry**(§2.4.1),不能只写 DB |
| POST | `/jobs/:key/run` | `job:run` | **手动触发**,返 `202` + `run_id`(不阻塞) |
| GET | `/jobs/:key/runs` | `job:list` | 该任务的执行历史(分页) |
| GET | `/jobs/history` | `job:list` | 全部执行历史(跨任务,管理页 Tab2 用) |
| GET | `/jobs/history/:runId` | `job:list` | 单次执行详情(轮询手动触发结果) |
| DELETE | `/jobs/history` | `job:history:purge` | 清历史(按保留期) |
| GET | `/jobs/runtime` | `job:list` | 运行时健康:`lock_mode` / `redis_enabled` / `degraded` / 各任务下次触发时间 |

**几个刻意的设计:**

- **`POST /:key/run` 返 202 不阻塞。** 任务可能跑几分钟,HTTP 挂着不现实。返 `run_id`,前端轮询 `GET /jobs/history/:runId`。SSE 推送留到 P1(本仓已有 SSE 基础设施:`auth/permission-events` + 25s 心跳那套)。
- **`POST /jobs/validate` 是给前端用的。** 输一个表达式,后端用 `cron.ParseStandard` 校验并用 `Schedule.Next()` 循环 5 次返未来触发时间。**成本极低、体验提升极大** —— 运维改频率时能立刻看到「下一次是明天 03:00」,而不是提交后等到 03:00 才发现表达式写错、任务根本没注册。
- **锁冲突对定时/手动区别对待**(见 §2.4)。

⚠️ **路由注册的坑**:`GET /jobs/runtime`(静态段)与 `GET /jobs/:key`(通配段)在同一层。hertz 路由树对 static + param 混合的处理在不同版本间有差异。**实现时先写一个注册冒烟测试**;若 panic,把 runtime 挪到 `/system/job-runtime`。这属于「不做冒烟测试就会在启动时炸」的坑,必须提前钉住。

### 6.4 cron 表达式的人类可读化(照抄 WeKnora 的做法)

`0 3 * * *` 直接显示在表格里没人看得懂。WeKnora 的解法(`frontend/src/utils/cronHumanize.ts:4-20`)很朴素:**预设表达式映射到中文,匹配不上就原样显示**。

```ts
const CRON_PRESET: Record<string, string> = {
  '0 3 * * *':   '每天 03:00',
  '0 4 * * *':   '每天 04:00',
  '0 * * * *':   '每小时',
  '*/30 * * * *':'每 30 分钟',
  '0 0 * * 0':   '每周日 00:00',
}
export function humanizeCron(expr: string): string { return CRON_PRESET[expr] ?? expr }
```

**照抄,但比它多给一层**:预设命中显示中文,**未命中时由后端 `POST /jobs/validate` 返回的未来 5 次触发时间兜底** —— 「未命中」最大的问题不是看不出意思,而是**不知道它下次什么时候跑**。两层叠加后,表达式再冷僻也能一眼看出它是不是自己想要的。

同一文件里的 `relativeTime(ts)` 也直接可用(3小时前 / 2天前,超过 30 天回落日期)—— Tab1「上次执行」列需要它。

**落地情况(2026-10-30,M120 —— 与上面这段规划不一致,以本节为准)**:

预设映射表这条路**没有照抄** —— 一张 `Record<string, string>` 只认那 5 个写死的字符串,
而运营真正会写的是 `7,17,27,37,47,57 * * * *`(本仓 `sms_template_sync` 就是这一条)、
`17 4 * * *` 这类**没进过任何预设**的表达式。命中不了就"原样显示"等于什么都没做。

实际落地是一个**真解析器**(`web/src/pages/system/job/cronDescribe.ts`):
按 robfig 的语义把 5 段展开成取值集合,再按形态组句。三条硬规则:

1. **描述不了就闭嘴** —— 认不出的形态返回 `null`,界面上一句都不显示。
   描述错了比不描述更糟:运营会照着错的描述去核对"我以为它是每天跑的"。
2. **不猜 robfig 的语义** —— robfig v3 在**日和星期同时受限时走 OR**
   (`dom || dow`,见 `spec.go` 的 `dayMatches`),这种表达式含义不唯一
   ("每月 1 号"和"每周一"两个都触发),一律不描述。月份受限同理不描述。
3. **"每 N 小时 / 每 N 分钟"必须走满一整轮** —— `0 0,1,2,3 * * *` 一天只触发 4 次,
   说成"每 1 小时"是错的;只有 `0 */2 * * *`(0,2,…,22)这种走满一圈的才叫"每 N 小时"。
   同理 `7,17,27,37,47,57 * * * *` 不是"每 10 分钟"(它跳过了每个整点的 0 分),
   只能逐字列出分位。

"未命中时由后端返回未来 5 次触发时间兜底"这层**本来就有**(`M69` 做的
`CronInput` → `GET /platform/jobs/cron/preview`),M120 是在它上面**加**一句人话,
两层是叠加关系,不是替代关系。

英文侧的星期名是**先翻译再拼接**的(不是参数):`weekly` 键是 `每周{dows}` / `Every {dows}`,
`{dows}` 装的是**已经翻译好的**星期名列表 —— 参数是字符串,参数里的东西没法再翻译。

**M123 补做(2026-10-30 —— 分钟列表这一形态必须把「范围」说全)**:

M120 把 `7,17,27,37,47,57 * * * *` 描述成「每小时第 7、17、27、37、47、57 分」。
这个说法**只说了一半** —— 它没说这条任务的**日期范围**。
「每小时第 7 分」读起来像"每天每个小时的第 7 分",
但同样的分钟列表配上 `7,17 * * * 1`,它其实是"**每周一**的每小时第 7、17 分" —— 差一个量级。

用户把口径说准了(原话):

> `7,17,27,37,47,57 * * * *` 里面后面几个 `*` 的意思就是表示**每小时、每日、每月、每星期**。
> 然后前面的数字是**第几分钟**。所以要这样去匹配翻译。

按这个口径,分钟列表这一形态**把日期范围整个写进句子**,不再"范围 + 分句"两块拼:

| 表达式 | 描述 |
|---|---|
| `7,17,27,37,47,57 * * * *` | 每月每日每星期每小时的第 7、17、27、37、47、57 分钟各执行一次 |
| `7,17 * * * 1` | 每周一每小时的第 7、17 分钟各执行一次 |
| `7,17 * 1 * *` | 每月 1 日每小时的第 7、17 分钟各执行一次 |
| `7,17 * */5 * *` | 每 5 天每小时的第 7、17 分钟各执行一次 |

实现上三条约束:

1. **四句都是完整的一句话**,不是"范围 + 分句"拼出来的 ——
   中文「每月每日每星期每小时的第 7 分钟各执行一次」中间**不能有空格**
   (「…每小时的第…」),英文 "Every hour at minutes 7 on …" 又**必须有空格**。
   拼接规则随语言变,那就得把分隔符也做成字典项(三个可变件拼一句);
   不如让翻译直接看到**整句** —— 语序也能整句调整,不会被拆散的片段绑死。
2. **日期拆成"形态 + 参数"两层**(`DayScope`):同一形态在短句式
   (`每周{dows}`)和长句式(`每周{dows}每小时的第 {mins} 分钟各执行一次`)里
   是**两个不同的模板**,所以 `describeDay` 返回"形态 + 插值参数",
   由**调用点**决定用哪句模板。
3. **分钟不补零**("第 7 分"不是"第 07 分")—— 补零是给 `03:00` 这种**时刻**用的;
   分钟列表里的数本来就是裸数字。

### 11.2 与规划不符的 6 处(以实测为准)

**D1 — HTTP 路由是 7 条,不是 10 条。**
原 §5/附录写的「10 路由」是按「列表 + 详情 + 改 + 删 + 触发 + 运行态 + 记录 + 预览 + …」
逐项列的,落地时砍掉了 create / delete(理由见 §8)与重跑接口(手动触发即是重跑)。
最终 7 条:**没有 create / delete**,与 dict / config 同一条规矩 —— DB 里长不出任务。

**D2 — 手动触发同步返回 200,不是 202。**
这是刻意偏离 REST 惯例,换取三样东西:失败原因 / duration / trace_id 都在响应体里。
用 202 的话这些全丢,而且「点了没反应」会立刻变成「是不是没生效」的重启冲动。
⚠️ **由此产生一条前端必须遵守的契约**:任务**自身**失败时返回
**HTTP 200 + `status:"failed"` 的记录**(不返 error);只有「没能跑起来」
—— 404 不存在 / 403 已停用 / 409 正在执行 / 500 去重降级 —— 才返 error。
前端必须判 `status !== 'success'`,不能只看 HTTP 码。
混成一个 500 的话,监控上分不开「任务跑了但失败」和「你无权触发」。

**D3 — 执行记录是同步写,没有异步批写。**
原 §5 的文件清单里写了 `history.go 历史异步批写(同 cryptaudit 模式)`,实际**没有这个文件**,
`CreateRun` / `FinishRun` 直接在 `Trigger()` 里同步调。两条理由:
1. 手动触发要把 duration / error / trace_id 一起返回 —— 异步批写意味着响应里的
   duration 是空的,那就等于放弃 D2 的全部理由。
2. Layer 0 去重依赖 `status='running'` 那行**在 handler 开跑之前就落库**。
   异步批写会开一个「查库时记录还没写进去」的窗口,去重直接失效。
代价是多两次 DB 往返(一次 Create + 一次 Finish),相对任务本身的耗时可忽略;
换来的是去重链路没有时序假设。

**D4 — 文件划分与 §5 清单不同。**
规划里的 `run.go` / `history.go` 两个文件不存在。执行逻辑并进了 `scheduler.go`
(Trigger / TriggerNow / Reload / Shutdown 都在一个文件里,因为它们共享同一把 `entries` 锁),
持久化边界单独抽到 `store.go`(接口 + gorm 实现 + nop 实现)。
**抽 `store.go` 比规划更进一步**:它让 45 条单测一条都不连真 DB。

**D5 — 分页字段是 `page` / `size`,不是 `page_size`。**
`handler.GetPage` 读 `c.Query("page")` / `c.Query("size")`(`api/handler/handler.go:86-92`),
`response.PageData` 也只回 `size`(`pkg/response/response.go:23-28`)。
⚠️ 本仓共享的 `PageResponse<T>`(`web/src/types/api.ts:117-122`)写的是 `page_size`,
**照抄它会让每页条数永远落到后端默认值上,而且看起来一切正常**。
故 `types/job.ts` 单独定义 `JobRunPage`,不 `extends PageResponse`。
⚠️ 已知存量 bug:`web/src/pages/system/config/audit.tsx` 现在就是这个状况
(每页条数选了不生效)。**本轮未修**,不在 cron 模块范围内,单列待办。

**D6 — `cronx.Config` 里的 `HistoryKeepDays` / `HistoryKeepMax` 已删。**
M67 声明了这两个字段但**一行都没读过** —— 调度器从不自己清理历史。
清理归属是 M70 的 `framework.job_history_purge` 任务,它直接读
`config.JobConfig.HistoryRetention*`。留着这两个字段只会让人以为清理逻辑在调度器里,
找半天找不到。M70 一并删掉,并在 `Config` 上写明归属。

### 11.7 后续补做:M123 —— 分钟列表这一形态把「范围」说全(2026-10-30)

M120 的描述在**分钟是列表**、**小时不受限**这一形态上是**不完整的**:
它只说"每小时第 7、17、27、37、47、57 分",**不说日期范围**。

| 项 | M120 落地 | M123 修正 |
|---|---|---|
| `7,17,27,37,47,57 * * * *` | 每小时第 7、17、27、37、47、57 分 | **每月每日每星期每小时的第 7、17、27、37、47、57 分钟各执行一次** |
| `7,17 * * * 1` | 每周一每小时第 7、17 分(范围在前面) | **每周一每小时的第 7、17 分钟各执行一次**(范围并进整句) |
| `7,17 * 1 * *` | 每月 1 日每小时第 7、17 分 | **每月 1 日每小时的第 7、17 分钟各执行一次** |
| `7,17 * */5 * *` | 每 5 天每小时第 7、17 分 | **每 5 天每小时的第 7、17 分钟各执行一次** |

改的是**形态的表达方式**,不是**识别范围** —— 认不出的形态仍然闭嘴(§6.4 三条硬规则不变)。

**实现改动**:`describeDay` 的返回值从"日期短语(字符串)"改成
**"日期形态 + 插值参数"**(`DayScope`)。原因:同一形态在短句式和长句式里
是**两个不同的模板**(`每周{dows}` vs `每周{dows}每小时的第 {mins} 分钟各执行一次`),
返回字符串就没法两用。短句式由 `dayPhrase()` 还原,长句式由
`describeTime()` 直接选模板(`MINUTE_LIST_KEY` 按形态挑键)。

`TimeDesc` 加一个 `whole` 标记:长句式**自带完整句子**(日期范围已经写在里面),
所以 `describeCron` 拼装时**不再往前拼日期短语** ——
忘了这一条就是「每周一 每周一每小时的第 7、17 分钟各执行一次」。

**可逆探针 5/5 全部转红**:

| # | 拆掉什么 | 变红的断言 |
|---|---|---|
| C1 | `whole: true` 标记 | 「每周一 每周一每小时的第 7、17 分钟各执行一次」(范围被拼两次) |
| C2 | 分钟改回补零(`pad2`) | 「第 07、17、27 分」(时刻的补零规则不该用在分钟列表上) |
| C3 | 模板固定用 `minuteListAll` | 每周一 / 每月 1 日 / 每 5 天 三种形态全说错 |
| C4 | 中文字典改回旧短句式 | 「每小时第 7 分」(范围整个消失) |
| C5 | 英文字典改回旧短句式 | "At 15, 45 minutes past every hour" |

⚠️ **C1 是这轮最该有的一条**:「多拼一次范围」这种错,
**肉眼看截图很难发现**(句子读起来仍然通顺),只有逐字断言才抓得住。

产出:`cronDescribe.ts` + 两侧字典各 4 个键(替掉 1 个 `hourlyMinutes`)
+ 68 条 vitest(纯函数逐字断言)+ 5 条 `CronInput` 渲染用例
(证明这句话**真的渲染到了界面上**,而不只是纯函数返回得对)。
