# 数据字典管理规范

> **生效时间**: 2026-10-18
> **覆盖范围**: `sys_dict` 表 + 字典管理页(系统管理 → 数据字典)+ 全部业务页
> **配套约束**: [[dict-enforcement-5-layer]] (5 层防御) + [[dict-page-hardcoded-group-options-p0-2026-10-18]] (历史事故)

## 一句话总结

**字典 = 代码 enum 的中央仓库 + 显示属性的微调面板,不是自由 CRUD 工具。**

- ✅ **允许**: 编辑已有字典项的展示属性(`label` / `sort` / `is_active` / `description`)
- ❌ **禁止**: 新增字典项(走 seed 流程)
- ❌ **禁止**: 删除字典项(改 `is_active=false` 替代)

---

## 字典的两种属性

### 代码契约(强,任何人不能改)

| 字段 | 含义 | 例子 |
|---|---|---|
| `group_code` | 字典分组 ID | `user_status` / `delivery_stage` / `issue_priority` |
| `item_key` | 字典项 key | `user_status.active` / `delivery_stage.signed` |
| `item_value` | 字典项 value | `active` / `signed` |

**改 group_code / item_key / item_value 的影响**:
- 前端 `useDict(groupCode).getLabel(value)` 拿不到 label,显示退化成原 value
- 后端 GORM 查询 `Where("status = ?", "active")` 不受影响(后端用 value)
- 业务方投诉"为什么我看不到状态了" / "为什么显示'active'不显示'正常'"

### 展示属性(运营可调)

| 字段 | 含义 | 运营调整频率 |
|---|---|---|
| `label` | 中文显示名 | 中(产品改文案) |
| `sort` | 排序 | 低 |
| `is_active` | 启用/禁用 | 中(临时下线某项) |
| `description` | 说明 | 低 |

## 三条规则

### ❌ 规则 1: 禁止新增字典项

**为什么**: 新增字典项 = 孤儿数据(没有任何代码引用,前端 useDict 拿不到)。

**正确路径**:
1. `server/internal/seed/seed.go` 的 `mustDicts` 加 groupCode(强制契约)
2. `server/internal/seed/seed.go` 的 `seedAllDicts` 加种子项(每个 group 至少 1 条)
3. `web/src/types/dict.ts` 的 `DictGroupCode` 联合类型加(TS 自动补全)
4. `server/internal/seed/seed.go` 的 `dictGroupLabels` 加中文 label(给字典管理页下拉用)
5. 跑 `go run ./cmd/migrate -c configs/config.dev.yaml` 自动 seed
6. 跑 `pnpm tsc --noEmit` + `pnpm lint` 验证

**之后**: 跑 `SeedDictGuard` 验证不 panic(已在 migrate 末尾自动跑,commit fa4d5c3 修复)。

**如果想新增 item 不新增 group**:
- 不允许。所有新 item 必须先有 group(在 `mustDicts` 里登记)。

---

### ❌ 规则 2: 禁止删除字典项

**为什么**: 删除 = 破坏代码契约,前端 `useDict()` 拿不到 label。

**正确路径**: 在字典管理页点"编辑",把 `is_active` 改为 `false`(禁用)。
- **下线口径 = 不再提供新选择,既有数据照常可读**:
  - `useDict()` 的 **`options`** 只给 `is_active=true` 的项 → 下拉里自动消失;
  - `useDict()` 的 **`getLabel` / `getColor` / `raw`** **保留**禁用项 → 历史记录里已存了这个 value,
    表格照常显示中文标签和颜色(否则老记录会变成一串裸 value,比如 "closed" 而不是"已关闭")。
- **过滤发生在前端 `useDict`,不是后端**:
  - `GET /system/dicts` **一个端点**同时喂业务页下拉(`dictApi.byGroup`)和字典管理页浏览全表(`dictApi.list`),
    后端过滤 ⇒ 管理页看不到禁用项 ⇒ 运营**永远恢复不了**;
  - 后端 `ListDict` 返全表(正确),`ListDictGroups` 过滤(正确)—— 两个接口不矛盾。
- 后端 GORM 查询仍能命中(后端查 `Where("item_value = ?", ...)`)
- 数据保留,未来想恢复直接改回 `is_active=true`

> ⚠️ **2026-10-28(M107)补记**:这条规则以前**只写在文档里,代码从来没做** ——
> `useDict()` 的 `options` 每一项都 map 进去,后端也不过滤 ⇒ **"临时下线"是个死开关**,
> 11 个业务页的下拉里禁用的项照常出现。M107 已在 `hooks/useDict.ts` 补上过滤,并加了回归网
> (`web/src/hooks/__tests__/useDict.test.tsx`)。
> **教训**:规范里"前端会过滤"这种描述,**必须有一行代码 + 一条用例**撑着,否则它只是愿望。

---

### ✅ 规则 3: 允许编辑展示属性

**允许改的字段**:
- `label`(中文显示名)
- `sort`(排序,数字越大越靠后)
- `is_active`(启用/禁用,**boolean**:`true`=启用 / `false`=禁用)
- `description`(说明)

> ⚠️ **`is_active` 在 wire 上是 boolean,不是 1 / 0**(2026-10-28 M107 更正)。
> 后端 `model.SysDict.IsActive` 是 Go `bool`,`json:"is_active"` 序列化出来就是 `true` / `false`
> (SQLite 里存成 1 / 0 只是**存储层**表示,不是 wire)。
> 而字典页的表单层是 antd `Select`,它的 option value **只收 `string | number`**,
> 塞 boolean 进不去 ⇒ 前后端各有一层表示,靠两个纯函数显式转换:
>
> | 层 | 表示 | 位置 |
> |---|---|---|
> | 表单层 | `1` / `0` | `web/src/pages/system/dict/index.tsx` 的 `toFormIsActive` / `toWireIsActive` |
> | wire 层 | `true` / `false` | 同上(`toWireIsActive` 的返回值) |
>
> ⚠️ **wire 层必须是 boolean,不能退化成 1 / 0**:后端 `UpdateDict` 走 `h.BindJSON(c, &body)`
> 绑到 `model.SysDict`,Go 的 `encoding/json` 把 `1` 往 bool 字段塞会**直接报错**
> ("cannot unmarshal number into Go struct field ... of type bool")——
> 不是"当成启用",是**整条 PATCH 请求挂掉**。回归网:`web/src/pages/system/dict/__tests__/isActive.test.ts`。

**不允许改的字段**:
- `groupCode`(代码契约,EditModal 已 disabled)
- `itemKey`(代码契约,EditModal 已 disabled)
- `itemValue`(代码契约,EditModal 已 disabled)

## 违规检测

### 怎么知道有人违规了?

1. **有人绕前端调 API**:
   - 后端 POST /dicts 直接 404(路由卸了)
   - 后端 DELETE /dicts/:id 直接 404
   - 改用其他方式调 CreateDict / DeleteDict → service 直接返 403

2. **有人手改数据库**:
   - 没种子保护:改了数据库,跑 migrate 时 `seedAllDicts` 会**自动覆盖**回种子值
   - 这就是为什么 seed.go 里的数据是"代码契约的真相之源"

3. **有人改前端 PermButton.DICT_ADD / DICT_DELETE 引用残留**:
   - `web/src/constants/permissions.ts` 里这俩 perm 常量**保留**但**前端没人引用**了
   - 未来 `PermButton.DICT_DELETE` 可以标记 deprecated,本规范期不动

## 跟字典 5 层防御的关系

| 防御层 | 约束方向 | 拦截场景 |
|---|---|---|
| L1 seed guard | 后端启动时 | mustDicts 里某 group 没 seed → panic |
| L2 ESLint | 写代码时 | 硬编码 enum map → 红线 |
| L3 TS 类型 | 写代码时 | `useDict('随便')` → TS 错 |
| L4 pre-commit | 提交时 | 扫新增 STATUS_MAP → 阻断 |
| L5 集成测试 | 测试时 | mustDicts 被误删 → 测试红 |
| **本规范** | **运行时** | **用户在字典管理页乱增/删 → 路由卸掉 / service 403** |

**两者互补**:
- 5 层防御管"代码必须用字典"
- 本规范管"字典管理页别乱动"

12/15 上线后,这两套约束一起把字典变成"代码 enum 契约的强约束中央仓库"。
