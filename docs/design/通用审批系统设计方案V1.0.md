**这一节是 V2.0 的核心。** 每条都写了"什么时候该加回来",避免将来有人凭想象补功能。

## §2 设计决策

### D1 单租户,不加 `tenant_id`

仓库所有业务表都没有 `tenant_id`。审批表跟随之。外部引擎按多租户设计,每张表带 `tenant_id` 并进唯一索引 —— **本仓不需要,加了就是纯冗余索引开销**。

### D2 七张表,不合并

```
sys_approval_template        模板:一条审批链的定义
  └ sys_approval_stage       阶段:第几关、叫什么、全过还是一人过
      └ sys_approval_assignee_rule  审批人规则:这一关谁审
sys_approval_instance        实例:某条业务记录的一次审批
  └ sys_approval_task        任务:某个审批人在某一关的一个待办
sys_approval_round           轮次:每次提交的内容快照(V2.1)
sys_approval_log             日志:纯追加的审计流水
```

**为什么不把 stage 和 rule 合成一张**:`review_type`(全过/一人过)和"这一关有几个人审"是**关卡属性**,不是规则属性。合成一张就得在每个 rule 行上重复一遍关卡属性,而且没有天然位置放。三层是最小的正确形状。

**阶段用行式表存,不用 JSON 文档**:本仓的配置界面是**表格**(D3)。表格配置意味着管理员会查"哪些模板用了第 3 关"—— JSON 文档查不了。代价是丢掉任意嵌套/并行图能力,**而本设计本来就不要**(第 1 条)。

**日志不带 `seq`**:轮次靠"打回时把本实例所有 task 置 `stale`"表达(D4),不需要旁路推导边界。

⚠️ **`round_no` 只出现在两处,而且两处都只用于展示**:`sys_approval_round.round_no`(快照轮号)和 `sys_approval_log.round_no`(意见归属哪一轮,供前端分组)。**判定路径一条都不读它** —— 会签分母仍只看 `task.status`(§4.1)。理由:一个"当前轮次"的权威答案只能有一个,一旦判定也去读 `round_no`,写错它就从"历史展示错"升级成"审批算错票"。

### D3 配置用表单,不用拖拽画器

需求是"管理员设置多级审批,每一级指定审批人" —— **表格配最直观**。拖拽是好看不是必需,而拖拽设计器是前端 2000+ 行 + 节点坐标持久化 + 缩放/连线/撤销/兼容地狱。**页面里没有画布组件。**

### D4 轮次靠 `stale`,不靠日志分界

`task` 有第五个状态 `stale`,**只在打回时被写入**:

```
打回:  本实例所有 task(不管什么状态)→ stale
重提:  从第 1 关重新生成 task(全新行)
```

于是"本关的会签分母"= `status IN ('pending','approved','rejected')`,**`stale` 自然排除上一轮的行**。

对比:调研中见的另一种做法是从日志里算 `MAX(seq)` 定轮次边界,前提是所有写路径都严格按序插日志 —— **任何一条旁路写入就会把分界算错**。用数据状态表达边界,没有旁路可写。

历史不会丢:上一轮的意见全在 `sys_approval_log` 里。

**⚠️ `stale` 只是"判定机制",不是"历史展示机制"** —— 用户要翻"第 2 轮改了什么"时,`stale` 一行字也答不出来。所以 V2.1 加了 `sys_approval_round` 显式建表(§6①),但 **`stale` 一个字都没改**。两者不是两个真相源:`stale` 决定"这条票算不算数",`round` 决定"这条记录属于第几轮的内容快照",**引擎在同一个事务里写它们**,不存在能只写一边的地方。

### D5 或签 = 首个动作终局

| 关卡类型 | 某人通过 | 某人拒绝 |
|---|---|---|
| `all` 全过(会签) | 不推进,等其他 pending | **立即 `rejected` 终局**,其余 pending → `skipped` |
| `any` 一人过(或签) | **立即 `approved` 终局**,其余 pending → `skipped` | **立即 `rejected` 终局**,其余 pending → `skipped` |

即:**或签"谁先处理谁的说了算",会签"全过才过、一票否决"。**

⚠️ 调研中确认存在另一种或签语义:"或签某人拒绝**不**定局,等其他所有人投完"。**本版不采用**,理由三条:

1. **用户预期相反。** 中文语境里"或签"的直觉是"我拒绝,这事就该黄了",尤其**上级在或签名单里**的时候
2. V1 的或签关卡人数 ≤ 3,等待成本很低
3. 改成"拒绝不定局"只是 `reject` 分支里多一个条件 + 推进判定多认一个状态,**将来加的成本极低**(§12 第 5 条),不值得现在就付

### D6 打回只回发起人

你已拍板。推论:**没有 `RollbackTo` 列,没有 `ReturnStage` 列**。重提一律从第 1 关重走。

这同时简化了 `submit`:`returned → running` 和 `draft → running` 是**同一段代码**,只是起点不同。

**死循环防护**:实例保留 `return_count`,`>= 5` 时 `resubmit` 硬拒并提示"该单已打回 5 次,请联系管理员"。⚠️ 这个计数器**不是正确性关键路径**(没有并发写者 —— 只有发起人能 resubmit)。

### D7 模板不版本化,改结构时禁改

模板表一个 `code` 唯一索引,**没有 `version` 列**。

- 想改流程结构 → **新建一条模板**(新 `code`),老模板 `is_active=false`
- 想改已有模板 → **仅当该模板下没有任何非终态实例**(`draft`/`running`/`returned`)时,否则 `PUT` 拒绝并说明"该模板有 N 条在跑的审批,请新建一条代替修改"

这覆盖了"改配置影响在跑的实例"的全部风险(改阶段数、改审批人、改顺序),**代价是一个查询,而不是一整套版本机制**。

- **软删:`code` 改写为 `原code#deleted#<id>` 再释放** —— 与文件模块 M80 的做法一致(照抄,不发明)。不做的话"删掉再传同一个 code"会 duplicate key(唯一索引不含 `deleted_at`,软删行仍占槽位)
- 实例只存 `template_id`,不存阶段快照。**已完成实例的详情看日志,不看模板**,所以模板改名不会让历史记录失真

### D8 `BizHandler` 与审批同事务,失败整体回滚

```go
// service 包导出,业务线在 registry.go 按 biz_type 注册。
// ⚠️ 硬性约束:实现体只允许做同事务的 DB 操作。
//   禁止发短信 / 调三方 / 写文件 / 起 goroutine ——
//   这些不受事务保护,回滚也撤不掉,会造成"审批已通过但业务没动"。
//
// 🔴 **三个方法都收 tx**(2026-10-23 M84 改签)。原签名是
// `OnApproved(ctx, inst) error` —— 那样实现方只能拿自己持有的 db 去写,
// 那是**另一条连接、另一个事务**:实例回滚了业务写不会回滚,业务写成了
// 实例回滚不了。**D8 在原签名下根本无法实现**。收 tx 是它唯一能落地的写法。
type BizHandler interface {
    // ValidateBiz 发起时校验业务记录存在且状态允许发起。
    // 防止 biz_id 传错 → 审批单挂到一条不存在的记录上。
    ValidateBiz(ctx context.Context, tx *gorm.DB, bizType string, bizID uint64) error
    // OnApproved 审批通过。⚠️ 在事务内被调用,失败会回滚审批状态。
    OnApproved(ctx context.Context, tx *gorm.DB, inst *model.SysApprovalInstance) error
    // OnRejected 审批拒绝。同上。
    OnRejected(ctx context.Context, tx *gorm.DB, inst *model.SysApprovalInstance) error
}
```

**失败语义:整体回滚,报错,用户重试。**

这个决定**推翻了 V1.1 的方案**(当时想"不回滚审批,记 Error 日志 + 补偿任务"),理由:

1. **补偿队列/outbox 被 §1 第 7 条明确排除**。没有补偿队列,"不回滚"就是让审批单说"已通过"而业务记录说"待审",**不一致状态没有自愈路径**
2. **V1 的回调就是一次单字段 UPDATE**(`biz_digital_material.status: 1 → 2`)。这个操作失败,几乎必然是瞬时数据库错误;回滚后两边都没变,用户重试即可 —— **回滚在这里是自洽的**
3. **回滚的代价只是"用户以为没点上,再点一次"**。这在审批场景是可接受的体验;不一致状态的代价是不可接受的

代价写在这里:**将来 `BizHandler` 要发短信,本决定就不成立**,必须先补 outbox(§12 第 7 条)。

**注册方式**:按 `biz_type` 查注册表。

🔴 **未注册的 `biz_type` 硬拒,不是"WARN 并放行"**(2026-10-23 M84 改)。原设计想的是
"框架层不该因为某个业务没接回调就让全平台审批不可用" —— 但**放行等于"审批通过了
而业务状态永远不变"**,正是 R11 要防的那件事。**连草稿都不给建**(`NotImplemented`),
错误信息点名是哪个 `biz_type` 没注册,让业务方自己来改。
⚠️ M86 会对 material 强制注册并断言 —— 那时"未注册就硬拒"才有第一个真实调用方。

### D9 同一条业务记录只允许一个审批实例

`UNIQUE(biz_type, biz_id)` —— **不带任何"活跃"条件,是硬唯一**。

- 想对同一条记录审两次 → **业务侧建新记录**(比如"资料 v2"),而不是让框架放宽
- 打回后重提走 `resubmit`(同一实例),不撞索引
- **审批单不提供删除端点**(有意的):误建的只能 `cancel`。这样 `deleted_at` 永远为空,唯一索引上不会有"软删行占坑"的怪问题

⚠️ **两条推论,别踩**:

1. **`cancel` 只允许从 `draft` / `returned`,不允许从 `running`。** 理由:已经送审的单子可能有人正在审,申请人单方面作废会打断别人的工作。要撤 → 找当前关审批人 `reject` 或 `rollback` 打回
2. **`cancel` 之后 `(biz_type, biz_id)` 的审批槽位被永久占用。** 这是有意的:`cancel` 的语义是"我不想审这个了",不是"我还没想好"。**没送审过的单子根本不该走到 `cancel` —— 它该留在 `draft`。**

   > **V2.1 找到了让这条边角不再硌手的办法,而且比放宽索引便宜得多**:`PUT /approvals/:id/draft`(§7.1)允许在 `draft` 状态下**直接改 `template_code`** —— 阶段是在 `submit` 时才读的,不是建草稿时快照的,所以改字段即可,不用重建任何东西。
   > **"建草稿时选错模板"这个最高频的场景,现在根本不需要 `cancel`,也就碰不到这条边角。**
   > 而 `draft` 阶段本来也没有 round 快照(没提交过),改多少次都不留痕、不占轮次、不产生垃圾。

### D10 不维护会签计数器

task 表**没有** `total_count` / `approved_count` 之类的冗余列。会签判定在持有实例行锁的前提下,每次**重新 COUNT**(§4.1)。

理由见 §14.2 —— 有开源项目就是这么写崩的。

### D11 强制"提交人 ≠ 审批人"

复用已分配的 `errcode.SameAuditor = 20200`。发起时若解析出的审批人集合**含发起人** → 直接报错。

⚠️ 三种 `dept_leader` 都可能解析出发起人自己(小部门里负责人就是自己),这不是配置错误而是数据常态 —— 所以**必须在解析后判,不能靠配置校验**。

⚠️ **`dept_leader` 必须先定"发起人在哪个部门",而一个人可以属于多个部门**:`sys_user_department.is_primary`(`department.go:39`)就是干这个的。
**本仓目前没有任何 service 用过 `is_primary` 查"用户的主部门"**(只有 seed 写入和模型定义)—— 所以 M85 要自己写这条查询,**不能假设有现成方法可调**。
三种落空都要走 §5.3 的报错路径,**不许静默往上爬一格**:
| 落空情形 | 后果 |
|---|---|
| 用户不属于任何部门 | `dept_leader` 解析为空 → submit 失败 |
| 用户多部门且全都不是 primary | **数据脏**。同上报错,但错误信息要点名"该用户没有主部门",否则用户会去改审批流程配置,方向就错了 |
| 部门 `leader_id = 0` | 该级无人可审 → 报错,**不许跳到上一级**(跳了就成了另一套流程) |

### D12 审批人认 `user_id`,不认 `identity_id`

审批是"**这个人**干的",不是"这个身份干的"。切了身份不影响他能不能审批。

**推论**:会签去重按 `sys_user.id`,**不按 identity**。否则同一人两个身份会拿到两条 task,会签永远凑不齐。

### D13 资源码分 `flow:*` / `approval:*` 两组

`middleware.RBAC(module, action)` 是两段签名,塞不下两个子域。

**推论:`approval:read` 必须存在** —— `handler/v1/event.go:148` 已经在等它。

## §3 状态机

### 3.1 实例状态

```
draft ──submit──▶ running ──approve(全部关卡通过,或 或签首个动作)──▶ approved  ✅ 终态
                      │
                      ├──── reject ──────────────────────────────────▶ rejected  ❌ 终态
                      │
                      └──── rollback ──▶ returned ──submit(重提)────▶ (回到 running)

draft    ──cancel──▶ cancelled  ⚪ 终态
returned ──cancel──▶ cancelled  ⚪ 终态

⚠️ running ──cancel──▶ ✗ 不存在(D9):已送审的单子可能有人正在审
```

| 状态 | 含义 | 可做动作 |
|---|---|---|
| `draft` | 草稿,业务记录已建但未提交,无人能审。**可改标题/事由/模板** | `update` / `submit` / `cancel` |
| `running` | 审批中 | `approve` / `reject` / `rollback`(**不可 `cancel`**,见 D9) |
| `returned` | 已打回,等申请人改完重提。可改内容与模板 | `update` / `submit` / `cancel` |
| `approved` | ✅ 终态 | 无 |
| `rejected` | ❌ 终态 | 无 |
| `cancelled` | 终态 | 无 |

⚠️ **字符串一律用 `cancelled`(双 l)**,与仓库既有词表一致(`activity.go:46`、`seed.go:1081`、`push/event.go:129`)。**不要写成 `canceled`。**

### 3.2 任务状态

| 状态 | 何时写入 |
|---|---|
| `pending` | 关卡启动时为每个审批人生成一行 |
| `approved` | 该审批人点了通过 |
| `rejected` | 该审批人点了拒绝 |
| `skipped` | 终局时**其余未处理的 pending 全部置此**(或签首个动作、会签一票否决、cancel) |
| `stale` | 打回时**本实例所有 task** 置此。表示"上一轮,不再计入"(D4) |

⚠️ **没有 `terminated`**。外部引擎用它表示"审批人中途离职,这一票作废",它需要配套的减签/转办流程。V1 这两个都不做(§1 第 2、6 条),所以这个状态没有生产者 —— **没有生产者却有消费者的状态是 bug 温床**。

⚠️ **没有 `transferred`**。同上。

### 3.3 动作表

**全部 6 个动作**:`submit` / `update` / `approve` / `reject` / `rollback` / `cancel`。下表是 **7 行**,因为 `submit` 按两种前置状态拆成两行(首次提交 / 打回后重提),守卫条件完全不同。

> ⚠️ **V2.0 这里写着"6 个动作"但表里其实只有 5 个**(`submit` / `approve` / `reject` / `rollback` / `cancel`)—— 数错了,没人数。V2.1 加了 `update` 才凑成真的 6 个。**表行数 ≠ 动作数,`submit` 占两行。**

| 动作 | 端点 | 谁能做 | 前置状态 | 守卫条件 | 效果 |
|---|---|---|---|---|---|
| `submit` | `POST /approvals/:id/submit` | 发起人 | `draft` | 模板 `is_active`;审批人解析非空;不含发起人(D11) | → `running`,`current_stage=1`,生成第 1 关 task,**写 round 1 快照**,写 log |
| `submit`(重提) | 同上 | 发起人 | `returned` | `return_count < 5`;**⚠️ 内容必须与本轮快照不同**(下) | → `running`,`current_stage=1`,**旧 task 已是 `stale`,不动**,生成新 task,**写 round N+1 快照** |
| `update` | `PUT /approvals/:id/draft` | 发起人 | `draft` / `returned` | **不是审批动作**,不生成 log | 改 `title` / `variables` / `template_code`。**`draft` 下改模板不需要重建**(D9) |
| `approve` | `POST /approvals/:id/act` | 持本关 pending task 的人 | `running` | §3.4 | 见 D5 |
| `reject` | 同上 | 同上 | `running` | §3.4 + 备注 ≥5 字 | 立即终局(D5) |
| `rollback` | 同上 | 同上 | `running` | §3.4 + 备注 ≥5 字 | → `returned`,**本实例所有 task → `stale`** |
| `cancel` | `POST /approvals/:id/cancel` | 发起人 | `draft` / `returned` | **不在 `running`**(D9) | → `cancelled`,所有 `pending` → `skipped` |

**为什么 approve/reject/rollback 合并成一个端点**:三者的守卫完全相同("你是不是本关的 pending task 的 assignee"),差异只在落库结果。合并后**前端不需要传 `task_id`** —— 待办由服务端按 `(instance_id, current_stage, caller)` 定位,**少一个可被篡改的参数**。

**动作必须在 service 层分开实现**(3 个方法),只是共用一个 HTTP 端点 —— 拆成 3 个 handler 会让锁+事务+通知这条链路复制 3 份。

**`update` 不是审批动作,所以不叫它 `edit` 也不给它 log**:它是"改还没送审的东西",记进 log 会让意见流里出现一堆"提交人修改了标题"的噪音。**它的可见性只体现在 round 快照上** —— `returned` 状态下改的内容,要等下次 `submit` 写成新 round 才留痕。

⚠️ **重提必须改内容(新守卫)**:若 `title` + `variables` 与**本轮**快照逐字节相同 → `InvalidParam`。
理由:被驳回却原样重提,会让所有审批人把上一轮做过的事重做一遍,纯属浪费,且烧 `return_count`(上限 5 次)直到锁死。**比的是"本轮"不是"第 1 轮"** —— 连续两次重提、第二次相对第一次有改动,就该放行。

### 3.4 守卫细则

```
approve / reject / rollback 的前置(缺一不可):

  1. 实例存在且 status = 'running'                    → 否则 StateInvalid
  2. caller.UserID 在本关有 status='pending' 的 task   → 否则 Forbidden
  3. 该 task 的 stage_index == 实例的 current_stage    (隐含于 2,防御性断言)
  4. comment 通过校验
```

⚠️ **第 2 条必须查 `status='pending'`**,不能只查"有没有我的 task"。否则 `stale` 的上一轮 task 会让打回后的人还能再审一遍 —— 这是最容易写出来也最容易漏的一处。

⚠️ **第 3 条不能省。** 省了它,第 3 关的审批人可以在第 1 关还在跑的时候提前把自己的任务批掉,第 1 关通过后系统发现第 3 关已经批完了 —— **这就是 `asset_impl.go:439` 的同款 check-then-act**。

**备注规则**(你已拍板,§14 Q2):

- `reject` / `rollback`:**必填,最少 5 个字符**
- `approve`:选填(允许"同意"两个字直接过,也允许写条件)
- 5 字符按 **rune** 计,不是字节 —— "不同意。"是 4 字符 12 字节

⚠️ **校验放 service 层,不在 binding tag 层** —— `action` 是动态的,`binding:"required_if=..."` 表达不了。前端也要拦(§9.1),但**前端校验只是体验,service 层才是边界**。

### 3.5 并发:实例行锁

**每个写动作的第一行都是锁住实例行**:

```go
err := s.db.WithContext(ctx).
    Clauses(clause.Locking{Strength: "UPDATE"}).
    Where("id = ?", instanceID).
    First(&inst).Error
```

**为什么锁实例而不是锁 task**:会签是**并发**审批 —— A 和 B 同时点通过。如果锁各自的 task 行,两个事务锁的是不同行,谁也看不见对方,都判定"还没到齐",结果单子永远停在最后一关。

锁实例行则强制串行:A 先提交,B 的 `SELECT ... FOR UPDATE` 等 A 提交完才返回,这时 B 读到的是 A 写完的状态。

**三条必须记住的**:

1. **锁实例行,不锁任务行**
2. **不要在 task 行上维护会签计数器**(D10)。读出来 `--` 再整行写回,只要漏了锁、事务、或 `Where` 里的计数条件,就会**静默丢票**(§14.2)
3. **锁等待要设 30s 应用层超时**。`FOR UPDATE` 会阻塞同一实例上的所有并发审批,一直撑到数据库的 `lock_wait_timeout`(MySQL 默认 **50s**)。超时映射成 `StateInvalid` + "审批处理中,请稍后重试" —— **不重试、不排队**,用户重试的成本远低于一个挂死的请求

## §4 会签 / 或签的判定

### 4.1 判定流程

```go
// 全程持有实例行锁(§3.5)
func (s *ApprovalSvc) advanceStage(ctx, inst, stageIndex) (final bool, err error) {
    st := loadStage(inst.TemplateID, stageIndex)

    switch st.ReviewType {
    case ReviewTypeAny:  // 一人过 —— 首个动作就已终局,走不到这里
        return false, errors.New("或签不应走到推进分支")

    case ReviewTypeAll:  // 全过
        rows := countTasksByStatus(ctx, inst.ID, stageIndex)

        // ⚠️ 防御性检查放最前面:空集不能按 0==0 判完成(那是静默放行)
        if rows["pending"]+rows["approved"]+rows["rejected"] == 0 {
            return false, errors.New("本关无有效审批人,流程已损坏")
        }
        if rows["rejected"] > 0 { return true, terminateRejected(inst) }  // 一票否决
        if rows["pending"]  > 0 { return false, nil }                      // 还有人没处理
        // pending==0 → 本关全过,进入下一关
    }
    return s.enterStage(ctx, inst, stageIndex+1)
}
```

对应的 SQL(**这个 WHERE 条件写错 = 上一轮的人被数两遍**):

```sql
SELECT status, COUNT(*) FROM sys_approval_task
 WHERE instance_id = ? AND stage_index = ? AND deleted_at IS NULL
   AND status IN ('pending','approved','rejected')   -- ⚠️ stale 被排除 —— 这是 D4 的全部意义
 GROUP BY status
```

⚠️ **`IN` 列表的三个成员各司其职,少一个都错**:

| 状态 | 为什么要 / 不要 | 漏了会怎样 |
|---|---|---|
| `pending` | 要 —— "还有人没处理"是唯一推进判据 | `pending==0` 恒成立,**会签第一票通过就推进** |
| `approved` | 要 —— 空集防御检查(§4.1 第一行)用 | 空集检查失效,**0==0 被当成"全过"静默放行** |
| `rejected` | 要 —— "一票否决"判定用 | 有人拒绝仍继续等,**单子卡死** |
| ~~`stale`~~ | **排除** —— 上一轮的行(D4) | 上一轮的人被数两遍,**永远凑不齐** |
| ~~`skipped`~~ | **排除** —— 终局标记 | 本关被标记跳过的行混进来 |

⚠️ 注意 V2.0 的或签是"首个动作终局"(D5),所以不存在"或签第一个人 reject 后分母变化"这条路径。
`rejected` 进列表的理由是**会签的一票否决判定**,不是分母。

### 4.2 同一关同一个人只有一个 task

生成 task 前**按 `user_id` 去重**:

```go
uniq := map[uint64]struct{}{}
for _, uid := range resolved {
    if _, dup := uniq[uid]; dup { continue }
    uniq[uid] = struct{}{}
    createTask(inst.ID, stageIndex, uid)
}
```

**为什么必须去重**:审批人可能同时匹配多条规则(既是"角色:财务经理"又是"直属主管 1 级")。不去重会生成两行 task,会签分母翻倍,单子永远卡住。

⚠️ 这也意味着**将来加转办不能作为"新增一行"实现**(§1 第 2 条)—— 会破坏一人一行的不变式。

## §5 审批人解析

### 5.1 三种来源

| `rule_type` | 配置 | 解析结果 |
|---|---|---|
| `user` | 指定 `user_id` | 就是这个人 |
| `role` | 指定 `role_id` | 该角色下所有在职用户 |
| `dept_leader` | `levels` = 向上几级 | 从发起人所在部门逐级向上找负责人 |

**只有三种。** V1.1 设计过五种,砍掉两个:

- ~~`dept_leader` 和 `leader_n` 合并~~ → 一个 `dept_leader` + `levels` 字段,`levels=1` 即直属主管,`levels<=0` 视作爬到顶
- ~~`dept_role`(指定部门 ∩ 指定角色)~~ → 场景太窄。`role` + 按人配已经能覆盖

⚠️ V1.1 还有一个 `applicant_manager`("申请人数据域内的负责人")—— **删了**:`Caller.ProjectIDs` 记的是**项目**,而负责人字段在 `sys_department.leader_id`(`department.go:10`)是**部门**维度,**项目维度没有负责人字段,这个 resolver 无法实现**。

### 5.2 三条硬规则

**在 `submit` 时一次性解析并落库,不是每关现算。** 理由:发起时把审批人快照下来,中途改组织架构不会让在跑的流程跳人。代价是部门调整后在跑的流程用旧人 —— 走 §9.4 的告警兜底。

**1. `error` ≠ 空集合。**

```go
ids, err := resolver.Resolve(ctx, req)
if err != nil {
    // ⚠️ 故障 ≠ 无人审。绝不能把 err 当"空集合"然后走兜底 ——
    //    兜底若是 auto_approve,等于数据库抖一下单子就自己过了
    return errcode.New(errcode.Internal, "解析审批人失败")
}
if len(ids) == 0 {
    // 真的没人审(部门没配主管 / 角色没人 / 超出层级)
}
```

- **查得到、结果为空** = 数据常态("这个人在组织里没有上级")
- **查不到**(DB 报错、缓存 miss)= 故障,**整个 submit 失败**

把这两者混为一谈是调研中确认的高危错误 —— 数据源故障时会静默走降级,单子被发给一个随便挑的人。

**2. 部门树有环则报错。**
`dept_leader` 沿 `parent_id` 向上走,走满 10 步还没到顶 → 返回 error 而不是死循环。仓库的 `sys_department` 是自引用树(`SysDepartment.ParentID` 自指,`department.go:6`),`dept-seed` 的 `parent_id` 第二轮回填说明它确实会成环。**现成可复用:`roleService.DepartmentTree`(role_impl.go:516)已经能把树组好,不要另写一套。**

**3. 过滤条件固定。**
`sys_user` 只取 `is_active = 1` 且 `deleted_at IS NULL`。离职/停用的人不生成 task。

### 5.3 空审批人:配置期拦,提交期报错,**不降级**

三层防线,**全部前置**,没有运行期兜底:

| 层 | 时机 | 做法 |
|---|---|---|
| **① 配置期** | `POST /flows` **保存模板时** | 每个阶段的规则**预检解析一次**,空的就**拒绝保存** |
| **② 提交期** | `submit` | 再次解析,空 → **error**,提示"第 N 关解析不到审批人,请联系管理员" |
| **③ 运行期** | — | **不做兜底**。V1 由 cronx 巡检告警(§9.4) |

⚠️ 调研中确认主流引擎有"空审批人自动升级到租户管理员"的策略。**V1 不采用**:静默把单子发给一个无关的人,**比直接报错糟糕得多** —— 报错至少让申请人知道要找谁。

⚠️ 相比之下,"该财务审的单子没人审就放行"是本模块最危险的静默降级,**任何情况下都不做**。

> 🔴 **这张表只 append,永不 UPDATE / DELETE。`DeletedAt` 字段继承自 `BaseModel`,在本表上永远不该有值。**
>
> 原因不是"不会有人删",而是:**`gorm.DeletedAt` 存在,就意味着 GORM 给该 model 的每一条查询自动加 `deleted_at IS NULL`。只要有任何一处代码对 log 调了 `Delete()`,全表意见立刻从详情页消失,而且没有任何报错。**
>
> **V2 的防护**:① model 注释写死禁令;② **加一条单测** —— `COUNT(*)` 与该实例的 log 总数断言一致,不等就红。

> ⚠️ **V2.1 新增。** 它是**纯展示表**:判定分母、状态推进一律不读它(§4.1 照旧只看 task)。

```go
type SysApprovalRound struct {
    BaseModel
    InstanceID uint64 `gorm:"uniqueIndex:uk_app_round_inst,priority:1" json:"instance_id,string"`
    RoundNo    int    `gorm:"uniqueIndex:uk_app_round_inst,priority:2" json:"round_no"`
    Title      string `gorm:"size:256" json:"title"`   // 本轮提交时的标题快照
    Variables  string `gorm:"type:json" json:"variables"` // 本轮提交时的内容快照
    SubmitterID uint64 `gorm:"index" json:"submitter_id,string"`
    SubmittedAt time.Time `json:"submitted_at"`
    Outcome     string `gorm:"size:16;index" json:"outcome"` // running|approved|rejected|rolled_back
    OutcomeBy   uint64 `json:"outcome_by,string"`
    OutcomeAt   *time.Time `json:"outcome_at"`
}
```

**三个设计要点**:

1. **写入时机只有一处**:每次 `submit`(含重提)开一行。`draft` 阶段改来改去**不产生 round** —— 没送审的东西没有"第几轮"可言。
2. **不存 `comment`** —— 打回/拒绝的理由仍然只存在于 `sys_approval_log`(唯一真相源)。前端拿 `rounds[]` 拿结构、拿 `logs[]` 拿意见,按 `round_no` 拼。**冗余一份评论就要有两个可能写错的地方,而这里省下来的只是一个 join。**
3. **`roll back` 时把本轮 `outcome` 写成 `rolled_back`,不改实例历史** —— 之后 `submit` 开 `round_no+1`。`UNIQUE(instance_id, round_no)` 保证并发重提撞不出两行。

⚠️ **`round_no` 从 1 开始,连续,不跳号**(与 §6② `stage_index` 同一条规矩)。⚠️ **`DeletedAt` 在本表同样不该有值**,理由同 ⑥。

### 6.2 Go 模型的约定

- **全部嵌入 `model.BaseModel`**(`model/common.go:14-19`):`ID uint64` 雪花 ID(`autoIncrement:false`)、`CreatedAt`、`UpdatedAt`、`DeletedAt`。**不要自己写 ID 生成**
- 测试用 `github.com/glebarez/sqlite` 的 `:memory:`(**纯 Go,不需要 cgo**),**不要用 `gorm.io/driver/sqlite`**

**迁移机制核实结果(2026-10-23)**:本仓**没有手写 SQL 迁移文件**,`internal/migrate/migrate.go:134-165` 直接 `db.AutoMigrate(&Model{})`,**唯一索引也来自 struct tag**(GORM 的 Migrator 走 `schema.ParseIndexes`)。
所以 §6① 那七个 `uniqueIndex` tag **就是迁移产物本身**,不需要额外写 DDL —— 但也因此:

> ⚠️ **struct tag 拼错,DDL 就是错的,而且没人会报错。** 仓库已有现成的防线,直接照抄:
> `model/file_test.go:27-42` 的 `uniqueIndexes(t, model)` helper —— 用 `schema.Parse` + `ParseIndexes()` 断言
> **GORM 实际会建出的唯一索引名字和列顺序**。M83 必须为 `uk_app_tpl_code`、`uk_app_stage_tpl_idx`、
> `uk_app_inst_biz`、`uk_app_round_inst` 各写一条断言。**这四条唯一索引里任何一条 tag 写错,都是"上线才发现全员 403 / 重提撞唯一索引"级别的事故。**

> ⚠️ **`migrate.go:172` 自己写着"AutoMigrate 自动补列,不需要在这里单列"** —— 反过来说,**AutoMigrate 不会给你改列的语义**(把 varchar 改成 text 之类)。V1 的七张表都是**新表**,不触碰既有列,所以这件事不成立;**将来若要改既有列,得另写 `migrate.go` 里的预清理 SQL**,那是另一轮的事。

> 💡 **一条本仓既有的经验,正好印证 D9**:`model/user.go:89` 的注释写着
> "复合索引 (user_id, is_primary) 加速'查主身份'查询;**唯一性由 service 层事务保证(MySQL 无 partial unique index)**"。
> 本仓早就知道 MySQL 没有条件唯一索引,并且选了"**service 层保证**"这条路 —— **D9 用硬唯一而不是 `active_key` NULL 技巧,是顺着仓库既有立场走的,不是我的偏好。**

### 7.2 模板 CRUD

**`POST /flows`**

```json
{
  "code": "material_review",
  "name": "交付资料审核",
  "biz_type": "digital_material",
  "stages": [
    { "name": "资料管理员初审", "review_type": "all",
      "rules": [
        { "rule_type": "role", "role_id": "12" },
        { "rule_type": "user", "user_id": "10086" }
      ] },
    { "name": "专业审核", "review_type": "any",
      "rules": [ { "rule_type": "dept_leader", "levels": 2 } ] }
  ]
}
```

⚠️ **ID 一律是字符串,不是数字** —— 全仓主键是 sonyflake 的 19 位数(超出 JS 的 2^53),
请求 DTO 用 `json:"...,string"` 收发。**这不是风格问题**:
`encoding/json` 对带 `,string` 的整数字段收到**裸数字**会直接报
`json: invalid use of ,string struct tag, trying to unmarshal unquoted value into uint64`。
(实测过,不是推测。详见 §13 的 M86-1b。)

**服务端校验**:
- `code` 格式 `^[a-z][a-z0-9_]{1,63}$`
- `stages` 长度 1~10,`stage_index` 从 1 连续
- 每个 stage 的 `rules` 非空,且**预检解析结果不为空**(§5.3 第①层)
- 整个写入在**一个事务**里,`template_id` / `stage_id` 保存后回填

**`PUT /flows/:id`**:有非终态实例 → **拒绝**,报"该模板有 N 条在跑的审批,请新建一条代替修改"(D7)。无在跑实例 → 允许改阶段和规则(整体替换:硬删旧 stage/rule,写新的)。

⚠️ **「硬删」是落地时的更正,原稿写的是「软删」** —— 唯一索引
`uk_app_stage_tpl_idx(template_id, stage_index)` **不含 `deleted_at`**,软删的关卡行
仍然占着 `(template_id, stage_index)` 这个坑位,于是"改模板"写回同样的第 1 关时
数据库直接拒绝。**照原稿写,`PUT /flows/:id` 第一次改就报错。**
这两张表是配置表(不是流水表),没有"历史要留"的要求。详见 §13 的 M86-1a。

**`DELETE /flows/:id`**:同上的在跑检查;软删 + **`code` 改写为 `code#deleted#<id>`**(D7)。

### 7.3 `POST /approvals` —— 建草稿

⚠️ **这是唯一业务侧必须调用的端点,且必须与业务记录的创建在同一事务里**:

```go
// 业务侧(service 层,非 HTTP)
err := s.db.Transaction(func(tx *gorm.DB) error {
    if err := createBusinessRecord(tx, input); err != nil { return err }
    _, err := approvalSvc.CreateDraft(ctx, tx, &approval.CreateInput{
        BizType: "digital_material", BizID: rec.ID,
        Title: input.Title, TemplateCode: "material_review",
        Variables: map[string]any{"house_no": input.HouseNo},
        Caller: caller,
    })
    return err
})
```

⚠️ **不要做成"前端建业务记录 → 前端调这个端点"两步**:两者之间业务记录已落库而审批单没建,单子就丢了。**业务记录和审批单必须同生共死。** 建记录失败时整体回滚,不留"孤立的草稿业务记录"。

响应返回 `approval_id`,前端拿它跳 `/approval/{id}`。

**为什么是两步而不是一步**(你已拍板,§14 Q1):给用户"提交前预览审批链是谁、补充事由"的窗口。代价是多一次交互且草稿会堆积 —— 接受。

#### 7.3.1 业务侧的入口形状(M86-2 落地)

> ⚠️ **本小节在 2026-10-24(M86-2)按落地代码补写** —— 原稿只写了引擎的
> `POST /approvals`,没写**业务侧怎么把"资料 ID"翻译成"审批单 ID"**。

引擎的 `Submit` 收的是**审批单 ID**,而业务侧对外只认**业务 ID**(前端手里只有
`biz_id`)。这个翻译**不能放在引擎里** —— 引擎不认识任何业务表(§16.2 的第一句)。
所以每个业务线要自己提供一个「以业务 ID 为入口」的薄方法:

```go
// asset.go —— 资料这一侧
func (s *assetService) SendMaterialForReview(ctx context.Context, caller *Caller, id uint64) error {
    // 1. 按 D9 的硬唯一 (biz_type, biz_id) 找审批单
    inst, err := s.materialApprovalInstance(ctx, id)
    if inst == nil { return errcode.New(errcode.NotFound, "这份资料没有审批单,无法送审") }
    // 2. 翻译完再调引擎 —— 状态判定全在引擎里,业务侧不重复判
    return s.engine.Submit(ctx, caller, inst.ID, SubmitReq{})
}
```

于是资料这条线有**两个 HTTP 端点**,形状一致(都是"资料 ID 进"):

| 端点 | 作用 | 返回 |
|---|---|---|
| `POST /rapid-admin/v1/biz/materials` | **第一步**:建资料 + 同事务建审批草稿(D8) | `{material_id, approval_id}` |
| `POST /rapid-admin/v1/biz/materials/:id/submit` | **第二步**:把草稿送审 | 空 |

⚠️ **`POST /materials` 的响应返两个 ID** —— 这是 M86-2 改的契约(原来只返资料 ID)。
前端要拿 `approval_id` 去 `GET /rapid-admin/v1/system/approvals/{id}` 预览审批链(谁审),
确认后再调第二步送审。**两个 ID 都是 string**(§7.5)。

⚠️ **"没有审批单"是一条真实存在的错误**(不是防御性代码)—— 引擎接管之前建的老资料
永远送不了审。它那个年代没有审批单,这是 D9 的诚实结果,不是 bug。

### 7.4 入参校验

> ⚠️ **本节在 2026-10-23(M84)按落地代码改写过** —— 改了两处,理由见 §13 的 M84 条目:
> ① **`SubmitReq` 的 `TemplateCode` 删掉了** —— 模板在 `CreateDraft` 时就定死,
>    提交时换模板 = 换审批链,§3.3 的动作表里没有这条;
> ② **`UpdateDraftReq` 的字段改成指针** —— 值类型的零值表示"清空",不是"不改"。

```go
type SubmitReq struct {
    // Comment 提交说明,**选填**。只有驳回/打回才强制 5 字。
    Comment string `json:"comment"`
}

type UpdateDraftReq struct {
    // 三个字段都是**可选的指针式语义**:nil = 不改
    Title        *string `json:"title"`
    Variables    *string `json:"variables"`
    TemplateCode *string `json:"template_code"`  // 选填,传了就换模板
}

type ActReq struct {
    Action  string `json:"action"`   // approve | reject | rollback
    Comment string `json:"comment"`
}
```

```go
switch req.Action {
case "approve":
    // 选填,不校验长度
case "reject", "rollback":
    if n := utf8.RuneCountInString(strings.TrimSpace(req.Comment)); n < 5 {
        return resp.Fail(errcode.StateInvalid, "拒绝/打回必须填写不少于 5 个字的意见")
    }
}
```

⚠️ `utf8.RuneCountInString` 不能用 `len()` —— 中文一条意见通常 15~30 字节,`len()` 会让 5 字的要求变成实际只要 2 个字。
⚠️ **先 `TrimSpace` 再数** —— 五个空格满足"5 个字符"却没有任何内容,放过去等于把守卫变成摆设(只多拒不少拒,安全)。

⚠️ **`action` 必须用白名单校验**,不能直接进 switch 拿去做更新。

⚠️ **`UpdateDraftReq` 的守卫是 `status ∈ (draft, returned)` + `caller` 是发起人**,没有别的。
⚠️ **`template_code` 传了要校验 `is_active`** —— 否则草稿改成了一个停用模板,submit 时才炸,错误信息离操作点太远。
⚠️ **`Variables` 整体覆盖,不 merge** —— 合并语义会让"用户删掉了一个字段"永远删不掉,这是所有"合并式编辑"的通病。
⚠️ **`Variables` 落地成 `*string`(JSON 文本)而不是 `map[string]any`** —— 引擎要**逐字节**比较
"这次重提的内容和本轮快照是否完全一样"(`map` 会被 Go 的序列化顺序打乱,比不出"逐字节相同")。

### 7.5 响应约定

- **所有 ID 用 `string` 返回**,不是 `uint64`。⚠️ 雪花 ID 是 19 位数,超出 JS 的 `2^53`,裸数字会被 `JSON.parse` 静默截断 —— 这是 `pkg/push/event.go:126-127` 已写明的教训,**审批接口必须遵守同一条**
- DTO **全部带 `json:"snake_case"` tag**。⚠️ Go 的 `encoding/json` 大小写不敏感但**认不出下划线**,缺 tag 会导致前端绑定不到(仓库历史踩过)
- **`GET /approvals/:id` 一次返回 `rounds[]` 和 `logs[]` 两个数组,前端按 `round_no` 拼。** ⚠️ **不为轮次单开端点** —— 它只有一个消费者(详情页),单开端点等于多一处路由/权限码/前端请求要同步

## §8 可见性与权限

### 8.1 权限码(11 个)

```
flow:list      flow:read      flow:create      flow:update      flow:delete
approval:list  approval:read  approval:create
button.flow.add  button.flow.edit  button.flow.delete
```

⚠️ **6 个动作不设权限码。** 审批按钮的可见性由**数据**决定(你手里有没有 pending task),不是由 RBAC 决定 —— 这比权限码**更准确**:有权限但没待办的人不该看到按钮,有待办的人一定该看到。

⚠️ V1.1 的 30 个资源码里 **19 个是这么砍掉的**。

`button.flow.*` 三个是**纯配置页**的按钮,那里权限驱动是对的(有 `flow:update` 不代表能删)。

### 8.2 列表的三个盒子

| `box` | SQL 条件 |
|---|---|
| `todo` | `EXISTS(SELECT 1 FROM task WHERE assignee_user_id=我 AND status='pending')` **且** 实例 `status='running'` |
| `mine` | `applicant_user_id = 我` |
| `done` | `EXISTS(SELECT 1 FROM task WHERE assignee_user_id=我 AND status IN ('approved','rejected'))` |

**没有 `box=all`。** 每个盒子都由"我和这条单的关系"定义,**结构上不可能越权** —— 这是 §1 第 8 条砍掉全量列表换来的好处。

⚠️ `todo` 的判定**必须带 `status='pending'`**,理由同 §3.4。

### 8.3 详情可见性

`GET /approvals/:id` 允许访问:**发起人**、**当前关的待办人**、**本轮已处理的审批人**。其他人 → `Forbidden`。

⚠️ **V2.0 曾写"用 `authz.Assertor` 表达这条规则",核实后是错的。** `GenericAssertor` 的决策链(`assertor.go:22-29`)只有五步:`caller==nil → IsSuperAdmin → **OwnerUserID==caller.UserID** → deny override → ActiveGrants 命中`,**它没有任何"你是不是这条审批的审批人"的概念**,而且它是**纯内存、不碰 DB** 的 —— 结构上就表达不了"在 `sys_approval_task` 里有行"。

把 `OwnerUserID` 填成 `ApplicantUserID` 的后果是:**申请人能看,所有审批人都 403** —— 恰好把最该看的人挡在外面。

**正确的组合(两条都走,不互相替代)**:

```go
// ① 先走框架层的资源级断言 —— 它负责"所有人"和"委托(ActiveGrants)",不要绕过
err := s.assertor.AssertCan(authz.CallerSummary{UserID: caller.UserID, RoleCode: caller.RoleCode},
    principal, authz.Resource{ResourceType: "approval", ResourceID: inst.ID, OwnerUserID: inst.ApplicantUserID},
    "approval:read")

// ② Assertor 拒了,再问审批域自己的"当事人"判定 —— 这条只有 approval service 有资格判,
//    因为它要查 sys_approval_task
if err != nil && !s.isParty(ctx, caller, inst) {
    return err   // 原样返回 Assertor 的错误,保留它的 errcode 与审计
}
```

⚠️ **`isParty` 的三个来源**(一条 SQL 搞定,不要写三条):
```sql
SELECT 1 FROM sys_approval_instance WHERE id = ? AND applicant_user_id = ?
UNION ALL
SELECT 1 FROM sys_approval_task WHERE instance_id = ? AND assignee_user_id = ?
```
⚠️ **不要加 `status IN (...)` 过滤** —— 历史轮的 task 也是当事人,§9.1 的多轮历史要给他们看。
⚠️ **`isParty` 绝不能反过来给 `Assertor` 兜底** —— 一旦写成 `if isParty { return nil }`,`ActiveGrants` 委托路径就绕过了。**顺序是 Assertor 先、isParty 后兜底,不是二选一。**
⚠️ **super admin 会从 Assertor 第 2 步直接放行** —— 这是仓库既有立场,`role_super_admin` 能看全平台审批单。**这是 §8.4 "广发 `approval:read` 安全" 那个前提的另一个例外**,写在那里时要记得它不是无条件的。

⚠️ **不做这个 = 全公司审批单裸奔**:`approval:read` 发给了多个角色,详情接口只靠 RBAC 的话,任何有该权限的人都能看全平台所有单据的事由和意见。

**会签意见可见性**(你已拍板,§14 Q9):**同一关的审批人互相可见对方的意见** —— 会签人要互相知道进度,否则不知道还有几个人没批。⚠️ 将来若改成部分可见,**返回空 `comment` 而不是 404 整条**,否则时间线渲染会崩。
⚠️ **"互相知道进度"这件事有两个实现,别只做一个**:① **看得见** —— 详情页返回同关其他人的意见(就是上面这条);② **知道进度变了** —— 有人投完票时推一条 `approved` 事件(§9.2,M89-1 补的)。⚠️ **②原来漏了** —— 会签的这一票落地时不发任何事件,于是同一关的人只有主动刷新页面才知道有人批了。

**结论仍然成立,但理由换了一个真的:** 让 ctx 死掉的是**调用方**,不是 GORM —— HTTP 请求超时、上游断开、网关掐连接,`ctx.Err()` 就是非 nil。拿它写 Redis 直接失败,表现是「审批成功了但前端不刷新」。

```go
safeCtx := context.WithoutCancel(ctx)   // 剥离取消链,但保留 ctx 里的值
go func() {
    defer func() { if r := recover(); r != nil { /* 记日志,不炸主流程 */ } }()
    push.Publish(safeCtx, ...)
}()
```

📌 **正因为原理由是假的,端到端断言测不出这条** —— 跑一遍正常流程,ctx 根本不会死,`assert(deadCtx == 0)` 恒绿。M84 的做法是**直接测 `publish`**:传一个已取消的 ctx 进去,断言 publisher 拿到的是活的。**别改回端到端断言**,那条是假绿。

⚠️ `push/event.go` 现有的 `Publish` 没有任何 `WithoutCancel`,它假定调用方给的是长命 ctx。cronx 场景成立(根 ctx),**审批这种"事务提交后立刻发"的场景不成立**。

⚠️ **`ApprovalPayload` 不带 `comment`** —— 这是 M73 有意为之的白名单设计(`event.go:117-122`)。**不要因为"前端想显示最新意见"就加字段**,让前端自己回查详情接口。

```go

//    `init()` 里拿不到 db / notifier,只能靠包级全局变量传进去。
func RegisterApprovalScanJob(db *gorm.DB, notifier inbox.Notifier) {

        Cron:        "10 3 * * *",                       // ⚠️ **5 段,不是 6 段** —— 每天 03:10
        Enabled:     true,
        NonIdempotent: false,                             // 零值即幂等 —— 只发告警不改单,天然幂等
        Handler: func(ctx context.Context) error {
            return scanStaleApprovals(ctx, db, notifier)
        },
    })
}
```

| 约束 | 出处 | 踩了会怎样 |
|---|---|---|

| 🔴 **注册必须早于 `cronx.New` / `Start`** | `scheduler.go:227` 的 `keys := registeredKeys()` —— **Start 时对注册表拍快照** | 运行期再注册的任务**永远不会被调度**,而且**不报错**。所以注册要么在 `init()`,要么在 `main` 装配期、`cronx.Start` 之前 |

## §12 将来要加的东西(带完整方案)

**不是"以后再说",是将来真要做时不用重新想。**

1. **模板版本** —— 不需要。`code` 就是版本(D7)
2. **转办 / 减签 / 催办** —— 在 `sys_approval_task` 上加 `assignee_user_id` 的变更接口,加一个终局无关状态 `terminated`。**前置条件:§4.2 的"一人一行"不变式必须保住** —— 所以转办是"改行"不是"加行",且**目标人不能是本关已有的审批人,需校验**
3. **审批人中途离职的自动修复** —— §9.4 告警 + 管理端手动换人接口。**不做全自动**,因为"自动换成谁"需要组织架构的代理人概念,V1 没有
4. **打回到指定关卡** —— 加 `sys_approval_stage.rollback_to`,重提从 `rollback_to` 而不是 1 开始;同时"打回时全量置 `stale`"的范围不变(仍是全量),**轮次语义不受影响**
5. **或签"拒绝不定局"** —— `reject` 分支改成:或签时不立即终局,把该 task 置 `rejected` 后走 §4.1 的推进判定(需支持 `any` 类型,即"至少一个 approved 且无人还在 pending")。**改动集中在 §4.1 一个函数**
6. **会签按比例/票数** —— `sys_approval_stage` 加 `threshold` 列,`review_type` 扩成 `all|any|majority|percent|count`,§4.1 按阈值算。**分母口径不变**,是在现有判定上加分支,不是重写。⚠️ 比例类必须带**提前判死**(`approved + (total - done) < required` 时立即判死,不等永远等不到的人)
7. **外部回调(outbox)** —— 加 `sys_outbox` 表,审批事务里写一条"待发事件",独立 worker 消费重试。⚠️ **前置条件:必须先改 `BizHandler` 的接口契约**,把同步回调换成"写 outbox"。**这条一旦做,R11 和 D8 的整套假设都要重写,不能半途插入**
8. **允许对同一业务记录二次审批** —— 业务侧建新记录(当前做法,D9),或加 `attempt` 列进唯一索引(放弃硬唯一,重引入 `active_key` 的 NULL 技巧)。**优先业务侧建新记录**,因为它对审批的语义更清晰。⚠️ **V2.1 已补第三条路且成本更低**:还没送审时直接改草稿的 `template_code`(`PUT /approvals/:id/draft`),只有"已经 cancel 了"才需要落到前两条
9. **全量列表 / 统计** —— 加 `box=all` 时必须同时定义「谁能看别人发起的单」,这是**数据级权限**,RBAC 的 module/action 表达不了,要落到 `authz` 的 projectID 域校验。
   ⚠️ **加它的同时必须收窄 `approval:read` 的授予范围** —— §8.4 之所以敢把 A 组广发给 13 个角色,前提正是"没有 `box=all`,拿权限码也看不到别人的单"。这条前提一旦不成立,广发就变成越权。**两件事必须同一个 commit,不能只做第一件。**

#### 三个真 bug

**M89-1 —— 会签投票后一条事件都不发** 🔴

引擎 `advanceStage` 在"这一关还有人没批"(会签没齐)时直接 `return nil, nil`。
后果三条:

1. **投票人自己的待办角标不刷新** —— 他那一票已经落成 `approved`,`box=todo` 里不再有它,但前端**只有收到事件才会重拉**(M88 的设计:事件是唯一的刷新信号)。角标停在错的数上。
2. **同一关的其他人不知道有人批了** —— §8.3 写的是"会签人要互相知道进度",详情页那半边做到了(返回同关其他人的意见),但"进度变了"这个信号没推出去。
3. **§9.2 那张表写着 `act(approve)` → `approved`**,这里是空的 = 违约。

修法:那一支改成返回一条 `approved` 事件。⚠️ **它的语义是"这一票记下了",不是"整单通过了"** —— 整单通过由 `finishApproved` 那条终局事件表达(同一条 action,不同语境)。前端两个事件一视同仁(都只触发"重拉待办数",M88-a),**分不出来也不影响**;真要区分得加新词表,而事件名"从 M73 起就不许改"。

⚠️ **另外三个分支一个都没动** —— `finishApproved` / `enterStage`(无下一关)/ `enterStage`(有下一关)本来就发事件,多发一条就是重复。

**M89-2 —— `PUT /flows/:id` 能把模板 code 改成任意字符串** 🔴

`normalizeFlow` 的 code 格式检查整体挂在 `if forCreate` 里面,于是改模板时那段检查**根本不跑** —— 大写、数字开头、含横线、含中文、含空格,全收。

后果不只是"编码不好看":

1. `deletedFlowCode` 按**字节**截断(`prefix[:64-len(suffix)]`),**一个中文 code 会被从中间劈开** → 库里躺了半个 UTF-8 字符。
2. `code` 是业务侧引用模板的键(`template_code`),脏值一路传下去,而 §7.2 的"服务端校验"清单里明写着这条格式。

修法:把检查挪出 `forCreate`,**但空 code 不参与校验** —— 改模板时它是"不改"(指针语义,§7.4)。

**M89-3 —— 审批动作后前端不主动刷角标** 🔴

详情页 `doAct()` 做完 approve / reject / rollback 之后只调 `await load()`(重拉详情),**待办角标完全依赖服务端 SSE 广播**。而广播这条路有两个洞:① M89-1 那个(会签时一条都不发);② Redis 挂了 / SSE 降级时(M88-y)事件根本不来。

修法:`doAct()` 在 `await load()` 之后直接调 `refreshApprovalTodo()`。**自己刚做完的动作是最确定的一次数据源,不该等广播。** ⚠️ **仍然不自己算 ±1** —— 数字必须来自 `box=todo` 的 `total`。

#### 🔴 关键设计:为什么 `Result` 必须在引擎侧给

`approved` 有两种语境(§9.2 那张表),而"要不要给发起人发一条'审批已通过'"**必须**分得出这两种。

- **旁路读实例 `status` 猜 → 有竞态**:会签的中间票与最后一票前后脚投递,谁先被读到是随机的 —— 要么**漏发**(中间票恰好读到最后的状态,终局那条反而被吞),要么**重发**(中间票读到最后的状态,于是发两条一样的"已通过")。
- **引擎是唯一知道答案的地方**:它发事件的那一刻就在事务里,知道这次 approve 是"最后一票"还是"还有别人没批"。

**代价**:引擎动了 5 行(埋点)。**收益**:竞态从根上消失,且**每次结果事件恰好一条消息**。

### M90 —— 审批列表页:三个 Tab → 搜索栏里一个必选 Select(2026-10-26)

**起因**:用户问「我的审批界面,为什么上面通过 tabnav 来做切换,而不是在 searchbar 里面加 select?」,
并给出反驳:**「如果换 Select,然后让 Select 必选项,就不会有空。」**

#### 先撤回一条论据 ⚠️

改之前的答复里有一条论据是:**"空 box 会被后端 400,所以把它做成一个看起来可选的下拉会误导用户"**。
**这条撤回 —— 它站不住**:

- `allowClear={false}` + 默认 `todo` ⇒ **"空"在 UI 上不可能出现**;
- 必选 Select 和三个 Tab 在**契约上等价** —— 后端只认 `box ∈ {todo, mine, done}`,
  两种形态发出去的都是这三个值之一,**这个页面**的请求一次都不会走到
  `approval_query_impl.go` 的 `default:` 分支(那个分支是给"直接调 API 的人"兜底的)。

也就是说,"必选"这条约束**本来就能由 Select 满足**,它**不是**选 Tab 的理由。
把一条站不住的论据留在文档里,下一次读它的人会被带偏 —— 所以明写撤回。

#### 那为什么还是改成 Select(三条理由)

| # | 理由 | 证据 |
|---|---|---|
| 1 | **全仓一致** | 其它列表页的筛选器都在 `ManagementTable` 的 `searchExtra` 槽位里,**全部是 `Select`**:issue / notice / material / audit / file / dict / job / permission / flow —— **10 个页面,零例外**。⚠️ permission 那个"全部/菜单/按钮/API"原先是 `Segmented`、flow 那个原先是一个可点的 `Tag`,**两者都在 2026-10-26 改成了 `Select`**(commit `92c4c14` / `894b10b`,和这一轮同一天)。**审批页用 Tab 是当时唯一的例外** —— 而它扮演的正是同一个角色(互斥的范围选择器),不是"页面分区" |
| 2 | **省一行垂直空间** | Tab 那行是 `Card(size="small")` + Tabs 内边距 ≈ 60px,而表格是 **auto-height**(`ManagementTable` 按可用高度算 `scroll.y`)—— **那 60px 全是数据行** |
| 3 | **顺带修掉一个真 bug** | 见下一节 |

⚠️ **代价要说清楚**:三个盒子**不再同时可见** —— Tab 是三个平级入口一眼看得见,
Select 要点开才知道有几个、每个什么意思。**这是 Tab 唯一仍然占优的地方,接受它。**
理由是 §8.2 的硬约束(没有"全部")**已经在服务端兜住了**,
而"界面上少露一个入口"不构成越权风险 —— 真正构成风险的是"多一个**能选到全平台**的入口",那个一个也没有。

#### 顺带修掉的一个真 bug:重置之后"显示"和"数据"是两套 🔴

旧实现:

```tsx
const [box, setBox] = useState<ApprovalBox>('todo')   // ← 独立的第二份状态
<Tabs activeKey={box} onChange={(k) => { setBox(k); setQuery(...) }} />
```

而 `useTable.reset()` 是 `setQuery({ page: 1, size: 20, ...initialQuery })`
(`web/src/hooks/useTable.ts:185`)—— **它只改 `query`,不碰那个 `useState`**。

后果:切到「我发起的」→ 点「重置」→ 表格刷的是 **`box=todo` 的数据**,
**Tab 却还高亮着「我发起的」**。界面在说一套、数据是另一套 —— 用户会以为"重置没生效"。

修法:选框的值**只从 `query.box` 取**(`value={query.box}`),不再有第二份状态。
`useTable.reset()` 本来就是 box-aware 的(`initialQuery` 里带 `box:'todo'`),
所以受控之后"重置"自然回到 todo,**显示和数据不可能再分叉**。

### 15.1 调研了什么

### 15.2 一个被实证的失效模式

`go-workflow` 的会签判定是在实体表上维护 `AgreeNum` / `UnCompleteNum` 两个计数器:

```go
completeLock.Lock()                    // ① 进程内 sync.Mutex —— 多副本部署下完全无效
task, err := GetTaskByID(taskID)       // ② 读走全局 db,不在 tx 里 —— 锁没护住这次读
task.AgreeNum++
task.UnCompleteNum--
if task.UnCompleteNum == 0 { task.IsFinished = true }
err = task.UpdateTx(tx)                // ③ 整行 Updates,Where 只有主键
```

**并发下**:两个审批人都读到 `UnCompleteNum=2` → 都 `--` 成 1 → 都写回 1。
**永远到不了 0,会签永远凑不齐,单子静默卡死。而且不可自愈** —— 丢一票,那个 task 的计数就永远错 1,后面再打回多少次都救不回来。

这就是 V2.0 的 D10("不维护会签计数器,锁内重算")和 §3.5("锁实例行而不是锁 task 行")的直接来源 —— 不是设计洁癖,是这个失效模式在真实项目里存在。

⚠️ **顺带印证 §0.2**:它的 bug 形态(`Updates` 整行 + `Where` 只有主键)与本仓 `asset_impl.go:439` 的 check-then-act **完全同型**。同一个错在两个独立的代码库里各犯了一次。

### 15.3 调研中被自己推翻的结论

诚实记录,避免后来者重走:

1. 曾断言某引擎"多级主管解析未实现",读源码后发现**完整实现且带环检测** —— 基于二手资料的结论不可靠
2. 曾断言某引擎"没有离职兜底",实际有**三层**(配置期守卫 / 提交期降级 / 运行期告警)—— V2.0 的 §5.3 和 §9.4 就是照这个思路写的
3. 曾把某引擎的一个字段当作"轮次字段"来举例说明反模式,读源码后发现**它是会签子任务的序号,和轮次无关**,例子不成立 —— 已撤回,并因此改用 `stale` 表达轮次(D4)
4. 曾认为 log 表的 `seq` 用非主键自增列在 MySQL 下有兼容问题,为此专门做了核实 —— **V2.0 把这个列删掉了,问题自然消失**

> 📌 **一条方法论**:写"某项目没实现 X"之前,没读过源码就只能写"未查到 X 实现"。这两句话的差别,在选型决策里可能就是错的。

### 16.2 Go 接口定稿

> ⚠️ **本节在 2026-10-23(M84)按落地代码改写过 —— 抄这里的代码,别抄原稿。**
> 改了三处,理由见 §13 的 M84 条目:
> ① **模板 CRUD 从 `ApprovalEngine` 上拆走了**(归 `ApprovalFlowService`,M86 接);
> ② **`BizHandler` 的三个方法都加了 `tx`**(原签名下 D8 无法实现);
> ③ 读接口(`GetApproval` / `ListApprovals`)归 M86,本节只留引擎已落地的部分。
>
> ⚠️ **2026-10-24(M86-2)又加了第 4 个方法 `OnCancelled`** ——
> 理由见 §13 的 M86-2 偏离表。**这是全篇唯一一处"接口比原稿多一个方法"**,
> 抄这段代码的人必须知道 `OnCancelled` 是后加的,不是原稿就有的。

```go
// internal/service/approval.go

// ApprovalEngine 审批引擎。本体不认识任何业务表。
type ApprovalEngine interface {
    // —— 实例 ——
    // ⚠️ CreateDraft 收 tx 是**故意的**:业务记录与审批单必须同事务(D8)
    CreateDraft(ctx context.Context, tx *gorm.DB, in *CreateDraftInput) (uint64, error)
    UpdateDraft(ctx context.Context, caller *Caller, id uint64, req UpdateDraftReq) error

    // —— 动作 ——
    Submit(ctx context.Context, caller *Caller, id uint64, req SubmitReq) error
    Act(ctx context.Context, caller *Caller, id uint64, req ActReq) error
    Cancel(ctx context.Context, caller *Caller, id uint64) error
}

// BizHandler 业务侧要实现的 SPI。**由业务线注册,框架只定义。**
//
// 🔴 **四个方法都收 tx** —— 原稿是 `OnApproved(ctx, inst) error`,那样实现方
// 只能拿自己持有的 db 去写,那是**另一条连接、另一个事务**:实例回滚了业务写
// 不会回滚。**D8 在原签名下根本无法实现**。收 tx 是 D8 唯一能落地的写法。
//
// ⚠️ **`OnCancelled` 是 M86-2 加的第 4 个方法**(原稿只有三个)——
// 作废是终局(§3.2 `cancelled`),业务记录不会因为审批单作废而自己变回去。
// 没有这个钩子,资料会永远停在「待审核」:审批单没了,资料还在等一个不会来的审批。
type BizHandler interface {
    ValidateBiz(ctx context.Context, tx *gorm.DB, bizType string, bizID uint64) error
    OnApproved(ctx context.Context, tx *gorm.DB, inst *model.SysApprovalInstance) error
    OnRejected(ctx context.Context, tx *gorm.DB, inst *model.SysApprovalInstance) error
    OnCancelled(ctx context.Context, tx *gorm.DB, inst *model.SysApprovalInstance) error
}

// AssigneeResolver 审批人解析器(M85 实现)。
//
// ⚠️ **收 db 而不是只收 ctx** —— §5.3① 的配置期预检要在**事务外**解析一次,
// 提交期要在**事务内**再解析一次。给一个只认 ctx 的接口,配置期那条路就得
// 自己开事务,反而更容易写错。
//
// ⚠️ **"解析失败"必须用 error 表达,不能用空列表表达** —— 空列表会被当成
// "暂时没人",而 error 才是"配置坏了"。
type AssigneeResolver interface {
    ResolveStage(ctx context.Context, db *gorm.DB, req ResolveStageRequest) ([]uint64, error)
}

// AssigneePrechecker 配置期预检(M85 已落地,**引擎一次都不调**,归 M86 的模板 CRUD)。
//
// ⚠️ **它收的是"待保存的规则",不是按 stage_id 查出来的规则** —— 模板 CRUD 是
// 「先在内存里拼好整棵树、校验、再一次性落库」,预检必须校验**即将写进去的那份**。
type AssigneePrechecker interface {
    PrecheckTemplate(ctx context.Context, db *gorm.DB, in TemplatePrecheckInput) error
}

// ApprovalResolver 装配时构造器返回它(引擎取窄接口,M86 的 POST /flows 取宽的那半)
type ApprovalResolver interface {
    AssigneeResolver
    AssigneePrechecker
}

func NewApprovalResolver(db *gorm.DB) ApprovalResolver

// ApprovalPublisher 审批事件出口(M88 装配 push 实现)。
type ApprovalPublisher interface {
    PublishApproval(ctx context.Context, ev ApprovalEvent)
}
```

### 16.5 事务与行锁骨架

```go
func (s *engine) withLockedInstance(ctx context.Context, caller *Caller, id uint64,
    fn func(tx *gorm.DB, inst *model.SysApprovalInstance) error) error {

    return s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // 30s 应用级超时(§3.5)。⚠️ 必须设,否则 SQLite/网络抖动下会一直挂着
        lockCtx, cancel := context.WithTimeout(ctx, 30*time.Second)
        defer cancel()

        var inst model.SysApprovalInstance
        // ⚠️ 锁在 **instance 行** 上,不是 task 行上 —— 会签并发发生在不同 task 行,
        //    锁 task 行两个审批人还是能同时进去(D10 / §3.5)
        err := tx.WithContext(lockCtx).
            Clauses(clause.Locking{Strength: "UPDATE"}).
            Where("id = ?", id).First(&inst).Error
        if err != nil {
            // ⚠️ **两种错必须分开映射**(M84 落地时补的,原稿只写 `return err`):
            //   查不到 → NotFound("审批单不存在")
            //   锁等到超时 → StateInvalid("审批处理中,请稍后重试")
            // 直接 `return err` 会把"等锁等到超时"变成 500 —— 而它其实是
            // 一个**用户可以重试**的正常状态(§3.5 第 3 条)。
            if errors.Is(err, gorm.ErrRecordNotFound) {
                return errcode.New(errcode.NotFound, "审批单不存在")
            }
            if errors.Is(err, context.DeadlineExceeded) {
                return ErrApprovalLocked
            }
            return err
        }
        return fn(tx, &inst)
    })
}
```

⚠️ **`glebarez/sqlite` 会忽略 `clause.Locking`** —— 测试里所有流转天然串行(**用例 9 已标注**)。
⚠️ **30s 超时要在锁的 ctx 上,不在事务的 ctx 上** —— 后者会被 GORM 在 COMMIT 后取消。
⚠️ **COMMIT 之后才发事件**,且用 `context.WithoutCancel`(§9.2)。
