## 2. 关键设计决策(含被否决的方案)

### 2.1 D1 — 路径根词选 `res`

| 候选 | 结论 |
|---|---|
| **`res`** | ✅ **采用**。短(URL 里省 4 字节 × 每层)、CDN/对象存储惯例、无歧义 |
| `assets` | ❌ **语义冲突**。本仓 `biz_digital_asset` 已经是「交付资产」的业务表,用 `assets/` 当存储根会让人以为是那张表的数据 |
| `media` | ❌ 不只存媒体(还有 pdf/xlsx/zip) |
| `files` / `blobs` / `objects` | ❌ 都比 `res` 长,且 `objects` 是 COS 专有词 |

> `res` 做成配置项 `file.root`(默认 `res`),将来要改不用动代码 —— 但**改它等于全量数据迁移**,所以它该在第一版就定死。

### 2.2 D2 — 双通道上传:OSS 直传 + 服务端中转

| 方案 | 结论 |
|---|---|
| **A. OSS 直传(客户端 → OSS,服务端只签凭证)** | ✅ **OSS 模式采用**。服务端不中转字节,省带宽、省内存、可断点续传 |
| **B. 服务端中转(客户端 → 服务端 → OSS)** | ✅ **local 模式采用**。本地磁盘没有"直传"概念 |
| C. 全部中转 | ❌ OSS 模式下白白吃服务端带宽,大文件必崩 |
| D. 全部直传 | ❌ local 模式做不到 |

**阈值**:`file.multipart_threshold`(默认 100MB,对齐既有 `MultipartMinSize`)以下走单次直传,以上走分片。

**一个必须记住的推论**:本仓**没有内存池**(见 `框架层未完成项清单v1.md` §1.11.2,评估后决定不引入)。所以中转路径上的 `[]byte` 必须**显式限并发 + 限单片大小**,不能指望 GC 兜底。§9.3 给了具体数字。

### 2.3 D3 — `info.json` 是**生成物**,DB 是唯一真相源

| 方案 | 结论 |
|---|---|
| **A. info.json 由框架按 DB 重新生成** | ✅ **采用** |
| B. info.json 作为写入时的记录,DB 只是索引 | ❌ 两个真相源,必然漂移 |
| C. 只写 info.json,不要 DB 表 | ❌ 文件名/大小查不了,列表页没法分页 |

**理由**:任何"先写 DB 再写文件"的方案,在进程崩溃/磁盘满时都会留下半截状态。选 A 之后,`info.json` 丢了可以随时重建,DB 行才是不可再生的。

**生成时机**:文件夹创建、文件注册、删除、封面变更之后各调一次。写的是**整个文件夹的快照**,不是增量。

> ⚠️ **2026-10-31(M140)补上"文件夹创建"这一条** —— 原来只有文件事件才生成,
> 于是**一个刚建的空文件夹里永远没有 info.json**,而 §3.4 的物理布局写着
> "每个文件夹里都有一份"。这条约定从来没被兑现过(用户 2026-10-31 报)。
> 现在建文件夹就写一份(内容是空快照:`files: []`),启动期还会补齐历史缺的那份。

### 2.4 D4 — 配额放 DB 字段,不放 `/rapid-admin/{userId}/` 下的文件

需求里给了两个选项,选第二个:

| 方案 | 结论 |
|---|---|
| A. `/rapid-admin/{userId}/usage.json` | ❌ |
| **B. `sys_user.storage_used_bytes`** | ✅ **采用** |

选 B 的四条理由:

1. **热点**:并发上传并发读写一个 JSON 文件,需要文件锁 + 原子 rename,跨实例更没戏 —— 而 DB 单行 `UPDATE ... SET storage_used_bytes = storage_used_bytes + ?` 是原子的。
2. **不可查询**:文件形式没法 `ORDER BY 占用量 DESC`,做不了"空间占用 TOP10 用户"这种后台看板。
3. **与文件记录不同源**:崩溃在"文件落盘成功、DB 记账失败"之间时,JSON 里的数字永远对不上。
4. **污染命名空间**:它会出现在该用户的文件夹列表里,还得特判过滤。

> ⚠️ **代价要写清楚**:计数器会漂移。所以必须有 §4.4 的**定时对账**,否则 `storage_used_bytes` 只是个大概数。漂移不可怕,没有对账才可怕。

### 2.5 D5 — 单桶单树:文件没有「公开/私有」两套形态

> 🔍 **2026-10-30 修订 —— 本节整条推翻重写。**
> 原设计是「公开/私有两层访问,静态目录只挂 `res/public` 子树」,依据是
> 「参考项目是内部素材库,本平台涉及业主交付物,不能默认公开」。
> **这个前提不成立**:参考项目的双桶双前缀是它自己的历史包袱,不是行业惯例。
> 阿里云 OSS **本来就没有「多个桶 = 公开/私有」这个概念** —— 一个账号下当然
> 可以有多个 bucket,但那是运维拓扑的选择,不是访问模型的表达方式。
> 本地磁盘更是连「public 文件夹」这个说法都没有。

#### 终态模型

```
rapid-admin/{userId}/{biz}/{folderId}/{对象名}   ← 唯一形态,恒 5 段,不带 public/
```

| 维度 | 终态 | 被否掉的旧形态 |
|---|---|---|
| 桶 | **一个** `aliyun.oss.bucket`,ACL 必须 **public-read** | `bucket_admin` + `bucket_public` 双桶 |
| key | **一种**,恒 5 段 | 公开树 `res/public/...` + 私有树 `res/...` 两种 |
| 文件的「公开状态」 | **没有这个概念** —— `sys_file` 没有 `is_public` 列,也没有「改成公开」的接口 | `PATCH /files/:id/public` + `is_public` 列 |
| 转公开时 | **什么都不用做** —— key 不变、对象不搬、URL 不变 | 改 key 前缀 + 搬对象 + 删旧前缀 |
| 静态挂载 | 挂**整棵树**(`/rapid-admin`),不是只挂 `res/public` 子树 | 只挂 `res/public` |

#### 为什么「没有公开状态」是对的

1. **存储侧本来就没有两套东西**。一个对象在桶里就是在那儿,ACL 是**桶的属性**
   不是对象的属性(OSS 的 object-level ACL 默认继承 bucket)。要「区分公开私有」,
   唯一的办法就是**两个桶**或**两棵前缀** —— 而两者都要在「改公开」那一刻
   **搬数据**。搬数据 = 一次全量复制 + 一次删除 + 一次配额回退 + 一次失败重试,
   而收益是零。
2. **私密靠「地址不可猜」就够**。key 第一段是雪花 id(`userId`)、第二段是业务段、
   对象名带 8 位随机十六进制后缀,外部用户**猜不到完整路径**,所以拿不到 URL。
   这跟「文件在不在同一个目录」无关。
3. **直链必须是稳定的**。前端把它塞进 `<img src>`、塞进交付单、发给业主 ——
   带签名、带 TTL 的 URL 一过期就裂图 / 403。而「签名直链」是**私有桶**才需要的
   东西,公共读的桶上根本不需要签名。

> ⚠️ **这条设计有一个硬前提:桶必须是 public-read。**
> 直链是**不带签名、不带过期时间**的稳定 URL,私有桶上访问它会 403。
> 这个前提写进了 seed 的配置描述(`aliyun.oss.bucket` 的 Description)、
> 也写进了 `docs/配置项清单.md`。部署时必须把桶 ACL 设对。

#### 与「归属校验」的关系 —— **一条没少**

⚠️ **「文件都能按 URL 访问」不等于「任何人都能访问你的文件」**。
`StaticFS` 没有任何鉴权,所以**只要 URL 泄露,谁都能下** —— 这是本模型的
**已知边界**,登记在 §13 的风险表里。

但**应用层的权限模型一条没少**:

| # | 机制 | 拦住什么 |
|---|---|---|
| 1 | key 全程由服务端生成 | 前端拼不出「别人的目录」 |
| 2 | 每条路由查库比对 `user_id` | 即便 key 泄露了,A 也拿不到 B 的 `file_id` |
| 3 | 直传登记从 key 解析归属再比对 | key 是客户端上次拿到的,可能指向任何人目录下 |
| 4 | `GenerateIndexPages: false` | 不能枚举目录列表 |

前三条管的是「**不能通过应用**越权访问别人的文件」;第四条管的是「**不能猜**」。
合起来就是本模型的完整边界。

#### 被否掉的方案(留档)

| 方案 | 为什么否 |
|---|---|
| A. 双桶(admin / public) | OSS 上「公开/私有」要靠桶表达,于是改一次公开状态就要搬一次对象;两桶的配额 / 生命周期 / 对账全要写两遍 |
| B. 单桶双前缀(`res/public/` + `res/`) | 同上,只是把桶换成前缀。**而且更隐蔽**:前缀是 key 的一部分,改状态时忘了改 key ⇒ 对象永远留在旧前缀,而清理任务按行驱动、看不到它 ⇒ **存储用量只涨不降**(这个 bug 真的发生过,见 §16 的 A2) |
| C. 保留 `is_public` 列但不改 key | 列是死的:它不影响任何行为(ACL 在桶上,URL 在 key 上),只会让人以为「改了这一列文件就公开了」 |

> **B 的教训值得单独记一笔**:两套前缀一上,「删文件夹要删两个前缀的对象」
> 就成了必须写对两次的代码。少写一次 ⇒ 一半对象永远删不掉,而且**没有任何报错**
> —— 行软删了,清理任务按行驱动就再也看不见它。**双形态的代价不在「多写一点代码」,
> 而在「每个只有一份的清理逻辑都要写两遍,而人总会漏掉一遍」。**

> 🔍 **2026-10-22 实施中发现的那一层,现在自己消失了。**
> 当时记的是「`SignDownloadURL` 不是所有 provider 都签得出来 —— local 的私有
> key 直接返回 `ErrDirectURLUnsupported`」。**在单桶单树模型下不存在私有 key**,
> 所以 local 的直链(`URLBase + key`)对每个文件都成立。
> `GET /files/:id/content`(服务端中转)保留,但它的定位从「私有文件的唯一出路」
> 降级成「直链拿不到时的兜底」(见 §8.1)。

### 2.6 D6 — 封面由**客户端**生成,服务端不抽帧

> 🔄 **2026-10-31 M141 推翻本节**。本节原决策是「客户端抽帧、服务端不抽帧」,
> **而方案 C(客户端抽帧)从未被实现过** —— 前端一行 canvas 提帧代码都没有。
> ⇒ 所以实际状态是:**封面这件事,前后端都没做**,直到 M141 补上服务端抽帧。
>
> ⚠️ 留档这段不是为了"证明当初错了",而是为了说明**当初的顾虑本身是对的**,
> 只是解法不是"换到客户端",而是**换一种方式解决 ffmpeg 依赖**(见下)。

#### 2.6.1 原决策(留档)

| 方案 | 当时的结论 |
|---|---|
| A. 服务端 ffmpeg 抽首帧 | ❌ 要打包 ffmpeg 二进制,容器镜像膨胀 + 跨平台 + 内存尖峰 |
| B. OSS 图片处理 `x-oss-process` | ❌ 只能处理图片,不能从视频抽帧 |
| **C. 客户端抽帧后单独上传** | ✅ **采用** |

前端做法:`<video>` 定位到 0.1s → `drawImage` 到 canvas → `toBlob('image/jpeg')` → 作为普通文件上传,落 `cover.jpg`。

#### 2.6.2 ⚠️ **当年的三条顾虑,一条都没消除 —— 解法是绕开,不是无视**

| 当初的顾虑 | M141 怎么绕开的 |
|---|---|
| 要**打包 ffmpeg 二进制**,镜像膨胀 | **不打包**。ffmpeg **不随仓库分发**,靠 `FFMPEG_PATH` / `FFPROBE_PATH` 指向每台机器自己的安装(§22.8)。**路径配错的症状是"没有时长和封面",不是报错** —— 启动时会打一行工具路径,排查不用猜 |
| 跨平台 | 同上 —— 每个平台装自己的 ffmpeg,代码里没有任何平台分支 |
| 内存尖峰 | 探测是**流式**的(ffmpeg 读路径,不整份读进内存);**副本有大小闸**(默认 2GB);**转码是异步的**(M145,§24.4),不占上传请求 |

#### 2.6.3 现在的结论

| 事 | 谁做 | 章节 |
|---|---|---|
| 视频封面(每个视频一张) | **服务端 ffmpeg 抽帧**,落 `__cover__{文件id}.jpg` | §22 |
| 文件夹封面(整个文件夹一张) | **用户自己传一张图片**,`POST /folders/:id/cover` 关联 | §18.4 |
| "这个文件浏览器播不播得了" | **服务端判**(容器/编码两张表),判出来播不了就转码 | §24 |

⚠️ **方案 C(客户端抽帧)为什么不该再捡回来** ——
① 客户端 canvas 提帧要**把整个视频解一遍**(浏览器还得能解那个编码 ——
而"播不了"恰恰意味着浏览器解不了,于是**提帧和播放是同一个死结**);
② 抽出来的帧要**再上传一次**,多一次往返、多一份存储;
③ 移动端后台标签页会**冻结 canvas 渲染**,抽出来是黑帧;
④ 判据要复制到每一个客户端(小程序 / Web / 将来别的端),抄三遍迟早对不上。

⇒ 判据和抽帧都留在服务端,客户端只负责**显示**(§24.6)。

### 2.7 D7 — 文件夹**可以是嵌套的**(M125 修订:原决策是「扁平」)

> 🔄 **2026-10-30 M125 修订**。本节原决策是「文件夹是扁平的,不支持嵌套」,
> 依据是需求给的路径 `res/{userId}/{biz}/{folderId}/` 里没有父文件夹层。
> 用户 2026-10-30 提「要能创建多级文件夹,文件夹点击可以去子文件夹」—— **扁平不再是需求**。

#### 2.7.1 原决策(留档)

扁平是一个**有代价的决定**:当时担心将来若要支持 `A/B/C` 三级文件夹,路径规范必须改
(要么把完整父链编进 key,要么换目录 id 方案),届时需要一次**全量数据迁移**。

所以当时:`sys_folder` 表**保留 `parent_id` 字段但恒为 0**,并写进 §13 R1 与 §14 待确认项。

#### 2.7.2 M125 的结论:**不需要全量迁移**

⚠️ **这个担心没有成立 —— 因为路径规范从头到尾就不需要改。**

路径是 `rapid-admin/{userId}/{biz}/{folderId}/{对象名}`,`folderId` 那一段放的是
**文件所在的那个叶子文件夹的 id**,不是"根目录 id"、也不是"路径链"。
文件夹嵌套之后,叶子文件夹照样有自己的雪花 id,它的文件照样落在
`rapid-admin/{uid}/{biz}/{叶子fid}/` 下 —— **一个字节都不用挪**。

| | 扁平时 | 嵌套后 |
|---|---|---|
| `rapid-admin/{uid}/{biz}/{fid}/` 里的 `{fid}` | 根级文件夹 id | **叶子文件夹 id**(同上) |
| key 段数 | 恒 5 段 | **恒 5 段** |
| 已有文件的 key | 不变 | **不变** |
| `info.json` 落在哪 | 根级文件夹 | 叶子文件夹(各自一份) |

⇒ **零迁移**。这正是当初"表结构留 `parent_id`、不改 key 生成逻辑"这个选择的红利:
`parent_id` 本来就是预留列,启用它不需要动任何已落库的数据。

#### 2.7.3 启用嵌套后必须一起成立的三件事

1. **唯一索引要带 `parent_id`** —— 原来 `unique(user_id, biz, name)` 的语义是
   "一个用户一个业务段下文件夹名唯一";嵌套之后语义应该变成
   "**同一个父级**下名字唯一"(A 下可以有"图纸",B 下也可以有"图纸")。
   ⚠️ GORM 的 `AutoMigrate` **不会删旧索引** ⇒ 必须有一条显式的
   `dropLegacyFolderIndex` 迁移步骤(见 §18.3)。
2. **删除要删整棵子树** —— 删一个文件夹,它的子文件夹、以及子文件夹里的文件都要没。
   少删一段就是"文件还在云存储里,但库里已经没了"(账单照收,而且没人会知道)。
3. **业务段(biz)要继承** —— 子文件夹跟父级必须在同一个业务段,否则父级里看不到它
   (而且不报错)。前端建子文件夹时不显示 biz 输入框。

⇒ 详见 §18。

### 2.8 D8 — X2 防盗链密钥:修

## 3. 路径规范

### 3.1 完整形态

```
rapid-admin/{userId}/{biz}/{folderId}/{对象名}
```

**恒 5 段,没有第 6 段。** 曾经的 `[public/]` 整段前缀已退役(§2.5)—— 存储侧只有一棵树,
「公开 / 私有」不是一个能出现在路径里的字面段。

> 🔍 **2026-10-31 修订 —— 根段从 `res` 改成了 `rapid-admin`。**
>
> 根段(`file.path_root`)**一处决定两件事**:key 的第一段 + 静态挂载点。
> 改它不是改个常量 —— 存储上的对象在旧前缀下、库里的 key 指着旧根段,
> 两边都不搬 ⇒ 每个历史文件 404,**而且是静默的**(直链不经后端,
> 日志里可能一次请求都没有)。所以这是一次**数据迁移**:
>
> 1. 存储上把 `res/` 前缀整段搬到 `rapid-admin/`;
> 2. 库里所有文件引用(`sys_file.file_key` / `sys_folder.cover_key` /
>    `sys_user.avatar` / 各业务表的图片数组 JSON …)的根段一起改;
> 3. 删掉旧前缀。
>
> ⚠️ **顺序不能乱** —— 先删存储再改库,中间那一小段时间里文件全 404。
> ⚠️ **根段不是 `file.root`** —— `file.root` 是 local 模式的**磁盘根目录**
> (`data/files`),`file.path_root` 才是路径里的第一段。两个名字挨着,
> 配错的那个症状同样是 404。
>
> ⚠️ **`info.json` 里也存着 `cover_key` 的快照** —— 它是**生成物**(DB 才是
> 真相源),但 `GET /folders/:id` 把原文直接吐出来 ⇒ 不一起改,用户会看到一个
> 指向旧根段的死链接。(下一次文件变动会按 DB 自动重建,但那要等下一次上传。)
>
> **本仓的实际迁移范围**(2026-10-31):本地运行时数据 `server/data/` 是
> **gitignored** 的(`/server/data`),新克隆根本不会带旧的 `res` key ⇒
> **不需要通用迁移工具**,改库 + 改目录名即可:
> `data/files/res` → `data/files/rapid-admin`(4 个文件);
> 库里 5 行(`sys_user.avatar` ×1、`sys_file.file_key` ×3、`sys_folder.cover_key` ×1);
> 全库 TEXT 列重扫后**严格匹配 0 处**残留。

| 段 | 规则 | 校验 |
|---|---|---|
| 根 | `rapid-admin`,配置项 `file.path_root` | 固定 |
| `userId` | 十进制数字,**从 JWT 里取,绝不信请求体** | 服务端填充 |
| `biz` | `[a-z][a-z0-9_-]{0,31}` | **语法 + `file.allowed_biz` 白名单(留空 = 不限)** |
| `folderId` | 雪花 ID,十进制 | 查库确认归属 |
| 对象名 | `{unix}-{rand8}-{清洗后原名}` | 见 §3.3 |

**`biz` 不做硬编码白名单**,是刻意的:框架不该硬编码业务枚举(与本仓字典/配置单一来源的思路一致)。哪个 `biz` 合法由业务侧自己判断 —— 但框架提供一个 `file.allowed_biz` 配置项,**留空表示不限,填了就当白名单用**。

> 🔍 **2026-10-22 收尾更正 —— 这个配置项原本是死配置,配了不生效。**
> `config/file.go` 读得进 `allowed_biz`,而 `FileOptions.AllowedBiz` 在实现里**从头到尾没有任何一处读过**:只有 `validateBiz` 的语法校验在跑。配置注释写着"填了就当白名单用",代码里没有对应的那一段。
>
> 后果不是"多收了一个不合法的值"这么轻:`biz` 是 key 的**第二段**,也是静态挂载与 OSS 生命周期规则的输入。不限的话,任何登录用户都能 POST `{biz:"<任意合法小写串>"}` 建出一整棵新的目录树,而运维按已知 biz 配的生命周期规则**盖不到它**(规则是按具体前缀写的)—— 那棵树永远清不掉,还会一直按量计费。
>
> 已修:`folderService.checkBiz` 统一做「语法校验 + 白名单」,由 `resolveBiz`(上传/取凭证/分片 Init)和 `Create`(建文件夹)两条入口共用,见 `internal/service/file_common.go`。**留空 = 不限**,所以这道闸默认关闭,对既有部署零行为变更;配了才生效。回归测试 `TestAllowedBiz_WhitelistIsEnforced` / `TestAllowedBiz_EmptyMeansUnrestricted`。

### 3.1.1 `userId` 那一段是**隔离边界**,不是分类标签

用户隔离**不能只靠路径形状**。路径是给人看的,真正拦人的是下面四道,四道都要在:

| # | 机制 | 拦住什么 | 位置 |
|---|---|---|---|
| 1 | **key 全程由服务端生成** | 前端拼不出"别人的目录" —— 因为它压根不参与造 key | `buildFileKey` / `File.UploadToken` |
| 2 | **每条路由查库比对 `user_id`** | 即便 key 泄露了,A 也拿不到 B 的 `file_id` / `folder_id` | `loadFile` / `loadFolder`(§8.4) |
| 3 | **直传登记从 key 解析归属再比对** | key 是客户端上次拿到的,它可能指向任何人目录下 | `File.Register` 的 `parseKeyOwner` + `ownerID != uid → 404` |
| 4 | **文件夹软删改名** | 删掉 A 的文件夹不能靠"同名重建"顶掉 B 的 | `deletedFolderName`(§4.1) |

第 3 条最容易漏。`POST /files`(application-json 分支)是唯一一条 **key 由客户端回传**的路径 —— 直传模式下 key 是上次 `UploadToken` 给的,客户端确实拿得到。只做 `SafeKey` 语法校验是不够的(`SafeKey` 只管路径穿越,不管归属),必须**从 key 里把 `userId` 解析出来跟当前登录人比**。少这一条,任何人拿到别人的 key 就能把它登记成自己的文件(写是写不进去,但会占着配额、也会出现在自己的列表里)。

而 `super_admin` **读**可以跨用户(§10.2),**写**不可以 —— 所以 `loadFile`(读)和 `loadFileForWrite`(写)是两个函数,不是一个带 flag 的。

### 3.2 为什么对象名要带前缀

直接用原文件名当 key 有三个真问题:

1. **大小写撞车**:本地磁盘在 Windows/macOS 上大小写不敏感。`报告.pdf` 和 `报告.PDF` 在 DB 里是两行,在磁盘上是同一个文件 —— 第二行会静默覆盖第一行。**加 `{unix}-{rand8}` 前缀就绕开了**:前缀保证唯一,原名只用来让人看得懂。
2. **编码地狱**:中文 + emoji 文件名进 URL 要 percent-encode,签名 URL 的 `Signature` 又是按原始串算的,SDK 各家实现对空格的编码还不一致(`%20` vs `+`)。
3. **长度**:`rapid-admin/1844.../asset/1234.../` 已占约 50 字节,原文件名得限在 ~180 字节。

原文件名**完整存在 DB 的 `file_name` 字段**里,下载时通过 `Content-Disposition` 还原,用户体验不受影响。

### 3.3 文件名清洗规则

```
拒绝:空串 / "." / ".." / 含 "/" 或 "\" / 含控制字符(\x00-\x1f) / 超过 180 字节
允许:中日韩、字母、数字、空格、. - _ ( ) 【】 等常见符号
处理:Unicode NFC 归一化(避免 macOS 的 NFD 分解形式造成同一文件两个 key)
替换:"/" "\" 之外的非法字符 → "_"
```

### 3.4 文件夹内的物理布局

```
rapid-admin/{uid}/{biz}/{fid}/
├── info.json          ← 生成物(§2.3),可随时重建
├── cover.jpg          ← 文件夹封面(用户自己传的一张图片,§18.4)
├── 1730483200-a3f9c2e1-户型图.pdf
├── 1730483265-b71e0d44-宣传片.mp4
└── 1730483301-5c92af60-户型图.pdf
```

`cover.jpg` 是**文件夹级**的(整个文件夹一张封面)—— 需求原文「文件夹里面存放文件、视频的话还要存放jpg封面」的字面读法。

> 🔄 **M141 补上了另一种"每视频一张"** —— 服务端 ffmpeg 从视频里抽首帧,
> 落 `__cover__{文件id}.jpg`(§22.6),**不入 `sys_file`、不计配额**。
> ⚠️ **它和上面那个 `cover.jpg` 是两件事**:
> 前者是**用户指定的文件夹封面**(一张图片,任何用户都能设),
> 后者是**视频文件自己的缩略图**(自动抽的,只在文件列表里显示)。
> 别把两者混成一个字段。

> ⚠️ **`info.json` 是**每一个**文件夹都有的一份**(M140 起)——
> 建文件夹时就写(哪怕是空快照),文件变动时重建,启动时补齐历史缺的那份。
> 详见 §21。

> 🔄 **2026-10-30 M125 更正**。原索引是 `unique(user_id, biz, name)`
> (见下面那段 2026-10-22 的更正块 —— 那段讲的是**为什么不能把 `deleted_at`
> 放进索引**,结论仍然有效)。改成带 `parent_id` 是因为嵌套之后
> "一个用户一个业务段下名字唯一"这个语义**太严了**:
> A 下有"图纸"、B 下也有"图纸"是合法的,但旧索引会拒掉第二个。
>
> ⚠️ **GORM `AutoMigrate` 不会删旧索引** —— 它只加不删。所以光改 struct 上的
> tag 是不够的:旧索引 `uk_folder_owner_biz_name` 会**继续生效**,于是
> "A/图纸" 能建、"B/图纸" 建不了(报 `同级下已有同名文件夹`,但 B 下明明没有)。
> 必须有一条**显式**的 `DROP INDEX` 迁移步骤 —— 见 §18.3。

> 🔍 **2026-10-22 更正 —— 原文写的是 `unique(user_id, biz, name, deleted_at)`,那一版是错的。**
>
> SQL 里 UNIQUE 索引认为**所有 NULL 互不相等**,而未删除的行 `deleted_at` 恰好就是 NULL。
> 所以把 `deleted_at` 放进唯一索引之后,**活跃行之间根本不互斥**。实测(SQLite,M79 期间跑过):
>
> ```
> CREATE TABLE t (id INTEGER PRIMARY KEY, a TEXT, b TEXT, deleted_at DATETIME, UNIQUE(a,b,deleted_at));
> INSERT INTO t (a,b) VALUES ('u1','默认文件夹');   -- OK
> INSERT INTO t (a,b) VALUES ('u1','默认文件夹');   -- 也 OK,没有报错
> SELECT COUNT(*) FROM t;                          -- 2
> ```
>
> MySQL 同样如此。也就是说原方案既没防住想防的重复,**又失败得毫无声响** —— 不报 duplicate key,
> 于是"一个用户两个默认文件夹"就这么混进库里,列表页还照常显示。
>
> **代价与配套**:索引不含 `deleted_at` ⇒ 软删**不会自动释放同名**,重建同名文件夹会撞唯一索引。
> **M80 的 `DeleteFolder` 必须在软删时把 `name` 改写成带 id 后缀的形式**(如 `默认文件夹#del:123`),
> 这条不做的话"删掉再传"就传不进去了。这是索引改法带出来的**必做配套**,不是可选项。
>
> 备选方案(未采用):加一个 `deleted_id uint64 default 0` 列进唯一索引,删除时置为自身 id、
> 查询时恒传 0。这样软删后同名自动可复用,且 0 非 NULL 能正确互斥。改动面比"改名"大
> (多一列 + 所有查询都要带上它),本轮选了改名;若将来出现"文件夹名必须可原样复用"的需求再切。

> **2026-10-22 补充三列**(`quota_held` / `expires_at` / `part_size` 的存法):
>
> - **`quota_held`** —— 过期清理靠它**精确回滚**预扣。只存个标志位的话,清理任务就得靠 `file_size` 猜,
>   猜错就是配额凭空少一截或多一截,而且用户完全看不出来(表现只是"传着传着就传不进去了")。
> - **`expires_at` 存绝对时刻**,不存"创建时间 + 配置值"。配置随时可能改,而清理任务要判的是
>   "按当初的约定它该不该过期" —— 存相对量等于让清理结果取决于清理时读到的配置值。
> - **`part_size` 必须落库**,不能每次重算默认值:默认值以后可能改,而**已经传上去的分片是按旧
>   partSize 切的**,改了偏移全错位,断点续传会往错位置拼。

**过期清理**:超过 `file.session_ttl`(默认 24h)未完成的会话由定时任务清理:调 `AbortMultipartUpload` + 删 local 临时文件 + `storage_used_bytes` 预扣回滚。

### 4.5 配额扣减时序(预扣 - 结算)

```
① 初始化(token 或 multipart/init):  used + fileSize > quota ? → 拒绝
                                    否则 storage_used_bytes += fileSize   ← 预扣
② 上传完成 / 分片合并:              写 sys_file 行,置 session=1
③ 实际大小 < 预扣:                  storage_used_bytes -= (预扣 - 实际)  ← 结算找零
④ 超时未完成 / 用户取消:             整个预扣回滚
```

**为什么预扣**:如果只在完成时扣,用户可以同时发起 10 个 5GB 上传,全部传完才检查配额 —— 那时磁盘已经满了。预扣把拒绝点提前到最便宜的时刻。

> 🔍 **2026-10-22 实施时修正 —— 直传这一路根本没有 ①,它必须在 ② 整份扣。**
>
> 上面的时序图默认"每条路都有预扣",但**直传(OSS PostObject)不适用**:
> `UploadToken` 那一刻客户端只申报了 `file_size`,而客户端可以随便填这个数
> —— 拿它预扣等于"用户说占 1 字节,实际写 10GB"。所以直传这条路**没有预扣**
> (见 `FileService.UploadToken` 的注释)。
>
> 于是 `commitFile` 的 `held` 参数就有个陷阱:它的语义是"**之前已经预扣了
> 多少**",`settleQuota` 算的是 `delta = held - actual`。直传这里若照抄
> multipart 的写法传 `held = meta.Size`,`delta` 恒为 0 —— **净变化 0,
> 每个直传文件都完全免费**。
>
> 症状极其隐蔽:文件在、列表里有、字节在存储里,只有 `storage_used_bytes`
> 纹丝不动,而且**全程没有任何报错**。用户可以绕开配额上限无限传,而配额页面
> 显示的还是"已用 0 B / 100 MB"。
>
> **正确写法是 `held = 0`**,走 `commitFile` 的 `holdQuotaOrFail` 分支 ——
> 那才是"没有预扣 → 整份扣下来,扣不动就拒"。
>
> 附带一件必须做的事:直传被拒时**对象已经在存储里了**(是客户端自己传上去的,
> 服务端拦不住),所以要在登记失败后 `prov.Delete` 掉它。留着就是一份没人
> 认领、也没人计费的孤儿对象,按量计费会一直烧钱。删失败只记 Warn,不要覆盖
> 原错误 —— 用户看到的应该仍然是"空间不足"这个真正的失败原因。
>

> 也验"超额被拒"和"被拒的对象被回滚")。

### 5.1 `SignUploadToken` 的签名要从 `(dir, ...)` 改成 `(key, ...)` —— 破坏性

**理由**:现签名让客户端在 `dir` 下**自选文件名**。本设计的 `userId`/`biz`/`folderId` 三段必须由服务端决定(否则就是越权访问别人的目录),客户端只能填最后一段文件名。而 `SignUploadToken` 现在签的是 OSS PostObject policy,条件只有 `starts-with $key = dir`(`aliyun.go` 内已确认)—— **客户端仍能在前缀下乱写**,写进别人的 `{folderId}` 目录完全不受拦。

改成对**完整 key** 签 `eq $key = <key>`:签名绑定到唯一 key,客户端无处可逃。

> 🔍 **2026-10-22 更正 —— 本节原先的结论是错的。**
> 原文写的是"PostObject 的 form 表单天然按前缀约束,必须换成 presigned PUT URL 才能精确到 key"。**核实后不成立**:PostObject policy 的 `conditions` 数组支持 `eq` / `starts-with` / `in` / `not-in` 四种匹配方式,`["eq", "$key", "完整key"]` 是官方文档里的标准写法。
>
> 更关键的是,**换成 presigned PUT 是净损失**:预签名 URL **没有 `content-length-range`**,换成它就等于把单文件大小上限(防单请求打爆内存/防超配额)这个闸门扔掉。而 PostObject policy 里 `eq` 和 `content-length-range` 是**可以并存**的。
>
> 所以终态是:**留在 PostObject,把 `starts-with` 换成 `eq`**。改一行,两个闸门都在。
> 来源:[PostObject API](https://help.aliyun.com/document_detail/116277.htm) · [设置 POST 请求的策略](https://intl.aliyun.com/help/zh/oss/policies-for-setting-post-requests-in-oss)

**`UploadToken` 不需要为此瘦身** —— 仍走 PostObject 表单直传,`Host`/`Policy`/`Signature`/`AccessKeyID` 都还要用。之前"presigned URL 里已有签名,前端不需要这些字段"的推论随之上游结论一起作废。真正让前端不必关心形态的是 `Mode` 字段(proxy/direct 各填各的),已在 M77 落地。

> ⚠️ **不要把它说成"现状泄露了密钥"** —— `UploadToken`(`provider.go:23-33`)只有 `AccessKeyID`,**没有** secret 字段,注释也明确写了「真实生产 secret 不返回前端」。PostObject 模式返 AK ID 是标准做法。改动的理由纯粹是**key 精度**,不是凭证暴露。

**迁移成本:零** —— 因为零调用方(§0.2)。

## 6. `LocalProvider` 实现要点

### 6.1 目录穿越防御(**这个模块最重要的一段**)

OSS 是按 key 前缀索引的,`../` 只是个普通字符,天然安全。**本地磁盘不是** —— `filepath.Join(root, key)` 会真的走出 root。所以必须三层:

```go
func (l *LocalProvider) resolve(key string) (string, error) {
    // ① 语法闸:与 OSS 共用同一套规则(§5.1 把 SafeKey 提到 oss 包顶层)
    if !SafeKey(key) {
        return "", ErrInvalidKey
    }
    p := filepath.Join(l.root, filepath.FromSlash(key))
    // ② 边界闸:Join 之后必须仍在 root 之下
    rel, err := filepath.Rel(l.root, p)
    if err != nil || rel == ".." || strings.HasPrefix(rel, ".."+string(os.PathSeparator)) {
        return "", ErrInvalidKey
    }
    // ③ 符号链接闸:① ② 都只看字面路径,root 内若已存在 symlink
    //    (root/data -> /etc),字面检查全过,实际写出去却逃逸了。
    //    ⚠️ 只能对**父目录**求值 —— Put 时目标文件还不存在,
    //    对文件调 EvalSymlinks 会返回 ENOENT。
    realDir, err := filepath.EvalSymlinks(filepath.Dir(p))
    if err != nil {
        return "", fmt.Errorf("local oss: eval parent dir: %w", err)
    }
    if real, err := filepath.Rel(l.root, realDir); err != nil ||
        real == ".." || strings.HasPrefix(real, ".."+string(os.PathSeparator)) {
        return "", ErrInvalidKey
    }
    return p, nil
}
```

> **为什么第③层不能省**:本仓 `SafeKey`(`aliyun.go:241-258`)拒的是 key 里的 `..` 和非法字符,防的是**调用方传入的恶意 key**。但如果 root 内部有人(运维误操作、或某个业务进程)建了个软链 `rapid-admin/data -> /etc/passwd`,那么 key = `data/x` 通过了 ① ②,写出去却落在 `/etc/passwd` 旁边。**两层防的是不同的人。**
> ⚠️ 代价:`Put` 必须先 `MkdirAll(filepath.Dir(p))`,否则第③层会因父目录不存在而返错。

> ② 绝对不能用 `strings.Contains(realPath, root)` 判前缀 —— `root=/data/res` 时,`/data/res2/x` 也 `Contains` 成立。`filepath.Rel` 的返回值天然是「相对于 root 的路径」,判断 `rel == ".."` 或 `strings.HasPrefix(rel, "../")` 就够了,不需要再做字符串包含。(参考项目踩的是另一个形状的坑 —— 对**请求路径**做 `strings.Contains`,见 §12 第 1 条。)

### 6.2 写入原子性(**新增,仓里没有现成的**)

⚠️ **更正**:我一度以为可以复用已有实现 —— 查证后不成立。`grep -rn "func.*[Aa]tomic.*[Ww]rite|os.CreateTemp" internal/pkg/` **零命中**,Go 侧没有可复用的原子写 helper(commit `c298982` 的原子写在 wenjuan 的 Node 侧,是另一套东西)。所以要在 `pkg/oss/local` 里**新写**。

### 6.4 local 的分片上传

local 没有真分片,用**定长偏移写临时文件**模拟:

```
init:     建 .mpu/{uploadId}.part,记 part_size 到 session 表
part N:   offset = (partNumber-1) * partSize
          os.OpenFile(O_CREATE|O_WRONLY) → WriteAt(body, offset)
parts:    从 session 表返回已传 part 清单(断点续传的依据)
complete: 校验实际大小 == 声明大小 → os.Rename 到最终 key → 删 .part
abort:    os.Remove(.part)
```

**必须用 `WriteAt(定长偏移)`,不能用 `O_APPEND` 追加。** 三个理由:

1. **乱序/重传**:`O_APPEND` 一律写到文件末尾。客户端并发上传 part 3 和 part 4,或者断点续传时**重传** part 3,追加就会把内容接在错的位置 —— 文件看起来"大小对了"但内容全是乱的。
2. **偏移可推导**:`(partNumber-1) * partSize` 是纯函数,所以 session 表**不需要存偏移**,重传天然幂等(覆盖同一段,不追加)。这比"记录已传偏移"少一个状态,也少一类不一致。
3. **大小可预知**:第 N 片写完后,文件长度至少是 `N * partSize`,可以据此判定"至少传到了第 N 片",给续传一个廉价校验。

⚠️ **并发闸**:同一 session 的多个 `WriteAt` 会并发写同一个 fd,**必须按 session 加写锁**(或用 §9.3 的 per-session semaphore),否则两个 part 的写会互相覆盖。
⚠️ **崩溃残缺**:`WriteAt` 不是原子的,进程崩溃会留下半截。`complete` 阶段**必须**校验实际大小 == 声明大小,不匹配就拒绝并删临时文件 —— 这是最后一道闸,不能省。

## 7. HTTP 静态挂载

**hertz v0.9.6 自带 FS,不需要 `hertz-contrib/static`,不新增依赖。**

```go
// 挂载点 = key 的第一段。磁盘上是 <file.root>/rapid-admin/...,URL 是 /rapid-admin/... ——
// 同一个 path_root 推出两处,不可能对不齐。
mount := "/" + cfg.File.PathRoot        // 例如 "/res"

h.StaticFS(mount, &app.FS{
    // ⚠️ Root **必须含 path_root**,见下面第 0 条
    Root: filepath.Join(cfg.File.Root, cfg.File.PathRoot),
    // 剥掉 URL 的 1 段(/res),剩下 /1/house/2/a.jpg 才去 Root 下找
    PathRewrite:        app.NewPathSlashesStripper(1),
    GenerateIndexPages: false, // ⚠️ 必须显式 false,见下
    Compress:           false, // ⚠️ 必须显式 false,见下
    AcceptByteRange:    true,  // 视频拖进度条要它
})
```

终态实现把这段提成纯函数 `staticFSTarget(cfg)`(`internal/api/router/staticfs.go`),
并**直接断言 root / strip 的值**(`staticfs_test.go`)。

**五个必须知道的坑**(都来自 `pkg/app/fs.go`):

0. **`Root` 必须带 `path_root`,即 `<file.root>/<path_root>`。**
   > 🔍 **2026-10-22 更正 —— 原文写的是 `filepath.Join(cfg.File.Root, "public")`,少一层,公开图会全部 404。**
   > 核对了 `LocalProvider.resolve`(`internal/pkg/oss/local/local.go:132`):磁盘路径是 `filepath.Join(自己的Root, key)`,而 key 是 `rapid-admin/{uid}/...`(§2.5)。所以文件实际落在 `<file.root>/rapid-admin/...`,挂载点写成 `<file.root>` 就指向了一个不存在的目录 —— 而请求**确实命中了路由**,所以是静默 404。
   > 终态实现把这段提成纯函数 `staticFSTarget(cfg)`,并**直接断言 root 的值**(`staticfs_test.go`)。只靠 HTTP 往返反推是不够的:路由模式是 `/rapid-admin/*filepath`,URL 空间够不到挂载点之外,所以"Root 挂高了"这种错在 HTTP 上测不出来(测试假绿)。
1. **`PathRewrite` 的剥除段数 = 挂载路径 `/res` 的 URL 段数,就是 1。**
   ⚠️ **不要写成 `len(strings.Split(storePath, "/")) + 2`** —— `Root` 是磁盘路径,URL 段数和磁盘路径的段数毫无关系。参考项目里那个 `len(storePathLen)` 之所以对,是因为它的**挂载路径恰好就是 StorePath 本身**,两者是同一个字符串,属于巧合不是规律。
   段数算错的表现是「找不到文件」而不是报错,**必须配一条集成测试**:直接 GET 一个已知存在的文件,断言 200。
2. **`GenerateIndexPages` 必须显式写 `false`**。`FSConfig` 结构体零值是 `false`(安全),但 hertz 的**全局默认 `rootFS` 是 `true`**(`fs.go:81`)。用结构体字面量是安全的,任何走默认的路径就不安全了 —— 显式写出来,不依赖调用形态。
3. **`Compress` 必须显式写 `false`**。开启后 hertz 会**把压缩缓存写回 Root 目录**(`fs.go:141-146` 注释:需要 write access)。文件存储目录通常该是只读挂载,而且这会在存储目录里凭空多出一批 `.gz` 文件,`DeletePrefix` 和对账任务都会被干扰。
4. **挂的是整棵树,不是某个子树。**
   > 🔍 **2026-10-30 修订 —— 原文第 4 条写的是「只挂 `res/public`」。现在挂的是整棵树。**
   > 单桶单树模型(§2.5)下**没有"私有目录"这个概念**,所以没有"该不该挂"的判断题:
   > 每个文件都有直链(§2.5),直链必须能落到磁盘上的那个对象。
   > ⚠️ 但要清楚这条的后果:**`StaticFS` 没有任何鉴权** —— 它是纯文件服务,
   > URL 落到哪个目录就返回哪个目录的内容。所以**URL 一旦泄露,谁都能下**。
   > 这是本模型的**已知边界**(§13 的风险表),不是疏漏。
   > 应用层的归属校验(§3.1.1 那四道)一条没少 —— 它管的是"不能通过应用越权",
   > 静态挂载管不了的是"不能猜"(靠 §2.5 的 key 不可猜 + 这里的禁目录列表)。

⚠️ **`StaticFS` 不能进鉴权中间件链**。它必须挂在根 `h` 上而不是 `biz` 组里 ——
在单桶单树模型下,"文件直链不带鉴权"是**模型本身的前提**(§2.5),
而不是"恰好公开区没挂鉴权"。挂了鉴权等于所有文件都要登录才能看,直链就没意义了。

本地磁盘模式下生产环境建议前面放 Nginx;hertz 直出适合开发/单实例。

### 7.1 部署契约:**谁服务 SPA,谁就得把 `/res` 也接上**

> 🔍 **2026-10-30 补 —— 用户报「复制直链的路径 http://localhost:5173/res/... 还是 404」。**
> 查下来是**开发期的路由缺口**,不是后端的问题(后端那个 URL 直接打过去是
> 200 + `image/jpeg` + 137756 字节,一个字节不差)。根因和契约写在这一节。

#### 不变式(只有一条,但推出来的部署要求有三条)

**local provider 返的直链是「同源相对路径」`/rapid-admin/...`**,不是绝对 URL
(`local.Provider.SignDownloadURL`,§7 那段 `p.urlBase + "/" + ...`)。于是:

> **SPA 与文件树必须在同一个 origin 上。**

这不是风格问题,是**浏览器解析规则**:页面在 `https://a.cn/`,`<img src="/rapid-admin/x.jpg">`
就一定打到 `https://a.cn/rapid-admin/x.jpg`。前端两处已经按这个前提写好了 ——
`resolveFileUrl` 的注释写着「local 是 `/rapid-admin/...` 同源路径」,`downloadFile` 判
「同源才挂 `download` 属性」(OSS 直链是跨源的,走 `target=_blank`)。
**后端改 URL 形态 = 改前端契约**,不能单边动。

同一条约束的另外两个推论:

1. **API 基础路径也是相对的**(`web/.env.production`:`VITE_API_BASE=/rapid-admin/v1`,
   注释写着「同源部署,使用相对路径」)。所以「SPA 同源」这件事本来就成立,
   `/res` 只是**同一套同源部署里的第 N 个路径**,不是新问题。
2. **`file.path_root` 改名 = 前端要跟着改**(默认 `rapid-admin` → 挂载点 → 直链前缀)。
   开发期 vite 的代理前缀、后端配置、前端拼 URL,三处都得在同一个 commit 里改。
   `web/src/api/__tests__/static-mount-proxy.test.ts` 盯着前两处(它直接读后端
   `config.go` 的默认值,不抄一份)。

#### 开发期(vite dev server)

**vite 必须代理 `/res` → 后端**,这条是**必需项**,不是"开发期方便"。

⚠️ **不加这条的症状是"404",但后端日志里一次请求都没有** ——
因为 vite 的 **SPA fallback 对未知路径返回 index.html + 200**,请求**根本没到后端**。
更坑的是 **200 + HTML 在 `<img src>` 里不报错**(浏览器当"解码失败"),图片裂开,
控制台最多一条 decode 报错。粘贴到地址栏更坑:看到的是**登录页**(SPA 认路由),
很容易被当成"404"。

所以这条洞是**完全静默**的,只有真跑起来看图才发现 —— 2026-10-30 就是这样。

落地:`web/vite.config.ts` 的 `server.proxy` 里加了 `'/res'`(前缀跟后端
`file.path_root` 一致,**不 rewrite** —— 后端认的就是 `/rapid-admin/...` 这个完整 key)。

#### 生产期:三种部署形态,各有一条要满足的规则

| 形态 | `/res` 怎么到后端 | 要满足的条件 |
|---|---|---|
| **整域名反代**(技术方案 §15.7 内网 Caddyfile:`admin.xxxx.cn { reverse_proxy 127.0.0.1:8888 }`) | 自动 —— 整个域名都转给后端,`/res` 是后端自己的静态挂载 | SPA 也要由**这个 origin** 提供(同一台机器、同一个域名) |
| **SPA 独立 origin**(云上 Caddyfile:`static.xxxx.cn` 是 SPA 静态域名,`admin.xxxx.cn` 才是 API) | **必须给 SPA 那个 origin 补一条 `/rapid-admin/*` → 后端的规则** | ⚠️ 不补的话,相对路径会解析到 `static.xxxx.cn/rapid-admin/...` → **404**,症状跟开发期一模一样 |
| **nginx 托管 SPA**(技术方案里 nginx 是"前端静态资源") | nginx 必须显式加 `location /rapid-admin/ { proxy_pass http://127.0.0.1:8888; }` | ⚠️ 不加的话,SPA 的 `try_files` 会把 `/rapid-admin/xxx` **兜成 index.html(200)**,症状还是一模一样 |

**一句话:不管前面挂的是 Caddy 还是 nginx,凡是能出 SPA 的那个 origin,
都必须能把 `/rapid-admin/*` 转给后端的静态挂载。** 忘了这一条,部署上线时才会炸 ——
而且是**静默**地炸(裂图 / 登录页),不是响亮地炸。

#### 症状对照表(下次见到直接查这张表)

| 现象 | 根因 |
|---|---|
| 地址栏打开直链看到**登录页 / SPA 首页** | 请求被 **SPA fallback** 兜走了(index.html + 200),没到后端 |
| `<img>` **裂图但控制台没有 404** | 同上 —— 200 + HTML 在 `<img>` 里不报错,只报"解码失败" |
| **后端日志里一次请求都没有** | 同上 —— 请求根本没到后端(这是最好认的特征) |
| 地址栏打开直链是**404 且后端有日志** | 路径算错了:挂载点 / `path_root` / key 的段数对不上(§7 那五个坑) |
| 后端日志有请求但**404** | 同上,重点查 `PathRewrite` 剥的段数是不是 1(§7 第 1 条) |
| 前端能显示、**复制出去的链接打不开** | 相对路径没补全 origin —— 前端「复制直链」那条要补 `window.location.origin` |

## 8. HTTP API 清单

统一前缀 `/rapid-admin/v1/biz`,RBAC 码 `file:*` / `folder:*`。

### 8.1 文件

| 方法 | 路径 | RBAC | 说明 |
|---|---|---|---|
| POST | `/files/upload-token` | `file:upload` | 取直传凭证。body: `{folder_id, file_name, content_type, file_size}` → 返回 `{mode: "direct"|"proxy", url, key, headers, expires_in}` |
| POST | `/files` | `file:upload` | 服务端接收(`multipart/form-data`),写 `Put`。**同时用于直传完成后登记元数据** |
| GET | `/files` | `file:list` | 列表。query: `folder_id` / `biz` / `status` / `keyword` / `page` / `size` |
| GET | `/files/:id` | `file:read` | 详情(含 `file_name` `file_size` `content_type` `url`) |
| GET | `/files/:id/url` | `file:read` | 取访问 URL。**恒返一条 URL**(每个文件都有直链,§2.5)。query: `ttl`(默认 15m,上限 24h)—— OSS 侧生效;local 侧的直链是稳定的、忽略 ttl |
| GET | `/files/:id/content` | `file:read` | **服务端中转读字节**(直链兜底,见下方说明) |
| DELETE | `/files/:id` | `file:delete` | 删文件 + 扣配额 + 重建 info.json |

> 🔍 **2026-10-30 契约变更 —— `/files/:id/url` 恒返一条 URL,不再有「空串」这一档。**
>
> 单桶单树模型(§2.5)下**每个文件都有直链**,所以这条路由的契约变成:
>
> | 情况 | 响应 |
> |---|---|
> | 正常 | **200 + `{url}`** —— local 是 `/rapid-admin/{uid}/{biz}/{fid}/{name}` 同源路径,OSS 是 `https://{bucket}.{endpoint}/{key}`(配了 CDN 域名则是 CDN 形式) |
> | 文件不存在 / 不是你的 | **404**(跨用户一律 404,不是 403,§8.4) |
> | provider 没初始化 / 磁盘读失败 / 桶访问失败 | **500**「生成访问地址失败」 |
>
> **「200 + 空串」这一档被撤掉了。** 以前有,是因为 local 的「私有 key」签不出
> 直链(`ErrDirectURLUnsupported`),service 层把它翻译成空串,好让前端落到
> `/content`。现在**没有私有 key 了** —— 签不出来就是**真故障**(对象真不在 /
> 磁盘读失败 / provider 没配静态挂载点),必须报出来,不能返空串糊过去。
>
> ⚠️ **这一步依赖 §2.5 的整个改造**,不是单点改动:`ErrDirectURLUnsupported`
> 这个哨兵**整个删掉了**。留着它就会变成"永远不会被返回的 error",
> 而它的存在会让人以为"还是有可能签不出来" —— 于是又有人会把它翻译回空串。
>
> 前端 `resolveFileUrl` 的 blob 兜底**仍然保留**,但触发条件变了:
> 现在只有「直链这条路真的坏了」才会走中转(直链拿不到 → 500 → 兜底),
> 而**不是**「这个文件本来就没有直链」。
> `web/src/api/upload.ts` 里那段「吞掉 `/url` 的失败当成没有 url」的注释
> 相应改了 —— 它现在兜的是**故障**,不是**正常结论**。

> 🔍 **2026-10-22 收尾更正 —— `status` 这个 query 参数是"替换默认值"而不是"叠加",而且查非正常态必须绕过软删作用域。**
>
> 早先的写法是无条件 `status = 正常`,之后再来一句 `if q.Status > 0 { … status = q.Status }` 追加 —— 两个条件 AND 在一起恒空。而注释写着"要看历史要显式传 status",于是**传了必然返回空列表,且 HTTP 200**,调用方只会以为自己参数写错了。
>
> 现在是 `status` 显式传了就替换默认;不传(或传 0 = `FileStatusNormal`)仍只看活着的。
>
> ⚠️ **"替换"这一半还不够**:`sys_file` 走的是 `BaseModel.DeletedAt`(GORM 软删作用域),所有查询自动加 `deleted_at IS NULL`,而 `Delete()` 恰好**同时**写了 `status` 和 `deleted_at`。所以即使把 status 条件写对了,「已删」那些行照样被作用域挡在查询外面,结果仍然是恒空。**查非正常态必须显式 `Unscoped()`** —— 这是两套删除标记并存(`model/file.go` 的类型注释里写了这件事)唯一需要绕的地方,而且必须是调用方**明确要求**才绕。
>
> 回归测试 `TestList_StatusFilterReplacesDefault`(同时钉住"传 0 仍等价于默认,不能变成不过滤")。

> 🔍 **2026-10-22 新增 `/files/:id/content` —— 直链的兜底(原定位:私有文件在 local 下的唯一出路)。**
>
> **为什么要有**:`SignDownloadURL` 在 OSS 上能签,但 **local 的直链只覆盖
> `res/public`** —— 私有段签出来就是一条**没有任何路由会响应**的路径。
> 少了这条路,默认部署(local + 默认私有)下 `FileView.URL` 恒为空串 ——
> 文件传得上去、列表看得到,打开是裂图,而且全程没有任何报错。
>
> ⚠️ **2026-10-30 定位降级 —— 现在它是「兜底」不是「唯一出路」。**
> 单桶单树模型(§2.5)下 local 的直链对**每个文件**都成立,所以正常路径
> 永远走 `/files/:id/url`。这条路由只在「直链这条路真的坏了」时才被用到
> (provider 没配静态挂载点 / 磁盘读失败 / 前端跑着旧后端)。
>
> **它怎么实现的**:`oss.ContentProvider` 是**可选接口**(和 `MultipartProvider`
> 同一套 type-assert 模式),**只有 local 实现**。OSS 侧不实现是刻意的:
> 中转会把大文件带宽拉回应用服务器,与「直传」的存在意义相反。
>
> | 场景 | 行为 |
> |---|---|
> | 正常(任何 provider) | 走 `/files/:id/url` 的直链,这条**不会被调用** |
> | 直链拿不到(500) | 前端落到本路由 |
> | provider 没实现 `ContentProvider` | 返 **501 NotImplemented**,不是 500 |
>
> 返 501 而不是 500 是有意的:"这个部署走直链"是一个可预期的形态,不是故障,
> 用 500 报出来会把它算进监控的故障率。
>
> **三条必须知道的响应头约定**(`internal/api/handler/v1/file.go`):
>
> 1. **`Content-Type` 取库里存的服务端探测值**,不是浏览器上报的。探测不出
>    就退到 `application/octet-stream` + `nosniff`。
> 2. **`Content-Disposition` 的文件名必须转义**。`FileName` 是原样入库的用户
>    输入,而它必须原样带出(否则用户下载到的全是 `download`)。CRLF 能拼出
>    第二个响应头,引号能提前闭合 quoted-string,中文在部分代理下会变乱码 ——
>    三样都在 `setContentDisposition` 里处理,并有 `file_content_test.go` 盯着。
> 3. **`image/svg+xml` 永不走 `inline`**。SVG 能塞 `<script>`,而这是**同源**
>    响应,内联一个用户上传的 SVG 等于把本站存储变成 XSS 投放位。
>
> 5. **支持单段 `Range`(RFC 7233 §2.1),206 / 416 / 忽略三态分明。**
>    > 🔍 **2026-10-22 收尾新增 —— 这条不是锦上添花。**
>    > 没有它,`<video>` 拖不动进度条,而且 **iOS Safari 直接拒绝播放**(它要求服务端
>    > 给 206)。直链那条路(OSS 公共读桶 / 静态挂载)自带 Range,**只有这条中转
>    > 兜底没有**。这是复审时才发现的:§2.5 写这张表时没有把「中转这条路和直链
>    > 的能力对等」当成一条硬要求。
>
>    | `Range` | 响应 | 说明 |
>    |---|---|---|
>    | 未传 / 单位不认识 / 非法(`bytes=abc`、`bytes=9-3`、`bytes=0-1,5-6`多段) | **200 整份** | 规范允许忽略 Range;多段**不实现**(会引入只有测试见过的 `multipart/byteranges` 分支) |
>    | `bytes=0-49` / `bytes=90-` / `bytes=-10` | **206** + `Content-Range: bytes a-b/size` | 终点越界**夹到末尾**(`0-99999` → `0-99`),不是 416 |
>    | `bytes=500-600`(起点已在文件外) | **416** + `Content-Range: bytes */size` | |
>    | `size <= 0`(库里的记账值为 0) | **200 整份** | 宁可多发字节也不能发错范围 —— 错的 Content-Range 会让客户端把两段拼成一个坏文件 |
>
>    ⚠️ **`9-3` 是"非法"不是"越界"**,按 416 报的话,一个客户端的边界 bug 会变成用户
>    眼里的"视频播不了",日志里只有一个没头没尾的 416。
>    ⚠️ **长度未知必须传 `-1` 给 `SetBodyStream`,不能传 0** —— 传 0 等于宣告"响应体是空的",
>    hertz 会直接把 body 丢掉(200 + 0 字节)。
>    实现见 `parseRange` / `contentRangeHeader`(`internal/api/handler/v1/file.go`),
>    回归测试 `file_range_test.go`(**直接调生产函数,不要在测试里复刻一遍拼法** ——
>    复刻的那种测试改坏了生产代码也照样绿)。
>
> 4. **响应体走 `SetBodyStream`,前提是中间件链不碰它**。这是本路由唯一
>    没有"看起来就危险"的地方,也是最隐蔽的:`middleware.Gzip` 是**全局**挂载的,
>    它在 `c.Next` 之后调 `c.Response.Body()` 拿长度 —— 而 hertz 的 `Body()` 就是
>    `BodyE()`,**把整个 `bodyStream` 全量 copy 进堆上的 `bytes.Buffer`,再
>    `CloseBodyStream()`(把 `bodyStream` 置 nil)**。所以每个浏览器(都带
>    `Accept-Encoding: gzip`)下载大文件时,整个文件会先进内存再吐出去,
>    "边读边发"名存实亡;`video/mp4`、`image/*` 还能靠 content-type 名单幸免,
>    `application/pdf`、`text/plain`、docx 这些不在名单里的还要再叠一份 gzip 输出缓冲。
>    **字节不会错**(置 nil 后改从缓冲写),所以症状是"并发几路就 OOM",
>    不报错、不丢数据。已在 `gzip.go` 第 4 步加 `IsBodyStream()` 挡掉,并由
>    `gzip_test.go` 的 `TestGzip_SkipsBodyStreamResponse` 钉死(去掉守卫当场打红:
>    5000 字节的流被压成 45 字节)。
>    ⚠️ 守卫**必须放在 `c.Next` 之后**。写在 handler 之前时 `bodyStream` 恒为 nil,
>    等于没写 —— 第一版就是这么错的,被同一个用例当场抓住。
>
> **前端怎么用**:`web/src/api/upload.ts` 的 `resolveFileUrl(id)` 先试
> `/url`,**拿不到(失败 / 空串)才落到 `/content`**。⚠️ **中转这条路必须带
> `Authorization` 头**,`<img src>` 带不了,所以前端是 axios 拉成 blob 再
> `createObjectURL`,**返回的可能是一个 `blob:` 地址,调用方负责 `revokeFileUrl`**。

> 🔍 **2026-10-22 更正 —— 表格里 `init` 和 `complete` 两行是实施时改的,原文写的两件事做不到。**
>
> **① `init` 不返回"已传分片",因为那次调用一定是空的。**
> 原文写"返回 `session_id` + `part_size` + 已传分片(支持重连续传)"。核实 `oss.NewObjectName`(`internal/pkg/oss/path.go`)的实现:它返回 `{unix_ts}-{8 位随机 hex}-{清洗后的文件名}` —— **文件名里带一段随机数**。于是每一次 `init` 造出来的 key 都是全新的,不存在"同一个 key 的上一次会话",`MultipartInitResp.UploadedParts` 从设计上就永远是空的。加这个字段等于对外承诺一个假能力,不如删掉。
>
> 断点续传的真实形态不是"重新 init 再问服务端传过哪些",而是 **客户端自己记着 `session_id`**(页面还开着,或重试时从 localStorage 取回),下次直接 `GET /files/mp/parts?sid=` 查这条 session 的进度。服务端按 **session** 记,不按 **key** 记 —— `sys_upload_session` 表本来就是为它建的。
>
> **② `complete` 不收客户端报的 part 列表,改由服务端 `ListParts` 自查。**
> 原文写 `body: [{part_number, etag}]`。provider 的 `CompleteMultipartUpload` 本身要做三道校验(客户端列表 vs 服务端记账 / 分片号 1..N 连续 / 合并后尺寸 == 声明大小),而它**同时有服务端自己的记账**(`LocalProvider` 是 sidecar JSON,`aliyun` 是 `ListParts`)。让客户端再报一遍等于引入一个**可以撒谎的第三方**:报少一片 → 拿一个带洞的文件去建 `sys_file` 行;报错 ETag → 校验被绕过。
> 所以 `CompleteReq` 只留 `session_id`,合并前先 `prov.ListParts` 拿真相。代价是多一次 API 调用,换来"分片清单只有一个来源",值得。
>
> **受影响字段**:`MultipartInitResp.UploadedParts`(删除)、`CompleteReq.Parts`(删除)。对应实现 `internal/service/upload.go` / `upload_impl.go`。
>
> 🔍 **2026-10-22 收尾更正 —— `complete` 不是"无 body",是 `{"session_id":"…"}`,而且这条绑定规则写错了**不报错**。**
>
> 表格里那行"无 body"是笔误。前端 `completeMultipart()` POST 的是 `{session_id}`,而 `service.CompleteReq` 当时写的是**只有字段、没有任何 json tag**:
>
> ```go
> type CompleteReq struct {
>     SessionID uint64   // ← 没有 `json:"session_id,string"`
> }
> ```
>
> Go 的 json 字段匹配是「大小写不敏感、**但忽略不了下划线**」。前端发 `{"session_id":"123"}` → 字段名匹配不上 `SessionID` → **静默解成 0**:不 400、不报错,然后拿着会话 id 0 去查会话,`loadSessionForWrite(0)` 恒返「上传会话不存在」。用户侧症状是**「所有分片都传完了,合并永远失败」**,而且看不出是哪个字段的问题。
>
> 修法是 `json:"session_id,string"` —— **两个都要写**:少字段名就是上面那个静默 0,少 `,string` 则是字符串解不进 uint64 直接 400(至少响亮)。值必须是字符串,因为 `MultipartInitResp.SessionID` 那边带 `,string`,序列化出来就是 `"123"`。
>
> ⚠️ **`,string` 在 hertz 的 decoder 上是严格模式**:裸数字 `{"session_id":42}` 会被判为类型不匹配并 400。这是**实际契约,不是设想**,前端发的确实是字符串。而 `/files/mp/part` 那一路走的是 header(`X-Session-Id`),`headerUint` 自己 ParseUint,**两种形态都收** —— 两路形态不一致是既有设计,不是 bug。
>
> 回归测试 `multipart_bind_test.go`:直接拿 `service.CompleteReq` 走一遍真实 `BindJSON`(不是 mock service 断言"传进去什么")—— **绑定对了但没人调**是另一回事,**绑定错了但测试全绿**是这里真正要防的那一种。顺带把 `MultipartInitReq.FolderID` 这个同一个坑一起锁住(`file_size` / `part_size` 前端传的是**数字**,**不能**加 `,string`)。

### 8.3.1 用户层(M139):**先选用户 → 再看文件夹**

存储侧的目录形态是 `rapid-admin/{uid}/{biz}/{fid}/`(§3.4)—— **第一段就是用户**。
文件夹管理页照着它分层,就是三层:

```
用户层(谁有文件夹) → 该用户的文件夹 → 子文件夹
```

**为什么以前是错的**:§8.3 的 `GET /folders` 只按 `(调用方 user_id, biz)` 列,
于是超管在文件夹管理页**根本列不出别人的文件夹** —— 而 §10.2 明说超管可跨用户**读**。
这个失效**不报错**(列表照常返 200,只是内容永远是自己的),所以必须靠断言守住。

#### `user_id` 是三态,和 `parent_id` 一个套路

| 取值 | 含义 |
|---|---|
| 不传 | **列调用方自己的** —— 默认口径永远是"我的" |
| 某个 id | 列那个用户的文件夹 —— **只有 `super_admin` 能传别人的 id** |
| 别人的 id + 非超管 | **403** —— 不静默改回自己 |

⚠️ **静默改回自己是最坏的一种**:接口返 200、列表"看起来正常",只是内容不是用户要的
—— 数字和预期对不上,而且没有任何报错。回归测试
`server/internal/service/folder_users_test.go::TestFolderList_NonSuperAdminCannotListOtherUsers`。

⚠️ **跨用户时路径按"那个用户"的祖先链算**,不是按调用方 —— 否则 `path` 算成空串,
界面上"所在目录"那一列整列消失(`TestFolderList_CrossUserPathsUseThatUsersTree`)。

#### `GET /folders/users` 的两个标志位

| 字段 | 含义 |
|---|---|
| `cross_user` | 调用者能不能跨用户读(`super_admin` = true)。**前端据此决定要不要显示用户层** —— 普通用户多一层"用户"是纯噪音 |
| `current_user_id` | 调用者自己的 id。**据此判断"当前看的空间是不是我的"** —— 别人的空间**不能写**(§10.2) |

⚠️ **判定在后端,前端不自己猜角色** —— 前端那份 role code 和后端对不上过
(见 M103 审计:前端 role code 10/13 对不上后端,导致"超管切身份免短信验证"那个安全洞)。
前端把「新建 / 删除」藏起来只是体验,**真正的闸是后端**
(`loadFolderForWrite` → `callerOwns` → 404)。

#### 归属人展示名放哪一层

`owner_name` 放在 `FolderPageResult`(**不在 `FolderView` 里**)—— 同一个列表里所有行的
归属人都是同一个,每行带一遍是冗余(行数一多就是 N 倍的传输)。空串 = 查不到
(用户被删 / 三个名字字段全空),前端退回显示 `user_id`,不该让整个列表 500。

### 8.4 归属校验(每条路由都要,不是某几条)

`folder_id` / `session_id` / `file_id` **一律从库里查出 `user_id` 再跟当前登录人比对**,不一致返 404(不是 403 —— 403 会泄露"该 id 存在")。

⚠️ 这正是本仓已记录的 4 类 handler IDOR 的典型形态,新增路由不要再犯。

### 8.5 BodyLimit 修复(X1)

> 🔍 **2026-10-22 更正 —— 原文的结论("改一行配置就够了,代码没坏就别改")是错的。**
> 实施时逐行核实发现三处:**照原文只改配置,413 依然不会触发**。
>
> **① 配置改了也不生效 —— 匹配条件把上限"取小"而不是"覆盖"。**
> 原文引用的实现是:
>
> ```go
> if l > 0 && (limit == 0 || l < limit) { ... }   // ← 只接受比当前 limit 更小的
> ```
>
> 而上传路由的白名单是 20MB、全局 `Default` 是 1MB —— **20 < 1 不成立,这条白名单永远匹配不上**。给上传放宽正是 `PathLimits` 存在的唯一理由,而这个条件把它否掉了。更糟的是 `limit` 是遍历过程中累积的,结果还取决于 Go map 的随机迭代顺序 —— 同一份配置在不同进程里行为可能不同。
> 改成:**命中最长 pattern 的那条直接覆盖 `Default`**,不管比它大还是小。
>
> **② `matchPath` 的 `/*` 前缀**多匹配**兄弟路由。**
> 原文说"带 `/` 的前缀不会误伤兄弟路由",但 `prefix := pattern[:n-2]` 砍掉的是 `/*` **两个**字符,`/a/b/*` 拿到的前缀是 `/a/b` 而不是 `/a/b/`。于是 `/a/b/*` 会命中 `/a/bc`、`/a/bXXXX`。改成 `pattern[:n-1]`(只砍 `*`),语义才唯一地是"这条路径及其所有子路径"。
> 同时把**裸路径也算命中**(`/files/*` 也管 `/files`),因为"配了 `/*` 忘了再配一条精确的"是这里最常见的漏配,而漏配的症状(上传莫名 413)最难查。
>
> **③ 中间件从来没有真的拦下过请求 —— 漏调 `c.Abort()`。**
> 这条比 ①② 更严重,原文完全没提。hertz 的 `RequestContext.Next()`(`pkg/app/context.go:830`)是 gin 那一套索引循环:
>
> ```go
> ctx.index++; for ctx.index < len(ctx.handlers) { run(ctx.handlers[ctx.index]); ctx.index++ }
> ```
>
> 引擎只在入口调一次 `ctx.Next(c)`(`pkg/route/engine.go:768`)。所以中间件**直接 `return` 并不等于拦下请求** —— 回到那个 for,index 继续 +1,后面的 handler 照样跑,然后用自己的 200 + body 把刚写的 413 覆盖掉。必须显式 `c.Abort()`(把 index 设成 `AbortIndex`)。
> **症状极具迷惑性**:响应完全正常(200 + 业务数据),只是 handler 多跑了一遍。所以 `BodyLimit` 从上线到现在一次都没真正拦下过任何请求,而只断言状态码的单测恰好能"通过"(handler 也返回 200)。
>
> 同一个坑 `Idempotency` 也踩了:409 in-flight 和命中重放两条路都直接 `return`,导致同一个 `Idempotency-Key` 的并发请求**真的执行了两遍**(正是幂等要防的那件事),而客户端看到的是"成功了两次"。两条路都补了 `Abort()`。
> 回归网见 `internal/api/middleware/abort_semantics_test.go`(含一条"不 Abort 会复现旧行为"的反面对照)和 `bodylimit_test.go`。

终态配置(只一条,`/*` 前缀同时覆盖裸路径和 `/files/mp/*` 子路径):

```go
PathLimits: map[string]int64{
    "/rapid-admin/v1/biz/files/*": 20 << 20,
},
```

⚠️ **20MB 同时也是单个分片的上限**,而 `file.multipart_part_size_mb` 可以配得比它大。真配了 >20 的分片大小,分片会被这个阈值而不是业务校验拒掉(413),调分片大小时要一起抬。

## 9. 分片上传时序

### 9.1 OSS 模式

```
客户端                                    服务端                        OSS
  │  POST /files/mp/init                 │
  │  {folder_id, name, size, type}       │
  │─────────────────────────────────────▶│ 查归属 + 校验配额
  │                                      │ 预扣 storage_used_bytes
  │                                      │ 写 sys_upload_session
  │                                      │──InitMultipartUpload──────▶│
  │  ◀────────── {sid, part_size, parts} │◀────── UploadID ────────────│
  │                                      │                             │
  │  PUT part#1 (直传,不经服务端)        │                             │
  │──────────────────────────────────────────────────────────────────▶│
  │  PUT part#2 ...                      │                             │
  │                                      │                             │
  │  POST /files/mp/complete             │                             │
  │  {sid, parts:[{n,etag}...]}          │                             │
  │─────────────────────────────────────▶│ Stat 核对实际大小
  │                                      │ 结算找零(预扣-实际)
  │                                      │ 写 sys_file
  │                                      │ 重建 info.json
  │                                      │──CompleteMultipart───────▶│
  │  ◀────────────── {file_id, key, url} │                             │
```

**断点续传**:重新 init 同 `(user_id, folder_id, file_name, file_size)` 时,先查 `sys_upload_session` 有没有进行中的会话 —— 有就返回 `sid` + 已传 part 清单,客户端只补缺的。

⚠️ **`InitMultipartUpload` 每次都新建一个 UploadID**(`aliyun/advanced.go:68`),所以复用逻辑必须在**服务端查 session 表**之后才决定要不要真的调 OSS —— 不能每次都调。

⚠️ **分片尺寸以 `resp.part_size` 为准,客户端自己请求的不作数**(2026-10-22 实施 M80 时补记)。
local 的 `UploadPart` 用 `(partNumber-1)*session.PartSize` 算 offset,而 `session.PartSize`
是**服务端定的**;客户端按自己请求的 partSize 切片,切出来的边界和服务端算的对不上 →
分片内容错位(拼出来的文件是坏的,但大小对得上,更难查)。
`POST /files/mp/init` 的响应里已经带 `part_size`,**客户端必须按它切片**。
参考实现:`web/src/api/upload.ts` 的 `uploadMultipart` ——
`const partSize = init.part_size || DEFAULT_PART_SIZE`。

### 9.2 local 模式

同上,但:
- init → 建 `.mpu/{uploadId}.part` 临时文件,不调 OSS
- part → 服务端 append(走 §6.4)
- complete → 校验大小 + rename

### 9.3 内存边界(因为**没有**内存池,必须显式限)

`UploadPart(ctx, key, uploadID, partNumber int, body []byte)` —— **入参是 `[]byte`**,一次 10MB 分片 = 服务端堆上 10MB。

| 约束 | 值 | 理由 |
|---|---|---|
| 单 part 大小 | 默认 10MB(既有 `MultipartPartSize`),允许客户端调到 **≤ 16MB**,超出返 `PayloadTooLarge` | 超过就直接让客户端切小分片 |
| **全局并发 part 数** | ≤ 16 | 16 × 16MB = **256MB 峰值**,是刻意设的上限 |
| 单用户并发 part 数 | ≤ 4 | 防单用户占满全局配额 |

并发闸复用 `pkg/syncx.Semaphore`(本仓已有,`NewSemaphore(n)` + `Acquire(ctx)`),**不新建**。

⚠️ **middleware 的 `matchPath` 精确匹配问题(X1)会让分片路由落到默认 1MB**,16MB 分片直接 413 —— 所以 §8.5 的修复是分片功能的前置条件,不是可选优化。

1. `server/internal/seed/seed.go` —— 资源码列表(`:97-98`)+ 角色绑定矩阵(`:521`)
2. `server/internal/api/router/router.go` —— `rbac("module", "action")` 调用
3. `web/src/constants/permissions.ts` —— 前端权限常量
4. `web/src/router/routes.tsx` —— 前端路由 meta

### 10.2 数据级权限

RBAC 只管"能不能调这个接口",管不了"能看谁的文件"。后者靠 §8.4 的归属校验 —— **所有涉及 `file_id`/`folder_id`/`session_id` 的路由都过一遍**。

管理员角色(`super_admin`)可跨用户读,但**仍然只能读、不能改**别人的文件。

跨用户读的入口有两条(M139 补齐):

| 入口 | 场景 | 判定 |
|---|---|---|
| `GET /folders?user_id=<别人的 id>` | 文件夹管理页的「用户层」 | 非超管传别人的 id → **403**(不静默改回自己) |
| `GET /folders/users` | 列出"有文件夹的用户" | 超管看全部有文件夹的人;普通用户只有自己 |

写路径(建文件夹 / 删文件夹 / 设封面)一律走 `loadFolderForWrite` → `callerOwns`,
**别人的空间返 404**(§10.3),不返 403 —— 别泄露"这个 id 存在"。

### 10.3 `ErrNoPermission` 不返回 404

统一约定:文件/文件夹不存在、或存在但不属于你,**都返 404 + 同一个错误码**。分开返会让攻击者靠状态码差异枚举有效 ID。

#### ⚠️ 真正的坑:**行内交互元素的点击会冒泡到行上**

行里坐着「删除 / 详情 / 新建子文件夹 / 查看文件」这些按钮,以及名字链接、封面缩略图(点它会放大预览)、若干标签。
它们的点击**会冒泡到行上** ⇒ 不挡一下的话,用户点「删除」会**顺带把那个文件夹打开**:
确认弹窗一闪就没,层级还多了一层 ⇒ 用户看着就是"按钮坏了"。

挡法是 `isInteractiveTarget(target)` —— 按 **DOM 祖先链**(`closest`)判,**不是**按 React 组件树。

⚠️ **为什么必须按 DOM 判**:卡片右上角的「⋯」菜单是 **portal** 渲染的 —— DOM 上它不在卡片里,
但 **React 事件沿组件树冒泡** ⇒ 菜单项的点击照样会冒到卡片的 `onClick` 上。
按 DOM 祖先链判,`closest('.ant-dropdown')` 正好把这类"看着不相干、却真的冒上来"的点击挡住。

被挡掉的:`a` / `button` / 表单控件 / `[role=button]` / `.ant-image`(封面预览) /
`.ant-tag`(标签) / `.ant-checkbox-wrapper` / `.ant-dropdown`(「⋯」浮层)。

## 17. M124 —— 头像走文件系统:`biz = "avatar"`(2026-10-30)

**用户诉求**:「个人中心用户头像现在不能设置,可以兼容文件系统让它传头像到用户 id 的
相关文件夹中」。

### 17.1 落点

| 项 | 值 |
|---|---|
| 业务段 `biz` | `avatar` |
| 路径 | `rapid-admin/{user_id}/avatar/{folder_id}/{name}` |
| `folder_id` | `0` ⇒ 文件系统**懒建** `(user_id, "avatar")` 这个文件夹 |
| 存进 `sys_user.avatar` 的 | **稳定直链**(不是签名 URL —— 签名 URL 过期头像就裂图) |
| 大小上限 | 5 MB |
| 类型白名单 | PNG / JPEG / GIF / WEBP / BMP(**扩展名 + 文件头魔数**双重判定) |

⚠️ **为什么落在"用户 id 底下"而不是全局目录** ——
`rapid-admin/{user_id}/…` 那一段是**隔离边界**(§3.1.1):别人的头像在自己的段里,
一个用户既看不到也覆盖不了另一个用户的头像文件。
`biz = "avatar"` 把它和同用户下的其他业务段(素材 / 附件 …)分开,
便于将来按段做生命周期策略。

⚠️ **`file.allowed_biz` 白名单一旦收窄,必须把 `avatar` 加进去** ——
默认 `[]` = 不限(§2.5);生产环境收窄后忘了加 ⇒ 头像上传直接被
`folderService.checkBiz` 拒掉(报「业务段不允许」)。

### 17.2 头像**只有一条写通道**(M124 顺手堵掉的一个洞)

早期设计里 `PATCH /rapid-admin/v1/auth/profile` 收一个 `avatar` 字段(任意 URL),
前端可以直接贴一个**外链**。那条路已**删**:

- 外链头像会渲染在**别人的浏览器**里(管理端用户列表 / 顶栏)
  ⇒ 那等于一个**跟踪像素**(对方一打开后台就替你上报一次)。
- 类型层面也堵死了:`UpdateProfileRequest` 里**没有 avatar 字段**(web 同 commit 删)。

现在头像只有 `POST /rapid-admin/v1/auth/avatar`(multipart,字段名 `file`),
服务端三道闸:大小 / 扩展名(MIME 白名单)/ **文件头魔数** ——
只信浏览器上报的 `Content-Type` 是能被伪造的。

⚠️ **这三条闸全在服务端**。前端那两条(大小 + 类型)只是"友好拦截",
目的是**当场给一句人话**,不是安全边界 —— 注释里不能把它写成安全边界。

### 17.3 旧头像回收 + 并发

换头像时,同一 `(user_id, biz='avatar')` 下**更旧**的文件会被软删并释放配额 ——
否则换 10 次头像就把 10 份配额吃掉了。

⚠️ **并发**:事务里对 `sys_user` 行加锁(`clause.Locking{Strength:"UPDATE"}`),
并校验新文件行仍 `status = normal`(已被上一次并发清理掉就报 Conflict,让用户重试);
物理删除放在**事务提交之后**做(事务里不做 IO)。
⚠️ **SQLite 忽略行锁**(开发库)⇒ 最坏情况是头像指向一个刚被删掉的文件(404);
前端的 `UserAvatar` 会自动回落到首字母头像,不会裂图。

### 18.1 数据模型改动:唯一索引带 `parent_id`

```go
// server/internal/model/file.go
UserID   uint64 `gorm:"index;not null;uniqueIndex:uk_folder_owner_biz_parent_name,priority:1"`
Biz      string `gorm:"size:32;not null;uniqueIndex:uk_folder_owner_biz_parent_name,priority:2"`
ParentID uint64 `gorm:"index;not null;default:0;uniqueIndex:uk_folder_owner_biz_parent_name,priority:3"`
Name     string `gorm:"size:128;not null;uniqueIndex:uk_folder_owner_biz_parent_name,priority:4"`
```

语义从"一个用户一个业务段下名字唯一"变成"**同一个父级**下名字唯一"。
A 下可以有"图纸",B 下也可以有"图纸"。

⚠️ **软删改名那条配套照旧** —— 删文件夹时把 `name` 改成 `原名#del:{id}`,
否则这个名字会被唯一索引一直占着,用户"删掉再传"就传不进去(§4.1 那段更正块)。

### 18.2 骨架:一份代码算路径 / 祖先 / 子级数

新增 `server/internal/service/folder_tree.go`,把"这棵树怎么算"从各个调用点里
抽出来,只算一次:

| 函数 | 干什么 |
|---|---|
| `loadFolderTree(ctx, db, userID, biz)` | 把用户(可选按业务段)的全部文件夹拉进内存,建索引 |
| `path(id)` | **含自身**的完整路径,形如 `素材/图纸` |
| `ancestors(id)` | 根 → 直接上级(**不含自身**),带 visited 集合,遇环/父级缺失就停 |
| `childCount(id)` | **直接**子文件夹数(不含更深层) |
| `subtree(id)` | 整棵子树(删除时用) |
| `depth(id)` | 层数,根级 = 1 |

⚠️ **路径 / 子级数 / 封面直链都是现算的,没存冗余列** ——
冗余列(如 `parent_path`)一旦有行没同步,界面上就会有一条路径是错的,
而且**没有任何地方会告诉你它错了**。

⚠️ **祖先链只能从后端要** —— 前端手里只有当前文件夹的 id,
分页列表里未必有它的祖先,自己拼是不可行的。所以 `FolderDetail` 带 `Ancestors`。

⚠️ **`maxFolderDepth = 10`** —— 层级上限在应用层判,不在 DB 判
(`parent_id` 是应用层写的,唯一索引管不了深度)。上限存在的理由是
"建了 30 层"的用户会让路径字符串长到面包屑一行放不下。

### 18.3 迁移:旧唯一索引必须**显式**删掉

⚠️ **GORM `AutoMigrate` 只加索引,不删索引。**

光改 struct 上的 tag 是不够的:旧索引 `uk_folder_owner_biz_name` 会**继续生效**,
于是"A/图纸"能建、"B/图纸"建不了 —— 报的还是"同级下已有同名文件夹",
但 B 下明明没有。**报错信息对不上真实原因**,这类最难查。

所以 `server/internal/migrate/migrate.go` 加了一步 `dropLegacyFolderIndex(db)`:
存在就 `DROP INDEX`,不存在就跳过(幂等),在 `Run()` 里 `cleanupDuplicatePrimaries`
之后、且 `!dryRun` 时执行。

### 18.4 封面:只有图片能当封面(SVG 也排除)

服务端(`folder_impl.go::SetCover`):

```go
func isCoverImage(contentType string) bool {
    ct := strings.ToLower(strings.TrimSpace(contentType))
    if !strings.HasPrefix(ct, "image/") { return false }
    if strings.Contains(ct, "svg")       { return false }
    return true
}
```

⚠️ **为什么 SVG 也排除** —— SVG 里能塞 `<script>`,而封面会被"点开看大图"
打开成**同源文档**。同一个用户自己的 SVG 危害有限,但封面是**共享**的
(放在文件夹列表里给所有人看),脚本会在**别人的会话里**跑。

⚠️ **判据只看 `content_type`**,不看扩展名 —— 浏览器上报的 `Content-Type`
能被伪造,但这里是"要不要给这个按钮",不是安全边界;真边界是后端那三道闸。

前端(`web/src/constants/file.ts::canBeCover`)**同口径**,并且**按钮直接禁用**:

```
disabled = !row.folder_id || row.folder_id === '0' || !canBeCover(row.content_type)
disabledTip = 不在文件夹里 ? "不在文件夹里的文件没有封面" : "只有图片才能设为封面"
```

⚠️ **前端禁掉不是为了"少一次请求"** —— 后端本来就会拒。
前端禁是为了**当场给一句人话**:否则用户点下去吃一个 400,
而错误信息里没有"为什么是图片"这句。

### 18.5 封面**在哪显示**(用户问的 d)

|---|---|---|
| **文件夹列表的「封面」列** | 48×48 缩略图(`antd Image`,可点开看大图) | `FolderView.cover_url` |
| **文件夹详情抽屉** | 320px 大图(`object-fit: contain`) | 同上 |
| **文件列表行** | 文件名后面的金色「封面」标签 | `FileView.is_cover` |
| 没封面时 | 「无封面」占位文字,**不是一张裂图** | `cover_url == ""` |

⚠️ **`cover_url` 是稳定直链**(`/rapid-admin/...` 或 OSS 的 `https://{bucket}.{endpoint}/{key}`),
**不是签名 URL** —— 签名 URL 过期封面就裂图(单桶单树模型 §2.5 的直接结果)。

⚠️ **拿不到封面就返空串,不返错** —— 封面是锦上添花,
不能因为封面文件已被删就让整个文件夹列表 500。

⚠️ **本地直链要 vite dev server 代理 `/res`** —— 否则请求落到 SPA fallback,
返回 index.html + 200,`<img>` 拿到的是一坨 HTML 而不是图片(静默裂图,控制台才有错)。

### 18.6 层级过滤是**三态**,不是两态

后端 `FolderListQuery.ParentID *uint64`:

| 值 | 含义 | 谁在用 |
|---|---|---|
| `nil`(**不传**) | **不限层级** | 老调用方、文件夹下拉框 |
| `0` | **只列根级** | 文件夹页的根级视图 |
| `> 0` | **只列它的直接子级** | 进入某个文件夹之后 |

⚠️ **"不传"绝不能翻译成 "0"** —— 那样"进入文件夹"和"看全部"就变成同一个请求,
而界面上表现为"进去之后列的还是全部文件夹"。

前端 `listFolders` 用 `parentId?: string` 表达这个三态,**并且值必须是字符串** ——
后端 DTO 是 `json:"parent_id,string"`,传数字会被 Go 的 `encoding/json` 拒掉
("invalid use of ,string struct tag")。
⚠️ axios 会**跳过 `undefined`/`null` 的 query 参数**,所以 `undefined` 正好就是
"没传" —— 这也是为什么不能用 `''` 或 `0` 顶替。

⚠️ **有关键字时不限层级** —— 根级搜"图纸"要能搜到 `A/图纸`。
死守当前层级的话,多级之后根级搜索就是个摆设(子文件夹永远搜不到),
而用户看不出为什么。前端在有关键字时显示一个橙色标签「搜索:全部层级」。

### 18.7 前端:文件夹页 = 目录浏览器

`web/src/pages/file/folder.tsx` 整个重写。**当前所在文件夹放在 URL 里**
(`?folder_id=`),URL 是唯一真相源:

- 刷新不丢;
- 直接把链接发给同事也能落到同一个文件夹;
- 深链进来时**首屏就列那个文件夹的直接子级**(不先列一遍根级再跳)。

| 事 | 靠什么 | 少了会怎样 |
|---|---|---|
| 表格只列当前这一级 | 请求带 `parent_id` | 进去之后还是列的全部文件夹,像没进去 |
| 点名字能进去 | URL 变 `?folder_id=` | 只能靠 URL 手改,用户进不去子文件夹 |
| 面包屑显示层级 | 后端 `FolderDetail.ancestors` | 进去了不知道自己在哪 |
| 同名文件夹分得清 | 名字旁边的灰色「所在目录」标签 | `A/图纸` 和 `B/图纸` 看着一模一样 |

⚠️ **文件夹名里禁止 "/"(服务端拦)** —— 路径(`素材/图纸`)是用 `/` 拼的,
名字里带 `/` 会让路径有歧义("a/b" 到底是两级还是一个名字"),
而前端要靠路径拆出"所在目录"来显示同名文件夹的区别。
这条不做,界面上会出现两条一模一样的路径。

⚠️ **建子文件夹时不显示业务段输入框** —— 后端会**继承上级**的业务段
(`Create` 里 `biz == "" → biz = parent.Biz`)。让人填的话,填错了后端会直接报错
("子文件夹必须与上级文件夹属于同一业务段"),白填一趟。
显式传了**不一致**的 biz → 报错,不静默改写:调用方明确说了要放哪,
偷偷改成另一个地方比报错更难查。

⚠️ **删文件夹 = 删整棵子树** —— 子文件夹里的文件也会一起没。
删除确认框里写明了"它下面的 N 个子文件夹(以及里面的文件)也会一起删掉"。

### 18.8 这次没做的

- **重命名 / 移动**(拖拽改 `parent_id`)—— 后端没有这两个接口。
  页面上的每个按钮都必须对应一个**真实存在**的后端动作。
- **子文件夹的文件数/总大小聚合** —— `file_count`/`total_size` 目前是**该文件夹直属文件**
  的统计,不递归累加子文件夹。要"整棵树的用量"得另做聚合。
- **封面的默认选取**(比如自动取第一张图)—— 用户手工设。

### 18.9 RBAC:**没动**,所以也不用迁移

M125 **没有新增任何路由,也没有新增任何权限码** —— 复用既有的
`folder:list` / `folder:create` / `folder:delete` / `folder:upload`。

⇒ `CheckResourceConsistency(h, db)`(`cmd/server/main.go`)的
"受保护路由数 == `rbac()` 调用数"两条腿**仍然对得上**,不用跑 `cmd/migrate` 改 RBAC 表。
⇒ `后台权限模型设计V1.0.md` **本次无需改动** —— 文件模块的权限码本来就记在本文档 §10.1。

⚠️ **为什么"新增路由"这件事在本仓是敏感的** —— 每加一条路由就要同步四处
(seed 资源码 + 角色绑定矩阵 / router 的 `rbac()` 调用 / 前端权限常量 / 前端路由 meta),
漏一处的后果是**启动直接 fatal**,或者前端按了按钮吃 403。
所以「先有后端动作、再有前端按钮」这条规矩(§18.8)在 M125 里是硬约束 ——
文件夹页的每个按钮都对应一个**已经存在**的接口。

### 19.3 endpoint 的两个:外网 vs 内网

用户要求「endpoint_private、endpoint 分两个,一个是内网调用 oss 更快,一个是外网更慢」。
实现(`internal/pkg/oss/aliyun/aliyun.go`):

- `oss.endpoint` = **外网**,只用来**拼直链**(给浏览器看)
- `oss.endpoint_private` = **内网**,只给 **SDK 客户端**用(同地域 VPC 内流量不走公网)

⚠️ **直链永远用外网** —— 直链是给公网上的浏览器看的,给它 `-internal` 地址它根本访问不到。

⚠️ **判据是"连得上",不是"DNS 解析得出来"** —— 这是真机跑出来才发现的:

```
nslookup oss-cn-shenzhen-internal.aliyuncs.com
  Address: 100.118.78.2     ← 解析成功(阿里云 VPC 内部网段,公网也能解析)
dial tcp 100.118.78.2:443   → i/o timeout   ← 路由不通
```

所以启动时探的是 **TCP 连通性**(`probeEndpointReachable`,1.5s 超时),
连不上就自动回落到外网 endpoint,并打一条 Warn。
⚠️ 只探 DNS 的后果是:启动日志说"走内网",然后**每一次 OSS 操作都等满 60 秒超时**。

⚠️ SDK 的 urlMaker 在 endpoint **没写 scheme 时默认按 http 处理**
(`conn.go:InitExt`)⇒ "配置里没写 https"就等于"悄悄降级成明文传输"。
所以给 SDK 的 endpoint 统一补 scheme(已有 scheme 不动 —— 用户显式写 `http://` 是在说"我要明文")。

### 20.4 两种视图的"操作"是**同一份**

## 21. M140 —— 头像文件夹有专属名字 + 每个文件夹都有 info.json(2026-10-31)

> **起因**:用户 2026-10-31 报了两件事 ——
> 「用户的头像文件夹名称也叫默认文件夹,而且用户头像文件夹里面没有 info.json 这个文件,
> 按道理每个文件夹里面应该都有这个 info.json 文件」。
>
> 这两条**都不会报错**:文件夹照样建得出来、文件照样传得进去、列表照样有数据。
> 区别只在**存储里的物理布局**和**界面上的名字** ⇒
> 「接口返 200」不能证明它们是对的,只能去看存储里那一层。

### 21.1 头像文件夹:一个用户一个,而且有专属名字

| 项 | 值 |
|---|---|
| 业务段 | `avatar`(§17,不变) |
| 文件夹名 | **`头像`**(原来是"默认文件夹",因为懒创建时复用了默认名) |
| 落点 | `rapid-admin/{user_id}/avatar/{folder_id}/{name}`(不变) |
| `is_default` | **false**(原来是 true) |

⚠️ **为什么名字要单独占一个** —— 头像段是"一个用户一个文件夹"的专属空间,
叫"默认文件夹"会让人在文件夹管理页分不清哪个是头像、哪个是普通素材。

⚠️ **名字进了唯一索引** `uk_folder_owner_biz_parent_name`
(user_id, biz, parent_id, name)⇒ **只改常量是不够的**:
老用户的头像文件夹不会自动改名,而查找**改成按名字找**的话
就找不到历史上那一个 ⇒ 会**再建一个"头像"** ⇒ 同一个用户有两个头像文件夹,
头像文件散落在两处 —— 而两个都显示得出来、都不报错。

⇒ 三条规则配套:

1. **查找按 `(user_id, biz, parent_id)`,不按名字**(`findEnsureFolder`)——
   头像段是"一个用户一个文件夹",按段找才不会漏掉历史那一个;
2. **启动期批量改名**(`NormalizeAvatarFolders`)—— 历史行统一改成"头像",
   并把 `is_default` 归零;
3. **懒路径上顺手纠正**(`normalizeAvatarFolderName`)—— 只要有人动了头像段,
   名字就一定是对的(启动期自愈是"尽力而为",这里是最后一道收敛)。

⚠️ **改名不碰存储** —— 文件夹名是**展示用**的,不进 key(key 用的是 folder_id,§3.1)
⇒ 改名字不需要搬对象,**零迁移**。

⚠️ **`is_default` 必须归零** —— 前端按 `is_default` 定位"默认文件夹"
(上传按钮落点)。头像文件夹标成"默认" ⇒ 普通文件会传进头像文件夹。

⚠️ **目标名被占就不改名** —— 撞唯一索引会失败,而失败发生在写库这一步
⇒ 整个改名动作回滚,连 `is_default` 也归不了零。这种情况下只归零 `is_default`
并记一条 Warn(说明有历史脏数据要人工看)。

⚠️ **`is_default` 归零的副作用:头像文件夹变成"可删"了** —— 它以前删不掉,
是因为**被误标成了 `is_default`**(删除闸是 `if f.IsDefault`)⇒ 那是**顺带**挡住的,
不是设计。现在 `is_default` 回到它本来的语义("上传落点",§21.1),
删除闸就得**显式**补一条:`biz = "avatar"` 的文件夹不可删。

不补的后果:用户删掉"头像"文件夹 ⇒ 头像文件被连带删掉,
而 `sys_user.avatar` 还指着那个已经死掉的 URL ⇒ 全站头像裂图
(前端回落到首字母头像,但"删除头像文件夹"本来的效果不该是"头像变成首字母")。
而且这个文件夹本来就不是用户该管的东西(§17:头像只有一条写通道 = `POST /auth/avatar`)。

### 21.2 每个文件夹都有一份 info.json

§3.4 的物理布局写着"每个文件夹里都有一份 info.json",但**这条约定从来没被兑现过**:

| 生成时机 | 改之前 | 改之后 |
|---|---|---|
| **文件夹创建** | ❌ 不生成 ⇒ **空文件夹里永远没有** | ✅ 建完就写(空快照 `files: []`) |
| 文件注册 / 删除 / 改封面 | ✅ 生成(M133 补的) | 不变 |
| **历史数据** | ❌ 不补 ⇒ M133 之前传过文件的文件夹也可能缺 | ✅ 启动期补齐 |

⚠️ **"文件夹创建"这一条是这次补的** —— 原来 info.json 只在**文件事件**之后才重建,
而**一个刚建的空文件夹没有文件事件** ⇒ 它永远没有 info.json。
用户在存储里一看就是"少了一个文件"。

⚠️ **启动期回填**(`BackfillFolderInfo`)是**幂等**的:
先问存储"在不在"(一次 HEAD),**缺了才写**。
无脑重写的话存储侧凭空多 N 次 PUT,而内容一样,写了也是白写。

⚠️ **回填有上界**(单次 500 个)—— 补 info.json 要逐个问存储"在不在",
文件夹多了就是启动期的网络风暴。超出的部分留给下一次启动(分几次补完没差别)。

⚠️ **单个文件夹失败不中断整批**,也不拦启动 —— info.json 是**生成物**,
DB 才是唯一真相源(§2.3 D3)。为一个可随时重建的快照拒绝启动是本末倒置。

⚠️ **软删的文件夹不补** —— 它的 info.json 早就跟着前缀一起删了,
补回去是给一堆死数据续命。

### 21.3 顺带修掉的两条测试

⚠️ **"存储里有多少个对象"这类断言要分开数** ——
`info.json` 现在**建文件夹时就写**,于是"这次上传被拒了"之后,
存储里留下的那个对象是**文件夹的清单**,不是"被拒的那个文件"。
把它算进"被拒的上传不该留下对象"那条断言里,那条断言就永远不成立
—— 而它真正要守的是「**用户文件**没被留下」(配额 / 计费 / 孤儿对象)。

⇒ 加了 `countStoredFileObjects`(数用户文件,排除 `info.json`),
两条断言改用它。**别把这两类对象混在一个数里**。

### 21.4 探针记录(可逆探针)

| 编号 | 把实现改回什么 | 结果 | 实际红了的用例 |
|---|---|---|---|
| M140-A | 删掉"建文件夹时写 info.json"(两处) | **RED** | 「新建文件夹立刻有 info.json」「懒建的文件夹也有」「头像文件夹里也有」 |
| M140-B | 头像段的名字改回"默认文件夹" | **RED** | 「头像文件夹必须有自己的名字」 |
| M140-B1 | 头像段**按名字找**(不按段找) | **RED** | 「必须复用历史上那一个头像文件夹」「碰到历史那一个时名字被纠正」 |
| M140-C | `is_default` 不归零 | **RED** | 「头像文件夹不能标成默认」「历史那行被改成"头像"」 |

B 只证明"名字对不对",B1 才证明"会不会多出一个头像文件夹"。

那个同名的历史行)—— 也就是说 **B 单独做会漏掉真正的那个失效**。

⚠️ **D 是"归零 is_default"引出来的副作用** —— 归零之前头像文件夹是靠
`is_default` **顺带**挡住的删除;归零之后必须**显式**补一道闸(§21.1 末)。
不补的话 D 这条用例根本不会存在,也没有任何东西守着它。

### 21.5 这次没做的

  头像文件夹**自动**改名,不是让用户改);
- **没把 info.json 做成"文件夹里可见的一个文件"** —— 它是**生成物**,
  不在 `sys_file` 里、不计入文件数(§2.3 的老约定),界面上依然看不到它;

  删完头像位会裂图(前端回落到首字母)。这条**一直如此**,不是这次引入的。

## 22. M141 —— 音视频时长 + 视频封面(ffmpeg)(2026-10-31)

> **起因**:用户 2026-10-31 提的 ——
> 「上传文件时候如果是视频文件,都调用环境变量里面默认的 ffmpeg 工具提取视频时长,
> 截取封面,这样 grid 里面就可以显示视频封面,同时显示视频时长;
> 如果上传的文件是音频格式的,封面就用音频图标,同时也要提取显示音频时长。」
>
> M134 把缩略图视图做出来了,但**视频和音频只能摆一个图标** ——
> 时长看不见、封面也看不见。

### 22.1 分两层:命令怎么拼 / 什么时候跑

| 层 | 位置 | 职责 | 能不能脱离对方测 |
|---|---|---|---|
| 命令层 | [internal/pkg/media](../../server/internal/pkg/media/media.go) | 跑 ffprobe / ffmpeg,解析输出 | **能** —— 命令执行器是注入的(`Runner` 接口) |
| 接线层 | [internal/service/media_probe.go](../../server/internal/service/media_probe.go) | 什么时候跑、结果存哪、失败了怎么办 | 需要整个 service |

分层的理由:命令怎么拼、输出怎么解析是**纯逻辑**;而"什么时候跑、结果存哪"
是业务编排。混在一起的话,测命令拼装就得把整个 service 搭起来。

⚠️ **命令执行器必须注入** —— `Runner` 接口让测试塞一个假执行器进去,
断言**命令怎么拼、输出怎么解析**,不需要真的装 ffmpeg。
真实的 ffmpeg 集成测试是**另一件事**(`media_integration_test.go`,
装了 ffmpeg 才跑,没装就跳过 —— 跳过的那条会在测试名里写明原因)。

### 22.2 ⚠️ **探测失败绝不影响上传**

时长和封面是**锦上添花**,不是上传的前置条件。
没装 ffmpeg、文件解不开、ffmpeg 超时 —— 任何一种都只影响"列表里少一个时长"。

⇒ **这一层没有一个错误会往上抛**,全部只记日志。

| 情况 | 记什么级别 | 为什么 |
|---|---|---|
| ffprobe 找不到(二进制不存在) | **Info** | 那是**部署状态**,不是错误。每个媒体文件上传都打一条 Warn ⇒ 日志里全是噪音,而用户看不出任何区别(前端就是少个时长) |
| ffprobe 跑了但解不开这个文件 | Warn | 文件本身有问题,值得看 |
| 抽帧失败 | Warn | 时长已经拿到了,封面是附加品 |

⚠️ **"没装 ffmpeg"必须是一个可识别的哨兵错误**(`media.ErrUnavailable`)——
它和"文件解不开"是两件完全不同的事:前者是部署状态,后者是文件本身有问题。
混在一起的话,运维看到满屏 error 会以为文件坏了。

### 22.3 ffmpeg 只能读本地文件 ⇒ 三条上传路各建一份本地副本

| 上传路 | 副本怎么来 |
|---|---|
| 单次中转(`Receive`) | `io.TeeReader` —— 一边转发一边落盘,不多读一遍 |
| 分片(`Init` / `UploadPart` / `Complete`) | `Init` 建副本;`UploadPart` 按 `(partNumber-1) * PartSize` 偏移 `WriteAt`;`Complete` 探测 |
| 直传登记(`Register`) | 从存储读回来(`probeStoredMedia`)—— ⚠️ **只有实现了 `oss.ContentProvider` 的 provider 能走这条路** |

⚠️ **分片的偏移必须是 `(partNumber-1) * PartSize`** —— 和存储侧合并分片的
偏移一致,本地副本和最终对象才是同一份字节。写错偏移**不会报错**,
只会让探出来的时长是错的(用户看到"3 秒"而视频其实 30 秒)。

⚠️ **`UploadPart` 用 `O_WRONLY` 而不是 `O_CREATE`** —— 副本是 `Init` 时建好的,
这里打不开说明它没了(机器重启、临时盘被清)。这时候**不要重建**:
重建出来的是一份中间全是 0 的假文件,探出来的时长是编的,**比没有还糟**。

⚠️ **副本大小必须和文件对上才探测**(`mediaTempUsable`)——
副本是"尽力而为"攒出来的:超了上限会被截断,分片没传全会留缺口。
这两种情况下文件都**存在**、**非空**,ffprobe 也能跑出一个数 ——
但那个数是假的(时长偏短、抽出来的帧是黑的)。

### 22.4 ⚠️ **本地副本是有代价的**

探测要求文件完整落一次本地磁盘 —— **一个 2GB 的视频就是 2GB 的临时文件**。

⇒ 有 `file.media_max_size_mb` 这道闸(默认 2048 = 2GB),超过就不探测。
副本用完立刻删(临时目录名前缀 `ha-media-`,清理时**只删自己建的那种目录** ——
路径来自数据库,理论上可被篡改,前缀对不上就不动)。

⚠️ **超时必须有上界**(60 秒)—— ffprobe 探一个坏文件可能卡住
(网络盘上的文件、索引损坏的大文件),没有超时就是一个能把上传请求挂死的线程。

### 22.5 判据:扩展名优先,MIME 只兜底

`media.Classify(fileName, contentType)`:

| 情形 | 判据 | 理由 |
|---|---|---|
| 有扩展名且在媒体名单里 | 扩展名 | 与前端那套图标映射(`EXT_ICONS`)保持一致 |
| 有扩展名但**不在**名单里 | **就是不是媒体** | ⚠️ 别再拿 content_type 兜底 —— 一个叫 `a.mp4.txt` 的文本文件会被浏览器报成 `text/plain`,而用户眼里它就是个 txt |
| 没有扩展名 | content_type | 兜底 |

⚠️ **为什么扩展名当主判据** —— Go 的 `mime.TypeByExtension` 在 Windows 上会去查注册表,
`.mkv` / `.flac` 这种冷门格式**不一定**有值,查不到就落到
`application/octet-stream` ⇒ 视频被判成"不是媒体" ⇒ 不抽封面。

⚠️ **名单的判据是"能不能被 ffmpeg 解"**,不是"官方标准格式" ——
mkv / flv / wmv 在 Windows 上双击打不开,但 ffmpeg 全都能解,
而"用户传了个视频结果列表里只有个图标"正是这个功能要解决的。

### 22.6 封面帧不是用户文件

| 点 | 做法 |
|---|---|
| 对象名 | `{文件夹前缀}__cover__{文件id}.jpg` —— 与用户文件的对象名(`{时间戳}-{8位随机}-{清洗后的原名}`)区分开 |
| 入库吗 | **不入 `sys_file`** —— 不计文件数、不占用户配额 |
| 库里存什么 | 只存一个 key(`sys_file.cover_key`) |
| 谁删 | 文件被删时一并删(`deleteCoverObject`)—— 删失败只记日志,留个孤儿封面只是浪费一点存储 |

⚠️ **音频不抽帧** —— 音频的"封面"是图标(前端按扩展名画),
抽出来的波形图对一张唱片封面没有任何意义,还白占一份存储。

### 22.7 抽帧的落点

`media.FramePosition(durationMs)`:

| 时长 | 落点 | 为什么 |
|---|---|---|
| ≤ 3 秒 | 一半 | 1 秒处可能已经在片尾 |
| > 3 秒 | 10%,**但不超过 3 秒** | 10 秒的视频落在 1 秒,10 分钟的视频落在 3 秒(而不是 1 分钟 —— 那多半还在片头) |

⚠️ **不是"从头开始"** —— 很多视频开头是黑屏/片头,抽出来是一片黑,
用户看到的就是"这个视频没有封面"。

⚠️ **落点抽不到就退回第 0 帧** —— 有些视频在声明的时长之前就有问题
(moov 缺失、时间戳乱),按中点抽会失败,而第 0 帧通常还在。

⚠️ **`-ss` 放在 `-i` 前面**(输入端 seek)= 快但可能不准 ——
它跳到最近的关键帧。对"抽一张封面"完全够用;放在 `-i` 后面才准,代价是要解完整个文件。

⚠️ **缩到 640 宽**(`-vf scale=640:-2`;`-2` = 高度取偶数,H.264 要求偶数边长)——
封面只是列表里的一张缩略图,原分辨率(4K)纯属浪费存储和带宽。

### 22.8 配置:环境变量优先

```yaml
file:
  ffmpeg_path: ffmpeg        # 默认走 PATH
  ffprobe_path: ffprobe      # 默认走 PATH
  media_max_size_mb: 2048
```

⚠️ **优先级:环境变量 `FFMPEG_PATH` / `FFPROBE_PATH` > yaml > 默认值** ——
ffmpeg 不是 Go 依赖,不会随仓库分发,每个部署环境装的位置都不一样
(Windows 上常常是某个绿色版目录)。**环境变量才是"这台机器上它到底在哪"的唯一真相**,
yaml 只是仓库内的默认值。

⚠️ **默认值是 "ffmpeg" / "ffprobe"(走 PATH),不是留空** ——
留空会被当成"没有工具",于是连"PATH 里明明有 ffmpeg"的机器也不探测;
而绝大多数装了 ffmpeg 的环境都能从 PATH 直接找到。

⚠️ **但"PATH 上有 ffmpeg"不是常态** —— 绿色版解压到 `D:\ffmpeg\bin`
就完事了,没人往系统 PATH 里加(本机就是这样)。这种机器上
**必须配 `FFMPEG_PATH` / `FFPROBE_PATH`**,否则探测会一路静默走
"ffprobe 不可用"那条分支:上传照常成功,只是永远没有时长和封面 ——
**症状是"功能没生效",不是"报错"**,不看日志会以为是代码没写。

⚠️ **ffprobe 和 ffmpeg 是两个二进制** —— 发行包里通常两个都有,
但也有只装了 ffmpeg 的精简包。分开配:只配 ffprobe 的部署**拿得到时长但拿不到封面**,
这是"能显示什么"的分级,不是一个故障。

⚠️ **启动时打一行工具路径** —— "视频没有时长/封面"最常见的原因就是
路径指错了(或者压根没装)。日志里有这一行,排查时不用去猜。

## 24. M145 —— 「浏览器能不能播」的判据 + 音视频转码(2026-10-31)

> **起因**:用户 2026-10-31 提的 ——
> 「音视频文件的编码,你知道哪些是浏览器不支持的吗?如果不支持的音视频编码方式,
> 文件上传以后估计要重新给他转码,否则浏览器播放不了。」
>
> 紧接着的第二问(同一段对话里):
> 「**怎么触发后端转码?**」
> 以及第三问:
> 「为什么不是选择文件上传时候,如果是音视频文件,这时候就判断一下是否能够播放,
> 然后调用上传接口时候,把是否需要转码参数传递到后端,文件传输完成以后后端就自动启动转码。
> 这样做不是更简单?」
>
> ⚠️ **第三问的前提是错的** —— "转码没有被触发"这件事不成立;
> 转码**一直在自动触发**(§24.2 有真机实测记录)。
> 但第三问里**有一个地方是对的**:OSS 直传登记那条路**真的没有转码**(§24.8)。

### 24.1 判据:「浏览器能不能播」

判据表在**后端**,[internal/pkg/media/playback.go](../../server/internal/pkg/media/playback.go):

| 维度 | 判据 |
|---|---|
| 容器 | `playableVideoContainers = {mp4, webm}`;`playableAudioContainers = {mp3, m4a, mp4, wav, flac, webm, opus}` |
| 视频编码 | `playableVideoCodecs = {h264, vp8, vp9, av1}` |
| 音频编码 | `playableAudioCodecs = {aac, mp3, opus, flac, vorbis, pcm_*}` |

⚠️ **口径是"主流浏览器都能播"**,不是"某一个浏览器能播"——
Chrome 能播 HEVC、Safari 能、Firefox 依平台。用户不会为了看一个视频去换浏览器。

⚠️ **判不出来 ≠ 播不了** —— 空值**不拦**。
容器/编码探不到(文件损坏、格式怪)时,状态是"未知",不是"拒绝"。

⚠️ **判据的输出是一句话**(`media_reason`),不是一个布尔 ——
"视频编码 MPEG-4 Part 2 浏览器不支持"这样一句能直接给人看的解释。
只给布尔的话,前端只能显示"不支持",用户还是不知道为什么。

### 24.2 ⚠️ **转码怎么触发:上传时自动触发,没有手动接口**

**触发链路**(全部在服务端,客户端不需要做任何事):

```
上传(单次中转 / 分片合并)
  └─ 留下本地副本(为了抽封面,§22.3)
     └─ probeAndApply:ffprobe 探容器/编码
        └─ 判"浏览器播不了"(res.Reason != "")
           └─ enqueueTranscode:落 transcode_status=pending
              └─ goroutine 抢并发闸(transcodeSlots)
                 └─ runTranscode:ffmpeg → H.264 + AAC / MP4
                    └─ 传回存储,key = {前缀}__play__{文件id}.mp4
                       └─ 写回 transcode_status=done + playback_key
```

⇒ **"怎么触发"的答案:上传一个浏览器播不了的音视频,就行了。**
没有"手动触发转码"的端点,**也不应该有** ——
手动触发意味着"用户点一下就烧一个核",而真正需要转码的文件在上传时就已经知道了。

⚠️ **上传响应里就已经带 `transcode_status = 1`(待转)** ——
不是"上传完成之后前端再去问一次要不要转码",是**上传这一次请求里就派出去**了。

⚠️ **转码是异步的,上传请求不等它** —— 一个 100MB 的视频要转几十秒,
同步做的话 HTTP 请求会超时,客户端会重试,然后**上传两遍**(两份字节、两次配额)。

⚠️ **请求的 ctx 不能传给 worker** —— 请求结束 ctx 就被取消了,
传过去的话转码刚开始就被杀掉(症状:状态永远停在"转码中",
日志里只有一句 "context canceled")。worker 用 `context.Background()` + 30 分钟超时。

⚠️ **抢并发闸必须在 goroutine 里** —— 在请求线程里抢的话,
闸满 = **把上传请求堵住**。用户传 20 个 wmv,第 3 个之后的请求会一直挂着。

⚠️ **副本的清理权交给 worker** —— 两边都删的话,
worker 转码时拿到的是"文件不存在",ffmpeg 报 exit status 1,
而真因是"文件被人删了"。

### 24.3 ⚠️ **为什么不改成"前端判断 + 传标志位"**

第三问提的方案(前端在选文件时判断能不能播,把"要不要转码"传给后端)在
**主链路上更差**,四条理由:

| # | 理由 |
|---|---|
| 1 | **前端判不出文件里真正的编码**。前端只有扩展名和 MIME。一个 `.mp4` 可能是 H.264(能播)、也可能是 HEVC / MPEG-4 Part 2(不能播)—— **扩展名一模一样**。前端唯一能问的 `canPlayType('video/mp4')` 答的是"这个浏览器认不认 mp4 **容器**",不是"这个文件里的**编码**是什么" |
| 2 | **标志位是客户端可控的**。前端说"要转码"但文件其实能播 ⇒ 白烧一次 ffmpeg(一个核几十秒)。前端说"不用转"但文件其实不能播 ⇒ 正好是用户想避免的那个 bug:文件躺在那儿,没徽标、没原因,点开"点了没反应"。**正确的判据必须由看得到字节的一方给** |
| 3 | **后端本来就有字节**。中转上传时字节刚写过一遍磁盘(为了抽封面已经留了副本),再 ffprobe 一次是**毫秒级** —— 比"再传一个字段 + 多一次跨端约定"便宜得多 |
| 4 | **上传协议有三条路**(单次中转 / 分片合并 / 直传登记)。标志位要挂三条路的请求体;而服务端侧触发点**只有一个**(`probeAndApply`),三条路都汇到那儿 |

⚠️ **前端该做的是"显示",不是"判断"** ——
`mediaStatusOf` 只做状态映射(§24.6),判据表不抄第二份。
抄一份的后果很具体:后端加一个容器名,前端忘了加 ⇒ 那个格式在列表里
**永远显示"浏览器不支持"**,而后端其实判它能播。

### 24.4 转码的四个边界

| 边界 | 做法 | 为什么 |
|---|---|---|
| **并发** | `transcodeSlots` 信号量,默认 2 | 每个转码是一个 ffmpeg 进程,**吃满一个核**。20 个用户同时传 wmv 就是 20 个 ffmpeg 一起跑,那台机器就废了 |
| **超时** | 30 分钟 | ffmpeg 转一个坏文件可能卡住(坏帧、畸形时间戳),没有超时就是一个能**永久占住并发闸**的僵尸任务 |
| **panic** | `runTranscode` 里 `recover` | 它跑在上传请求的 goroutine 之外 —— Go 里任何 goroutine 的 panic 都会**终止整个进程** |
| **失败不重试** | 记 `transcode_status=4` 就完事 | 这一版的失败绝大多数是"这个文件 ffmpeg 也解不开",重试一百次也一样。**原文件还在,能下载** |

⚠️ **转码不覆盖原文件** —— 副本是**额外**的一个对象
(`{前缀}__play__{文件id}.mp4`),原文件原样保留。
⇒ 用户随时能下到原件;文件被删时副本一并删(删失败只记日志)。

⚠️ **空产物 = 转码没成功** —— ffmpeg 退出码 0 但写出 0 字节的情况真实存在
(某些畸形输入)。上传一个空对象,前端会拿到一个"点开是 0 字节"的播放链接,
**比没有还糟**。

### 24.5 配置

```yaml
file:
  ffmpeg_path: ffmpeg        # 默认走 PATH;环境变量 FFMPEG_PATH 优先
  ffprobe_path: ffprobe      # 默认走 PATH;环境变量 FFPROBE_PATH 优先
  media_max_size_mb: 2048
  transcode_enabled: true    # ⚠️ **布尔零值是 false = 关**
  transcode_workers: 2       # 并发数;0 = 整个转码功能关着
```

⚠️ **`transcode_enabled` 的零值是 `false` = 关** ——
布尔值没法像 int 那样区分"没配"和"配成 0",所以**模板里必须显式写 `true`**,
否则"配了 ffmpeg 却不转码"这件事没有任何提示。

⚠️ **关掉转码只是不转码,不影响别的** —— 时长、封面照旧,
列表里会显示"浏览器不支持" + 原因。**功能是分级的,不是全有全无**。

⚠️ **三个开关各自独立** ——
① `FFMPEG_PATH` 配错 ⇒ 没有时长/封面/转码(探测那层就断了);
② `transcode_enabled = false` ⇒ 有时长/封面,但播不了的文件**不转码**;
③ `transcode_workers = 0` ⇒ 同上(并发为 0 = 整个功能关着)。

### 24.6 前端契约

`FileView` 六个新字段(都带 `omitempty`):

| 字段 | 含义 | ⚠️ |
|---|---|---|
| `media_container` | 探测到的容器名(`mp4` / `mkv` …) | 探不到就没有 |
| `media_video_codec` | 视频编码(`h264` / `mpeg4` …) | 同上 |
| `media_audio_codec` | 音频编码 | 同上 |
| `media_reason` | **为什么浏览器播不了**(一句人话) | **空 = 能播**。这是唯一的判据 |
| `playback_url` | 可播副本的直链 | 只有转码完成才有 |
| `transcode_status` | `0`不需要 `1`待转 `2`转码中 `3`完成 `4`失败 | 与 `model.TranscodeStatus` 同值 |

前端呈现(`web/src/pages/file/`):

| 件 | 作用 |
|---|---|
| `mediaStatus.ts` | 纯函数 `mediaStatusOf` / `playbackSrcOf` + `MEDIA_STATUS_LABEL_KEY` |
| `MediaStatusTag.tsx` | 徽标组件(两个视图**共用同一个**) |
| `list.tsx` | 表格视图:徽标挂在**文件名那一格** |
| `FileGrid.tsx` | 缩略图视图:徽标贴在缩略图盒子的**右下角**(左上「封面」、右上「⋯」菜单、左下时长,四个各占一角 —— 见 §20.3.1) |

⚠️ **判据顺序不能反:先看转码状态,后看原文件播不播得了** ——
转码完成(3)之后文件**是能播的**(走 `playback_url`)。
这时候还标"浏览器不支持"就是在**骗用户**。
`media_reason` 是**原文件**的判据,它一直在,但状态优先。

⚠️ **i18n 键写字面量,不用模板串拼** ——
拼出来的键(`t(\`...media${x}\`)`)查不到时**原样返回那串键**,
而拼错的键两边字典可能**同时没有** ⇒ locale-parity(只比两边键集合)**发现不了**
⇒ 界面上直接显示 "page.fileList.mediaUnplaable"。

### 24.8 这次没做的

- **OSS 直传登记的视频没有时长、没有封面、也没有转码** ——
  aliyun 刻意不实现 `oss.ContentProvider`(见它的注释:"中转大文件与直传的意义相反"),
  所以这条路**拿不到字节**,探测和转码都无从下手。
  ⇒ **这是第三问里唯一说对的地方**:直传那条路如果要有转码,
  确实只能靠客户端传点什么进来 —— 但即便如此,后端**还是得从 OSS 把文件拉回来**
  才能转(带宽代价一分不少),所以"前端传标志位"并没有省掉那笔开销,
  只是把"要不要拉回来"这件事的决定权交给了客户端。
- **没有"重转"接口** —— 转码失败只能重传。
- **失败不重试** —— 见 §24.4。
- **转码产物没有独立配额** —— 副本不计入 `sys_user.storage_used_bytes`
  (和封面一样,§22.6),所以"转一堆视频"的账号,存储占用会比界面显示的大。
