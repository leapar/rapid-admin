# 后台权限模型设计 V1.0

> **状态**:草案 V1.0
> **日期**:2026-10-17
> **范围**:后台管理系统的权限模型(角色 / 资源 / 数据范围 / 字段级可见性),通用后台通用

---

## 1. 背景

### 1.1 当前实现

后端 `server/internal/api/middleware/rbac.go` 已经定义了 `RBAC(module, action)` 中间件,模型用 `casbin_rbac.conf`(RBAC with domains),但**零调用方**;策略只到"角色 → 权限码"这一层,数据存储在 `casbin_rule` 表。

### 1.2 业务侧三类"不好做"的需求

| 场景 | 业务描述 | 当前能否做 | 痛点 |
|---|---|---|---|
| **场景 A** 角色配置 | 给"运营管理员"角色开/关 12 项功能 | ✅ 能做 | 直接改 casbin_rule |
| **场景 B** 单用户勾选 | 业主甲允许"业主乙"看自己家的验房报告,只此一家、只此一人 | ❌ 不能 | RBAC 没有"按资源×用户"授权的维度 |
| **场景 C** 跨用户委托 | 业主甲邀请配偶丙"代签收房确认单",7 天有效 | ❌ 不能 | 委托链、有效期、操作人≠资源所有人,RBAC 表达不了 |
| **场景 D** 多身份并存 | 用户张三同时是"业主 + 物业经理",在不同项目下身份不同 | ⚠️ 部分 | 已有 `sys_user_identity`,但 Casbin sub 只用 `roleCode`,丢了"哪个身份"信息 |
| **场景 E** 个人功能开关 | 平台要灰度开放"AI 验房助手"给部分用户,其他用户看不到入口 | ❌ 不能 | 这是"功能级 flag"不是"权限码" |
| **场景 F** 权限继承 / 拒绝覆盖 | 客服 A 在项目 X 拥有所有权限,但"删除"操作被风控拒绝 | ❌ 不能 | RBAC 只有 allow,没有 deny + 优先级 |

### 1.3 微信小程序侧已确认的"邀请"语义(对照)

参考《微信小程序技术方案 V1.0》§6.6 与 §4.9.3,**家庭成员邀请** 是已经在产品里跑的需求:

- 业主在 `pages/family/invite.tsx` 调 `familyApi.invite({ phone, name, relation, permissions })`
- 后端校验:只有 `is_main=true` 的业主才能 invite / remove(§5.6.3 第 1347 行)
- **invite 接口必须显式传 `permissions: ['smart_view', 'smart_ctrl']`**(§5.6.3 第 1348 行)— 这意味着**不是按角色全开,而是按权限码按位勾选**
- 家庭成员登录后**默认只能看到被授权的房屋**(§5.6.3 第 1368 行)
- "收房确认 / 智能家居默认 / 智能家居控制"需要单独授权(§5.6.3 第 1371 行)
- 微信订阅消息模板 `accept_invite` 用作邀请触达(§4.9.3 第 1249 行)

这些**已经在产品里要做了**,后端必须能支撑。

## 2. 设计目标

1. **角色维度**(A 场景):保持现有 RBAC,不变。
2. **资源×用户维度**(B 场景):业主甲对业主乙**对**自己名下的资源 X 授予"看"权限。
3. **委托维度**(C 场景):业主甲对配偶丙**对**自己名下的资源 X 委托"代签"权限,7 天有效,可撤销。
4. **多身份维度**(D 场景):用户有多个身份时,Principal 必须能区分"我现在是以哪个身份在操作"。
5. **功能开关维度**(E 场景):灰度、个人化开启。
6. **优先级维度**(F 场景):deny > allow,显式 deny 必须赢。
7. **审计**:每一次 grant / revoke / override 全部留痕,带"谁授权谁、什么资源、什么权限码、什么时间、什么 IP"。
8. **可回滚**:模型升级要兼容旧 token、旧 casbin_rule 数据。

## 3. 授权模型选型

### 3.1 主流模型对比

| 模型 | 一句话 | 适合 | 缺点 |
|---|---|---|---|
| **RBAC** | 角色 → 权限 | 稳定的组织结构,权限按部门分 | 无法表达"按资源、按人"的临时授权 |
| **ABAC** | 用属性表达式判定 | 复杂规则(部门 == 资源 owner) | 规则不直观,审计困难 |
| **ReBAC** | 资源 + 关系图 | Google Zanzibar 风格,适合"我分享给谁" | 工程量大,需要关系数据库存储 |
| **PBAC** | 策略即代码(OPA、Casbin) | 跨系统统一决策 | 策略膨胀后难以维护 |
| **OAuth Scope** | 令牌带 scope | 第三方接入 | 不适合内部系统 |

### 3.2 我们的选择:**RBAC + ReBAC + 委托(delegation) 三合一**

- **角色基线**:不动,保持现有 `casbin_rule` 表 + `rbac_with_domains` 模型。
- **资源级授权**:新增 **`permission_grant` 表**,表达"谁对哪个资源有什么权限"。
- **委托/邀请**:复用 `permission_grant` 表,加 `grant_type='delegation'`、`expires_at`、`granter_user_id` 字段。
- **多身份**:在 JWT claims 里加 `active_identity_id`,中间件组装成 Principal。
- **优先级**:Casbin 模型升级为 allow + deny,deny 覆盖。
- **个人功能开关**:新增 **`user_feature_flag` 表**,独立维度。

> **为什么不直接上 ReBAC(Zanzibar)?** 工程量太大(要写关系图引擎、SpiceDB 等)。我们的资源类型不多(项目、楼栋、户型、房屋、合同、业主),用关系表 + Casbin 已经能 cover 99% 场景,后续真有需要再迁移。

## 5. 数据模型

### 5.1 `permission_grant` 委托授权表(P0 核心)

> 统一表达"按资源×用户"的所有授权动作 — **场景 B、C 的主载体**。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uint64 | sonyflake |
| `grant_type` | enum | `role_override` / `user_toggle` / `delegation` / `family_invite` / `project_grant` |
| `granter_user_id` | uint64 | 谁授予的。`role_override`/`user_toggle` 场景可为空(系统策略) |
| `grantee_user_id` | uint64 | 谁被授予 |
| `grantee_identity_id` | uint64 NULL | 限定到具体身份(如"业主 A 在 X 项目的身份")。空=任意身份生效 |
| `resource_type` | string | `house` / `contract` / `project` / `asset` / `feature` / NULL=全局 |
| `resource_id` | uint64 NULL | 具体资源 id,空=该类型所有 |
| `scope_project_id` | uint64 NULL | 项目域,空=不限定项目 |
| `permissions` | json | `["house:view", "house:delivery:sign"]` — 权限码白名单 |
| `constraints` | json | `{expires_at, max_uses, ip_whitelist, time_range, ...}` — 约束条件 |
| `status` | enum | `pending` / `active` / `revoked` / `expired` |
| `created_at` / `created_by` | timestamp / uint64 | |
| `activated_at` | timestamp NULL | `pending` → `active` 触发时间(邀请被接受时) |
| `revoked_at` / `revoked_by` / `revoke_reason` | timestamp / uint64 / string | |
| `note` | string | 邀请时附言 |

**索引**:
- `idx_grantee_active` (grantee_user_id, status, expires_at_partial) — 查询"我当前有哪些授权"
- `idx_granter` (granter_user_id, status) — 查询"我授权出去的"
- `idx_resource` (resource_type, resource_id, status) — 查询"这个资源被授权给谁了"

**为什么 json permissions?** 一个 grant 可以包含多个权限码,避免 N 行。校验时用 JSON_CONTAINS / GORM Where + json 字段。

**约束字段示例**:
```json
{
  "expires_at": "2026-12-31T23:59:59+08:00",
  "max_uses": 1,
  "ip_whitelist": ["10.0.0.0/8"],
  "weekday_only": [1,2,3,4,5],
  "time_range": ["09:00", "18:00"]
}
```

### 5.2 `user_permission_override` 单点拒绝/允许

> 场景 F 优先级需求 + 场景 B 单用户勾选(当资源类型是 NULL 时)。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uint64 | sonyflake |
| `user_id` | uint64 | |
| `permission_code` | string | `biz:owner:delete` |
| `effect` | enum | `allow` / `deny` |
| `reason` | string | 为什么加这条(风控 / 临时授权) |
| `expires_at` | timestamp NULL | 临时性拒绝 / 允许 |
| `created_by` | uint64 | 操作人 |
| `created_at` | timestamp | |

**索引**: `idx_user_perm (user_id, permission_code)` UNIQUE

### 5.3 `user_feature_flag` 功能开关(场景 E)

> 和权限码解耦,用于"灰度 / 个人化功能开关"。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uint64 | sonyflake |
| `user_id` | uint64 | |
| `feature_key` | string | `ai_inspection_assistant` / `wechat_smart_home` / `family_share_qr` |
| `enabled` | bool | |
| `enabled_at` | timestamp | |
| `enabled_by` | uint64 | 平台超管/运维 |
| `expires_at` | timestamp NULL | 试用性质 |
| `rollout_group` | string NULL | 灰度分组:`beta` / `canary` / `production` |

**索引**: `idx_user_feature (user_id, feature_key)` UNIQUE

### 5.4 与 Casbin 关系

- `casbin_rule` 表(已有):存**角色 → 权限码**的静态绑定。**不动**。
- `permission_grant` / `user_permission_override` / `user_feature_flag` 都是**应用层**表,中间件在内存里组装 Principal 时直接读,**不同步到 casbin_rule**。
- 原因:casbin_rule 适合"一次性灌入、跑生产";"按人按资源"的数据变更频繁,塞 casbin_rule 会导致策略爆炸、Reload 频繁、难以审计。

## 6. Casbin 模型升级

### 6.1 升级点

`configs/casbin_rbac.conf` 起点(只 RBAC + domains):
```ini
[matchers]
m = g(r.sub, p.sub, r.dom) && r.dom == p.dom && keyMatch2(r.obj, p.obj) && (r.act == p.act || p.act == "*")
```

升级到 **RBAC + allow/deny 优先级**:
```ini
[request_definition]
r = sub, dom, obj, act

[policy_definition]
p = sub, dom, obj, act, eft

[role_definition]
g = _, _, _

[policy_effect]
e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

[matchers]
m = g(r.sub, p.sub, r.dom) && (r.dom == p.dom || p.dom == "global") && keyMatch(r.obj, p.obj) && (r.act == p.act || p.act == "*")
```

关键变化:
1. `policy_definition` 加 `eft` 字段 — Casbin 显式支持 allow / deny
2. `policy_effect` 改成 `allow ∧ !deny` — **deny 永远赢**
3. **`keyMatch2` → `keyMatch`(M147,2026-11-01)** — 见下

#### ⚠️ 为什么 obj 的匹配必须从 `keyMatch2` 换成 `keyMatch`(M147)

**`r.obj` 装的是资源码,不是 URL 路径** —— 这是 Phase 1 起就有的事实(见 §6.3),
但 matcher 一直用的是给路径写的 `keyMatch2`,于是:

| keyMatch2 的行为 | 在资源码命名空间里的后果 |
|---|---|
| 把 `:xxx` 当成**路径参数**编译成正则 | `"user:list"` → `^user[^/]+$` ⇒ **绑了 user:list 的角色也能过 user:delete**(模块内串味) |
| `"*"` 编译成 `^*$` | **恒真** ⇒ 一条 `p, role:X, global, *, *, allow` 让**任何角色都能访问任何接口** |
| `"house:*"` 这种前缀通配 | `keyMatch2("house","house:*")` = false ⇒ **deny 规则永不生效** |

资源码命名空间里 `:` 是**字面量分隔符**(`"user"` + `":"` + `"list"`),
要的是「精确匹配 + `*` 后缀通配」—— 正好是 `keyMatch` 的语义。
(仓里 `authz.MatchPermissionCode` 是同一套语义,见 `internal/pkg/authz/permissions.go`。)

⚠️ **换 matcher 必须同时改另外两处,缺一不可**(M147 三处配套):

1. **`internal/seed/seed.go` `buildRolePolicies`** —— 删掉「每角色一条通配行」;
2. **`internal/api/middleware/rbac.go` `decideAccess`** —— 请求 obj 传**完整资源码**
   (`module + ":" + action`),不是模块名。

只做 1 ⇒ 从"人人能访问"变成"人人访问不了"(粒度错位);
只做 2 ⇒ 同上;
只改 matcher ⇒ 串味 + 通配恒真照旧。

### 6.2 sub 的设计:结构化字符串

`r.sub` 不再是裸 `roleCode`,而是结构化字符串:

| 场景 | sub 取值 | 含义 |
|---|---|---|
| 默认 | `role:house_admin` | 用角色鉴权 |
| 委托场景(Phase 2) | `grant:789` | 表达"我正在以 grant 789 的身份操作" |
| 个人覆盖 | `user:123` | 表达"我正在以用户 123 的身份操作",常用于 deny override |
| super_admin | `role:super_admin` | RBAC 中间件层短路,不必走到 Casbin |

**实际写入的 sub 形式**(Phase 1.1.5 决策): 由于 `SysRole.Code` 风格是 `role_house_admin`(下划线前缀),叠加 namespace 后得到 **双前缀** `role:role_house_admin`。丑但正确,避免历史数据大改。

**这样 Casbin matcher 不变**,只是 sub 的语义被扩展。`rbac.go` 中间件在调用 Enforce 时:
- 默认场景:`Enforce("role:" + caller.RoleCode, "global", code, act)`  → 实际就是 `Enforce("role:role_house_admin", ...)`
- 用户覆盖:`Enforce("user:" + caller.UserID, "global", code, act)` → `Enforce("user:123", ...)`
- 委托场景(Phase 2):额外调一次 `Enforce("grant:" + grantID, ...)`

⚠️ **`code` 是完整资源码**(`module + ":" + action`),**不是模块名** —— 见 §6.3 / M147。

**数据迁移(已实施,seed.go 自动调)**: 旧 casbin_rule 里裸 `role_house_admin` 通过 `MigrateCasbinSubPrefix()` 在 seed.Run 启动时自动补 `role:` 前缀;幂等(已带前缀的跳过),跨驱动安全(用 `CONCAT` 而非 `||`,兼容 MySQL 8 与 SQLite)。

**不允许的 sub 写法**:把 caller.UserID 直接当裸 sub(会爆炸,见 web 搜索 [m.php.cn 2878025](https://m.php.cn/faq/2878025.html) 的反例)。

### 6.3 obj 的设计:**资源码**(不是 HTTP 路径)

> ⚠️ **2026-11-01(M147)更正**:本节原文写的是「`r.obj` 始终是 HTTP 路径,
> 通过 `keyMatch2` 通配」—— **那是错的**,而且这个错直接导致了 §6.1 那个洞。
> 下面是**实现的真实口径**。

`r.obj` 是**资源码**,即 `sys_resource.code` 那一列的值,跟 HTTP 路径无关。

| 资源类型 | 码的形态 | 例子 |
|---|---|---|
| api | `模块:动作` | `user:list` |
| api(多级模块) | `模块:子模块:动作` | `audit:login:list` / `job:run:read` |
| menu | 点分 | `menu.system.user` |
| button | 点分 | `button.user.add` |

**请求侧的 obj** 由中间件拼出来:`module + ":" + action`,
其中 `(module, action)` 就是路由上 `rbac("user", "list")` 的那两个参数
⇒ 请求 obj 恒等于该路由对应的**资源码**。

```go
// internal/api/middleware/rbac.go
code := module + ":" + action
enf.EnforceEx("role:"+caller.RoleCode, "global", code, action)
```

⚠️ **模块名和资源码不是一回事,也不能从资源码反推模块名** ——
`audit:operation:list` 来自 `rbac("audit:operation", "list")`(**模块名自带冒号**),
而 `job:run:read` 来自 `rbac("job", "run:read")`(**动作自带冒号**)。
同一个前缀可能是模块也可能是动作 ⇒ 字符串切分必然切错 ⇒
**必须让请求端传完整资源码**(M147 改的就是这一处)。

**资源 ID(用于 L3 IDOR)不进 Casbin**,由 service 层在拿到资源 ID 后查
`permission_grant` 表 —— Casbin 只管「这个身份能不能碰这一类资源」,
不管「能不能碰这一条」。

## 7. Principal 解析(中间件核心)

### 7.1 Principal 数据结构

```go
type Principal struct {
    UserID         uint64
    IdentityID     uint64       // 当前激活身份
    RoleCode       string       // 当前身份的 role
    ProjectIDs     []uint64     // 当前身份能看到的项目列表

    // 应用层附加(从 DB / cache 加载)
    ActiveGrants   []GrantRef   // 当前对我有效的 grant 引用
    Overrides      []Override   // deny/allow 覆盖
    FeatureFlags   map[string]bool

    // 元
    LoadedAt time.Time // 加载时间(用于判断 TTL)
    CacheHit bool      // 是否命中缓存
}

func (p *Principal) IsSuperAdmin() bool { return p != nil && p.RoleCode == "role_super_admin" }
func (p *Principal) InProject(projectID uint64) bool { /* 见 loader_test.go */ }
func (p *Principal) HasFeature(key string) bool { return p.FeatureFlags[key] }
func (p *Principal) HasDenyOverride(permCode string) bool { /* deny 显式覆盖检查 */ }

type GrantRef struct {
    GrantID        uint64
    GrantType      string  // role_override / user_toggle / delegation / family_invite / project_grant
    GranterUserID  uint64  // 授权人(系统策略时可空)
    ResourceType   string
    ResourceID     uint64  // 0 = 全部
    ScopeProjectID uint64  // 项目域(0=不限)
    Permissions    []string
    ExpiresAt      *time.Time
}

func (g GrantRef) Active() bool { /* ExpiresAt 未过期 */ }

type Override struct {
    PermissionCode string
    Effect         string  // "allow" | "deny"
    ExpiresAt      *time.Time
}
```

> **Phase 2.4 实施后字段调整**: 相比原设计 `IsPlatformSuperAdmin bool` 字段,实现改为 `IsSuperAdmin() bool` 方法(基于 RoleCode 动态计算,不存字段 — 避免「身份切换后字段 stale」);`GrantRef` 增加 `GrantType` / `GranterUserID` / `ScopeProjectID` 字段(审计与项目域过滤需要);新增 `LoadedAt` / `CacheHit` 元字段(便于排错和监控命中率)。

### 7.2 加载顺序与缓存

```
1. Auth() 完成后, ctx.caller 已就绪
2. Principal() 中间件:
   a. 先查 Redis: key=principal:{user_id}:{identity_id} → 反序列化
   b. 命中:用缓存,直接挂到 ctx
   c. 未命中:
      - 查 permission_grant WHERE grantee_user_id=? AND status='active' AND (expires_at IS NULL OR expires_at>NOW())
      - 查 user_permission_override WHERE user_id=?
      - 查 user_feature_flag WHERE user_id=?
      - 合并 → 写 Redis(TTL 5 分钟)
   d. 挂到 ctx.principal
3. 写操作 grant/revoke 时:同事务删 Redis 缓存(避免读到 stale)
```

**为什么 Redis 缓存?** 委托授权会被频繁读取,但本身变更不频繁。**写时清缓存**是简单可靠的模式。

### 7.3 缓存击穿

- 用 `singleflight.Group` 保证同 user_id+identity_id 的并发请求只查一次 DB
- Redis 不可用时降级为直查 DB(类似现有 `loginlock.PreCheck` 模式)

> **2026-10-25(M90)更新**:本节描述的是**本包自建缓存**的方案,现已迁到统一缓存层
> `pkg/cachex`(见 §17.10)。单飞仍由 `singleflight.Group` 提供,但**不再由本包自己实现** ——
> `cachex` 的三防(单飞 / 空值占位 / TTL 抖动)只有一份实现,本包直接用。
> 因此本缓存**额外**获得了此前没有的两样防御:身份不存在时写空值占位(2min),
> 以及 TTL ±20% 抖动(避免改权限那 5 分钟所有 principal 同时到期)。

## 8. 中间件分层

### 8.1 L0.5 Principal 装配 — `middleware.Principal()`

```go
func Principal(loader PrincipalLoader) app.HandlerFunc {
    return func(ctx context.Context, c *app.RequestContext) {
        caller := service.FromContext(ctx)
        if caller == nil { return }  // 公开路由不挂
        
        p, err := loader.Load(ctx, caller.UserID, caller.IdentityID)
        if err != nil {
            response.Fail(c, errcode.Internal, "主体解析失败")
            c.Abort()
            return
        }
        ctx = service.WithPrincipal(ctx, p)
        c.Next(ctx)
    }
}
```

### 8.2 L1 接口级 RBAC — `middleware.RBAC(module, action)`

实际实现(Phase 1.2,commit `9e71580`):抽出 `decideAccess()` 纯函数做决策,中间件只翻译 HTTP。

```go
func decideAccess(caller *Caller, module, action string, projectID uint64) AccessDecision {
    if caller.HasRole("role_super_admin") { return AccessAllow }       // 短路
    code := module + ":" + action           // ⚠️ M147:obj 传**完整资源码**,不是模块名
    okR, rulesR, _ := Enforcer.EnforceEx("role:"+caller.RoleCode, "global", code, action)
    okU, rulesU, _ := Enforcer.EnforceEx("user:"+caller.UserID,    "global", code, action)
    if hasDenyRule(rulesR) || hasDenyRule(rulesU) { return AccessDenyForbidden } // §5.2 跨子 deny
    if okR || okU {                                                            // 任一路 allow
        if projectID > 0 && !caller.InProject(projectID) { return AccessDenyOutOfScope }
        return AccessAllow
    }
    // 两路都不 allow → 查 grant 路径(Phase 2.5),principal 为 nil ⇒ 直接 Forbidden
    ...
}
```

⚠️ **M147(2026-11-01)**:上面的 `code` 不是可选的细节 ——
策略行的 obj 是资源码(`user:list`),请求 obj 以前传的是模块名(`user`),
`keyMatch2("user","user:list")` = false ⇒ **一条绑定行都命中不了**。
这跟 grant 路径本来就在用的口径(`module + ":" + action`)**本来就是一套**,
之前是两条路径各用各的:同一个请求,走 casbin 和走 grant 会判出两个结果。

**grant 校验在 Phase 2 接入**:增加 `EnforceEx("grant:"+grantID, ...)` 第三路(需要 Principal loader 注入 active_grants)。

### 8.3 L2 项目域 — `middleware.ProjectScope()`

保留现有 `extractProjectID` + `caller.InProject` 检查。**增加**:若 Principal 有跨项目 grant,允许通过。

### 8.4 L3 资源级 — service 层强制

由 service 实现统一接口:

```go
// internal/pkg/authz/assertor.go
type ResourceAssertor interface {
    AssertCanRead(ctx, resourceID) error
    AssertCanWrite(ctx, resourceID) error
    AssertCanDelete(ctx, resourceID) error
}
```

每个 service 在获取资源后,**第一件事**调 assertor:
```go
func (s *HouseService) Get(ctx, id) (*House, error) {
    h := s.repo.FindByID(ctx, id)
    if err := s.assertor.AssertCanRead(ctx, h); err != nil {
        return nil, err
    }
    return h, nil
}
```

assertor 内部:
1. 资源.owner_user_id == caller.UserID → 通过
2. caller.IsPlatformSuperAdmin → 通过
3. 查 Principal.ActiveGrants:
   - `grant.resource_type == "house" && grant.resource_id == h.ID && "house:view" ∈ grant.permissions` → 通过
4. 否则 403

### 8.5 调用链总图

```
Auth (L0)
  → Principal (L0.5)
    → RBAC (L1) ← 拒绝短路 deny override
      → ProjectScope (L2) ← 跨项目 grant 放行
        → Handler
          → Service
            → assertor.AssertCan*(L3) ← 资源所有权 + grant
              → 业务逻辑
```

## 13. 风险与回滚

### 13.1 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **Phase 1 启中间件后大面积 403** | 高 | 业务中断 | 默认关,`config.Casbin.Enabled=false`;先在测试环境跑,逐步开 |
| **casbin_rule 灌错策略导致全锁** | 中 | 全员 403 | 灌前快照 casbin_rule 表;保留回滚 SQL |
| **缓存 stale** | 中 | 用户被撤销权限后仍能操作 N 分钟 | grant/revoke 走事务,事务 commit 后清缓存;TTL 上限 10 分钟 |
| **委托授权被滥用(社工)** | 中 | 业主被骗授权 | 邀请需短信验证码二次确认(对接 `SendSms`);定期 audit;异常授权风控告警 |
| **多身份切换泄露** | 低 | A 项目数据被 B 身份访问 | principal 缓存按 identity_id 隔离;L2 ProjectScope 必走 |
| **deny override 写错导致全部 403** | 低 | 全员锁 | override 写入要审批流;删除用 `expires_at` 自动失效 |

### 13.2 回滚

- **Phase 1**:把 `config.Casbin.Enabled` 设回 false,中间件短路放行(已有 super_admin 短路,加个 enabled 配置即可)
- **Phase 2-3**:删 `permission_grant` / `user_permission_override` 表(数据先备份);Principal 装配中间件从链路摘除
- **Phase 4-5**:前端 mock 替代后端接口

每个 phase 都有明确的"开启/关闭"开关,**任何 phase 都可以独立回滚**。

## 15. 开放问题

> 这些是设计时遗留的、需要在 Phase 1 实施时细化的问题。

1. **委托的"撤销"是否会级联?** 比如 A 委托给 B,B 再委托给 C,A 撤销时 C 还有效吗?
   - 建议:**A 撤销会级联到 B**,C 也失效。permission_grant 加 `parent_grant_id` 字段做链。
2. **同一人多个身份是否能"合并"查看?** 比如张三业主身份在 X 项目,物业身份在 Y 项目,能不能"全平台"看?
   - 建议:**不能**。主操作只能用一个身份;查看要切身份。
3. **跨项目的资源授权怎么处理?** A 在 X 项目是业主,授权 B 看自己在 X 项目的房屋,B 没有 X 项目身份。
   - 建议:grant 的 `scope_project_id` 必须等于资源所在项目;B 必须先有 X 项目的"任何身份"才能接受跨项目 grant。
4. **风控 deny override 的粒度?** 上面举的是"deny delete",要不要支持"deny 所有,只 allow 这一条"?
   - 建议:**allow + deny 都能做**,管理后台 UI 提供两种模式("黑名单" vs "白名单")。
5. **grant 的"接受"是不是必须?** 场景 B 业主甲允许业主乙,要不要乙先点同意?
   - 建议:**B2C 场景(业主甲→业主乙同小区)可默认直接 active**;**C2C 跨业主场景必须 pending→active**(对应微信家庭邀请)。`grant_type` 决定默认 status。

### 17.2 Phase 1.1.5 — sub 命名空间加 `role:` 前缀(已 commit `e050028`)

**决策背景**: §6.2 设计的 sub 形式是 `role:house_admin`,但 `SysRole.Code` 实际存的是 `role_house_admin`(下划线前缀)。两种补救方案:
- A. 把所有 `SysRole.Code` 去掉 `role_` 前缀(大改,影响业务字段)
- B. 让 Casbin sub 接受双前缀 `role:role_house_admin`(丑但稳,数据零迁移)

**关键点**:
- 数据迁移 SQL 用 `CONCAT('role:', v0)` 而非 `'role:' || v0` —— MySQL 8 默认 `||` 是布尔 OR 不是字符串拼接
- 幂等:WHERE 排除已带 `role:` / `user:` / `grant:` 前缀的行

- seed.Run 启动时自动调,`currentDriver() == "sqlite"` 时跳过(开发模式)

### 17.3 Phase 1.2 — rbac.go 决策流重写(已 commit `9e71580`)

**核心设计**:抽出 `decideAccess(caller, module, action, projectID) AccessDecision` 纯函数(无 HTTP 依赖,便于单测),`RBAC()` 中间件只做"决策 → HTTP 翻译"。

**决策流程**:
```
1. caller == nil           → AccessDenyInternal
2. caller.role == super    → AccessAllow  (短路)
3. Enforce("role:"+rc, ...) → (okR, rulesR)
4. Enforce("user:"+uid, ...) → (okU, rulesU)
5. 任一 rules 含 eft=deny    → AccessDenyForbidden  (deny 跨子短路)
6. okR || okU == false     → AccessDenyForbidden  (无策略)
7. projectID > 0 && 不在工作范围 → AccessDenyOutOfScope
8. 其余                      → AccessAllow
```

**为什么不用"单 sub + Casbin 内部 deny 处理"**? 选项是 `Enforce("user:123", ...)` + grouping policy `g(user:123, role:role_house_admin)`,deny override 在 Casbin 内部完成。这要求:
- 在身份创建/登录时注入 grouping policy(改 seed/auth)
- deny 策略也写在 user: 子下(与 role 策略分离)

**两路 OR + 显式 deny 短路的优势**:
- 不改 seed/auth 流程,seed 同步策略即可
- 审计日志同时看到 role/user 命中的规则,排错快
- 策略表结构简单:role 策略写 `role:*`,user 策略写 `user:*`,互不耦合

**EnforceEx 返回结构**(踩坑记录): Casbin v3 的 EnforceEx 返回 `([]string, error)`,整张规则作为一个 []string(不是 [][]string),格式 `[sub, dom, obj, act, eft]`。`hasDenyRule(rules)` 判断 `rules[len(rules)-1] == "deny"`。

**单测覆盖(8 个全过)**:
- `SuperAdminBypass` — super_admin 直通
- `RoleAllow` — 角色 allow 通过
- `UserDenyOverridesRoleAllow` — **P0 类关键**:用户 deny 覆盖角色 allow
- `NoPolicy` — 无任何策略
- `ProjectInScope` / `ProjectOutOfScope` / `ProjectZeroAllowed` — 数据级
- `NilCaller` — caller=nil 防御

### 17.10 Phase 2.4 — Principal + DBLoader + CachedLoader

**包结构** `server/internal/pkg/authz/`:
- `principal.go` — Principal / GrantRef / Override 结构 + `IsSuperAdmin` / `InProject` / `HasFeature` / `HasDenyOverride` 便捷方法
- `loader.go` — `Loader` 接口 + `DBLoader` 实现(`loadCaller` / `loadGrants` / `loadOverrides` / `loadFeatureFlags`)
- `cached_loader.go` — `CachedLoader` 包装(委托 `pkg/cachex` 提供缓存与三防)

**关键设计决策**:
- **Loader 接口抽象**:内层 `DBLoader`(无依赖,单测友好)+ 外层 `CachedLoader`(生产用,缓存 + 防击穿);后续可加 `MemcachedLoader` / `MultiTierLoader` 不动业务
- **缓存后端抽象**:2026-10-25(M90)之前是本包自定义的 `CacheBackend` 接口(3 方法)+ `repository/principal_cache.go` 的 Redis 适配器;**现改为直接用 `pkg/cachex`**(`cachex.Safe` + `cachex.Backend` 接口),`CacheBackend` 与 `repository/principal_cache.go` **均已删除**。好处有三:三防只有一份实现 / 空值占位与 TTL 抖动白拿 / 命中率进 `app_cache_ops_total`
- **缓存降级**:后端不可用 → 记 warn 日志后直查 DB,不阻断业务
- **singleflight**:100 并发同 key 实际只查 1 次 DB(单测 `TestCachedLoader_Singleflight` 验证);实现已上移到 cachex
- **TTL 默认 5 分钟**(带 ±20% 抖动);grant/revoke 之后由 service 调 `InvalidateUser(userID)` 删掉该用户**所有身份**的 principal 缓存(2026-10-25 M91 改口径,详见下方两条)
- **失效粒度是"用户",不是"身份"**(2026-10-25 M91):principal 缓存的 key 是 `principal:{userID}:{identityID}`(一个身份一条),但**授权是挂在用户上的** —— grant 记 `grantee_user_id`、override 记 `user_id`、feature flag 记 `user_id`。改一次授权 = 改"这个人",他名下每个身份缓存里的画像都带着旧授权。只清一个身份 → 对方换个身份进来照样能用被撤销的授权(最长一个 TTL,默认 5 分钟)。所以 `Loader` 接口的失效方法统一为 `InvalidateUser(ctx, userID)`,一次清光
- **用前缀失效,不用"先查有哪些身份再逐个删"**:逐个删要多打一次 DB,而且**查的那一瞬间之后新建的身份会漏掉** —— 漏掉的那条继续带着旧授权,正是要消灭的东西。前缀失效(key 前缀 = `principal:{userID}:`)一次扫完,不漏
  - ⚠️ 末尾的冒号不能省:少了它 `"principal:12:"` 会匹配上 `"principal:123:456"`(用户 123),把不相干的人的授权画像一起删了。**失效删多了和没删一样危险**
  - ⚠️ 前缀失效依赖后端支持 SCAN。`cachex.DeletePrefix` 在不支持时是 fail-open 返回 `(0, nil)`(语义是"没有可枚举的 key,不是错误")—— 对"撤销授权"来说就是**静默什么都没删**。所以 `CachedLoader.InvalidateUser` 先问一句 `SupportsScan()`,拿不到能力就**报错**,绝不假装失效成功
- **不加本地 L1**:L1 是进程内的,失效只能清本实例 → 多副本下"改完权限立刻生效"会退化成"最多 L1 TTL 后生效"。**安全属性不值那点 RTT 收益**
- **audience**:DBLoader 简化版 `Caller.Audience = "admin"`(小程序端在 Phase 4 联调时再补)

> **⚠️ M90 顺带修掉的两个真缺陷**:
> 1. **数据竞争**(`-race` 当场抓到):singleflight 路径下同一个 `*Principal` 会被多个 goroutine 拿到,
>    直接写它的 `CacheHit` 字段就是竞争 → 改为**先值拷贝再改**
> 2. **`ErrNotFound` 的语义**:`DBLoader` 现在只把 `gorm.ErrRecordNotFound` 映射成
>    `cachex.ErrNotFound`(→ 写空值占位)。**连接失败 / 超时绝不能被当成"查无此数据"** ——
>    那样一次 DB 抖动会被固化成 2 分钟的"该身份不存在"

> **⚠️ M91 补上的失效链**(2026-10-25,详见 `docs/框架层未完成项清单v1.md` M91 块):
> 1. **失效粒度从"按身份"改成"按用户"**:`Invalidate(userID, identityID)` → `InvalidateUser(userID)`。
>    旧口径下 `family.Revoke` 只清主身份 —— 被撤销的授权在对方**其它身份**上还能用满一个 TTL
> 2. **四个写路径补齐失效**:`family.AcceptInvite` / `family.Revoke` / `owner.CreateAuthorization` / `owner.RevokeAuthorization`
>    (owner 这两个此前**完全没有**失效调用 —— 授权建了/撤了,被授权人照样用旧授权)
> 3. **失效失败不吞**:写 DB 成功、失效失败 → 记 error 日志(**不回滚业务动作** —— DB 是真相,回报"失败"是撒谎),
>    缓存最迟一个 TTL 自然过期

### 17.14 Phase 3 — ResourceAssertor 通用接口 + 5 资源模式参考

**L3 资源级鉴权**(§8.4):在 L1 RBAC 通过后,service 层做"该 caller 对该资源 X 是否有权"的最后一道判定,防 IDOR。

**接口**(`internal/pkg/authz/assertor.go`):
```go
type Resource struct {
    ResourceType string  // "house" / "owner" / "asset" / "delivery" / "audit"
    ResourceID   uint64  // 0 = 该 type 全部
    OwnerUserID  uint64  // 0 = 平台共管
}

type CallerSummary struct {  // 不依赖 service 包,解耦
    UserID   uint64
    RoleCode string
}

type ResourceAssertor interface {
    AssertCan(caller *CallerSummary, principal *Principal, resource Resource, permissionCode string) error
}

type GenericAssertor struct{}
```

**决策流程**(短路顺序):
1. caller == nil → Internal
2. caller.IsSuperAdmin() / principal.IsSuperAdmin() → Allow
3. resource.HasOwner() && resource.OwnerUserID == caller.UserID → Allow
4. principal.HasDenyOverride(perm) → Forbidden(场景 F 显式 deny)
5. matchResourceGrant(principal, resource, perm):
   - g.ResourceType == resource.ResourceType
   - g.ResourceID == 0 || == resource.ResourceID
   - perm ∈ g.Permissions(支持通配)
6. 否则 → Forbidden

**5 资源模式参考**(`internal/service/assertor_ref.go`):
- `GetHouse` (house:view, owner = house.OwnerID)
- `GetOwner` (owner:view, owner = owner.ID 业主本人)
- `GetAsset` (asset:view, owner = asset.PublisherID)
- `GetDeliveryStage` (delivery:view, owner = stage.OwnerID)
- `GetOperationLog` (audit:view, owner = 0 平台共管,只信 L1 + deny)

**单测覆盖**(19 个 assertor 单测全过):

- `OwnerSelfAccess` / `NoOwnerNotMatched`
- `DenyOverrideWinsOverGrant` / `ExpiredDenyIgnored`
- `GrantExactResourceID` / `GrantResourceIDMismatch` / `GrantWildcardResourceID`
- `GrantResourceTypeMismatch` / `ExpiredGrantIgnored`
- `NilPrincipalNoOwnerNoGrant` / `NilPrincipalOwnerOK`
- `ResourceBuilders` / `ResourceString` / `CallerSummary_IsSuperAdmin`

### 17.15 Phase 4.2 — FamilyService 邀请/接受/撤销 端到端

**业务流**(§6.6 / §1.3):
```
业主(房主) → Invite(toPhone, resource, permissions)
            → 创建 biz_family_invite (status=0 待接受) + auth_permission_grant (status=pending, grantee_user_id=0)
            → 返回 inviteCode (16 hex 字符) 给业主 → 业主短信/微信发给被邀请人
被邀请人 → AcceptInvite(inviteCode)
            → 校验 invite 未过期
            → 找到 pending grant(通过 grantee_user_id=0 + granter + 时间窗口匹配)
            → 事务:grant 激活 (grantee_user_id=caller, status=active) + invite 标记已用 (status=1)
            → 失效被授权人 principal 缓存(让新授权立即生效)
业主 → Revoke(grantId, reason)
            → 校验只有 granter 能撤销 + 幂等
            → grant 标 revoked + revoked_at/by/reason
            → 失效被授权人 principal 缓存
```

**文件清单**:
- `internal/service/family.go` (464 行):FamilyService 接口 + familyService 实现 + 5 个 API + 4 个 helper
- `internal/api/handler/v1/family.go` (134 行):Invite/AcceptInvite/Revoke/ListMyInvites/ListMyGrants 真实 handler + 9 个 CRUD 暂留 NotImplemented stub
- `internal/service/family_test.go` (新增,11 个测试):端到端 sqlite 真实单测
- `internal/service/registry.go`:Registry 增加 `Family FamilyService` 字段
- `cmd/server/main.go`:FamilyService 构造(§7 占位 nil → §9.1 回填 finalLoader,使 `InvalidateUser` 生效)

**关键设计决策**:

1. **inviteCode 16 字符 hex**:`crypto/rand` 取 8 字节 → hex.EncodeToString,32 字符命中 64 bit 熵,业务可视性好
2. **双表同事务**:`biz_family_invite` + `auth_permission_grant` 在一个 `db.Transaction` 中创建,失败回滚
3. **grant lookup 简化**:Phase 4.2 通过 `grantee_user_id=0` + `granter_user_id` + `created_at` 时间窗口(1 min 容差)匹配 — 已知限制,后续 phase 加 `FamilyInvite.GrantID` 显式外键
4. **缓存失效时机**:
   - `AcceptInvite` 成功 → 失效**被邀请人**的 principal 缓存(让其立即可访问新资源)
   - `Revoke` 成功 → 失效**被授权人**的 principal 缓存(让其立即失去权限)
   - `Revoke` 撤销 pending grant(grantee=0)→ 跳过失效(无意义)
5. **jsonMarshalStringArray**:手写 `["a","b"]` 序列化,避免在 service 层引 `encoding/json`(保持 service 包轻)
6. **isValidPermissionCode**:仅校验 `module:action` 格式,具体权限码合法性由 L1 中间件 + L3 assertor 联合保证

**11 个单测全过**(`go test ./internal/service/ -run TestFamilyService -v`):
| # | 测试 | 覆盖点 |

**关键设计决策**:

#### 1. Caller.JTI 字段
```go
// Caller.JTI 当前 token 的 jti,用于 logout/改密时 revoke 单个 jti
JTI string
```
- middleware 解析 token 后把 `claims.JTI` 注入到 `Caller`
- service 拿到 Caller 即可在 Logout/ChangePassword/ResetPassword/SwitchIdentity 中 revoke **当前** jti
- **2026-10-21 更新**:`Caller.JTI` **不再承担**强制下线的责任。原来"改密码只 revoke 当前 jti"
  留下的敞口(同 user 其它设备纹丝不动、短信重置路径什么都不吊销)由**作废线**接手 —— 见第 2 条。

#### 2. 作废线(2026-10-21)—— 按用户整体强制下线

`jti` 吊销是 per-token 的,改密码需要的是 per-user 的效果。两者是**独立的两道闸**,
在 `middleware/auth.go` `Auth()` 里按固定顺序执行:

| 闸 | 键 | 触发点 | 管什么 |
| --- | --- | --- | --- |
| `IsRevoked(jti)` | 单张 token | 登出 / 切换身份 / refresh 轮换 | "眼前这一张"还能不能用 |
| `SessionInvalidated(claims)` | 整个用户 | 改密码 / 超管代重置 / 短信重置 | 这个用户的存量会话还该不该被认 |

- 判定式 `iat + 60s < 作废线`,理由与边界见技术方案 §7.7.4.16
- **refresh 侧必须自己查一次**:refresh 走 public 路由不经过中间件,少了这一步改密码只踢掉
  半个账号 —— 攻击者手里的 refresh 还能换出一张全新 access
- **刻意不触发**:登出 / 切换身份 —— 那是 per-device 动作,推线是 per-user 的

#### 3. 会话登记簿(2026-10-24 已落地)—— 强制下线其他设备

需求文档 §2.2.1 #6 的「可强制下线其他设备」(保留本设备、只踢别的)此前**做不了**,
只能做到「全部设备一起下线」(作废线)。现已用**会话登记簿**关闭(缺口 A2)。

**登记簿 = `sys_login_log`**(不新建 `sys_session` 表):一次登录 = 一行 = 一条会话,
靠 `session_id` 关联 sid;需求要的字段(设备 / IP / 浏览器 / 系统 / 登录时间)那张表全都有。
放 DB 而不是放吊销存储,是因为登记簿必须**跨实例一致** —— 吊销存储的内存实现是进程内的,
多实例部署时 A 实例看不见 B 实例上的会话。

| 端点 | RBAC | 说明 |
|---|---|---|
| `GET /rapid-admin/v1/auth/sessions` | `auth:sessions` | 我的活跃设备 + 历史登录记录。**不接 `userId`** —— 只能看自己,接口层面就没有可越权的入口 |
| `POST /rapid-admin/v1/auth/sessions/revoke` | `auth:revoke-sessions` | 点名吊销若干会话,返回**真正被吊销**的条数 |

**归属校验是硬要求**:`session_id` 是能直接递给吊销存储的句柄。不校验归属的话,
任何登录用户都能构造别人的 sid 把它吊掉 —— 变成「任意用户可踢任意用户下线」的 DoS。
所以先把 sid 与 `caller.UserID` **一起**查,只处理查得到的那些。

**不许吊销自己当前这条**:自己这条要走 `/auth/logout`(它连带把 access 的 jti 也吊了,
语义完整)。在这里吊掉它是「access 还活着、refresh 已死」的中间状态。

**中间件加第三道闸**(会话吊销态):前两道闸(jti / 作废线)都不认「这张 access 是哪条
会话发的」—— 少了第三道,被踢的设备手里那张 access 还能用 8h,「强制下线」在 8 小时内
形同虚设。

> **2026-10-24 更正(留档)**:上一版这里写着「同一份依赖还卡着:登出后 refresh 仍可续命最长
> 720h」,并把登记簿当成登出那件事的堵法。**那是把两件事混成了一件。**
>
> - **登出只挡住一半**(logout 杀不掉 refresh)是 **per-session** 问题,同日用
>   **会话绑定 sid** 关闭:一次登录一个 sid,access / refresh 共用,登出吊销 sid,两张一起死。
>   它**不需要**登记簿。
> - **「强制下线其他设备」**是 **per-user** 问题,要的正是"这个用户还有哪些会话"这个
>   索引 —— 这才是登记簿的用场,同日落地(缺口 A2 已关闭)。
>
> 换句话说:「per-user jti 索引解决不了它」这个结论仍成立,但它解决不了的是**登记簿
> 那一件**,不是登出那一件。

#### 4. 密码强度校验 — 移除
- 原 `auth.VerifyPasswordStrength` 假定输入是明文,校验大写/特殊/长度
- 实际前端契约: **SHA-256("rapid-admin::" + 明文) hex** 传给 service(参见 §6.1 + `web/src/utils/crypto.ts:preHashPassword`)
- 传入 service 的始终是 64 字符 hex,强度校验**永远不通过**
- **决策**: 强度校验移到前端(前端有明文,校验更准);service 只做格式校验 `len(newPwd) == 64`
- **风险**: 前端漏校验时,弱密码会被后端接受 — 用 §6.1 文档约束前端必须 pre-validate(若不 pre-validate,后端 fallback 6.1 节"前端强度规则"在登录失败计数 N 次时由风控兜底)

#### 5. ChangePassword 流程
```
caller  → CheckPassword(oldHash)         [bcrypt 比对 DB hash]
         → 验证 newHash 格式 (64 hex)    [sanity guard]
         → HashPassword(newHash)         [bcrypt(SHA-256 hex)]
         → DB 更新 + revoke caller.JTI
         → invalidateUserSessions(caller.UserID)  [推进作废线,见第 2 条]
```
- 旧密码错 → `errcode.LoginFailed`("原密码错误")
- newHash == oldHash → `errcode.InvalidParam`("新密码不能与旧密码相同")
- 失败不写 DB(事务),**失败不推作废线** —— 否则用户输错一次旧密码就把自己所有设备踢下线

#### 6. ResetPassword 流程
```
caller  → depth defense: target==caller OR caller.RoleCode==role_super_admin
         → HashPassword(newHash) + DB 更新
         → set MustChangePwd=true(target 用户下次登录被强制改密)
         → revoke caller.JTI(仅当 target==caller)
         → invalidateUserSessions(targetUserID)  [推进**目标**用户的作废线]
```
- **P0 IDOR 防御**: handler 已做 caller 权限判断,service 仍做二次校验 — 文档 §15.1 "Defense in Depth" 原则
- 非超管重置他人 → `errcode.IdorAttempt`(不返回 403/404,防止枚举)
- 写 `must_change_pwd=true`:目标用户下次登录由前端拦截弹强制改密(M7 用)
- **⚠️ 2026-10-21 修复**:整段吊销此前包在 `if target==caller` 里,于是**超管代重置对被重置者的
  存量会话毫无影响** —— 密码变了,被重置者所有设备上最长 720h 的登录照旧有效。现改为无条件
  推进**目标**用户的线,管理员自己不受影响

#### 7. SwitchIdentity 流程
```
caller  → 验证 identity 属于 caller.UserID     [防切他人]
         → 查询 identity + role
         → 若是高敏角色(super_admin / platform_ops_lead / platform_ops / finance)
              → 必须 smsCode,查 sys_sms_code(scene='change_phone'),验 UsedAt==nil 且未过期
         → JWTMulti.Sign(新 audience+identity+role+jti)
         → revoke caller.JTI        [不推作废线 —— 换身份是 per-device 动作]
         → 返回新 LoginResult(新 token + 新 userInfo)
```
- **高敏角色**: `role_super_admin` / `role_platform_ops_lead` / `role_platform_ops` / `role_finance`
- **SMS 验证**: 查 sys_sms_code 表(scene=change_phone)**且 phone 等于该账号登记的手机号**、未用过、未过期
  - 🔴 **2026-10-28(M104)修正**:这里原来写的是「M1 简化,不强制传 phone 字段,后续 phase 走 phone+SMSCode」。
    **那个"后续 phase"就是安全洞**:只要不绑手机号,任何人可以走**公开**接口
    `/public/auth/sms/send` 给**自己的**手机号发一条 scene=change_phone 的码
    (change_phone 对公众开放),拿到码之后拿来切**任意账号**的高敏身份 —— **二次验证形同虚设**。
    现在绑了,而且规则收口成**一处**实现 `consumeSmsCode(ctx, phone, scene, code)`
    (`WHERE code = ? AND scene = ? AND phone = ?` + used_at 检查 + TTL 检查 + 条件更新消费),
    `SwitchIdentity` 与 `VerifyAccountSms` 共用它,不会各自漂移。
  - ⚠️ 前端只有**脱敏**手机号(`/auth/me` 返 `138****5678`),所以身份切换的短信
    **由服务端代发**:`POST /rapid-admin/v1/auth/sms/account/send`
    (见技术方案 §7.7.4.7.1),手机号由服务端从 `sys_user` 取。
  - **场景复用 `change_phone`** —— 阿里云没有 `switch_identity` 模板,后端白名单里也没有。
- **Idempotency**: 切到自己当前 identity 也允许(返回相同 user/identity/token),便于前端无脑 refresh
- **关联**: §13.3 IdentitySwitcher + §17.18 死代码修复(M8 会改前端)

#### 8. UpdateProfile 流程
```
caller  → DTO 中每个 *string 字段独立处理:
            - nil    → 跳过(不改)
            - ""     → 大多拒绝(InvalidParam);Avatar 允许清空
            - 非空   → 校验 + 写
         → 校验邮箱格式(isValidEmail helper,简单 regex)
         → 校验昵称长度(1-32)
         → DB 更新
```
- **Pointer 字段** 区分"不改"和"改空串"(Go json 缺省语义)
- phone 变更**不在本接口**(M1 范围外),留 placeholder 走单独端点 + SMSCodeGuard

#### 9. Logout 流程
```
caller  → 非空校验
         → auth.RevokeSession(caller.SessionID, refreshTTL)  [吊销整条会话,失败时记 error 不阻塞]
         → auth.DefaultRevocation().Revoke(caller.JTI)   [Redis SET,失败时记 warning 不阻塞]
         → 写 sys_login_log.logout_at = NOW (按 caller.UserID 最新一条未登出记录)
         → **不推作废线**
```
- **JTI revoke**: 吊销写不进去时不阻塞登出(用户诉求优先),只记 warning
- **会话吊销(sid,2026-10-24 起)**: 一次登录生成一个 sid,access / refresh 两张 token 共用它;
  登出吊销 sid → **两张一起死**。TTL 取 **refresh 的寿命**(会话里寿命最长的就是它)——
  用 access 的 8h 的话,吊销记录会先过期而 refresh 还活着,等于没吊。
  这一步失败意味着"这次登出只做了一半"(refresh 仍可续期),记 **error** 让告警能捞到
- **⚠️ 刻意不推作废线**:作废线是全有或全无的,一推就是所有设备一起下线。登出要的是"这台
  设备退出",推线的后果是"手机上点了退出、电脑上的会话也一起没了",而且每次登出都这样
- **配套**:登出杀掉了 refresh,还必须在 `RefreshToken` 里**自查会话吊销态** ——
  refresh 走 public 路由,不经过中间件,中间件那两道闸(jti / 作废线)都查不到 sid。
  少了这一步,登出对 refresh 侧完全无效
- **「强制下线其他设备」已于 2026-10-24 落地**(见第 3 条):登记簿 = `sys_login_log`,
  `GET /auth/sessions` 列会话,`POST /auth/sessions/revoke` 点名吊销。**登出本身不踢别的
  设备** —— 要踢别的走那两个端点(登出是 per-device 动作)

**关键设计决策**:

#### 1. 菜单 code 命名空间 `menu.*` 解耦 api code
- 原因: `sys_resource.code` 是 uniqueIndex,菜单和 api 共用会撞
- 例: 菜单 `menu.system` (顶级目录, 无路由) vs api `user:list` (按钮权限) 完全不冲突
- 副作用: 路由 anyOf 守卫不能写 `menu.system.user` 来限制页面访问, 必须写 `user:list` (按钮级)
- 这是正确做法 — 菜单"可见"与"按钮级权限"是两个维度,不该用同一 code

#### 2. 菜单 type=menu + api type=api 共表
- 同一个 `sys_resource` 表,按 `Type` 区分 (`menu` / `button` / `api`)
- 后端 seed 一次性写入,前端按 type 过滤消费
- 优势: 不用新加表,RBAC 中间件(未来)只需看 type=api 的 policy

#### 3. AccessibleResources 加 typeFilter
- `?type=menu` → Sidebar 渲染
- `?type=api` → 按钮级 `<Permission perm="...">`
- 默认空=全部(向后兼容)
- 未来 RBAC 中间件挂载后,这个端点会被替代

#### 4. permissionCodes 双源: identities.permissions + accessible('api')
- `user.identities[].permissions` 已经在 LoginResult 阶段由 service 灌好(扁平 code 列表)
- 但 `identities.permissions` 是登录时的快照, 切换身份后会变
- 兜底: PermissionLoader 启动时拉一次 `accessible('api')`, 把所有 api code 加进去
- 冗余但安全 — 切换身份后没刷新页,按钮也至少有"按上次身份"的权限

### 17.34 M91 — 授权缓存失效链补全(2026-10-25)

**目标**:把"授权改了 → 被授权人的 principal 缓存要失效"这条链**补全**。M90 把缓存实现换成了 cachex(能力齐了),但**没人真正调用前缀失效** —— `cachex.DeletePrefix` 当时只有测试在用。

**审计发现的 4 个缺口**(全部是"授权已变、缓存还留着旧授权",最长一个 TTL = 5 分钟):

| # | 缺口 | 后果 |
|---|---|---|
| G1 | `owner_impl.go` `RevokeAuthorization` | **完全没有失效调用** —— 撤了授权,被授权人照样用旧授权满 5 分钟 |
| G2 | `owner_impl.go` `CreateAuthorization` | 同样没有 —— 刚授的权限要等 5 分钟才生效 |
| G3 | `family.go` `Revoke` | 只清**主身份**那一条 —— 对方换个身份进来照样能用被撤销的授权 |
| G4 | `family.go` `AcceptInvite` | 只清**主身份**那一条 —— 同上 |

**改动**:
- `internal/pkg/authz/loader.go`:`Loader` 接口的失效方法从 `Invalidate(userID, identityID)` 改成 **`InvalidateUser(ctx, userID)`**。理由:principal 里装的东西几乎全是**用户级**的(grant 挂 `grantee_user_id`、override 挂 `user_id`、feature flag 挂 `user_id`),只有 roleCode / projectIDs 是身份级的。**失效删多了只是多几次回源,失效删少了是安全事故**
- `internal/pkg/authz/cached_loader.go`:`CachedLoader.InvalidateUser` 用**前缀失效**(前缀 = `principal:{userID}:`)一次清光该用户所有身份
- `internal/pkg/cachex/prefix.go`:新增 `Safe.SupportsScan()` —— 让"安全关键的前缀失效"能区分"删了 0 条"和"后端根本不能扫"
- `internal/service/owner_impl.go`:`ownerService` 装上 `authz.Loader`;建/撤授权后失效被授权人
- `internal/service/family.go`:`AcceptInvite` / `Revoke` 两处改调 `InvalidateUser`,并**去掉"查主身份 ID"那次多余的 DB 查询**
- `cmd/server/main.go`:`Owner` service 按 `Family` 同样的"占位 nil → §9.1 回填 finalLoader"模式接上 loader

**接口变更的连带影响**(改 `Loader` 接口 = 改所有实现方):
- `internal/pkg/authz/loader_test.go`:`LoaderFunc.InvalidateUser`
- `internal/service/family_test.go`:`noopLoader.invalidated` 从 `[]struct{UserID, IdentityID}` 改成 `[]uint64`
- `internal/api/middleware/principal_test.go`:`loader.Invalidate(ctx, 100, 1)` → `loader.InvalidateUser(ctx, 100)`

**service 层测试**(新增 `internal/service/owner_test.go`,4 个):

| 测试 | 覆盖点 |
|---|---|
| `TestOwnerService_CreateAuthorization_InvalidatesGrantee` | 建授权后失效被授权人 |
| `TestOwnerService_RevokeAuthorization_InvalidatesGrantee` | 撤授权后失效被授权人 + DB 行真的变 `revoked` |
| `TestOwnerService_RevokeAuthorization_OtherUserCannotRevoke` | 越权撤授权被拒 |
| `TestOwnerService_NilLoader_NoCrash` | 没装 loader 不炸 |

**关键决策**:
- **失效失败不回滚业务动作**:写 DB 成功、失效失败 → 记 error 日志就完事。DB 是真相,回报"操作失败"是撒谎;缓存最迟一个 TTL 自然过期
- **不改缓存 key 格式**:key 格式跟线上 Redis 存量数据绑在一起,改了上线瞬间会有一波全量回源
- **不引入本地 L1**:L1 是进程内的,失效只能清本实例 → 多副本下"改完权限立刻生效"退化成"最多 L1 TTL 后生效"
- **fail-open 不适用于这里**:`cachex.DeletePrefix` 在后端不支持 SCAN 时返回 `(0, nil)`(语义"没有可枚举的 key"),但对"撤销授权"来说那等于**静默什么都没删**。所以 `InvalidateUser` 先问 `SupportsScan()`,拿不到能力就**报错**

**降级路径是 fail-closed**:principal 拿不到 → 授权判定跳过 → Forbidden。没 principal **不会**变成放行,所以这是"授权生效延迟",不是"越权"。

**可逆探针 7/7 全部变红**(拆实现看测试会不会红):

| 探针 | 必须变红的测试 |
|---|---|
| P1 `InvalidateUser` 换成按身份删 | `TestCachedLoader_InvalidateUser_ClearsAllIdentities` |
| P2 前缀少写末尾冒号 | `TestCachedLoader_InvalidateUser_PrefixIsolation` |
| P3 不问 `SupportsScan`,直接删 | `TestCachedLoader_InvalidateUser_BackendWithoutScanner` |
| P4 `ownerService` 撤销时不失效 | `TestOwnerService_RevokeAuthorization_InvalidatesGrantee` |
| P5 `ownerService` 新建时不失效 | `TestOwnerService_CreateAuthorization_InvalidatesGrantee` |
| P6 `family.Revoke` 不失效 | `TestFamilyService_Revoke_Happy` |
| P7 `family.AcceptInvite` 不失效 | `TestFamilyService_AcceptInvite_Happy` |

⚠️ P2 一开始**没红**:用例断言的方向搞反了(失效用户 12 时 `"principal:12"` 撞不上 `"principal:1:11"`,因为短前缀撞长 key 才是真撞)。改成失效**用户 1** 之后才红 —— 探针要照着**用例断言的方向**去拆,不是照着自己想的方向。

**刻意不做**:
- 不把 `Invalidate` 和 `InvalidateUser` 两种粒度都留着(留一个"按身份"的入口,调用方就会用错 —— 这正是 G3/G4 的成因)
- 不做"失效失败就重试 / 就回滚"
- 不改 `UserPermissionOverride` / `UserFeatureFlag`(全仓当前**没有写入方**,不构成陈旧风险)

### 17.37 M122 — 用户列表加一列「权限」(2026-10-30)

**起因**:§17.22 那一节写的用户管理页是 **9 列(头像/账号/昵称/部门/角色/手机-脱敏/状态/创建时间/最近登录)**,
但**「角色」这一列从来没有真的存在过** —— `web/src/pages/system/user/index.tsx` 里
压根没有渲染角色的列(文档写的是**规划**,代码没跟上,这类不一致本仓已吃过好几次亏)。

结果就是:想知道"这个人到底能干什么",管理员得**点进详情抽屉**才看得到,
而且详情还要**单独发一次请求**。用户管理页最该一眼自明的信息,恰恰要两步才能看到。

**改动**:

- **契约**:`UserListItem` 加 `Roles []UserRoleBrief`(`role_code` + `role_name`),
  `UserRoleBrief` 是列表行上的**角色摘要**。
  ⚠️ **与 `UserDetail.Identities` 的区别**:那是**身份**(含项目/部门/有效期/主身份),
  这只是**角色**(授权的最小单位)。两者不要混用 —— 身份清单在详情抽屉里。
- **实现**:`userService.userRoles(ctx, userIDs)` —— **一条 SQL** 查完本页所有用户,
  不是每个用户查一次(N+1)。
- **前端**:`web/src/pages/system/user/index.tsx` 加一列「权限」,渲染成 `Tag` 列表,
  `role_name` 为空时退回 `role_code`。
  ⚠️ **列标题的 i18n 键必须挂在 `field.*` 下**(用的是 `field.roles`),
  **不能挂 `page.user.*`** —— `table-column-i18n.test.ts` 有一条专门的断言:
  表格列标题只准用 `field.*` / `common.*` 这两个**共享组**
  ("别新开一个组" —— 挂页面专属组的话,别的页面要显示同一列就得各写一份)。
  ⚠️ 也**不是** `field.role` —— 那个键是编辑抽屉里单个角色的表单 label。

**三条语义边界**(这列最容易做错的地方):

| # | 边界 | 理由 |
|---|---|---|
| 1 | **只取 `is_active = true` 的身份** | 停用的身份不授予任何权限(`authz` 的 `loadCaller` 同样要求 `is_active = true`)。把停用身份的角色也列出来 = 让管理员以为这个人还有那个权限 —— **看得见的错权限比看不见的更危险**。M25 的级联停用(角色 `is_active=false` → 连带停用 identity)正是这条的来源 |
| 2 | **同一个 `role_code` 只保留一条** | 一个人可以在不同项目/部门持同一个角色。这一列回答的是"这个人有什么**权限**",不是"这个人有**几个身份**"(身份清单在详情抽屉里,那里才有项目/部门/有效期) |
| 3 | **没有角色返回空数组,不是 `null`** | `null` 在 JSON 里是"字段缺失",前端区分不了"这个人没有角色"和"接口没返这个字段" —— 两者都会渲染成空白,但**只有前者是真的** |

排序:`is_primary DESC, role_code ASC` —— 主身份的角色排最前,同一页里两个人的角色顺序一致,扫起来才舒服。

**测试**(`server/internal/service/user_role_test.go`,4 条 + 已有 1 条 = 5 条):

| 用例 | 断言 |
|---|---|
| `FillsRoles` | 列表项带上角色 |
| `ExcludesInactiveIdentityRoles` | 停用的身份**不出现在**列表里 |
| `NoIdentityReturnsEmptySlice` | 没有身份 → **空数组不是 null** |
| `DedupsSameRoleCode` | 同一 `role_code` 出现在两个身份里 → **只留一条** |

⚠️ **两个写夹具时的坑**(都踩过):

1. **`IsActive: false` 在 Create 时存不进去** —— `model.SysUserIdentity.IsActive` 带
   `gorm:"default:true"`,而 **GORM 会跳过带 `default` 标签的零值字段**。
   `db.Select("is_active").Create(...)` 更糟:`Select` 在 `Create` 上会把 INSERT
   **限制成只有那些列**,`user_id` 没了 → NOT NULL 报错。
   正确写法:**先 Create,再 `Update("is_active", false)`**,并**回读一次**确认落库
   —— 不回读的话,这条用例可能在"根本没写进去"的情况下照样绿。
2. **排序断言是假绿** —— 第一版把**主身份插在前面**,断言"主身份排最前"——
   但插入顺序恰好就是断言顺序,拆掉 `ORDER BY` 用例照样绿。
   改成**先插非主身份**,再插主身份,`ORDER BY` 才有牙齿。

**可逆探针 6/6(后端)+ 3/3(前端)全部转红**:

| # | 拆掉什么 | 后果 |
|---|---|---|
| S1 | `is_active = ?` 过滤 | 停用身份的角色冒出来 |
| S2 | 按 `role_code` 去重 | 同一个角色出现两次 |
| S3 | 过滤条件取反 | 有效的反而没了 |
| S4 | `ORDER BY is_primary DESC` | 主身份不再排最前(夹具已修正,这条是真的红) |
| S5 | 整个 `userRoles` 调用 | 列表一项角色都没有 |
| S6 | 空数组守卫 | 没有角色的人返 `null` 而不是 `[]` |
| W1 | 整个「权限」列 | 列不见了 |
| W2 | `'-'` 换成 `''` | 空角色渲染成空白,看不出是"确实没有"还是"没接上" |

### 17.39 M147 — 修 Casbin 通配策略洞(2026-11-01)

**起因**:上一轮(M143-M146)把「框架原语零覆盖」清单过了一遍,
在 `internal/api/middleware/rbac.go` 旁边挖出一个**从没被验证过的洞**:

> seed 给**每个角色**都加了一条通配策略
> `p, role:X, global, *, *, allow`,
> 而 casbin 的 `keyMatch2(r.obj, "*")` 编译成 `^*$` —— **恒真**
> ⇒ **任何角色都能访问任何接口**。

**13 × 394 的「角色-资源绑定矩阵」在强制执行层是空壳** ——
前端按矩阵渲染菜单(别人的菜单少了、按钮少了),
后端却谁都能调。矩阵只在「显示」这一层是真的。

#### 挖出来的是**三个叠在一起的洞**,不是一个

| # | 洞 | 单独看像不像 bug | 实际后果 |
|---|---|---|---|
| 1 | **通配行** | 像是「兜底方便」 | 任何角色都能访问一切 |
| 2 | **粒度错位**:策略行 obj = 资源码(`user:list`),请求 obj = 模块名(`user`) | 像是「两处约定不同」 | `keyMatch2("user","user:list")` = false ⇒ **一条绑定行都命中不了** |
| 3 | **`:` 被当 URL 路径参数** | 看不出来 | `keyMatch2` 把 `:xxx` 编译成正则 ⇒ 绑了 `user:list` 的角色**也能过 `user:delete`**(模块内串味);`house:*` 这种 deny 规则**永不生效** |

⚠️ **洞 2 决定了修法**:只删通配行(洞 1)⇒ 从「人人能访问」变成
「**人人访问不了**」—— 因为本来就没有任何一条绑定行能被命中。
⇒ 洞 1、2、3 必须**同一个 commit** 一起改。

#### 三处配套改动 + 一处补数据

| # | 位置 | 改动 |
|---|---|---|
| 1 | `server/configs/casbin_rbac.conf` | matcher 的 `keyMatch2(r.obj, p.obj)` → **`keyMatch(r.obj, p.obj)`** |
| 2 | `server/internal/seed/seed.go` `buildRolePolicies` | **删掉**「每角色一条通配行」;策略行只留真实的绑定 |
| 3 | `server/internal/api/middleware/rbac.go` `decideAccess` | 请求 obj 传**完整资源码** `module + ":" + action`(跟 grant 路径本来就在用的口径对齐) |
| 4 | `server/internal/seed/seed.go` `authBaseCodes` | **补 `resource:accessible`**(见下) |

#### 为什么必须补 `resource:accessible`(否则修洞修出新洞)

`/system/resource/accessible` 返的是「**当前 caller** 能访问哪些资源」,
前端拿它渲染侧边栏菜单和按钮。

- **不给**:该角色登录后**菜单和按钮全空**(前端不报错 —— 只是"什么都没有"),
  而它自己**没有任何办法恢复**。
- **为什么之前没人发现**:通配策略行让**所有角色**都能调这个接口。
  M147 把通配行删掉之后,这个洞才会露出来 ⇒ 必须**同一个 commit** 一起补。
- **只给 `accessible`,不给** `resource:list` / `resource:tree` / `resource:create` /
  `resource:update` / `resource:delete` —— 前者是「读自己的」,
  后五个是「管资源表的」(那是超管/用户管理员的权限)。

> 这跟 M93 补 `dict:list` 是**同一个洞的同一个形状**(见 §17.35)。

#### 安全审计先做了(确认删通配行不会误伤)

对 dev 库跑了一遍绑定矩阵审计:

- 43 个 rbac 码**只绑超管**(符合「系统配置只给超管」的设计意图);
- `auth:*` 覆盖**全部 13 个角色**;
- **0 个资源无人绑定** ⇒ 删掉通配行不会让任何人「本来就该能访问的东西」访问不了。

| `web/src/pages/flow/stage/[stageId].tsx`(审批规则页) | `user:list` / `role:list` | C 组(看流程配置):房源 / 资料 / 信息 / 交付管理员 |

这四个角色有 `flow:read` + `menu.flow`(进得了这一页),
但**没有** `user:list` / `role:list`。M147 之前它们靠通配行照样 200,
之后会连弹两个"没有权限",而且下拉框永远是空的。

⚠️ **其余"缺口"都在 `PermButton.*` 门控的按钮后面** —— 那些按钮 C 组
根本点不出来,接口压根不会被调 ⇒ 无害。

**修法:前端按权限码门控,不给 C 组补码。**

- 补 `user:list` / `role:list` 看着更省事,但那是**扩大权限面**:
  §8.4 的 C 组语义是「**看**」,D 组(改流程配置)才是超管专属;
  候选审批人名单是**编辑时**才需要的东西,而 C 组在本页的编辑入口
  全被 `PermButton.FLOW_*` 挡住了 —— 它们根本用不上这份名单。
- 前端只调自己调得动的接口,是**更小**的权限面。

```tsx
// web/src/pages/flow/stage/[stageId].tsx
useEffect(() => {
  if (has(PermSystem.USER_LIST)) { /* userApi.list(...) */ }
  if (has(PermSystem.ROLE_LIST)) { /* roleApi.list(...) */ }
}, [has, permissionCodes])
```

⚠️ **判据是"我要调的东西我有没有权限",不是角色码** ——
前端统一判权限码(见 `web/src/constants/permissions.ts` 头注释),
角色码在业务页里不该出现。

⚠️ **依赖项里为什么还有 `permissionCodes`(不能只写 `has`)**:

`usePermission()` 里的 `has` 是 zustand store 里**只创建一次**的函数
(`stores/permission.ts`:`has: (code) => get().permissionCodes.has(code)`)
⇒ 它的引用**永远不变** ⇒ 只把它放进 `useEffect` 依赖里,
**权限集换了也不会重跑 effect**。

而**切身份是不刷新页面的**(`IdentitySwitcher` 走 `fetchAccessible()`,
注释里明确写了"不 reload 页面")⇒ 组件不重新挂载 ⇒
mount 时那一次判断就成了「上一个身份」的判断:

| 切身份方向 | 只跟 `has` 走的后果 |
|---|---|
| 没有 `user:list` → 有 | 名单**永远是空的** —— 明明有权限却选不了人 |
| 有 `user:list` → 没有 | 名单还留着旧数据 —— 界面显示成有权限的样子 |

`permissionCodes` 每次 `setPermissions` 都是**新 Set**
⇒ 身份/权限一刷新就重拉名单。

**测试**:`web/src/pages/flow/__tests__/stage-rules.test.tsx`(新,**4 个用例**)——
① 没有 `user:list` / `role:list` 时**一个请求都不发**;
② 有哪个码才拉哪个名单;③ **权限集变了(切身份)⇒ 名单重新拉**。

> 可逆探针:① 把两道 `has(...)` 门去掉 ⇒ **前 3 个用例全红**
> ("expected spy to not be called at all, but actually been called 1 times");
> ② 把依赖改回 `[has]` ⇒ **第 4 个用例变红**;
> 两条都还原 ⇒ 全绿。
> ⚠️ 断言的是**"请求有没有发出去"**,不是 DOM ——
> 名单为空时"没权限"和"还没加载完"在 DOM 上长得一模一样。

#### M147-e — 自建角色的「自服务能力」绑定(M147 的配套,同一个 commit)

- ⚠️ **界面上的表现**:这几个码取消勾选后保存,**保存完又回来了**。

#### M147-f — 运行时改绑定,casbin 不同步(真机验证撞出来的第二个洞)

**起因**:M147 收尾的真机探针(建角色 → 查绑定 → 切身份):

| 步骤 | 结果 |
|---|---|
| 建角色 → 查绑定 | ✅ 自服务码都在 |
| 分配权限 → 再查绑定 | ✅ 自服务码还在 |
| **切到那个身份 → `GET /auth/me`** | ❌ **403** |

**根因**:`casbin_rule` 是绑定矩阵的**物化副本** —— 它只在
`seed` / `cmd/migrate` 时被**整体重建**一次。运行时管理员在界面上做的
三件事(建角色 / 改权限分配 / 删角色)改的是 `sys_role` /
`sys_role_resource`,**`casbin_rule` 不会跟着动** ⇒

> 前端(按绑定表显示):菜单出来了、权限勾上了
> 后端(按 casbin 判)  :一律 403
> 而且**没有任何报错** —— casbin 只是"没匹配到策略行",正常返 false。

⚠️ 这是 **M147 的直接后果**:在 M147 之前,绑定矩阵在强制执行层是空壳
(通配行兜着),运行时改不改绑定都无所谓;M147 让矩阵**真的生效**之后,
"副本不同步"就从"无所谓"变成"**管理员勾了权限却 403**"。

**修法**(新增 `internal/pkg/casbinx/sync.go` 一组函数):

| 函数 | 职责 |
|---|---|
| `casbinx.PolicyRow(roleCode, resCode)` | 策略行格式的**唯一来源**(seed 与运行时都调它) |
| `casbinx.SyncRolePolicies(tx, roleCode, resCodes)` | 重写某角色的全部策略行 |
| `casbinx.RemoveRolePolicies(tx, roleCode)` | 删掉某角色的全部策略行 |
| `casbinx.ReloadIfInitialized()` | 刷 enforcer 的**内存副本**(内存模型不会自动读库) |

接上三个写入口 + 一个触发点:

| 写入口 | 接了什么 |
|---|---|
| `CreateRole` | 建完绑完 → 同步策略行 |
| `AssignResources` | 覆盖式保存 → **整体重写**策略行(取消勾选的权限要**立刻**收回) |
| `DeleteRole` | 删角色 → 删策略行(否则同 code 的新角色**继承旧角色的全部权限**) |
| `UpdateResource`(启用状态变了) | 重算绑着它的角色(见下"停用资源") |

⚠️ **两条纪律**:

1. **同步写进调用方的 tx** —— 绑定改动与策略行改动**同一个事务**。
   反过来(先提交绑定、再单独写策略)的话,中间崩了就是
   "绑定改了、策略没改" ⇒ 失败方向是"**放行**",不能要。
2. **刷新内存副本必须在事务提交之后** —— 事务里刷到的是还没提交的库状态。

**附带口径统一:「停用资源」不再是死开关。**

停用一个资源(`sys_resource.is_active = false`)之前的表现是:
菜单消失(`AccessibleResources` 过滤 `is_active`)、**接口还能调**
(casbin 里那条策略行还在)⇒ 前后端两套真相。
现在三处口径统一成「只取启用中的资源」:

| # | 位置 | 口径 |
|---|---|---|
| 1 | `seed.buildRolePolicies`(整体重建) | 只取 `is_active = true` |
| 2 | `service.roleResourceCodes`(运行时同步) | 只取 `is_active = true` |
| 3 | `authService.AccessibleResources`(前端菜单/按钮来源) | 只取 `is_active = true`(本来就有) |

⚠️ **停用是临时收回,不是解绑** —— 重新启用会把权限还回去
(`UpdateResource` 触发重算)。

**测试**:

| 文件 | 内容 |
|---|---|
| `server/internal/pkg/casbinx/sync_test.go`(新) | ① 同步 + Reload 之后 Enforce 真的变了(**且**写完库没 Reload 时**不该**生效 —— 内存模型不会自动读库);② 覆盖式:第二次同步只留一个码,被收回的那个**立刻**失效;③ 删角色 ⇒ 策略行清空;④ `PolicyRow` 的行格式 |
| `server/internal/service/role_casbin_sync_test.go`(新) | ① 建角色 ⇒ casbin 里有自服务码;② 分配权限 ⇒ 加进来的有、被收回的没了;③ 停用的资源不给策略行;④ 停用/启用资源 ⇒ 绑着它的角色重算;⑤ 删角色 ⇒ 策略行清空 |

> 可逆探针(7 条,全部**变红**):拆掉 CreateRole 的同步 / AssignResources 的同步 /
> DeleteRole 的删行 / `is_active` 过滤 / UpdateResource 的重算 /
> casbinx 的 Reload / casbinx 的「先删后加」覆盖语义。

**真机验证(真起服务 + curl)**:

| 步骤 | 结果 |
|---|---|
| 建角色 → 查绑定 | ✅ 15 个自服务码 |
| 分配权限(`user:list`)→ 再查 | ✅ 自服务码还在,`user:list` 加上了 |
| 给 admin 加第三个身份 → 切过去 | ✅ |
| **`GET /auth/me`** | ✅ **200**(M147-f 之前是 403) |
| `GET /system/resource/accessible?type=menu` | ✅ **200**,45 条菜单 |
| `GET /system/dicts` | ✅ 200 |

⚠️ 清理时发现「切身份会吊销旧 token」⇒ 清理脚本必须**重新登录**再操作
(这是 M146a 的既有行为,不是新问题)。

#### M147-g — 软删的角色仍然占着 code(真机验证第三次撞出来)

**起因**:M147-f 的真机探针第二次撞出来:探针角色删掉之后**再建同 code**
⇒ **500 + 裸 SQL 错误** `UNIQUE constraint failed: sys_role.code`。

**根因**:

- `sys_role.code` 上有 uniqueIndex,而**软删的行还在表里** ——
  uniqueIndex **不看 `deleted_at`** ⇒ 这个 code 被永久占着。
- `CreateRole` 的唯一性预检用**默认 scope**(查不到软删的行)
  ⇒ 预检放行 → INSERT 撞 DB 约束 → 500 + 把 SQL 漏给前端。

⇒ 「删掉 → 再建同 code」是**死路**(而且报的是裸 SQL 错误,不是业务错误)。

**修法**:

| 情况 | 处置 |
|---|---|
| 活的同 code 角色 | **409「角色 code 已存在」**(与 user 服务的"用户名已存在"同一口径) |
| 软删的同 code 角色 | **复活**它 —— 绑定(`sys_role_resource`)与身份(`sys_user_identity`)在删除时**已硬删**,casbin 策略行也删了 ⇒ 它等于一个**全新**角色 |

- 唯一性预检改用 `Unscoped()`(软删的行也查得到)。
- ⚠️ **唯一还留着的是审批规则里的 `role_id`**(`sys_approval_assignee_rule`)
  —— 角色 ID 复用 ⇒ 那些规则会重新指向这个"新"角色。
  比留一条指向已删角色的**孤儿规则**更合理。

**测试**:`server/internal/service/role_casbin_sync_test.go` 里两个用例 ——
「删掉 → 再建同 code」能走通(且权限是全新算的、角色重新出现在列表里)、
「活着的同 code」被 409 拒。

> 可逆探针:① 不复活软删的同 code 角色 ⇒ 变红;
> ② 唯一性预检不用 `Unscoped` ⇒ 变红。

M147 删掉通配策略行

### 17.40 M149 — 显示层按「当前身份」算(2026-11-01)

**用户报的现象**:从超级管理员切到用户管理员,**界面完全一样** ——
菜单还是超管那一套(45 条),按钮一个没少,点下去才 403。

#### 根因:显示层与执行层两套真相

| 层 | 口径 | 位置 |
|---|---|---|
| 执行层 | **当前身份**(`caller.RoleCode` = token 里当前身份的角色) | `internal/api/middleware/rbac.go` `decideAccess`;`internal/pkg/authz/loader.go` `loadCaller`(按 `identityID` 查) |
| 显示层(改之前) | **这个用户所有身份的并集** | `service.AccessibleResources`;`service.GetCurrentUser` 的资源树;`service.platformFlags`(⇒ `is_platform_super_admin`);前端 `web/src/stores/permission.ts` 的 `roleCodes` 与 `ident.permissions` |

并集里只要有超管 ⇒ 显示层就按超管渲染 ⇒ 多身份用户切到低权限身份后
**界面纹丝不动**。执行层一直是对的 ⇒ 症状是"**看得见的都能点,点了才 403**"。

> ⚠️ **这不是 M147 造成的**。M147 之前后端就按当前身份判,
> 是显示层**一直**按并集算 —— 只是那时候矩阵还没真生效,两边都不准,
> 看不出"两套真相"(都放行)。M147 让执行层**收紧**之后,
> 两套真相才**显形**。

#### 显示层的四维口径(改完之后)

| 维度 | 口径 | 落点 |
|---|---|---|
| 资源启用态 | 只取 `is_active = true` | `seed.buildRolePolicies` / `service.roleResourceCodes` / `AccessibleResources`(M147-f 已统一) |
| 角色绑定 | 按 `sys_role.code` → `sys_role_resource` INNER JOIN | `service.resourcesForRole`(新) |
| **身份维度** | **按当前身份**,不是所有身份的并集 | `service.resourcesForRole` / `service.platformFlags` / 前端 `stores/permission.ts`(M149) |
| 权限码来源 | 当前身份的 `permissions` ∪ api 码 ∪ button 码 | 前端 `fetchAccessible`(M149) |
| **当前角色码** | **服务端权威值** `current_role_code`(= token claims 的 `role_code`),前端不再"猜" | `service.CurrentUserView.CurrentRoleCode`(M149-b) |

#### 改法

| 位置 | 改前 | 改后 |
|---|---|---|
| `service.AccessibleResources` | 身份列表的 role_code 并集;并集含超管 ⇒ 返回**全部**资源 | 按 `caller.RoleCode` 查 `sys_role` → `sys_role_resource` INNER JOIN;超管身份仍返回全部;**空角色码返回空集**(与执行层 `role:` 空角色 deny 一致) |
| `service.GetCurrentUser` 的资源树 | 同上(并集) | 同上 |
| `service.platformFlags` → `is_platform_super_admin` / `is_platform_ops` | 「身份列表里有没有」 | 「**当前身份**是不是」 |
| 前端 `stores/permission.ts` `fetchAccessible` | `roleCodes = identities.map(i => i.role_code)`;`permissions` 并所有身份的 | `roleCodes = [当前身份的 role_code]`;`permissions` 只并当前身份的。**找不到当前身份 ⇒ `roleCodes` 为空**(倒向拒绝) |

⚠️ **M149 阶段契约字段名一个没改**(`identities` / `current_identity_id` /
`is_platform_super_admin` 都在)⇒ 那一步**前端零改字段**,变的只是**派生口径**。
(**M149-b 之后就不是了** —— 新增了 `current_role_code`,见下面 M149-b 那节。)

⚠️ **`identities` 仍然返回全部身份** —— 身份切换器要的就是这张表;
改的只是「**按身份算权限/标志**」那部分。

⚠️ **角色绑定查表不过滤 `sys_role.is_active`** —— casbin 停用角色时
**不清策略行**,若这里过滤掉停用角色 ⇒「菜单没了但接口还能调」的**反向**不一致
(与「停用资源」那节的纪律相反:那次是资源停用要跟着收紧,
这次是角色停用**策略行还在**,过滤反而制造新的两套真相)。

#### 前端只改一处（订阅语义早就对了）

菜单树、按钮显隐、`RoleGuard`、`AuthButton` 全都已经是**订阅** store 的
(`usePermissionStore((s) => ...)`)—— M102/M103 那两轮已经把订阅语义修对了。
**口径一改,界面自动跟着变**。真正要改的只有 `fetchAccessible` 里那两行取值。

#### M149-b —「当前身份」不许靠猜(2026-11-01)

M149 把前端 `roleCodes` 改成「只认当前身份」,但**取值方式还是猜**:
`identities.find(i => i.id === current_identity_id)`。

猜会错在两处:

| | 场景 | 后果 |
|---|---|---|
| ① | 管理员改过该用户的身份 ⇒ `writeUserIdentitiesFromItems` 是**全量替换**(身份行 ID 全变)⇒ 旧 session 的 `current_identity_id` 在列表里**找不到** | `roleCodes` 变空 ⇒ 角色门控(`AuthButton` 的 `roleAnyOf`)整个失效 —— 按钮凭空消失 |
| ② | 库里角色改了、token 还是旧角色 | 前端显示**新**角色、后端按 token 里的**旧**角色判 ⇒ 看得见的点了 403 |

⇒ 服务端下发 `current_role_code`(= token claims 里那个 `role_code`,
**与 `decideAccess` 同一个来源**),前端优先用它;老后端不返时回退到「找当前身份」
(两条路都拿不到 ⇒ `roleCodes` 为空,倒向拒绝)。

服务端侧同步收口:`NewCurrentUserView` 的两个 bool 参数(`isSuper` / `isOps`)
收成**一个** `currentRoleCode` —— 平台标记只在 view 构造时按角色码**派生一次**
(唯一口径 `platformFlags`),`hasSuperRole` / `hasOpsRole` 两个薄壳删除
(零生产调用方;留着就是同一个判定做了两遍,迟早漂移)。

> ⚠️ **已知缺口(本期不做)**:管理员**降职**某用户后,该用户手里那张 access token

### 17.41 M150 — 工作台按业务域权限过滤(2026-11-01)

**用户报的现象**:切换身份后,工作台(看板)里
「没权限的指标还在显示、有权限的反而没显示」,而且**一堆接口 403**。

> 用户的原话:「切换身份时候 dashboard 里面没权限的不要显示,有权限的就显示,
> 否则会有很多接口没权限。」

#### 根因:两层,分别对应用户的两个诉求

| 层 | 用户说的 | 实际情况 |
|---|---|---|
| **接口闸门** | 「很多接口没权限」 | 看板 4 个端点挂 `rbac("dashboard", "read")`,而 `dashboard:read` **只绑给了 4 个角色** —— 另外 **9/13 的角色**点开工作台 = **4 个 403** |
| **内容过滤** | 「没权限的不要显示,有权限的就显示」 | service 层算的是**全平台统计**(业主总数 / 房屋总数 / 交付中 / …),**谁来都看得到全部 7 个指标** —— 一个域的权限都没有的角色,照样看到全平台业主数 |

两层都错,且**互相掩盖**:
第一层把 9 个角色挡在门外(他们连 403 都只看到 403,看不到"内容越界");
剩下 4 个角色能打开,但看到的是**全量**——
其中 `role_readonly` 是被 `filterByRead` 按 `:read` 后缀**顺手**捞到 `dashboard:read` 的
(与 M93 的 `dict:list` 一模一样的拧巴:真正该看的角色没有,不该看的只读员有)。

#### 改法:闸门开闸,内容按域过滤

**闸门**:`dashboard:read` 进 `authBaseCodes`(`internal/seed/seed.go`),
与 `dict:list` / `resource:accessible` 同一类 —— 「每个登录角色都该有的自服务能力」。

> 之所以敢开闸,是因为**内容已经在服务端按域过滤了**:
> 没有 `owner:list` 的角色,响应里**压根没有 `owner_total` 这个字段**。
> ⇒ **接口开闸 ≠ 数据放开**。这是本条与 M93 的关键差别。

**内容**:三层分工,判定**只在执行层**做一次。

```
handler 层  middleware.CanAccessQuiet(caller, principal, "owner", "list", 0)
                    ↓  6 个业务域各问一次
service 层  DashboardVisibility{code → bool}  →  只算允许的域
                    ↓  没权限的域**不出现在 JSON 里**(指针 + omitempty)
前端        字段缺省 = 这张卡片不画
```

| 位置 | 改动 |
|---|---|
| `internal/service/dashboard_visibility.go`(新) | 6 个业务域的码表 + `DashboardVisibility` 类型 |
| `internal/api/handler/v1/dashboard.go` | `dashboardVisibility()` —— 逐域调 `middleware.CanAccessQuiet` |
| `internal/api/middleware/rbac.go` | 新增 `CanAccessQuiet`(**同一个 `decideAccessOpt`,只关掉日志**) |
| `internal/service/dashboard.go` / `dashboard_impl.go` | `Overview` / `Trend` 的字段改**指针 / 切片 + `omitempty`**;每个指标 / 序列**独立判权限** |
| `internal/api/router/consistency.go` | 启动期检查 (4):域权限码必须在 `sys_resource` 里 |
| `internal/seed/seed.go` | `authBaseCodes` 加 `dashboard:read`;删掉 `platform_ops_lead` / `platform_ops` 里**重复**的显式绑定 |
| `web/src/api/dashboard.ts` | 所有字段改**可选**(`owner_total?: number`) |
| `web/src/pages/dashboard/domains.ts`(新) | KPI / 趋势的键清单(前端唯一一份) |
| `web/src/pages/dashboard/index.tsx` | 按「字段在不在」决定画不画;空态与失败态分开 |

#### ⚠️ 为什么用「字段缺省」而不是「数值 + 一个 visible 列表」

两种表示:

| | 缺点 |
|---|---|
| 数值 + visible 列表 | 两份表示**可能互相矛盾**(值在、列表里没有)⇒ 前端得决定信哪个,**判错一次就是"显示了没权限的数"** |
| **字段缺省**(本轮采用) | 只有一种表示:**有就是有,没有就是没有** |

⇒ 服务端**自己**把矛盾消灭掉,不留给前端判。

⚠️ **指针 + `omitempty` 的坑:值为 0 依然会出现在 JSON 里**
(`omitempty` 对指针只判 `nil`)—— 这正是要的:
「看得见但这个月一个都没有」≠「看不见」。
⇒ 前端判「在不在」**必须用 `!== undefined`,不能用真值判断**(真值判断会把 0 当成"看不见")。

#### ⚠️ 判定为什么走 casbin 而不是绑定矩阵

M149 的规矩:「**显示层不许自己算,必须读执行层那个权威字段**」。

| | 是谁的真相 | 用它判的后果 |
|---|---|---|
| `sys_role_resource`(绑定矩阵) | **显示层**的真相(前端菜单 / 按钮读它) | 运行时改绑定 → casbin 同步之间有窗口 ⇒ 看板显示了、接口却 403 |
| **casbin** | **执行层**的真相 | — |

看板是显示层 ⇒ 读 casbin ⇒ `middleware.CanAccessQuiet`
(super_admin 短路 / role+user 两路 EnforceEx / deny 一票否决 / grant 委托,一条不落)。

> ⚠️ **没有另写一份判定** —— `CanAccessQuiet` 是 `decideAccessOpt` 的薄包装,
> 只多了个 `logDeny` 开关(看板一次页面加载要问 6 个域,每个没权限的域都打一条
> WARN ⇒ 日志被"权限不足"刷爆,真出事时反而看不见)。
> 两套实现分叉是本仓明确记过的失败模式。

#### 刻意不做

- **不按前端自己的权限清单过滤** —— 前端能拿到的码来自 `/resource/accessible`
  (= **绑定矩阵**),而服务端算可见性用的是 casbin。
  两者在运行时改绑定的那个窗口里会分叉 ⇒ 前端自己判会出现"显示了但接口 403"。
  ⇒ 前端**只认"服务端给了没有"**。
- **不把待办 / 消息按业务域过滤** —— 它们是**自服务**内容:
  待办 = 派给我的问题 + 验房(`handler_id` / `assignee_id` = 我),
  消息 = 已发布公告(广播),与 `authBaseCodes` 里的 `inbox:*` 同一类
  (按 caller 收窄,不是越权)。
  少了它们,一个"只干活不看大盘"的角色连自己的待办都看不到。
- **不给 `dashboard:write` / 别的动作** —— 看板是**只读**页面。
- **不改 `menu.dashboard` 的绑定** —— 它本来就绑给每个登录角色(`commonMenus`),
  菜单可见与接口可调现在**对齐**了。
