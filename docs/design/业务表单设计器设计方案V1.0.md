## 0. 触发这件事的问题

### 0.1 需求原话

> 「做一个通用性的业务表单设计,用户设计完了以后,菜单就自动有该业务的相关增删改查接口、
> 同时后台还会有对应的列表管理界面,方便用户快速设计自己的业务管理功能。」

这句话拆开是**四件必须同时自动发生的事**:

| # | 产物 | 不自动会怎样 |
|---|---|---|
| 1 | 物理表 | 每次都要开发手工建表 |
| 2 | 增删改查接口 | 每次都要开发写接口 |
| 3 | 菜单 | 每次都要开发加菜单 + 配权限码 |
| 4 | 列表管理界面 | 每次都要开发写前端页 |

⚠️ **四件事的"自动"必须来自同一个源头** —— 如果菜单是自动的、接口是手写的,
或者反过来,两边一漂移就会出现"菜单点了 404"或者"接口能调但页面没有入口",
而这两条都是**不报错**的。

### 0.2 为什么不用现成的表单引擎

调研过(见 [`框架层未完成项清单v1.md` §2.7](./框架层未完成项清单v1.md)):

| 候选 | 结论 |
|---|---|
| SurveyJS `survey-creator-*` | **设计器收费**(378 版本 0 个 MIT 包)⇒ 不能进框架 |
| SurveyJS `survey-core` + `survey-react-ui` | MIT 免费,但**只有渲染器没有设计器** ⇒ 只能当"渲染别人设计好的表单"用 |
| Formily 官方设计器 | 锁死 antd4(停更 4 年)⇒ 与本仓 antd 5 体系冲突 |
| 自研 | 本模块的做法 —— 10 种字段类型够用,且与 RBAC / 动态表深度耦合 |

⇒ **自研动态集合**(`dynx` + `sys_dyn_*` + 动态物理表)。
它不是"表单引擎",是"**动态业务表**" —— 差别在于:它落的是**真实的数据库表**,
不是 JSON blob,所以可以直接被 SQL 查、被报表统计、被别的模块 JOIN。

### 0.3 与其它框架模块的关系

```
                  ┌──────────────────────────────────────┐
  用户在设计器里   │  业务表单设计器(dyn)                │
  设计一张表  ───► │  设计面 /system/dyn/**             │
                  │  数据面 /biz/dyn/:collection/**      │
                  └───────────────┬──────────────────────┘
                                  │ 自动产生
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        物理表 dyn_<code>   api 资源码 ×5        菜单 menu.dyn.<code>
        (+ 字段列 f_<key>)   dyn:<code>:*        path /dyn/<code>
                                  │                   │
                                  └─────────┬─────────┘
                                            ▼
                              前端 /dyn/:code 通用记录页
```

⇒ **数据范围(M155/M156)也能作用在动态集合上** —— 业务域是 `dyn:<集合编码>`,
一条一套规则,集合之间互相隔离(见 [§2.8](#28-数据面的行级权限))。

## 1. 这个模块是什么

### 1.1 两个面

| 面 | 谁在用 | 路径前缀 | 资源码形状 | 段数 |
|---|---|---|---|---|
| **设计面** | 管理员(设计业务表) | `/rapid-admin/v1/system/dyn/**` | `dyn:design:collection:*` / `dyn:design:field:*` / `dyn:design:type:list` | **四段** |
| **数据面** | 业务人员(录数据) | `/rapid-admin/v1/biz/dyn/:collection/**` | `dyn:<集合编码>:<动作>` | **三段** |

⚠️ **两套码形状不同,撞不了** —— 集合编码里不可能出现 `:`(`dynx.ValidateCode` 挡着),
所以数据面永远三段。

⚠️ **为什么设计面必须四段** —— 若设计面也用三段(`dyn:collection:list`),
用户建一个叫 `collection` 的集合,它的 `dyn:collection:list` 与设计面的
"列出所有集合"就是**同一个字符串** ⇒ 建表的人顺手拿到了读全部集合定义的能力。
⇒ 四段与三段**形状不同**,撞不了。

### 1.2 设计完之后自动有什么

建一个集合(比如编码 `inspection`)会自动产生:

| 产物 | 形态 | 谁登记的 |
|---|---|---|
| 物理表 | `dyn_inspection`(用户列统一带 `f_` 前缀,如 `f_device_name`) | `dyn_impl.go` 建表 |
| 5 条 api 资源码 | `dyn:inspection:list` / `:read` / `:create` / `:update` / `:delete` | `dyn_resource.go` |
| 1 个菜单 | `menu.dyn.inspection`,路径 `/dyn/inspection`,父节点 `menu.dyn`("自定义业务") | `dyn_resource.go` |
| 1 个前端页面 | `/dyn/:code` —— 列表 / 搜索 / 新增 / 编辑 / 详情 / 删除**全自动** | 前端静态路由 |

加一个字段会自动产生:一个物理列 + 一列表格 + 一个表单控件 + 一条校验规则。

### 1.3 名字的形状

| 东西 | 规则 | 来源 |
|---|---|---|
| 集合编码 `code` | `^[a-z][a-z0-9_]{0,63}$` | `dynx.ValidateCode` |
| 字段标识 `field_key` | 同上,且**不能是** `id` / `owner_id` / `created_at` / `updated_at` / `deleted_at` | `dynx.ValidateFieldKey` |
| 物理表名 | `dyn_<集合编码>` | `dynx.PhysTableName` |
| 物理列名 | `f_<字段标识>` | `dynx.ColumnName` |
| 数据面资源码 | `dyn:<集合编码>:<动作>` | `dynx.RecordCode` |

## 2. 设计

### 2.1 数据模型

#### `sys_dyn_collection` —— 集合定义

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uint64 | 雪花 ID |
| `code` | varchar(64) **唯一** | 集合编码,**不可改** |
| `name` | varchar(128) | 集合名称(中文,可改) |
| `description` | varchar(255) | 描述 |
| `phys_table` | varchar(64) | 物理表名,建表那一刻定死 |
| `owner_scoped` | bool | 行级权限:只看得见自己创建的记录 |
| `public_read` | bool | 公开只读:未登录可读(2026-11-03;与 `owner_scoped` 互斥,见 [§2.8](#28-数据面的行级权限)) |
| `icon` / `sort` | | 菜单图标与排序 |
| `is_active` | bool | 停用后菜单与权限码一并停用 |
| `deleted_at` | | 软删 |

#### `sys_dyn_field` —— 字段定义

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uint64 | 雪花 ID |
| `collection_id` + `field_key` | **联合唯一索引** `uk_dyn_field` | 同一集合里字段标识不能重复 |
| `label` | varchar(128) | 中文显示名(可改) |
| `column` | varchar(64) | 物理列名 `f_<field_key>` |
| `type` | varchar(32) | 字段类型(见 [§2.3](#23-字段类型注册表)) |
| `required` | bool | 是否必填 |
| `options` | text | `select` / `multiselect` 的选项集(JSON 文本) |
| `default_value` | varchar(255) | 默认值(文本形态,写入时按类型归一化) |
| `sort` | int | 排序 |
| `is_active` | bool | 停用后列表页与表单里不再出现,**物理列保留** |

⚠️ **两张表都是软删** —— 删集合/删字段只停用,物理表与数据保留(见 [§5.4](#54-停用与恢复))。

### 2.2 记录的 JSON 形状

物理表上的行是「系统列 + 用户列」,对外的 JSON 是:

```json
{
  "id": "1730000000000000000",
  "owner_id": "1001",
  "owner_name": "张三",
  "created_at": "2026-11-01T00:30:00Z",
  "updated_at": "2026-11-01T00:30:00Z",
  "<字段标识>": <值>
}
```

⚠️ **JSON 的键是字段标识,不是物理列名(`f_xxx`)** ——
前端拿到的是用户写的名字,不用知道物理层长什么样。

⚠️ **`owner_name` 不是物理列** —— 物理表上只有 `owner_id`(创建人,建记录时写入,
之后不覆盖)。`owner_name` 是**读的时候**从 `sys_user` 补出来的显示名,
口径与配置中心的"操作人"一致:`真实姓名 → 昵称 → 账号`。
取不到(用户被删了 / id 是 0 / 查表失败)时是**空串**,前端回落到显示 `owner_id`。

⇒ 为什么不在前端解析:前端唯一能拿到用户列表的接口是 `GET /system/users`,
它要 `user:list` 权限 —— **业务人员没有**,于是这一列对业务人员永远是空的。
⇒ 也不能加物理列:显示名会随用户改名而变,存进业务表就是第二份真相。

⚠️ **字段标识不能叫 `id`** —— 服务层"先写系统列、再遍历字段覆盖",后写的赢 ⇒
用户字段叫 `id` 会把系统 id 盖掉,之后所有按 id 的操作全错位。

### 2.3 字段类型注册表

一个字段的**三种行为挂在同一张表上**:落成什么列类型(DDL)、前端提交的值怎么变成能存的值
(归一化)、存进去的值怎么变回前端能显示的值(反归一化)。

⚠️ **这三个问题必须由同一张表回答** —— 各写各的就会出现
"DDL 说它是 VARCHAR、归一化却塞了个 int64"这种分叉,
表现是"存进去看着对、查出来类型变了",而且**不报错**。

| 类型 | 中文名 | MySQL | SQLite | 存进去的样子 | 读出来 |
|---|---|---|---|---|---|
| `text` | 单行文本 | VARCHAR(255) | TEXT | 文本 | 文本 |
| `longtext` | 多行文本 | TEXT | TEXT | 文本 | 文本 |
| `int` | 整数 | BIGINT | INTEGER | 整数 | 整数 |
| `number` | 小数 | DOUBLE | REAL | 小数 | 小数 |
| `bool` | 开关 | TINYINT(1) | INTEGER | `0` / `1` | 布尔 |
| `date` | 日期 | VARCHAR(10) | TEXT | `"2026-11-01"` | `"2026-11-01"` |
| `datetime` | 日期时间 | VARCHAR(32) | TEXT | `"2026-11-01T00:30:00Z"` | 同左 |
| `select` | 单选 | VARCHAR(255) | TEXT | 选项值文本 | 选项值文本 |
| `multiselect` | 多选 | TEXT | TEXT | JSON 数组文本 | `string[]` |
| `json` | JSON | TEXT | TEXT | JSON 文本 | **已解析的 JSON 值** |
| `file` | 附件 | VARCHAR(512) | TEXT | 文件 key 文本 | 同左(见 [§2.9](#29-字段类型-file附件)) |

⚠️ **MySQL 的 `number` 用 DOUBLE 而不是 DECIMAL** ——
DECIMAL 列经 go-sql-driver 读出来是 `[]byte("123.450000")`,
前端拿到的是字符串而不是数字;DOUBLE 直接给 float64。

⚠️ **json 列在两个方言里都是 TEXT** —— MySQL 的 JSON 类型要求插入的是
**合法 JSON 文档**,用户随手输入的半截 JSON 会直接报错;
TEXT 只存字符串,校验挪到归一化那一层(统一口径)。

⚠️ **类型清单由后端下发,前端不许硬编码一份** ——
`GET /system/dyn/field-types` 是唯一真相(见 [§4.3](#43-前端不许硬编码的东西))。

### 2.4 建表:DDL 怎么来的

建集合时按字段定义生成 `CREATE TABLE`,规则:

- 表名 `dyn_<code>`
- 系统列:`id`(BIGINT PK)、`owner_id`、`created_at`、`updated_at`、`deleted_at`
- 用户列:`f_<field_key>`,类型取上表
- ⚠️ **用户列必须可空** —— 见 [§5.5](#55-为什么字段列必须可空)

加字段时 `ALTER TABLE ... ADD COLUMN`。
⚠️ **SQLite 不支持 `ALTER COLUMN` 改可空性 / 改类型**,MySQL 支持 ——
这是"字段类型不可改"的物理原因(见 [§5.3](#53-不可改的三样东西与迁移路径))。

### 2.5 资源码与菜单的运行期登记

集合建好之后,`registerCollectionResources` 同步做三件事:

1. 建 5 条 api 资源码 `dyn:<code>:list / read / create / update / delete`
2. 建 1 个菜单资源 `menu.dyn.<code>`(path `/dyn/<code>`,父节点 `menu.dyn`)
3. 把这些资源**绑给创建者当前的角色**,并同步 casbin 策略行

⚠️ **必须绑给创建者的角色** —— 菜单是数据驱动的
(前端按 `sys_resource` 里 `type=menu` 的行渲染),
资源没绑给任何角色 ⇒ 角色的可访问集合里没有它 ⇒ **侧边栏不显示**。
而"设计了业务表却找不到入口"是最难排查的一类问题(不报错,就是没有)。

⚠️ **绑完必须 `syncRolePolicies`** —— 绑定表(`sys_role_resource`)只是"给界面看的",
真正放行的是 casbin 策略行。不同步的话:
管理员勾了权限 → 菜单出现了 → 点进去 403。
而且**没有任何报错** —— casbin 只是"没匹配到策略行",正常返回 false。

⚠️ **停用集合必须同步 casbin 策略行** —— `sys_resource.is_active=false`
只让**菜单消失**(前端按 `is_active` 过滤),
casbin_rule 里的 `dyn:<code>:list` 还在 ⇒ 直接打接口仍然放行。
那就变成"菜单没了但接口还能调"的反向不一致。

⚠️ **资源码是运行期生成的,不是 seed 里写死的** —— seed 是编译期的东西,
而集合是运行期才有的。写死就等于"业务表必须提前设计好"—— 那就不是设计器了。

⇒ **代价**:启动期一致性检查(`consistency.go`)扫不到这些码 ——
它扫的是 `rbac()` 闭包在注册期记的账,而动态路由走的是 `middleware.CanAccess`
(资源码要等请求进来才知道)。**这不是漏洞**:一致性检查保证的是
"启动时写死的码与 seed 对得上",运行时生成的码不在那个范畴里。

### 2.6 权限模型

#### 设计面 —— 编译期固定

| 资源码 | 路由 |
|---|---|
| `dyn:design:collection:list` | `GET /system/dyn/collections` |
| `dyn:design:collection:read` | `GET /system/dyn/collections/:id` |
| `dyn:design:collection:create` | `POST /system/dyn/collections` |
| `dyn:design:collection:update` | `PATCH /system/dyn/collections/:id` |
| `dyn:design:collection:delete` | `DELETE /system/dyn/collections/:id` |
| `dyn:design:field:list` | `GET /system/dyn/collections/:id/fields` |
| `dyn:design:field:create` | `POST /system/dyn/collections/:id/fields` |
| `dyn:design:field:update` | `PATCH /system/dyn/fields/:id` |
| `dyn:design:field:delete` | `DELETE /system/dyn/fields/:id` |
| `dyn:design:type:list` | `GET /system/dyn/field-types` |

⚠️ **10 条路由,每条恰好一个 `rbac()`** —— 一致性检查要求
"受保护路由数 == `rbac()` 调用次数",多挂少挂都启动失败。

#### 数据面 —— 运行期拼出来

`dyn:<集合编码>:<动作>`,集合编码由用户起 ⇒ **编译期枚举不了**。

⇒ 后端守卫按集合判定(`dynx.RecordModule(code)` + `middleware.CanAccess`),
前端按运行期拼出来的字符串问权限 store
(`web/src/api/dyn.ts` 的 `dynRecordPerm()`)。

⚠️ **动作清单住在原语层**(`internal/pkg/dynx/actions.go`),
同时被 service 侧(登记码)与 handler 侧(拼码)消费 ——
两边必须同源,否则会**静默失权**(M151 真踩过,见 [§9](#9-落地记录))。

⚠️ **表单结构接口归 `list` 管,不另开一个码** ——
能看列表却看不到字段,页面就是一张空表格 + 一个 403 弹窗;
而表单结构就是"这个集合有哪些字段",对能看记录的人没有信息增量。

### 2.7 谁有权限设计业务表单

| 角色 | 设计面 `dyn:design:*` | 设计器菜单 `menu.system.dyn` | 数据面 |
|---|---|---|---|
| **超级管理员** `role_super_admin` | ✅ 全部 | ✅ | ✅ 全部集合 |
| **用户管理员** `role_user_admin` | ✅ 全部 | ✅ | 建集合时自动绑给**创建者当前角色** |
| 其它角色 | ❌ | ❌ | 建集合时自动绑给创建者当前角色 |

⚠️ **为什么用户管理员也能设计业务表** ——
他已经有 `resource:create` + `role:assign`:
能凭空造一个资源码再绑给任意角色 ⇒ 权限层面早就是超管了。
不给设计器只是"换个名字再给一遍同样的权力",不给反而是
"他能给自己开任意权限却不能建业务表"的自相矛盾。

⚠️ **只给设计面(`dyn:design:*`)** —— 数据面是**运行期**按集合生成的码,
建集合时自动绑给创建者当前角色,**不在 seed 里写死**。

⇒ **实际用法**:用户管理员设计一张表 ⇒ 表的 5 个数据面码自动绑给他自己 ⇒
他自己就能录数据、别人要用就去「角色管理」页把 `dyn:<集合码>:*` 勾给对应角色。

### 2.8 数据面的行级权限

两层,**互相独立**:

| 层 | 机制 | 谁配 |
|---|---|---|
| **集合级** | `owner_scoped` = true ⇒ 普通业务人员只看得见**自己创建的记录** | 建集合时勾(集合属性) |
| **角色级** | 数据范围规则(M155/M156):全部 / 本项目 / 本部门 / 本部门及下级 / 仅本人 / 自定义 | 「角色管理」页 → 数据范围 |

⚠️ **超管不受 `owner_scoped` 限制** —— 超管在其它模块里本来就绕过一切,
这里保持一致(否则超管建的表自己都看不到数据)。

⚠️ **数据范围作用在动态集合上时,业务域是 `dyn:<集合编码>`** ——
不是 `dyn`。集合之间必须互相隔离:
给"巡检"集合配的行级规则**不能**影响"报修"集合。
这是 M156 由 `dynGuard` 显式写进 ctx 的原因(见 `server/internal/service/dyn_records.go`
与 `server/internal/api/handler/v1/dyn.go`)。

#### 公开只读(2026-11-03)

第三层,与前两层正交但**与 `owner_scoped` 互斥**:

集合 `public_read = true` 时,任何人**未登录**即可经公开镜像读:

```
GET /rapid-admin/v1/public/dyn/:collection/schema
GET /rapid-admin/v1/public/dyn/:collection/records
GET /rapid-admin/v1/public/dyn/:collection/records/:id
```

口径(为什么这么设计):

- **写路径没有公开版** —— 匿名可写是事故,不是特性;公开只读集合的写
  仍然走正常数据面 + 登录 + `dyn:<code>:create|update|delete`。
- **与 `owner_scoped` 互斥** —— 匿名调用者没有 owner,"公开"叠加
  "只看自己创建"要么全裸要么全空,语义就是错的。service 建 / 改集合时
  按生效值校验,设计器 UI 同步禁掉组合。
- **闸门在 service 层**(`PublicReadCollection`):集合在用 + public_read +
  非 owner_scoped,不满足一律 **401**,不区分"集合不存在"和"不能公开读"
  —— 不给枚举探测留信号。
- **公开路径强制看正常视图**:`trash=true` 被压掉,匿名请求翻不了回收站
  (trash 是登录用户的恢复工具);软删记录详情照常 404。
- **合成调用方** `RoleCode="public"` 什么权限都没有 ⇒ relation 字段选项
  读不到时照常降级(`option_readable=false`),不用为新 caller 写特判。
- 路由挂在 `/rapid-admin/v1/public` 组(已有 IP 限流 60 次/分),不需要进
  `rbacExemptRoutes` 一致性表(公开路由本就不参与受保护路由计数)。

### 2.9 字段类型 `file`(附件)

**需求原话**:「表单设计中的字段类型,应该加一个文件类型,可以复用现在的文件系统上传文件,
然后这个字段里面存储上传后的文件路径,不带域名的路径。」

#### 存的是什么

字段列里存的是**文件在存储树里的 key**:

```
rapid-admin/1844/dyn/0/1712345678-a1b2c3d4-户型图.pdf
└ 路径根     └ uid  └ biz └ fid └ 对象名
```

⚠️ **不存 URL,也不存"挂载点 + key"那种路径** ——
URL 里带域名(本地部署是 `/rapid-admin/...`,CDN 部署是 `https://cdn.../rapid-admin/...`),
域名会变;挂载点是 `file.path_root` 推出来的,也会变。
而 key 是**两种 provider 下形状一致**的那一个:
local 的直链 = `/` + key,OSS 的直链 = `<CDN 前缀>` + `/` + key。

⚠️ **key 的第一段是路径根词**(`file.path_root`,默认 `rapid-admin`)——
改它等于换了一棵树,已存的文件字段值会全部失效
(与 M80 的口径一致:改路径根是一次**迁移**,不是一次配置)。

#### 类型注册表上的一行

| 类型 | 中文名 | MySQL | SQLite | 存进去的样子 | 读出来 |
|---|---|---|---|---|---|
| `file` | 附件 | VARCHAR(512) | TEXT | 文件 key 文本 | 同左 |

⚠️ **长度对齐 `sys_file.file_key`(512)** —— 那边是 `varchar(512)`,
这里短一截就**存不下**(而不是截断),用户选了文件却存不进去。

#### 归一化(写)

`dynx.normalizeFile` 只做**形状校验**,不碰文件系统:

| 输入 | 结果 |
|---|---|
| `""` / `null` | 空(没填) |
| `https://cdn.x.com/rapid-admin/...` | **400**(带域名 ⇒ 不是"不带域名的路径") |
| `rapid-admin/../etc/passwd` | **400**(含 `..`) |
| `C:\xxx` | **400**(含反斜杠) |
| 超过 512 字节 | **400** |
| 其它非空文本 | 原样(去首尾空白) |

⚠️ **形状校验挡不住"指向别人的文件"** ——
key 本身就是 M80 意义上的"秘密"(不可猜),谁能写进字段谁就能分享这个文件。
这是 M80 单桶单树模型的固有性质,不是本功能引入的(见下面的「隐私口径」)。

#### 读出来:记录视图里多一个 `_files` 映射

字段列里只有 key,**原文件名与直链不在列里** ⇒ 读记录时由后端另外解析:

```json
{
  "id": "1730000000000000000",
  "attachment": "rapid-admin/1844/dyn/0/1712345678-a1b2c3d4-户型图.pdf",
  "_files": {
    "attachment": {
      "name": "户型图.pdf",
      "url": "/rapid-admin/1844/dyn/0/1712345678-a1b2c3d4-%E6%88%B7%E5%9E%8B%E5%9B%BE.pdf"
    }
  }
}
```

⚠️ **`_files` 不是字段** —— 字段标识必须以小写字母开头(`dynx.ValidateFieldKey`),
所以 `_files` 永远不可能与用户字段撞名。
⚠️ **写入时忽略它** —— 「读出来 → 改两个字段 → 原样提交」是很常见的用法,
回传 `_files` 不该被当成"未知字段"拒掉。
⇒ 写入路径**忽略所有以 `_` 开头的键**(字段标识规则保证没有真字段长这样)。

⚠️ **解析失败要降级** —— 文件被删了 / key 写错了 / 文件服务没装 ⇒
那一项**不出现**在 `_files` 里,前端显示原始 key 并标成「文件已失效」,
**不让整页记录失败**(旁路纪律)。

#### 前端控件

- 录入:「上传」按钮(走 M80 的 `POST /biz/files`,权限码 `file:upload`)+ 文件名 + 「清除」
- 显示:文件名做成链接,指向 `_files` 里解析出来的直链
- ⚠️ **上传必须走文件服务,不许让用户手填路径** ——
  手填就是让用户自己声明"这个文件存在",后端没法保证它真的存在。

#### 隐私口径(⚠️ 必读)

**字段的值就是文件的直链** ⇒ **能读这条记录的人就能拿到这个文件**。

M80 的隐私模型是「**私密靠 key 不可猜**」(整棵树挂在静态路由上,没有私有目录,
没有签名 URL)。把 key 写进一条业务记录,等于**把这份不可猜性转发给这条记录的每一个读者**。

⇒ 需要强私密性的场景(合同、身份证、工资单)不要用 `file` 字段,
用有独立读权限的专门模块。

#### 已知缺口

| 缺口 | 现状 | 计划 |
|---|---|---|
| 值的原文件名 | ✅ 列里只有 key,读记录时由后端解析进 `_files` | — |
| 存在性校验 | ✅ 写入时校验"key 存在"(查不到 → 400「文件不存在」) | ⚠️ 解析服务不可用时降级放行(只做形状校验) |
| 文件被删后的值 | ✅ 前端显示原始 key +「文件已失效」 | — |
| 附件的归属 | ⚠️ 任何能读这条记录的人都能拿到这个文件(见上面的「隐私口径」) | 需要强私密性的场景走有独立读权限的专门模块 |

### 2.10 单选 / 多选的选项来源:关联系统表

**需求原话**:「字段类型的单选多选,除了现在手动添加选项之外,应该还可以关联系统中的某些表,
这个就非常要注意关联表的读取权限的相关配置,不然读不到对应的表格数据。」

#### 两种来源

| 来源 | 选项从哪来 | 谁定 | 存进数据库的值 |
|---|---|---|---|
| **手工** | 设计器里逐条填 | 设计者 | 选项值文本 |
| **关联表** | 读系统表 | 设计者选一张表 | 那张表的行 id(字符串) |

⚠️ **两种来源互斥** —— 一个字段要么手工填,要么关联一张表。
⚠️ **关联表的选项不落库** —— 落库的只是"从哪张表取"这一条配置,
选项是**读的时候现查的** ⇒ 表里新增一行,表单里立刻多一个选项。

#### 配置长什么样(存在 `sys_dyn_field.options` 的 JSON 里)

```json
{
  "choices": [],
  "source": {"kind": "table", "key": "user"}
}
```

⚠️ **`choices` 为空 + `source` 非空** = 关联表来源。

⚠️ **`MarshalOptions` 以前在 `choices` 为空时返回空串** ——
那样**关联表的配置会被静默丢掉**(字段建好了,却变成一个没有任何选项的单选,
而且前端不报错)。⇒ 已改:有 source 时一定序列化出来。

⚠️ **选项集校验要放行"只有 source 没有 choices"** ——
`validateFieldShape` 原本硬性要求「单选/多选字段必须配置选项」,
不放松就**根本建不出这个字段**。

#### 可关联的表(注册表,写死在后端)

| key | 表 | 取值列 | 显示名列 | 需要的资源码 | 数据范围 |
|---|---|---|---|---|---|
| `user` | `sys_user` | `id` | `real_name → nickname → username` | `user:list` | 按 `user` 业务域(本部门 / 仅本人) |
| `role` | `sys_role` | `id` | `name` | `role:list` | 不限(角色是平台级配置) |
| `dept` | `sys_department` | `id` | `name` | `dept:list` | 不限 |

⚠️ **注册表是白名单,不是"任意表"** ——
让用户填表名等于把 SQL 的表名交给用户拼 ⇒ 那是注入面。
要加表 = 在注册表里加一行(带它需要的资源码与数据范围口径)。

⚠️ **动态集合(另一个 `dyn_<code>`)暂不支持作为来源** ——
它的取值列与显示名列都是**用户自己定的字段**,还要再套一层"选哪一列"的界面,
复杂度高一个量级。⇒ 记在 [§10](#10-遗留项)。

#### ⚠️ 权限:这是本节最要紧的一段

关联表的选项**是在读表单结构时现查的**,所以"能不能读到那张表"这件事
必须在**读之前**判,而不是"查了再说"。

三层闸门,顺序固定:

1. **资源码闸门(能不能调那张表的列表接口)**
   - `user` 来源要 `user:list`,`role` 来源要 `role:list`,`dept` 来源要 `dept:list`
   - 判定走 `middleware.CanAccess` —— **执行层的唯一一份实现**。
     ⚠️ **判定在 handler 层做**:`internal/api/middleware` 依赖 `internal/service`,
     反过来 import 就是循环依赖 ⇒ service 层不自己判权限,
     由 handler 判完把结果传下去(与看板可见性同一套路)。
   - ⚠️ **判定的对象是"当前调用方",不是"设计者"** ——
     设计师配了 `user` 来源,不代表录数据的业务员有 `user:list`。
     业务员没有 ⇒ 他的表单里这个字段的**下拉框是空的**,但**记录页不报错**。
2. **数据范围闸门(能看到这张表的哪些行)**
   - `user` 来源按 `user` 业务域套数据范围(与「用户管理」页同一套口径):
     配了"本部门"就只看到本部门的人。
   - `role` / `dept` 是平台级配置表,不套行级范围。
3. **降级闸门(读不到怎么办)**
   - ⚠️ **读不到就返回空选项 + 一个"来源不可读"的标记,绝不让整个表单结构失败** ——
     一个字段的选项读不到,不该让整页列表白屏(旁路纪律:装饰性的东西取不到就降级)。
   - 前端据此显示提示:「该选项来自系统用户,当前账号没有 `user:list` 权限」。

⇒ **三层的顺序不能换** —— 先判资源码(能不能读),再套数据范围(能读哪些),
最后才查表。反过来(先查表再判权限)等于"先偷看再问能不能看"。

#### 写入路径:为什么不校验"这个值在不在表里"

手工选项集在写入时**校验成员资格**(值必须在那份选项集里)——
因为手工选项集是"死的",写进去的值永远应该在里面。

关联表是"活的":表里的行会被删。⇒ 若也校验成员资格,
**一条历史记录只要它引用的那一行被删了,这条记录就再也存不进去任何修改**
(用户只想改个备注,后端报"不是合法选项")—— 这比"多存了一个野值"严重得多。

⇒ **关联表来源不做成员资格校验**(只校验值的形状:非空字符串)。
⚠️ **代价**:改个请求就能存进表里不存在的 id ⇒ 列表页那一格会显示空白标签。
与手工选项集同样的表现,但换了个原因(前者是"设计错了",后者是"表变了")。

⚠️ **要真的挡住,得做外键 + 级联**(本模块明确不做,见 [§7](#7-明确不做))。

#### 设计器里怎么配

单选 / 多选字段的选项区多一个"来源"切换:

- **手工添加**(默认,行为不变)
- **关联系统表** ⇒ 选一张表
  (下拉里只列**当前账号读得了**的表;读不了的标灰并说明缺哪个权限码)

#### 新增接口

`GET /system/dyn/relation-sources` —— 列出可关联的表 + 当前账号能不能读。

⚠️ **它属于设计面** ⇒ 权限码 `dyn:design:type:list`(与字段类型词表同一档)。

### 3.1 设计面(11 条)

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|

| GET | `/system/dyn/collections/:id/fields` | `dyn:design:field:list` | 字段列表(**含已停用的**) |
| POST | `/system/dyn/collections/:id/fields` | `dyn:design:field:create` | 新建字段(加列) |

| DELETE | `/system/dyn/fields/:id` | `dyn:design:field:delete` | 删字段(软删,物理列保留) |

⚠️ **`/fields` 含已停用的字段** —— 设计器要看得见"被停用了"才能恢复它。

⚠️ **`/relation-sources` 与 `/field-types` 同一档权限码** ——
两者都是"设计期用得上的词表",粒度一致;拆成两个码只会让配置页多一列可勾项
(勾漏一个就是"能建字段但配不了来源")。

### 3.2 数据面(6 条)

| 方法 | 路径 | 权限码(运行期) | 说明 |
|---|---|---|---|
| GET | `/biz/dyn/:collection/schema` | `dyn:<code>:list` | 表单结构(字段定义) |
| GET | `/biz/dyn/:collection/records` | `dyn:<code>:list` | 记录列表(keyword / owner / order_by / 分页) |

⚠️ **数据面不挂 `rbac()` 中间件** —— 集合编码是运行期的,挂不上编译期常量式的 `rbac()`。
权限在 handler 里按集合判(`dynGuard`),
这 6 条路由挂在 `rbacExemptRoutes` 豁免清单里(启动期一致性检查只数个数)。

### 3.3 公开只读镜像(3 条,2026-11-03)

集合 `public_read = true` 且非 `owner_scoped` 时,**未登录**可读(闸门见 [§2.8](#28-数据面的行级权限) 的「公开只读」):

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/public/dyn/:collection/schema` | 无(闸门在 service) | 表单结构(与登录版同形状,多 `public_read` 字段) |
| GET | `/public/dyn/:collection/records` | 无 | 记录列表(参数与登录版同一套,含筛选 DSL;`trash` 被强制压掉) |

不满足闸门一律 401;写动作没有公开版。`@rapid-admin/dyn-sdk` 的读方法
在未登录时自动走这三个路径(见 `js-sdk/README.md` 的「公开只读」一节)。

## 4. 前端

### 4.1 设计器页 `/system/dyn`

**文件**:`web/src/pages/system/dyn/index.tsx`(设计器)+ `OptionsEditor.tsx`(选项集编辑)

**布局**:左集合列表(搜索 + 选中) / 右选中集合的字段表
—— 与「部门管理」页同一套结构(左树右详情),因为交互形状一样:**左边选一个,右边编辑明细**。

**能做的**:

| 操作 | 说明 |
|---|---|
| 新建集合 | 填编码、名称、图标、排序、**是否仅自己可见**、**是否公开只读**(两个开关互斥,前端同步禁掉组合) |
| 改集合 | 名称 / 描述 / 图标 / 排序 / owner_scoped / public_read(**编码锁死**) |
| 删集合 | 软删 + 停用菜单与权限码 |
| 新建字段 | 填字段标识、显示名、类型、是否必填、默认值、排序 |
| 改字段 | 显示名 / 必填 / 默认值 / 排序(**标识与类型锁死**) |
| 删字段 | 软删,物理列保留 |
| 选项集 | 单选 / 多选的"值 = 存进数据库的,显示名 = 给人看的" |
| **选项来源** | 单选 / 多选多一个"来源"切换:**手工添加** / **关联系统表**(见 [§2.10](#210-单选--多选的选项来源关联系统表)) |

⚠️ **"要不要选项集"要跟后端的 `has_options` 走,不许前端写死类型名** ——
设计器现在的判断是 `fieldTypeDraft === 'select' || fieldTypeDraft === 'multiselect'`,
后端加一种带选项的类型(比如"标签")就会被漏掉 ⇒ **选项区不出现**,
用户选了那个类型却发现没有选项可配。

⚠️ **可关联的系统表由后端下发**(`GET /system/dyn/relation-sources`)——
前端不许自己抄一份表名清单:后端注册表改了而前端没改,
就是"设计器里能选一张表,后端不认识" ⇒ 建字段时报一个看不懂的错。

⚠️ **不可改的东西前端必须跟着后端一起"锁死"** ——
集合编码 / 字段标识 / 字段类型这三样,后端 DTO 里**根本没有对应字段**
(改了会被静默忽略)。前端必须自己锁住输入框,
否则用户填了个新编码、以为改成功了,下次进页面又变回旧值,数据还对不上。

### 4.2 通用记录页 `/dyn/:code`

**文件**:`web/src/pages/dyn/index.tsx`(列表页)+ `recordForm.ts`(值 ⇄ 表单 的纯规则)

**能力**:搜索 / 新增 / 编辑 / 详情 / 删除,列与表单**全部按字段定义生成**。

⚠️ **列的顺序是「用户字段 → 创建人 → 创建时间 → 更新时间 → 操作」** ——
「创建人」这一列取的是 `owner_name`(见 [§2.2](#22-记录的-json-形状)),
取不到时回落到显示 `owner_id`。⚠️ **这一列不是物理列**,
所以物理表不用动 —— 加列 = 给每张动态表改 DDL,而动态表是**运行期**建的,改不动。

**「API 接入」按钮(搜索区右侧)** —— 点开是一个弹窗,把这个集合怎么用 API 接进去
一次性说清楚:6 条接口的路径 + 各自要的权限码 + 请求体的键 + 一条能直接跑的 curl。

⚠️ **弹窗里的内容由 `web/src/pages/dyn/apiGuide.ts` 生成,不在组件里写死** ——
路径 / 权限码 / 请求体都得跟着集合走(集合编码是用户起的、字段是运行期的),
组件里写死一份就等于"文档说的"和"真的接口"会分叉。
⚠️ **路径与后端路由的对应关系由单测守着**(`web/src/pages/dyn/__tests__/apiGuide.test.ts`
把弹窗里印的路径逐条打向后端 `router.go` 匹配)—— 抄错路径这种错在运行时**完全静默**:
弹窗照常渲染,页面照常工作,只有抄走的人拿到 404。

⚠️ **`/dyn/:code` 路由刻意不加 `RoutePermissionGuard`** ——
集合编码是**用户起名、运行期才有的**,权限码 `dyn:<集合码>:<动作>` 编译期枚举不了
⇒ 任何写死的 `anyOf` 都表达不了"这个集合能不能看"。
⇒ **闸门在后端**(`dynGuard` → `middleware.CanAccess`),
前端按运行期拼出来的权限码控制**按钮的可见性**。

**`file` 字段(附件)** —— 表单里是一个「上传」按钮 + 文件名 + 「清除」,
列表格里是一列文件链接。

⚠️ **上传走 M80 的 `POST /biz/files`(权限码 `file:upload`)** ——
不新造一条上传通道。⚠️ **没有 `file:upload` 的角色看不到上传按钮**
(前端按权限码控可见性),但**看得见已有的文件名**(读是另一件事)。

⚠️ **文件名与直链来自后端的 `_files`,不是字段值本身** ——
字段值是 key,看不出原文件名;前端不许自己猜 key 的命名规则去还原文件名
(那是把后端的命名实现抄一份,改了就对不上)。

**关联表来源的单选 / 多选** —— 下拉框的选项是**后端在读表单结构时查出来的**,
前端不自己查那张表。

⚠️ **选项读不到时下拉框是空的,但页面不报错** ——
后端会把这个字段标成"来源不可读"并附上缺哪个权限码,
前端据此显示一句提示。⚠️ **这不是 bug,是设计**:
读不到选项的字段只能"看不能选",而历史记录里已存的值仍然显示得出来。

### 4.3 前端不许硬编码的东西

| 东西 | 唯一真相 | 前端怎么拿 |
|---|---|---|
| 字段类型词表 | `internal/pkg/dynx/dynx.go` 的 `specs` | `GET /system/dyn/field-types` |
| 可关联的系统表 | `internal/pkg/dynx/relation.go` 的来源注册表 | `GET /system/dyn/relation-sources` |

⚠️ **前端镜像的正则必须与后端逐字一致** ——
不一致的症状是"前端放行了一个后端拒绝的编码",后端返 400,用户看不懂。

⚠️ **新增字段类型还要顺手改前端的类型映射** ——

**未知类型一律当单行文本**(不是当"不支持"而是当文本)——

## 5. 维护与升级

> **这一节是本文件存在的主要理由** —— 前四节讲"它是什么",
> 这一节讲"半年后有人接手时怎么改它"。

### 5.1 加一种字段类型(最常见的改动)

**只改一处** —— `internal/pkg/dynx/dynx.go` 的 `specs` 切片加一行:

```go
{Type: "decimal", Label: "定点小数", MySQLType: "DECIMAL(10,2)", SQLiteType: "TEXT", HasOptions: false},
```

然后**顺手改前端**:

| 前端文件 | 改什么 |
|---|---|
| `web/src/pages/dyn/recordForm.ts` | `editTypeOf()` 加一个分支(不加则未知类型按单行文本处理,不会炸,但显示不对) |
| `web/src/pages/system/dyn/index.tsx` | 字段编辑弹窗的"类型"下拉是**后端下发的** ⇒ **不用改** |

⚠️ **`file` 这种"要一个专门控件"的类型,光加一行 `specs` 不够** ——
还要:前端 `recordForm.ts` 的 `editTypeOf()` 加分支(落到 `custom` 控件)
+ 新写一个控件组件(antd 的 `EditModal` 有 `custom` 类型,带 `render` 钩子)
+ 归一化 / 反归一化各加一个分支(见 [§2.9](#29-字段类型-file附件))。

⚠️ **类型清单由后端下发** ⇒ 加完类型后端重启,前端下拉框自动多一项。

⚠️ **`specs` 一行同时管三件事** —— 落成什么列类型、提交时怎么归一化、读出来怎么反归一化。
新增类型只加一行(若归一化逻辑特殊,再在 `normalize.go` / `denormalize.go` 加分支)。

⚠️ **DDL 是**已有表**的问题** —— 新类型只对**新建的集合**生效。
已有集合要用新类型 ⇒ 新建一个集合迁移数据(或手工 `ALTER TABLE`)。

### 5.2 加一个集合动作(增删改查之外的)

例如要加"导出"。**清单在原语层,两边引用同一份**:

1. `internal/pkg/dynx/actions.go` 的 `actions` 切片加一项 + `ActionLabel` 加中文名
2. `internal/api/handler/v1/dyn.go` 加一条路由 + `dynGuard` 调用传新动作
3. `internal/api/router/router.go` 加路由(数据面是豁免的,不用 `rbac()`)
4. `web/src/api/dyn.ts` 加 API 方法

⇒ **第 1 步漏了就静默失权** —— service 侧按 `Actions()` 登记码,
handler 侧按 `Actions()` 拼码,两边同源 ⇒ **加了动作就一定会被登记**。
反过来,如果在 handler 侧**手写**一个清单外的动作,`dynx.IsAction` 会返回 false
⇒ handler **当场 500**("未登记的动作,资源码在权限资源池里不存在"),
而不是留一个"看起来有权限、其实谁也用不了"的接口。

⚠️ **M151 真踩过这个坑** —— handler 多写了一个 `schema` 动作,
service 只登记 5 个 ⇒ `dyn:<集合码>:schema` 永远不存在 ⇒
角色配置页里压根没有这一行可勾 ⇒ 谁也绑不上 ⇒
表单结构接口对所有非超管一律 403 —— **而日志里一条错误都没有**。
⇒ 现在的防线是 `dynx.IsAction` + 清单单点。

### 5.3 不可改的三样东西与迁移路径

| 东西 | 为什么不能改 | 想改怎么办 |
|---|---|---|
| 集合编码 `code` | 同时是物理表名与资源码的来源,改了等于换了一张表 + 换了一套权限 | 新建一个集合,把数据搬过去,再停用旧的 |
| 字段标识 `field_key` | 同时是物理列名与记录 JSON 的键 | 新建一个字段,把数据搬过去,再停用旧的 |
| 字段类型 `type` | 改类型 = 改列类型(MySQL 可以,SQLite 不行 ⇒ 要重建表 = 全量数据搬迁) | 同上 |

⚠️ **停用 ≠ 删除** —— 物理表与物理列**都保留** ⇒ 迁移路径是
"新建 → 搬数据 → 停用旧的",而不是"删了重建"(旧的软删行还在,同编码再建会撞唯一约束)。

⚠️ **前端必须锁死这三个输入框** —— 后端 DTO 里没有这三个字段,
改了会被静默忽略。

### 5.4 停用与恢复

| 操作 | 后果 | 可逆? |
|---|---|---|
| 删集合 | 集合停用;菜单与 5 条权限码一并停用;**物理表与已有数据保留** | ✅ 重新启用同一个编码(软删行会被复活) |
| 删字段 | 字段停用;列表页与表单里不再出现;**物理列与已有数据保留** | ✅ 同上 |

⚠️ **软删行的"复活"有前提** ——
同标识的软删字段会被**复活**而不是新建一行(唯一索引 `(collection_id, field_key)` 覆盖软删行);
复活的前提是**类型一致**。

⚠️ **老表改不动** —— 本模块上线**之前**建的物理表,列是 `NOT NULL`,
而 SQLite **不支持** `ALTER COLUMN` 改可空性(MySQL 可以),
SQLite 只能重建表。
⇒ 而"删集合再重建"这条路也走不通(软删行还在,同编码撞唯一约束)。
⇒ **本模块上线前的动态集合直接换编码重建一个**。

### 5.5 为什么字段列必须可空

⚠️ **这是整个模块的一条硬约定,别改成 `NOT NULL`**。

`dynx` 的读侧与写侧都按「NULL = 没填」设计:

- 写:`Normalize(nil)` → `(nil, nil)` —— "没填"与"填了非法值"是两件事
- 读:`Denormalize(nil)` → `nil` ⇒ 界面显示"未填"

⇒ 字段列可空,否则"没填"这一路直接撞数据库约束:

```
NOT NULL constraint failed: dyn_inspection.f_count
```

症状是**用户清空一个选填的整数框就存不进去**(前端发的就是 `null`),
而后端返回的是 500 "更新记录失败" —— 报错说的是"更新失败",
跟"这个框不能清空"八竿子打不着。

⇒ 业务上的理由:**金额 0 元 ≠ 没填金额**。
零值顶替 NULL 的话,列表里那条"没填金额"的记录看起来就是"金额 0 元"。

⚠️ **NULL 文本列是会真实出现的** —— 给一个**已有数据**的集合**新加字段**时,
老行的这一列就是 NULL(新列可空 ⇒ 加列时老行填 NULL)。
⇒ 关键字搜索那一组因此必须用 `COALESCE(col, '')`
(见 `server/internal/service/dyn_records.go` 的 `recordWhere`),
否则 `col LIKE ?` 在 NULL 上求值是 NULL 而不是 false(SQL 三值逻辑)。

### 5.6 值的形态:几个必背的对应关系

| 场景 | 前端发什么 | 后端怎么接 |
|---|---|---|
| 空数字 | `null`(**不是 `""`**) | `""` 会被 `toInt64` 拒:"需要整数,收到 \"\"" |
| 空文本 | `""` | 存空串(这是"清空"而不是"不填") |
| 开关 | 布尔 | 认不出来的字符串**报错**(不静默当 false) |
| JSON | 文本 | 文本必须**是合法 JSON**,否则 400 |
| 多选 | `string[]` | 落库是 JSON 数组文本 |
| 单选 | 选项值 | 必须在选项集里,否则 400 |

### 5.7 时间口径:不带时区的输入按**东八区**解释

- `datetime` 存成 UTC 的 ISO-8601(`"2026-11-01T00:30:00Z"`)
- 用户在表单里填 `"2026-11-01 08:30:00"` ⇒ 按**东八区**解释 ⇒ 存成 UTC

⚠️ **前端不能自己换算** —— 一旦前端把本地时间转成 UTC 再发,
遇上"浏览器时区 ≠ 东八区"就整整差 8 小时,而且**当场不报错**
(存进去了,只是时间不对)。⇒ 前端的 `datetime` 字段用**文本框**,
让用户按后端认得的格式直接填;`date` 没有时区问题,可以用日期选择器。

### 5.8 兼容性承诺

| 改动 | 兼容性 |
|---|---|
| 加字段类型 | ✅ 老集合不受影响(老列类型不变) |
| 加集合动作 | ✅ 老集合的 5 个码不变,新集合多一个码 |
| 改显示名 / 排序 / 图标 / 描述 | ✅ 纯元数据 |
| 改物理表名 | ❌ **不允许**(见 [§5.3](#53-不可改的三样东西与迁移路径)) |
| 改记录 JSON 的键 | ❌ **不允许**(同上) |

⚠️ **一条硬承诺** —— **已建的集合,它的物理表名、物理列名、记录 JSON 的键
永远不变**。前端、后端、第三方脚本都依赖这个形状。

| 集合之间的关联视图 | `ui/src/base/erd.js` | ERD 图(我们没有,见 [§10](#10-遗留项)) |
| 前端 SDK 怎么调 API | npm `pocketbase` 包(v0.28.x)+ `ui/src/apiPreview/` | SDK 统一封装分页 / 鉴权 store / CRUD |

#### 5.10.2 三条值得直接抄的做法

| 做法 | PocketBase 在哪 | 抄到我们哪 |
|---|---|---|
| **单选与多选是同一个类型的两个模式,不是一个类型两个** | `core/field_select.go:139` —— `IsMultiple()` 就是 `MaxSelect > 1` | 我们的 `select` / `multiselect` 是**两个类型**,重复了两份 DDL 与归一化逻辑 ⇒ 可合并成一个 + 一个开关(⚠️ 但那是**破坏性变更**,已建的集合的类型字符串不能改 ⇒ 只在**新类型**上做) |
| **改字段前先把"这次改动影响什么"算出来给人看** | `collectionChangesConfirmationModal.js` 的那一串 getter | 我们的设计器是**直接禁掉**编码/标识/类型的编辑框 ⇒ 用户只会看到"不能改",**不知道会连带什么** ⇒ 加一个"影响预览"提示是更友好的做法 |
| **字段类型目录,后端一个文件、前端一个目录,一一对应** | `core/field_*.go` 14 个 ↔ `ui/src/fields/` 14 个 | 我们现在是 `dynx.specs` 一行 ↔ 前端 `recordForm.ts` 的 `editTypeOf()` 一个分支 ⇒ **加类型时容易只改一边** ⇒ 改成一一对应后,漏改一眼就看得出来 |

#### 5.10.3 差异表(不要照抄的地方)

| 维度 | PocketBase | 本仓 | 为什么不一样 |
|---|---|---|---|
| 规则缺省 | **默认拒绝**(非超管进不去) | **默认放行**(没配就不过滤) | 我们的数据范围是 **RBAC 之上的收窄层**,不是主授权;照抄它的默认拒绝 ⇒ 上线当天所有列表全空 |
| 删字段 | **真删物理列** | **只停用,物理列保留** | 我们没有"重建表"的迁移工具;SQLite 删列要重建表 ⇒ 代价与风险都不成比例 |
| 字段改名 | **支持**(临时列名中转) | **不支持** | 字段标识是记录 JSON 的键,改名 = 换契约 |
| 集合改名 | **支持**(改表名) | **不支持** | 集合编码同时是资源码的来源,改名 = 换权限 |
| 类型可变 | **支持**(含 single ↔ multi 的值搬迁) | **不支持** | SQLite 改列类型要重建表 ⇒ 全量数据搬迁 |
| 规则表达 | **过滤表达式字符串**(运行期求值) | **枚举 + 列模板**(编译期已知) | 我们的列模板要拼进 GORM / SQL,自由表达式没法做静态检查,也没法在启动期校验 |
| 权限模型 | 集合级规则 + 集合内 `auth` 集合 | 全局 RBAC 资源矩阵 + 角色绑数据范围 | 本仓的一致性检查要求"路由数 == `rbac()` 调用数",集合级规则进不了那套账 |
| 管理端 | 原生 JS + Vite(`ui/`) | React + antd 5 | 整个前端栈是 React,不可能抄 UI |
| 数据库 | SQLite(单文件) | MySQL(生产) / SQLite(开发) | 改列 / 删列的代价在两个方言上差很多 |

⚠️ **一句话** —— **PocketBase 是"怎么做"的字典,不是"为什么这么做"的答案。**
它的默认拒绝、真删列、支持改名,每一个都成立,但**每一个都是在它自己的场景下**成立的。
照抄做法要问一句"我们为什么也要这样";照抄取舍会直接把我们的场景改掉。

## 7. 明确不做

| 不做 | 原因 |
|---|---|
| 字段类型改成可改 | 要改列类型 ⇒ SQLite 要重建表 ⇒ 全量数据搬迁 |
| 集合编码改成可改 | 它同时是表名与资源码的来源 ⇒ 改了等于换表 + 换权限 |
| 公式字段 / 汇总字段 | 需要表达式引擎,是一条独立的产品线 |
| 子表单 / 关联表单(外键) | 需要跨集合引用与级联删除,复杂度高一个量级 |
| **任意表 / 自定义 SQL 作为选项来源** | 把表名(或 SQL)交给用户拼 = 注入面 ⇒ 只给白名单注册表 |
| **动态集合作为选项来源** | 取值列与显示名列都是用户自己定的字段,还要再套一层"选哪一列"的界面 |
| 字段级数据范围 | 数据范围是**行级**的;字段级要另做一套(见 `docs/框架层未完成项清单v1.md`) |
| 设计器的审批流 | 集合定义本身走的是普通 RBAC,不需要审批 |
| 历史版本 / 回滚 | 设计器页还没做"撤销",先不做版本管理 |

4. **上传按钮按 `file:upload` 控可见性** —— 上传走 `POST /biz/files`,

### 9.6 集合绑定审批模板 + 记录送审(2026-11-03,commit `f5e8b2c`)

业务表单设计器此前只有"建表 + 录数据",没有流转能力;通用审批系统
([通用审批系统设计方案V1.0.md](./通用审批系统设计方案V1.0.md))此前只接了 material 一条业务线。
这一刀把两者接起来:**设计器里给集合选一个审批模板,记录列表就长出"送审"动作和审批状态列**。

**四个设计决策**(完整版在 `server/internal/service/dyn_approval.go` 文件头):

1. **biz_type 恒为 `"dyn"`,不按集合细分** —— 审批引擎的 handler 注册表是**启动期静态的**
   (R11 硬线),而集合是运行期才建出来的,不可能为每个集合注册一个 handler。
   模板归属歧义用送审时的**显式 TemplateCode** 消歧(取集合绑定的模板)。
2. **审批结果不回写业务表** —— 状态经审批单实例联查(`_approval` 徽标)读出来;
   "通过/驳回写回记录哪个字段"是字段级契约,另起一轮设计(见 §11 分期)。
3. **送审 = CreateDraft + Submit 一步走** —— material 有"草稿预览窗",
   是因为它的业务数据在送审前不落库;dyn 的记录数据**本来就落了库**,
   再走一遍草稿是纯多余。
4. **handler 四个钩子全是 no-op + 日志** —— 不回写 ⇒ 没有联动要做。

**绑定关系**:`sys_dyn_collection.approval_template_id`,**绑 id 不绑 code** ——
审批模板删除时会改写 code 让出唯一坑位(D7),id 不变;`0` = 不绑定。

**⚠️ 三个"必须"**

1. **前置检查按序**:未绑定 → 引擎未装配 → 记录不存在 → 模板已停用。
   "未绑定"必须排在"引擎未装配"前面 —— 前者是业务配置问题,后者是装配事故,
   顺序反了用户会拿一句"未装配审批引擎"去查自己根本碰不到的部署。
2. **集合未绑模板时,徽标查询整个短路** —— 列表读路径是最热的路径,
   没绑模板的集合一个多余的 query 都不该有;绑了才查一次 `biz_id IN (...)`。
3. **动作权限码走 `dynx.ActionUpdate`** —— 送审本质是"推动自己这条记录的状态",
   与编辑同级;不新造 `submit` 动作(新动作 = 清单 + 资源码 + 绑定矩阵三处同步,成本不成比例)。

**前端**:记录页"送审"行内动作(绑模板 && 该记录没进过审批流时出现 ——
引擎 D9 同记录一辈子一张单,终局后不能重发,同 material 口径)+ 审批状态 Tag 列;
设计器集合弹窗加"审批模板"下拉(只列**在用**的模板 + "不绑定"='0')。

**可逆探针**

| 拆掉什么 | 哪条用例红 |
|---|---|
| `CreateCollection` 不校验模板(存进去一个 9999) | `TestDyn_审批_绑定不存在或停用的模板被拒` |
| 送审时跳过"模板仍 in_use"复查 | 同上(先绑后停用的分支) |
| 送审时跳过"未绑定"前置检查 | `TestDyn_审批_送审前置检查` |
| `attachApprovalBadges` 短路条件(未绑也查) | dyn_scope/dyn_relation 夹具无 `sys_approval_instance` 表,直接 SQL 报错红 |
| 前端"送审"动作的 `!row._approval` 条件 | 记录页手测:已送审的记录仍出现送审按钮,点了后端报"已有进行中的审批单" |

## 11. 内置业务模块 × 业务表单设计器 适配度分析(2026-11-03)

> 背景与授权:用户原话——左侧内置了业主管理、房源管理、数字资产、数字资料、
> 交付管理、问题管理、公告与活动,**"这里面应该全部可以用业务表单设计器来实现"**;
> 功能不满足的把设计器做得更通用;集合再绑上审批模板就基本齐了。
> 逐模块读了各自的 service / model / 前端页之后的结论如下——
> **"全部可以"不成立,7 个里 2 个能整体迁、1 个能迁一半、4 个不该迁或暂不迁**。

### 11.1 逐模块适配度

| 模块 | 适配度 | 结论 | 依据 |
|---|---|---|---|
| 房源管理(house) | 高 | **可迁** | 主体就是"楼栋→单元→房号 + 面积/户型/状态"的结构化台账,单表 CRUD + 项目行级权限;状态流转简单(在售/售罄)用枚举字段即可 |
| 公告与活动(notice / activity) | 高 | **可迁** | 纯内容发布:标题 + 富文本 + 上下架时间 + 已读;审批(发布前送审)恰好用上新绑的模板能力 |
| 数字资料(material) | 中(资料形态)/ 中(工程形态) | **资料形态可迁,工程审批形态暂留** | 资料台账(上传、分类、标签)是标准单表;但它是审批引擎**唯一已接入**的业务线(R11 的模板归属用 biz_type=material 区分),先动它就要先动审批注册表,收益配不上风险 |
| 数字资产(asset) | 中 | **缓迁** | 记录主体可建模,但它挂在 3D 展厅链路上(文件引用、发布状态机),换存储形态牵动另一个项目(三维展厅平台)的对接契约 |
| 问题管理(issue) | 低-中 | **缓迁** | 记录本身可建模,但"问题 → 派单 → 处理 → 回访"是多角色工单流(分派人、时限、催办),dyn 现有字段类型表达不了"指派给某人"与"办结时限",硬迁会做成一个不能派单的假工单 |
| 业主管理(owner) | 低 | **不迁** | owner 是**账号体系**的投影(sys_user 家属/成员关系 + 手机号 PII + 脱敏),不是一张静态台账;迁到 dyn 等于把认证域数据搬进自建表,登录/绑定/隐私合规全都得重做 |
| 交付管理(delivery) | 低 | **不迁** | 核心 7 阶段 pass **自动推进**(签到/交房/验房链上的状态机 + 定时任务),这是"阶段工作流引擎"不是表单;表格页只是它的展示层 |

**共性发现:这批模块普遍存在"请求字段已定义但实现未用"**
(通知类的 `Notify*`、事项的 `CopyTo` / `DueAt` 等)——DTO 里有、前端有输入框、
service 里没人读。迁移时**别照搬死字段**,按实际读写面重建字段清单。

### 11.2 分期方案

- **Phase 2a(先做,收益最大)**:公告与活动 + 房源管理,作为 **seed 出来的示例集合**
  (建集合 + 建字段 + 建角色绑定的脚本进 seed,不写迁移代码——老模块代码保留,
  菜单切换由运营在角色配置里勾)。每迁一个,内置模块的菜单在只读角色的绑定矩阵里摘除。
  **→ 2026-11-03 首批已落地**(§9.7:房屋台账 / 公告管理两个集合启动期播种);
  旧数据未迁、旧菜单未摘,切换由运营决定。
- **Phase 2b(等能力)**:问题管理/派单 —— 需要设计器先补两个通用件:
  ①**"人员"字段**(user 来源的特化:头像 + 搜索,§10 遗留 4 已登记);
  ②**"审批结果回写"字段级契约**(通过/驳回写回记录哪个字段,9.6 决策②)。
- **Phase 2c(不建议)**:owner / delivery 维持原实现,在设计器文档里写明原因,
  防止后人"补齐一致性"时把它们也迁了。

#### ⚠️ 摘除旧菜单(seed)的门槛(2026-11-03 用户问「实现了的怎么不摘」之后的对账结论)

**今天 7 个旧菜单一个都不能摘 —— 包括已经播种了 dyn 版的房源/公告。**
"播种了 dyn 集合" ≠ "实现了":2026-11-03 播种的房屋台账/公告管理是**新增的平行集合**
(显示名都刻意不同字),不是旧模块的替身。摘除一个旧菜单要同时满足四条:

1. **功能覆盖**:dyn 版没有功能缺口。现状:房屋台账是**平面台账**(项目/楼栋/户型是
   文本字段),旧房源管理是**四级结构**(项目/楼栋/户型/房屋四个子页);
   公告管理只覆盖「公告」,「活动」的报名(`ActivitySignup`,报名人绑 `sys_user`)
   没有 dyn 等价物 —— 都要等 §10 遗留 4 的"人员"字段 / 关联字段能力。
2. **数据归宿**:旧数据**未迁**(Phase 2a 拍板不迁)—— 摘了菜单旧数据就失联,
   要么先写迁移,要么运营确认旧数据可弃。
3. **三笔账本债(§11.3)先还**:`biz_scope.go` 行级权限、`biz_field_domain.go` 脱敏、

   迁走不还债 = 权限/脱敏/看板**静默失效**,一样都不报错。
4. **绑定矩阵逐行摘**(13 角色 × 377 资源,M147 后真生效):旧菜单/按钮/接口的绑定
   摘完跑对账;摘错 = 有人 403 或越权。

> 记录保留,**不再作为待办推进** —— 7 个旧模块全部维持原实现,播种的房屋台账/公告管理
> 作为平行台账共存(运营要用哪个在角色配置里自己勾)。设计器后续能力(关联 dyn 集合、
> 级联、人员字段、子集合)按自身节奏排期,**不再以"迁移旧模块"为目标**。

| 位置 | 硬编码 | 失效症状 |
|---|---|---|
| `service/biz_scope.go`(行级数据范围登记表,约 :213-301) | 按 `module` 字符串登记物理表名与子查询 SQL(`module: "house", table: "biz_house"`) | 迁走的模块行级权限静默失效——所有人看全量 |
| `service/biz_field_domain.go`(字段脱敏账本,约 :82-97) | 按 module 字符串登记 model 列表 | 迁走的模块字段脱敏静默失效——手机号等 PII 裸奔 |
| `service/dashboard*.go` 的看板 SQL | 直接 `COUNT(*) FROM biz_house` 等 | 看板数字归零或仍旧值,没人发现 |

 dyn 自己的数据面用的是裸 SQL + 运行期表名,这三处账本都是**系统表口径**的;
要么给 dyn 建对应的登记通道(集合码 → 行级域/脱敏域,实际上 M156 的
`dyn:<集合码>` 业务域已经是雏形),要么 Phase 2a 每迁一个模块,
把对应行从账本里显式摘除并跑一遍绑定矩阵对账——**不允许"代码删了账本留着"**。
