## 一句话总结

**配置中心 = super_admin 独享的"集中式配置 + 全量审计"后台**,只有一条写通道,所有改动自动留痕,其他角色完全无访问权限。

- ✅ **super_admin**:查看所有 17 个配置项 + 整组表单编辑 + 整组保存 + 审计日志
- ❌ **其他 12 个角色**:无 `menu.system.config` 菜单,无任何 config:* API 绑定,直接调 → 403

## 1. 设计原则(2026-10-18 收窄后)

| 原则 | 说明 |
|---|---|
| **单人独享** | 只有 super_admin 能改配置,无双签复核(产品 2026-10-18 拍板) |
| **只读审计** | sys_config_audit 表只记录 update,create/delete/view 接口已全删 |
| **配置项不可增删** | 17 个 key 由 `seed.go` 初始化,UI 改 `is_active=false` 即下架 |
| **不留 reason** | UI 没输入框,后端 model 删了 `Reason` 字段(2026-10-18) |
| **不强求 SMS 二次验证** | SecretInput 纯前端切明文/密文,后端无感(12/15 上线版,P1+ 再接 SMS) |

**与原方案差异**:之前 SRS 写过"双签 + 留痕 + Webhook + 热加载"完整版,2026-10-18 用户拍板"**不要双签、不要二次复核、只要有修改记录就行**",本规范对应收窄版。

## 2. 配置项 3 大类(强约束)

| 类别 | 存储位置 | 谁改 | 改完影响 | 举例 |
|---|---|---|---|---|
| **平台层**(必须 sys_config) | `sys_config` | super_admin 直改 | 热生效或下次启动 | aliyun.sms.access_key / aliyun.oss.bucket |
| **业务级**(可选 sys_config) | `sys_config` 或业务表 | super_admin 直改 | 业务规则变更 | 活动取消时间窗口 / 验房必办项 |
| **基础设施**(严禁 sys_config) | `config/*.yaml` | 平台组开发改 PR + 重启 | 必须重启 | JWT secret / DB / Redis / Casbin model |

**为什么基础设施严禁 sys_config**:
- 启动期要读的 config(数据库连接池大小)改完必须重启,sys_config 装不下
- secret 走 sys_config 后,所有有读权限的人(包括误授权的)都能看到明文 — 改 yaml 至少要走 git 流程
- 改动 hot reload 的代码量极大,JWT 三套 secret 的 in-flight token 全部失效,热更新业务行为不可预测

## 3. 唯一的写通道:PATCH 直改

```
任何登录用户(其他角色无 menu/API 绑定,实际只有 super_admin 走得通)
   │
   └─ PATCH /rapid-admin/v1/platform/configs/:id   ← 唯一写通道
        │
        ├─ body: { config_name?, value?, value_type?, is_sensitive?, is_required?,
        │          is_readonly?, regex_validate?, min_length?, max_length?,
        │          env_var_name?, sort?, is_active?, remarks? }
        │   (任意字段可选,后端白名单过滤,pointer 风格,缺省 = 保持原值)
        │
        ├─ 后端 DirectUpdate:
        │   - role ≠ super_admin → 403
        │   - 读 sys_config[id] → 改字段 → version+1 → last_changed_by/at 更新
        │   - value_encrypted 改时同步 value_preview(脱敏)
        │   - 写 sys_config_audit { action: "update", before, after, ip, user_id, user_role }
        │
        └─ 前端:整组保存(N 路并行 PATCH)→ 刷新列表
```

### 3.1 字段白名单(14 项)

`server/internal/service/config_center_impl.go` 的 `DirectUpdate.allowed` map:

```
config_name, description, value_encrypted, value_type, is_sensitive, is_required,
is_readonly, regex_validate, min_length, max_length, env_var_name, sort, is_active, remarks
```

前端 `<GroupConfigForm>` 的 `EDITABLE_KEYS` 数组镜像这 14 项,**description 暂留白名单但不进 EDITABLE_KEYS**(P1+ 补编辑入口)。

### 6.3 审计日志页(`audit.tsx`)

```
系统配置 · 审计日志
┌──────────────────────────────────────────────────────────────┐
│ [搜索配置键___________] [分组:aliyun.sms] [清除分组过滤] [刷新]  │

│ 2026-10-18 13:30 | aliyun.oss.endpoint     | update| 超级管理员│
│ ...                                                          │
└──────────────────────────────────────────────────────────────┘
```

数据源:`GET /rapid-admin/v1/platform/configs/audits?config_key=…&config_group=…&page=…&size=…`
后端 SQL:LEFT JOIN sys_user 拿 user_name(前端 audit.tsx 第 91-95 行降级显示 `用户#${id}`)

#### 两个过滤条件(2026-10-29 更正)

| query | 语义 | 后端实现 |
|---|---|---|
| `config_key` | **子串**匹配(搜索框) | `INSTR(config_key, ?) > 0` |
| `config_group` | **精确**匹配某个配置组 | `config_key IN (SELECT config_key FROM sys_config WHERE config_group = ?)` |

两个条件同时存在时是 **AND**。

> ⚠️ **用户报的「group 没有过滤效果」是三层叠加**(每层单独修都不够):
> 1. 审计页把 URL 上的 group code 当"config_key 前缀"发出去,而后端当时是**等值**匹配
>    ⇒ `aliyun.sms` 匹配不上 `aliyun.sms.access_key`;
> 2. **query 参数名对不上** —— 前端发 `config_key`,handler 读 `configKey`,
>    Hertz 的 `Query` 大小写敏感 ⇒ 读出来永远是空串 ⇒ **过滤条件从来没进过 SQL**
>    (搜索框也是死的);
> 3. 后端压根没有"按组过滤"这个维度。
>
> ⇒ 现在:group 走 `config_group`,关键字走 `config_key`,两个过滤彻底分开。
>
> ⚠️ **`config_key` 为什么用 `INSTR` 而不是 `LIKE`** —— config_key 里全是下划线
> (`access_key` / `sign_name`),`LIKE` 的 `_` 是**单字符通配符**
> ⇒ 搜 `access_key` 会把 `accessXkey` 一起命中。`INSTR` 是纯子串查找,不吃通配符。

- ❌ 任何外部 SDK(明源/华为/微信/邮件)
- ❌ 任何业务消费侧(service 读 sys_config 行为变更)
- ❌ 真加密 / 真热加载 / 真 Webhook / 真灰度 / TLS / API Key
- ❌ 变更工单 / 双签 / SMS 二次验证

## 10. FAQ

**Q: 配置项改了为什么服务行为没变?**
A: 因为本轮**没改任何 service 读 sys_config 的代码**。配置中心只是"配置项的编辑 UI",**配置项实际生效 = service 改成从 sys_config 读**,这是 P1+ 范围。

**Q: 改了一个 sms.access_key,sms 服务行为什么时候变?**
A: 当前不变化(没人读 sys_config)。重启服务后,alpine yaml 里那个旧 access_key 仍然生效 — 因为 sms service 从 yaml 读,不走 sys_config。

**Q: 为什么没有"双签"或"复核"流程?**
A: 产品 2026-10-18 拍板:**系统配置只 super_admin 一个人能改,不需要双签**。审计通过 sys_config_audit 表自动记录 update 行为即可。P1+ 视情况再讨论是否回炉。

**Q: 为什么没有"新建配置"按钮?**
A: 同上:**用户不会创建配置项**。17 个 key 已 seed 完整,新增配置项是 P1+ 需求;UI 改 `is_active=false` 即下架。

**Q: 为什么没有"删除配置"按钮?**
A: 同上:**用户不会删除配置项**。软删用 `is_active=false`。

**Q: 审计页只有 update 一种 action,有没有遗漏?**
A: 没遗漏。`create/delete/view` 三种后端接口 2026-10-18 已全部下架:
- create:POST /configs 已删
- delete:DELETE /configs/:id 已删
- view:GET /configs/:id/plain 已删(SecretInput 纯前端切,后端无感)

**Q: 审计表里没 reason 列,改配置时不填原因行不行?**
A: 行。审计只记录"谁 + 何时 + 改了哪个 key + before→after",原值新值已在表里,不需要再写原因。SysConfigAudit.Reason 字段 2026-10-18 已删。

**Q: 我能在配置中心看到 DB 密码吗?**
A: **不能**。`mysql.* / redis.* / jwt.*` 等基础设施类 config_key **不在 sys_config 里**,只走 yaml。配置中心页面**只展示**业务级 + 平台级 17 个 key。
