## 0. 触发这件事的问题

M69 的定时任务页交付后,状态刷新是**纯手动**的:

| 时机 | `load()` 被调 |
|---|---|
| 页面挂载 | ✅ |
| 手动触发任务后 | ✅ |
| 编辑保存后 | ✅ |
| 启停切换后 | ✅ |
| **任务自己跑完了** | ❌ |
| **任务失败了** | ❌ |
| **别人在另一个页面改了配置** | ❌ |

全仓无 `setInterval`,`ManagementTable` 不自带刷新按钮,没有 SSE 订阅任务状态。

**症状**:运维盯着定时任务页,一个跑了 5 分钟的任务,从头到尾页面不会变一次 ——
连"运行中"都要手动 F5 才看得到。唯一的"实时"是手动触发那一次(因为 `handleTriggerOk`
的 `finally` 里调了 `load()`),但那只覆盖点击者本人,覆盖不了 cron 定时触发。

这不是"体验不好",是**框架层能力缺口**:cronx 明明知道每个任务什么时候跑完,
前端却拿不到。

## 1. 仓库现状:SSE 的四层已经齐了,只差中间一层

排查后发现一件关键的事 —— **本仓早就有 SSE,而且是一条完整的链**:

| 层 | 已有 | 位置 |
|---|---|---|
| 发布/订阅 | `PublishInvalidateAll` / `Subscribe` | `pkg/permnotify/permnotify.go` |
| HTTP handler | `StreamPermInvalidate` | `api/handler/v1/auth.go:123` |
| 鉴权中间件 | `SSEAuth()` | `api/middleware/sseauth.go` |
| 前端 hook | `usePermissionStream` | `web/src/hooks/` |

已解决的真问题,一个都不用重新踩:

- **25s `:heartbeat` 注释行** —— 防 nginx / proxy 60s 空闲超时
- **`X-Accel-Buffering: no` + 立即 flush** —— 防 nginx buffer(不 flush 的话前端永远收不到)
- **`?access_token=` 兜底** —— `EventSource` 是 W3C 标准 API,**不能设自定义 Header**,
  所以 Bearer 走不通;`sseauth.go` 的三级兜底(Header → query → Cookie)就是为这个
- **Redis pub/sub 跨实例** —— 任务在 A 实例跑完,连着 B 实例的浏览器要能收到
- **`EventSource` 原生自动重连**

### 1.1 还有一个建好一半的半成品

`pkg/inbox` 的 `Subscribe(ctx, userID)` 注释写着 **"给前端 SSE handler 用"**,
`publishUnread` 也确实在往 Redis 的 `inbox:user:<id>` 频道发消息 ——
**但全仓没有任何 handler 消费它**。

`inbox` 的 4 条路由全是拉模式:

```
GET  /inbox/messages       列表
GET  /inbox/unread-count   未读数
POST /inbox/messages/:id/read
POST /inbox/mark-all-read
```

也就是说:**站内信的红点不会自己更新**,必须刷新页面或前端轮询。

## 2. 选型:SSE,不是 WebSocket

### 2.1 为什么不用 WebSocket

| 判据 | 本仓情况 | 结论 |
|---|---|---|
| 上行频率 | 触发任务 / 标已读 / 审批 —— 全是低频 HTTP POST | WS 的双向能力**用不上** |
| payload 大小 | 每条事件 ≤ 100 字节 | WS 的二进制帧优势**用不上** |
| 断线重连 | 丢事件的后果 = 页面数据陈旧,下次 REST 会纠正 | 不需要 WS 侧的序列号/补拉协议 |
| 代理兼容 | nginx / 企业网对 `Upgrade` 转发踩坑极多 | SSE 走普通 HTTP/1.1,无此问题 |
| 已有资产 | SSE 四层齐全,WS 零资产 | WS 要从零写握手 + 帧编解码 + 心跳 + 重连退避 |

**结论:数据流是单向的(服务端 → 客户端),所有上行都走普通 HTTP。SSE 完全够用。**

### 2.2 SSE 什么时候会不够

诚实登记:出现以下任一情况,**本模块应该重新评估**:

1. 需要客户端高频上行(每秒数十次,比如协同编辑 / 实时白板)
2. 单条消息 > 64KB(二进制 / 文件分片)
3. 服务端需要**主动**向客户端发指令并**确认收到**(SSE 无应用层 ACK,只能靠 REST 回执)

这三条本仓目前一条都不成立。真出现了,`pkg/push` 的 `Transport` 抽象可以直接换 WS,
**不动任何业务侧**(见 §3.6)。

## 3. 设计

### 3.1 分层

```
业务侧        cronx / inbox / (未来)approval
   │  publish(topic, event)
   ▼
pkg/push      ← 本模块地基。Event / Topic / Hub / Publish / Subscribe
   │  Redis pub/sub(push:* 命名空间)
   ▼
handler       GET /events(SSE,单连接多 topic)
   │
   ▼
前端          useEventStream.ts(一个 EventSource,按 topic 分发)
```

**依赖方向单向向下。** `pkg/push` 不依赖任何业务包,不知道 job / inbox 是什么。

### 3.2 事件是「信号」,不是「数据」

```go
type Event struct {
    Topic   string `json:"topic"`             // "job" / "inbox" / "perm" / "approval" / "dict"
    Event   string `json:"event"`             // "job.finished" / "inbox.unread"
    Payload any    `json:"payload,omitempty"` // 小;**不含业务数据正文**
    At      int64  `json:"at"`                // ms
}
```

前端收到 `job.finished` 后**重新调 `GET /jobs`**,而不是用 payload 直接改本地状态。

这样做的三个理由:

1. **不产生数据泄漏面** —— payload 里没有 error 正文、没有消息内容、没有审批单据。
   能收事件的人一定也能通过对应的 REST 接口看到数据,推送不扩大可见范围。
2. **不产生两份契约** —— 列表的字段定义只在 REST DTO 里存在一份。
   推送里塞一份完整对象 = 两份契约必然漂移。
3. **前端已有完整的加载 / 空态 / 错误处理** —— 复用现成的 `load()`,不写第二套渲染逻辑。

这与 `perm-stream` 现有的做法一致(`perm_changed` 事件不带数据,前端 re-fetch)。

### 3.3 Topic 与权限

| topic | 投递范围 | 前置权限 | 用途 |
|---|---|---|---|
| `push:user:<userID>` | 仅本人 | 登录即可 | 站内信未读、审批指派给我 |
| `push:job` | 广播 | `job:read` | 定时任务跑完 / 失败 |
| `push:perm` | 广播 | 登录即可 | 权限失效(迁自 `perm:invalidate:all`) |
| `push:approval` | 广播 | `approval:read` | 审批 / 待办(**本期只定义,无生产者**) |
| `push:dict` | 广播 | `dict:list` | 字典组被改了 → 前端作废该组缓存(2026-10-26 M94 补,**有生产者**) |

**订阅在连接建立时由服务端决定,客户端不能自选。**

这是本模块最重要的安全边界。如果允许客户端 `GET /events?topics=job`,
那么任何登录用户都能订阅到任务事件 —— 绕过 RBAC。所以:

```
GET /events   ← 无 topics 参数。服务端按 caller 的权限算出该订阅哪些
```

### 3.4 权限判定复用 `decideAccess`,不重写

handler 需要判断「这个人能不能收 `job` 事件」。本仓的判定逻辑在
`middleware.decideAccess`(`api/middleware/rbac.go:88`),**未导出**。

方案:导出一个薄包装

```go
// CanAccess 供 SSE handler 等非中间件场景复用同一套判定
func CanAccess(caller *service.Caller, principal *authz.Principal, module, action string) bool
```

⚠️ **绝不重新实现一遍权限判定。** `decideAccess` 里有 super_admin 短路、
role/user 两路、deny override、grant 委托 —— 漏掉任何一条就是权限绕过。
两套实现的分叉是本仓明确记过的失败模式。

### 3.5 背压与降级

**单路径:Redis pub/sub 就是唯一的投递路径。**

⚠️ 规划时一度考虑过「进程内 Hub + Redis 双投递」,写代码前否掉了 ——
**同实例的连接会收到两份事件**:Hub 投递一次,Redis 投递又一次。
事件是 refetch 信号,重复 refetch 会让长列表页反复重拉,而且这种 bug
只在"单实例部署"下出现,多实例部署恰好正常,极难复现。
去重要引事件 ID + LRU 集合,为一个不存在的收益付这个复杂度不划算。

**背压**:每个连接一个 `chan Event`(缓冲 64)。写不进去就**丢最旧的一条**并计数,
绝不阻塞 Redis 订阅 goroutine —— 一个卡住的浏览器不该拖住整个订阅循环。

丢事件时给前端发一条 `event: lag`,前端据此决定要不要立刻补拉一次列表。

**降级(Redis 不可用)**:

- 本仓 Redis 已经是多个模块的硬依赖(cachex / cronx 分布式锁 / inbox),
  所以「Redis 挂」不是一个需要独立优化的常态
- 但**不能静默**。`/events` 连接建立时若 Redis 不可用,发一条 `event: degraded`,
  前端切到轮询兜底并在 UI 上说明"此页非实时"
- `permnotify` 现在是 `rdb == nil` 直接 `return` —— 推送消失但没人知道。
  对任务状态来说这意味着"页面永远不更新",比报错更难查。**不学这个**

### 3.6 Transport 抽象(为 §2.2 的升级路径留口)

```go
type Transport interface {
    Publish(ctx context.Context, ev Event) error
    Available() bool
}
```

本期只实现 `redisTransport`。将来若要换 WebSocket,新增一个实现即可,
业务侧的 `Publish` 调用**一行都不用改**。

> ⚠️ 代价:比纯 SSE 多约 15% 代码量。值得 —— 因为"将来换 WS 不用重写所有业务侧"
> 是这个抽象唯一的存在理由,而现在正好是最便宜的时候(只有 0 个业务侧在用)。

## 4. 与现有包的关系

| 包 | 处置 | 理由 |
|---|---|---|
| `pkg/permnotify` | **保留 domain API,删掉自己的 Redis 代码** | `PublishInvalidateAll` → 改调 `push.Publish(TopicPerm)`,订阅交给 push |
| `pkg/inbox` | **保留 DB 读写,`publishUnread` 改投 push** | inbox 是业务域(pkg)依赖传输(pkg/push),方向合理 |
| `GET /auth/perm-stream` | **删除**,由 `GET /events` 接管 | 被完全覆盖。留两条 SSE 连接是浪费,留死路由是垃圾 |
| `usePermissionStream.ts` | **删除**,并入 `useEventStream` | 同上 |

### 4.1 换掉 perm-stream 的风险控制

删一条**在用**路由,缓解措施:

- **Redis 频道名不变** —— `pkg/push` 继续订阅 `perm:invalidate:all`
  这个**原有频道名**。发布端一行没改,订阅端换了实现。
  没有"双写 / 双订阅"的迁移窗口,不存在两个消费者同时收到或都收不到的问题。
- **前后端同一个 commit 换** —— `GET /events` 和 `useEventStream` 一起上,
  `perm-stream` 和 `usePermissionStream` 一起下。本仓是前后端同仓,不灰度。
- **行为等价性有测试兜底** —— `perm_changed` 事件名和 payload 保持不变,
  现有 hook 的处理逻辑原样搬进 `useEventStream`。

> 本仓的规矩是**不留下"声明了但一行没读"的字段 / 路由**(见 M70 删
> `cronx.Config.HistoryKeep*` 的先例),所以选择一次性换干净而不是长期并存。

### 4.2 顺带发现:站内信前端根本没有 UI

`inbox` 有 4 条 REST 路由、后端有完整 Manager、Redis 频道也在发消息 ——
但 `web/src/` 里**搜不到任何 unread / NotificationBell**。

也就是说站内信从落地到现在,用户在界面上**看不到任何入口**,只能手动调接口。
这是比"角标不实时"更严重的问题。

本模块(M71–M73)解决的是**推送通道**。站内信的列表页 / 消息详情页属于
独立的一块 UI 工作,登记在 §8「明确不做」里,M74 之后单独排期。
本轮只做:让未读事件**推得出**,并在前端 Header 加一个**未读数角标**
指向未来的列表页 —— 角标能点开之前先让它可见,比完全不可见好。

## 5. 前端

### 5.1 `useEventStream` —— 一个连接,按 topic 分发

```ts
const { subscribe } = useEventStream()

useEffect(() => subscribe('job.finished', () => load()), [load])
```

内部:`BasicLayout` 顶层挂载一个 `EventSource`,收到事件后按 `event` 名派发给注册的回调。
组件卸载 / 登出 → `close()`。

### 5.2 降级兜底

收到 `degraded` 事件 → 该页切到轮询(如 15s),并在 UI 上给一条说明。
**不给静默的空白页** —— 用户要知道"这个页面不是实时的"。

### 5.3 定时任务页订阅

| 事件 | 动作 |
|---|---|
| `job.finished` / `job.failed` | `load()` 重拉列表 |
| `degraded` | 切轮询 + Alert |

## 8. 明确不做

| 不做 | 为什么 |
|---|---|
| WebSocket / 双向通道 | §2.1:上行全走普通 HTTP |

## 9. 风险登记

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **每开一个标签页 = 一条 SSE 长连接**。100 个运维开 100 个标签页 = 100 条连接 + 100 个 Redis 订阅 | 事件都是低频的,连接本身很轻;`heartbeat` 25s 一次。真成为问题再上连接复用 / 广播 |
| R2 | 慢客户端拖住投递方 | §3.5 丢最旧 + 不阻塞 |
| R3 | 删 `/auth/perm-stream` 影响在用功能 | §4 三条缓解 |
| R4 | 推送成为"看起来在工作但其实没推"的假象(Redis 挂了) | §3.5 degraded 事件 + 前端切轮询,**不静默** |
| R5 | cronx 为了推送引入传输层依赖 | §6 M73:依赖倒置,main 注入回调 |
| R6 | 权限变更后,已建立的连接仍按旧权限收事件 | 连接期判定一次;权限变更会触发 `perm_changed` → 前端重新拉权限。**重新订阅需要前端主动重建连接**,本期在 `perm_changed` 处理里做 |

### 10.3 计划时没发现、落地时查出来的 4 个问题

**① 旧的权限 SSE 通道一直是坏的(最严重)**

规划时把「本仓 SSE 四层已经齐了」当成了既有能力,实际只查了代码存在性,没查

已删掉死条目,并把机制写进注释(免得下一个人再犯一遍)。

**④ `TopicApproval` 的 gate 现在对所有人是关的**

非超管返回 false。这是**预期状态**(行为与计划一致,所以没进 10.2),但意味着
审批骨架的两个事件在审批模块落地前不会到达任何人。写在这里,免得将来
排查时把它当成 bug。

## 11. M94 落地记录(2026-10-26)—— 字典「改了马上生效」

### 11.1 起因:30 分钟缓存让「改了不生效」成了默认行为

字典是「代码 enum 的中央仓库」,业务页的下拉 / 标签全靠 `useDict` 渲染。
而 `web/src/stores/dict.ts` 的缓存 TTL 是 **30 分钟** —— 于是:

> 管理员在字典管理页改了 label,**别人最长半小时看不到**;
> 管理员自己**刷新了页面**也看不到 —— 缓存在 module 级 store 里,刷新不清。

这个症状很容易被当成「缓存本来就是这样的」。但字典的写入口只有一处
(`PATCH /system/dicts/:id`),调用方是运营,而运营改完标签的预期就是**立刻生效**。

### 11.2 契约

| 项 | 值 |
|---|---|
| topic | `push:dict`(`push.TopicDict`) |
| 事件名 | `dict.changed`(`push.EventDictChanged`) |
| payload | `{"group_code": "issue_status"}` —— **只有 group_code** |
| 前置权限 | `dict:list` |
| 生产者 | `service.NewDictPublisher()`(`server/internal/service/dict_publisher.go`) |
| 触发点 | `roleService.UpdateDict` —— **写库成功之后** |

**payload 为什么不带字典内容** —— §3.2 的第 2 条理由(不产生两份契约)。
带内容等于在前端造出第二份字典数据契约,后端加个字段前端就会漂。
收到信号的人自己去重拉 `GET /system/dicts?groupCode=xxx`。

**`group_code` 取自库里那一行,不是请求体** —— group_code 是代码契约的一部分,
改它等于换 enum,走的是别的通道(PATCH 的 body 里**根本没有**它)。
取错字段的症状是「前端去作废一个不存在的组,真正的组不刷新」,而且**没有任何报错**。

**广播在写库成功之后** —— 顺序反了会发出「改了但没改」的信号,前端据此重拉、
拉到的还是旧值;下次真改的时候前端已经不信这个信号了。

> 🔴 **M95 之后这个顺序中间多插了一步** —— 后端字典读走了 cachex L2,
> 所以真正的顺序是「写库 → **失效缓存** → 广播事件」。理由见 §12。

### 11.3 前端怎么接

```
SSE dict.changed
  → useEventStream.onDictChanged(payload)   // 只认 group_code,别的字段一律不看
  → useDictStore.invalidate(group_code)     // 删掉 lastFetchAt[group_code]
  → useDict 的 effect 发现 lastFetchAt 没了 → 重拉
```

⚠️ **invalidate 只删 `lastFetchAt`,保留 `dicts`** —— 删掉 `dicts` 的话,
所有用这个组的下拉会**瞬间变空**。字典是全局的,一个组被改 → 几十个页面的下拉
同时闪一下,比「多显示半秒旧标签」糟糕得多。保留旧值,重拉落地后无缝切换。

⚠️ **invalidate 依赖两处实现细节** —— `useDict` 的 effect 条件
(`if (!dicts || !lastFetchAt)`)和 `fetchDict` 的 TTL 判断
(`Date.now() - (lastFetchAt[groupCode] || 0) < CACHE_TTL`)。
这两处任何一处被改,「作废」都会退化成「**静默不生效**」——
症状是字典改了但下拉还是旧值,**没有任何报错**。
回归网在 `web/src/stores/__tests__/dict.store.test.ts`。

### 11.4 门禁:为什么是 `dict:list`

M93 之后**每个登录角色都有 `dict:list`**,所以这道门禁实际等于「登录即可」。
仍然显式判,理由是将来字典可能改成只对部分角色可见,门禁已经在那儿了。

⚠️ `event_test.go` 的 E8 / E9 守的是「**门禁还在**」这件事,不是「生产行为」——
E8(无策略 → 订不到 dict)在生产里恒为真(因为人人都绑了 `dict:list`),
它防的是有人把 `if middleware.CanAccess(...)` 删掉改成无条件广播。

### 11.5 明确不做

| 不做 | 为什么 |
|---|---|
| payload 带字典内容 | §3.2 第 2 条 —— 两份契约必然漂 |
| 字典新增 / 删除也广播 | 后端路由已卸(字典是只读契约),`CreateDict` / `DeleteDict` 直接返 Forbidden,**没有真写路径** |
| 前端收到事件后自己重拉 | 会和 `useDict` effect 的重拉撞车,同一个组发两遍请求 |
| 字典管理页用 `useEventStream()` 持有连接 | 连接的持有者应该是常驻的 BasicLayout;字典页只 import 模块级 `subscribe` |

| `pkg/push` | `TestM94_Publisher_*`(5 条) | 事件名 / topic / payload 形状 / ctx 死了也要投出去 / transport panic 隔离 |

## 12. M95 落地记录(2026-10-26)—— 字典读走 cachex,以及它给 M94 加的那道锁

### 12.1 起因:M94 的「改了马上生效」只有前端那一半

M94 把前端的 30 分钟缓存接上了作废通道。但后端这一侧当时是**直查 DB**的 ——
`roleService.ListDict` 每次都打库。

那意味着:一次 `PATCH /system/dicts/:id` 会让**几十个页面同时重拉**,
每次重拉都是一次全表查询。M95 把字典读接上 cachex,这是收益。

但接缓存这件事**直接威胁 M94 的承诺**,这才是它真正的难点。

### 12.2 威胁:后端一缓存,M94 的信号就变成「假的」

M94 的链路是:

```
SSE dict.changed → 前端 invalidate → 前端重拉 → 显示新值
```

后端一旦有了缓存,这条链的**最后一环**就变了 —— 前端「重拉」回来的可能是
**后端缓存里的旧值**:

```
SSE dict.changed → 前端 invalidate → 前端重拉 → 后端吐缓存里的旧值 → 显示旧值
```

症状是「我明明让它刷新了,还是旧值」—— 比 M94 之前的「改了不生效」**更难解释**,
因为用户这一轮**明确要求过刷新**。

### 12.3 解法:顺序是死的 —— 写库 → 失效缓存 → 广播事件

`roleService.UpdateDict` 里三步的顺序不可交换:

| 顺序 | 后果 |
|---|---|
| 写库 → 失效 → 广播 ✅ | 广播那一刻前端重拉,拿到的是新值 |
| 写库 → 广播 → 失效 ❌ | 广播后前端**立刻**重拉,后端还在吐旧缓存;失效发生在重拉之后,前端把旧值又写回缓存(于是这次改动被**缓存层**永久记成旧值,直到 TTL 过期) |
| 失效 → 写库 → 广播 ❌ | 失效时库里还是旧值,写库后没有任何东西让缓存失效 —— 广播后的重拉照样拿到旧值 |

⚠️ **中间那行是最阴的** —— 「失效确实执行了、也确实清了缓存」,但清得太晚:
前端在失效之前已经重拉过一次,那次重拉把旧值又写回了缓存。**日志里一切正常,
用户就是看不到变化。**

这个顺序由 `server/internal/service/role_dict_cache_test.go` 的
`TestM95_UpdateDict_InvalidatesBeforePublish` 守着 —— 假 publisher 在**广播那一刻
同步读一次**字典,读到旧值就红。

### 12.4 为什么只用 L2(Redis),不挂 L1

L1 是**进程内**的:写路径的失效只能删掉**本实例**的 L1,别的副本仍持有旧值。

也就是说,挂上 L1 之后,「改了马上全网生效」在多副本部署下会退化成
「最多 L1TTL(默认 10s)之后生效」—— **M94 的承诺被悄悄削掉一截**。

`internal/config/cache.go` 自己写着这条规则(凡是「改了必须马上全网生效」的数据
要么显式失效各副本,要么就别走 L1),`authz.CachedLoader`(principal 缓存)也是
同一判断。字典是第一个**业务**接上缓存的,它不能是第一个破坏这条规则的。

**所以装配期只取 L2 通道**(`cachePool.Safe()`),不走 `TwoLevel`。

### 12.5 TTL 只是一道兜底,不是机制

字典缓存 TTL = **10 分钟**,后端 TTL 刻意**短于**前端的 30 分钟
(`web/src/stores/dict.ts` 的 `CACHE_TTL`)。理由:后端缓存永远不应该是那个
**更长的**陈旧窗口 —— 否则「前端刷新了、后端还在缓存」会叠成一个半小时的黑洞。

10 分钟只在下述情况兜底:失效失败(Redis 当时不可用 / 后端不支持 SCAN)。
这时陈旧数据最多活 10 分钟,并且**有日志**(`dict: 字典缓存失效失败`)。

### 12.6 失效失败时为什么**报错**而不是静默跳过

`cachex.DeletePrefix` 在后端不支持 SCAN 时 fail-open 返回 `(0, nil)` ——
那个语义对「清理一下不用的缓存」没问题,但对「改完必须马上生效」是灾难:
**什么都没删 = 数据没更新,而且没有任何报错**。

所以 `DictCache.Invalidate` 先问一句 `Safe.SupportsScan()`,不能扫就**返回 error**,
由调用方打 WARN 日志。与 `authz.CachedLoader.InvalidateUser` 同一判断。

### 12.7 与推送契约的关系:**一个字都没改**

M95 没有新增事件、没有改 payload、没有改 topic。

> **M94 的推送契约(SSE `dict.changed`)在 M95 之后依然是「信号」而不是「数据」。**
> 后端缓存的引入**没有**变成「让广播带上内容」的理由 —— 那会造出第二份字典契约,
> §3.2 的第 2 条理由仍然成立。

M95 改的只是**后端读路径**:从「每次打库」变成「读缓存,写路径负责失效」。

### 12.8 测试矩阵(补充 §11.6)

| 层 | 用例 | 守的是 |
|---|---|---|
| `service` | `dict_cache_test.go`(10 条) | key 方案 / 失效只删 `dict:` 一族 / nil 安全 / uint64 精度 / 超长 group_code 不进缓存 / 后端不支持 SCAN 时失效**报错** |
| `service` | `role_dict_cache_test.go`(4 条) | 读路径真走缓存 / 写路径真失效 / **失效早于广播** / 没装缓存时行为不变 |
