approvalx(通用审批)

approvalx —— 通用审批系统使用教程

这一章回答五个问题,全部按真实操作顺序写,每一步都标注了「系统内部发生了什么」:

  1. 审批是怎么逻辑走的(§1)—— 先建立整体图景,后面每一步都能对上号;
  2. 什么是或签、什么是会签(§2)—— 配错这一步,整条流程就白配;
  3. 怎么使用审批模板功能(§3-§5)—— 配置页导览 + 建模板前的准备;
  4. 怎么把模板跑起来:请假三级(§6)与报销四级(§7)两个完整教程;
  5. 用户日常怎么用(§8)—— 发起、待办、通过/拒绝/打回、重提。

本章全部流程于 2026-11-03 在本机 dev server 上真实跑通验证过(§11 实测记录), 不是照设计稿抄的。引擎内部机制(七张表 / SPI / 事务纪律)的完整定义见设计方案 §3-§6,本章只讲用得上的部分。

§1 先看懂:一张单子的旅程

审批系统的核心是一条单向状态机:

                    ┌────────── 打回(rollback,备注≥5字)──────────┐
                    ▼                                              │
 ┌───────┐ 发起/送审  ┌─────────┐   逐关通过    ┌──────────┐          │
 │ draft │──────────▶│ running │──────────────▶│ approved │          │
 └───────┘           └─────────┘               └──────────┘          │
    │                    │                                            │
    │ 作废               │ 任何一关:拒绝(reject,备注≥5字)            │
    ▼                    │            ┌──────────┐                   │
 ┌───────────┐            ├───────────▶│ rejected │                   │
 │ cancelled │            │            └──────────┘                   │
 └───────────┘            └───────────────────────────────────────────┘
                 (returned 状态即"停在发起人手里等重提",
                  重提后回到 running、从第 1 关重走)

 红线:cancelled 只有 draft/returned 能去(D9:running 的单子可能有人正在审,
      悄悄作废会让他审到一张不存在的单);rejected/approved 是终态,不可逆。

一次「提交」背后,系统在同一个数据库事务里做完这些事:

  1. 校验单子:状态必须是 draft(首次)或 returned(重提);重提要过两道闸 —— 内容必须真的变了(逐字节比较标题和表单变量),且打回次数没到 5 次上限;
  2. 解析第 1 关的审批人:按规则查角色成员 / 指定人 / 部门主管, 剔除发起人自己(D11:自己不能审自己的单),去重;
  3. 生成审批任务(task):解析出的每个人各得一行 pending task;
  4. 落一轮次(round):把本轮的标题和表单内容快照存档(打回重提时留痕就靠它);
  5. 实例置 running、current_stage = 1。

之后每有一个人处理(通过/拒绝/打回),引擎在锁住实例行的事务里判定走向 (会签数票数、或签直接定局,见 §2),该进下一关就生成下一关的任务, 该终局就把剩余没人处理的任务标成 skipped。

通知链路:每个动作落地后发一条事件——前端靠它刷新待办角标; 同时旁路投一条站内信给相关人(「你有新的审批任务」「你的单子被通过了」)。 站内信是尽力而为:投不出去只记日志,绝不会让审批本身失败。

后台巡检:有单子在某一关停了太久?cron 巡检任务会发站内信告警, 但绝不自动改单——"审批人离职了自动转办"这类聪明的修复会改动一张 正被人认真审的单子,V1 明确不做。真卡死了联系管理员处理。

§2 🔴 什么是或签、什么是会签(配错整条流程白配)

每一关都要选「审批方式」(review_type),它决定这一关有人处理之后怎么走:

review_type 名字 某人通过时 某人拒绝时
all 会签(全签) 这一关还有别人没批?等。全部通过 → 进下一关;最后一关通过 → 整单 approved 整单立即 rejected,其余没批的人的任务标 skipped
any 或签(任签) 整张单立即 approved 终局——后面还有关卡也不会启动 整单立即 rejected

一句话记:会签"全过才过、一票否决";或签"谁先处理谁说了算"—— 或签的第一个动作就是整张单的终局。

三个场景对照

场景 A:部门经理关,规则解析出 2 个人(老王、老李)

配置 老王批了「通过」之后
会签 all 什么都没发生——实例还停在这一关,老李的待办还在,等老李也批了才进下一关
或签 any 整单立刻 approved,老李的任务标 skipped,后面的关卡全部不启动

场景 B:报销四级链(项目经理 → 部门经理 → 总经理 → 财务)

必须每一关都配会签。任何一关有人拒绝 → 整单 rejected; 每一关所有人都通过 → 进下一关;财务那关通过 → approved,财务打款。

场景 C:有人想把「部门经理关」配成或签,想着"经理们谁批都行,批完找总经理"

❌ 不行。或签的语义就是"首个动作终局",不存在"或签批完再到下一关" (这是设计稿 D5 的拍板,不是实现 bug)。经理关想要"任何一个经理批了就算这关过、 再找总经理",V1 的等价配置是:这关配会签,规则只指向一个只有一个成员的角色, 或者用「指定人」规则精确到一个人——单人会签 = 这一个人批完即过,逐级推进。

实测证据(2026-11-03)

教程准备期把一条两关测试模板的两关都配成 any:部门经理一批, 实例直接 approved、current_stage 归零,总经理那一关的任务压根没生成; 把两关改成 all 后,部门经理批完 status=running, current_stage=2, 总经理的待办才出现。两条路径都截图级验证过。

⚠️ 配置页上「审批方式」下拉的两个选项文案就是「会签(全签)/ 或签(任签)」, 别凭直觉选——"逐级上报"选或签,整条链只剩第一关有人审。

§3 使用审批模板功能:配置页导览

入口:审批流程配置(/flow),需要 flow:read 权限 + menu.flow 菜单。

页面 能做什么 权限
模板列表 /flow 看所有模板(编码/名称/业务类型/启停),新建、删除,点进详情 flow:read / flow:create / flow:delete
模板详情 /flow/:id 改基本信息、整树编辑关卡(加/删/改关名、审批方式) flow:update
规则子页 /flow/:id/stage/:stageId 管理某一关的审批人规则:增删改、选来源(指定人/指定角色/部门主管) flow:update

配置期的行为,写代码对接的人要知道:

  • 保存即预检:建/改模板时,每一关的规则都会当场解析一次, 解析不出任何在职用户 → 拒绝保存(20601)。所以模板永远不是"配了但没人审"的状态。
  • 编辑是整树替换:PUT /system/flows/:id 要传完整的关卡+规则结构, 后端删旧写新——只传想改的那一关,其它关卡会被当成"删掉了"。 页面上不用操心(它总是传整棵树),直接调 API 的人要。
  • 有单子在审就锁编辑(D7):存在非终态实例时,模板整树改不了。 想换流程就停用旧模板、新建一条(编码不能重复)。
  • 启停:is_active=false 的模板不接新单,在跑的单子不受影响; 同一 biz_type 有多条启用模板时,发起必须显式指 template_code。

§4 第 0 步:先给角色配人,再建模板

规则按「指定角色」配置时,保存模板会预检解析该角色下的在职用户。 角色里没有人,模板存不进去:

{"code": 20601, "message": "审批模板 leave_approval 第 1 关:这一关的审批人规则当前都解析不出人(指定的人已停用/离职,或该角色下没有在职用户)"}

(实测踩过:先建模板后配人,第一次保存就是这个错。)

正确顺序:

  1. 系统管理 → 角色管理:建业务角色——role_project_manager(项目经理)、 role_dept_manager(部门经理)、role_general_manager(总经理)、 role_hr(人事专员)、role_finance(财务专员),按你的组织定;
  2. 系统管理 → 用户管理:给具体的人挂上角色身份(一个用户可以有多个身份, 审批按"当前身份"判定权限、按角色成员关系解析审批人);
  3. 回到「审批流程配置」建模板。

⚠️ 改角色的 API 陷阱:PATCH /system/roles/:id 收的是整个角色对象。 只传 {"name": "新名字"} 的话,没传的 is_active 会被解码成 false ⇒ 角色被顺手停用,且停用会级联停用所有挂该角色的用户身份 (重新启用角色不会级联恢复身份,要去用户管理逐个开)。 调这个接口要么传全量字段,要么走页面操作。

§5 模板的三个真实示例

📦 系统内置了三条案例模板(启动期自动落库,在「审批流程配置」页能直接看到): leave_approval 请假审批(3 关)、expense_approval 报销审批(4 关,最后一关 双规则会签)、purchase_approval 采购申请(2 关,末关或签)。 默认全部停用(is_active=false,发起侧零影响)—— 它们是起手案例,不是你 组织的审批流:把关卡/规则改成自己的组织后启用即可用。 内置规则的审批人全部按部门层级预配(dept_leader,levels 1=直属主管 / 2=上级主管 / ≤0=爬到顶),因为角色成员是运行期数据,seed 里写死角色 id 只会 落出一堆悬空引用;按角色配置的"正式版"就是下面三个示例的 JSON。 ⚠️ seed 的 upsert 是 create-if-missing:你改过的案例(改名/启用/改流程) 重启后原样保留,不会被冲掉。

示例一:请假审批(3 关)

业务逻辑:员工请假,项目经理先批 → 部门经理批 → 人事备案存档。 第三关配两条规则(或的关系):人事专员能备案,发起人的直属主管也能备案—— 小团队没有专职人事时主管兜底。

{
  "code": "leave_approval",
  "name": "请假审批",
  "biz_type": "leave",
  "remark": "请假需项目经理→部门经理逐级审批,人事备案",
  "is_active": true,
  "stages": [
    { "name": "项目经理审批", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_project_manager 的 id>" } ] },
    { "name": "部门经理审批", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_dept_manager 的 id>" } ] },
    { "name": "人事备案", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_hr 的 id>" },
                  { "rule_type": "dept_leader", "levels": 1 } ] }
  ]
}

字段说明:

字段 规则
code 全局唯一,^[a-z][a-z0-9_]{1,63}$。大写/连字符/中文 → 40002;重复 → 40900
biz_type 这条链归属的业务类型,必须是已注册审批处理器的类型(§7),否则单子发起不了(50100)
stages[].review_type 逐级链路一律 all(§2)
rules[] 同关多条 = 或。rule_type 三选一:user(填 user_id)/ role(填 role_id)/ dept_leader(填 levels,1=直属主管,≤0=爬到顶)

⚠️ 一条规则只认一种来源:同时带 user_id 和 role_id 不报错, 后端按 rule_type 静默清掉另一个(存进去就是 0)。想要"或"就写两条规则。

示例二:报销审批(4 关)

业务逻辑:报销单逐级上报,最后财务复核确认打款。四级链路,每关一个角色:

{
  "code": "expense_approval",
  "name": "报销审批",
  "biz_type": "expense",
  "remark": "报销需项目经理→部门经理→总经理逐级审批,财务复核打款",
  "is_active": true,
  "stages": [
    { "name": "项目经理审批", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_project_manager 的 id>" } ] },
    { "name": "部门经理审批", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_dept_manager 的 id>" } ] },
    { "name": "总经理审批", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_general_manager 的 id>" } ] },
    { "name": "财务复核打款", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_finance 的 id>" } ] }
  ]
}

和示例一的差别只在深度。两个都值得记住的行为差异:

  • 任何一关有人拒绝 → 整单终局 rejected,后面的关卡(包括财务)不再启动;
  • 打回重提从第 1 关重走(D6:打回只回发起人)。总经理打回的报销单, 张三改完后项目经理要重新批一遍——没有"回到某一关"的语义。

财务关想双人复核? 给 role_finance 配两个成员即可:两人都批才过(会签), 任何一人拒绝整单即黄。这是 §2 场景 A 的会签行。

示例三:采购申请(2 关 —— 会签 + 或签各占一关)

前两个示例的每一关都是会签,这一条演示或签怎么用、用在哪。 业务逻辑:采购先由项目经理确认需求 → 归口审核谁先看到谁办 (采购专员、财务专员都在归口组里,任一人审完即整单结束,不必等第二个人):

{
  "code": "purchase_approval",
  "name": "采购申请",
  "biz_type": "purchase",
  "remark": "项目经理确认需求后,归口审核(采购/财务任一人,或签)",
  "is_active": true,
  "stages": [
    { "name": "项目经理确认需求", "review_type": "all",
      "rules": [ { "rule_type": "role", "role_id": "<role_project_manager 的 id>" } ] },
    { "name": "归口审核", "review_type": "any",
      "rules": [ { "rule_type": "role", "role_id": "<role_purchase 的 id>" },
                  { "rule_type": "role", "role_id": "<role_finance 的 id>" } ] }
  ]
}

或签为什么只能放在最后一关 —— §2 场景 C 说过:或签的语义是 "首个动作即整单终局",通过 = 整单 approved,后面还有关卡也不会启动。 所以:

  • 链路中间的关配或签 = 白配(链条走到那关就停,后面的关卡永远不启动);
  • 链路最后一关(或单关模板)配或签 = 正确用法 —— 业务含义是 "这一关的几个人共享一个职责,谁先处理谁说了算",典型如归口审核、 备案确认、值班主管放行。

跑起来长什么样(时间线):设归口组有采购小赵、财务小钱 ——

  1. 张三提交采购单 → 第 1 关生成:项目经理小王的 pending task;
  2. 小王批「通过」→ 会签只有他一个人,数票即过 → 进第 2 关, 小赵和小钱各得一条 pending task(同关多条规则 = 或,两边的解析结果取并集);
  3. 小赵先批「通过」→ 整单立刻 approved 终局:小钱的任务自动标 skipped,不需要任何人再动作;
  4. 反过来,若小赵批的是「拒绝」→ 整单同样立刻 rejected 终局, 小钱的任务同样 skipped —— 或签下通过和拒绝都只看第一个动作;
  5. 谁也没处理?两条待办都挂在各自待办列表里,直到其中一人处理; 巡检任务会对停太久的单子发站内信告警(不会自动转办,§1)。

对照记忆:把第 2 关改成 all,就变成"小赵小钱都批了才算过" —— 那是示例二财务双人复核的形态。"任一人审完即完成"用 any, "必须人人过目"用 all,选错了不是报错,是业务含义整个变掉。

⚠️ 同关两条规则的角色都要有人(§4 的预检):归口审核的规则解析出 空集(两个角色都没人)→ 模板保存直接被拒(20601); 只有一边有人 → 预检能过(并集非空),单子只会派给有人的那边 —— 这通常就是你要的"专职岗 + 兜底岗"形态,和示例一第 3 关的人事备案同理。

§6 教程:把请假审批从零跑到通过

以「张三请假 3 天」为例,从零开始每一步(页面上点哪里 / 系统内部做什么):

① 建角色、配人(§4)——完成后:张三挂 role_employee, 项目经理小王挂 role_project_manager,部门经理老陈挂 role_dept_manager, 人事小刘挂 role_hr。

② 建模板(§5 示例一的 JSON)——系统内部:逐关预检解析(20601 就在这拦), 通过后模板 + 3 关 + 4 条规则一次落库。

③ 把模板接到业务上。本仓两条路:

  • 路 A(零代码):「自定义业务」→ 目标集合(如"请假申请"集合)→ 设置 → 「审批模板」选中 leave_approval。之后集合的每条记录出现「送审」动作, 权限沿用 dyn:<集合编码>:update。
  • 路 B(代码接):业务侧实现 BizHandler 四个钩子 (ValidateBiz 校验单子存在 / OnApproved 通过后改业务状态 / OnRejected 驳回后改状态 / OnCancelled 作废后善后), 在 main.go 装配期以 biz_type 为键注册进引擎。然后业务代码调 POST /system/approvals(biz_type+biz_id+title+template_code)建单、 POST /system/approvals/:id/submit 送审。

⚠️ 未注册的 biz_type 连草稿都建不了:

{"code": 50100, "message": "业务类型 leave 未注册审批处理器,不能发起审批"}

(实测——创建时就拦,不是审到最后才失败。"审批通过了但业务状态永远不变" 的单子比报错糟糕得多。dyn 路线的 biz_type 恒为 dyn,代码侧注册了哪些以 main.go 装配处为准。

④ 张三发起:在集合里填好请假表单(天数、事由),点「送审」。 系统内部:引擎建审批实例(草稿)+ 立即提交——解析第 1 关(项目经理角色 → 小王),生成小王的 pending task,落第 1 轮快照,实例 running @ 第1关, 事件发出去,小王的待办角标 +1、收到站内信。

⑤ 小王审批:「我的审批 → 待我审批」看到"请假申请 #记录id", 点开看表单内容,批「通过」。系统内部:他的 task 置 approved, 落一条审批日志(带他的意见);这是会签关、分母 1/1 齐 → 推进到第 2 关, 解析部门经理角色 → 老陈的 task 生成,老陈角标 +1。

⑥ 老陈通过 → 同样推进到第 3 关;「人事备案」关的规则解析出 小刘(或张三的直属主管),那人收到待办。

⑦ 备案人通过 → 最后一关通过,实例终局 approved。 系统内部:剩余 pending 任务标 skipped,落终局日志,发终局事件 (张三收到"你的请假已通过"站内信);业务回调 OnApproved 被调—— 路 A(dyn)的回调是空转(记录不动,审批状态以 (biz_type, biz_id) 连出, 挂在记录上的 _approval 徽标变成 approved);路 B 的回调由你的业务代码 把"请假单"置成"已批准"。

任何一步有人拒绝:整单立刻 rejected(备注必填 ≥5 字), 张三收到站内信,单子进「我发起的」列表可查看完整审批日志(谁在哪一关说了什么)。

任何一步打回:整单回到张三(returned),备注 ≥5 字; 张三必须真的改内容再重提(逐字节比较,原样重提报"重提内容没有变化"), 重提后从第 1 关重走,之前批过的人重新审。打回上限 5 次, 第 6 次硬拒"该单已打回 5 次,请联系管理员"。

§7 教程:报销审批(4 级链路)跑一遍

配置(§5 示例二)和请假完全同构,直接跑行为验证—— 2026-11-03 在 dev server 上用一条两关测试模板(与报销同构)实测的完整时序:

时刻 操作 系统状态 谁能看到什么
t0 发起人送审 running @ 第1关 第一关审批人 todo +1,发起人「我发起的」可见
t1 第 1 关审批人通过 running @ 第2关 第一关的人挪到「我已办理」;第二关的人 todo +1
t2 第二关审批人误点拒绝 rejected(终态) 发起人收到站内信;后面关卡不启动
t3 发起人改内容重提 新一轮,running @ 第1关 第 1 关重新出待办(轮次 +1,上一轮留痕可查)
t4 第 1 关通过 → 第 2 关通过 running @ 第2关 → approved 记录上的 _approval 徽标同步变 approved

差异点(相对 2 关的实测模板,4 关同理逐关类推): 每一关通过都是"数会签分母 → 齐 → 解析下一关审批人 → 生成 task → 角标 +1", 第 4 关(财务)通过才触发终局 approved 和业务回调。 多关的会签中间票也发事件(同 approved action、语义是"这一票记下了"), 前端拿它刷新角标——所以会签里"还有几个人没批"大家都能看到(§8.3 的决策)。

§10 审批逻辑 internals:对接代码前值得知道的三件事

  1. 审批人是提交时快照的,不是每关现算。发起(或重提)那一刻把每一关的 审批人解析好落库;中途调整组织架构、给角色加人,不影响在跑的单子 (它用旧名单)。代价:组织调整后要靠巡检告警兜底。想让人数变化生效, 只能等重提(重提重新解析)。
  2. 业务回调在审批事务内。OnApproved/OnRejected/OnCancelled 拿到的 tx 和审批状态变更同一个事务:回调里改业务表,要么和审批结果一起提交, 要么一起回滚——不会出现"审批过了但业务没改"的半截状态。 (dyn 的回调故意空转:记录不动,状态靠连查。)
  3. 事件是广播不是指令。前端收到审批事件只做一件事:重拉待办角标总数 (不 ±1——广播可能合并、可能乱序)。接前端的人不要试图从事件里推断 "角标应该变成几"。

顺带这轮实测抓出并修掉一个真 bug:dyn 送审曾把 engine.Submit 包在 CreateDraft 的外层事务里,而 Submit 自己再开一个事务——SQLite 上两个连接 嵌套等锁死锁,整库焊死(server 所有请求 30s 超时)。已改为草稿事务先落袋、 Submit 在外(资料线的两步走),并加了全链路回归用例 (TestDyn_审批_送审全链路_建草稿与提交不嵌套事务,带 10s 超时防挂死)。

§12 注意事项汇总

  1. 先配人,再建模板(20601)。改绑模板的角色前,确认角色里有在职用户。
  2. 逐级审批 = 每关会签(all);或签(any)首个动作即整单终局(D5)。
  3. biz_type 必须已注册,否则发起时 50100。内置的 dyn 路线 biz_type 恒为 dyn;代码侧注册了哪些以 main.go 装配处为准。
  4. 一条规则一种来源,多填的 ID 被静默清零;多条规则才是"或"。
  5. stage_index 从 1 开始(详情接口、日志、事件里的关号都是 1 基)。
  6. box 必填:GET /approvals 不带 box=todo|mine|done 直接 400,不退化成"全部"。
  7. 有非终态实例时改不了模板(D7);改模板是整树替换,别只传变更的关卡。
  8. 改角色 PATCH /system/roles/:id 要传全量字段,只传 name 会把角色停用并级联停用身份。
  9. 拒绝/打回备注 ≥5 字;打回重提必须改内容;打回上限 5 次。
  10. 审批人是提交时快照:中途改组织不影响在跑的单子,重提才会重新解析。
